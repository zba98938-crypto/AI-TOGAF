## 3. 元数据管理能力

简单地说，元数据可以称为“关于数据的数据”。例如，元数据表明数据的作者/创建者、创建时间、安全分级、数据质量属性等。根据《数据管理知识体系》（DMBOK2）第 417 页：

> “元数据帮助组织理解其数据、系统与工作流。它使质量评估成为可能，是数据库及其他应用管理不可或缺的部分；它有助于处理、维护、集成、保护、审计与治理其他数据的能力。”

元数据概念并不新鲜，IT 业界广泛用它定义“关于数据的数据”。早在数字时代之前的古代，作者、标题、泥板数量等元数据就已用于编目泥板藏品。因此，元数据提供额外信息，以便更好地了解和使用数据。

**元数据管理**是使高质量、集成元数据可被访问的规划、实施与控制活动 [DMBOK2]。它用额外信息增强数据，使其可用于：

- **了解你的数据**：
  - 减少数据的不确定性与可能的误解；
  - 了解可用数据的质量及相关业务规则（数据质量业务规则、转换业务规则等）；
  - 了解数据来源与使用情况；
  - 改进 BI 报表审计；
  - 监控整个信息系统的数据量，以降低环境影响。
- **管理数据风险并符合监管要求**：
  - 利用数据分级（保密性、隐私）支持数据风险管理（如支持数据保护影响评估），基于已定义元数据建立数据访问模型（角色、用户责任、处理目的等）；
  - 为企业最有价值的资产利用安全与隐私元数据，例如：安全元数据支持从以网络为中心转向以属性为中心的安全（如零信任等新标准把数据视为企业资产）；企业身份管理依赖联邦身份（共同属性）控制人或机器对数据的访问；许多国家/地区的隐私立法（如欧盟）使可识别个人数据的传播成为非法；
  - 改进数据血缘与使用审计，以满足监管要求。
- **管理数据生命周期**：
  - 需要元数据表明遵循企业政策与指令所需的内容；
  - 需要知道哪些必须归档并作为记录保留（往往是国家立法的要求）；
  - 需要识别保留生命周期以触发处置（删除）。
- **缩短上市时间**：
  - 对任何新业务举措，借助良好的数据文档（术语表、字典、分级）减少数据范围界定工作；
  - 识别用例所需的相关数据元素。
- **管理数据质量与共享**：
  - 实现信息互操作/共享，促进企业及扩展企业的协作、共享（态势感知）与决策支持；
  - 识别冗余与过时数据；
  - 支持业务利用外部数据。

元数据常被推给 IT，但它本质上是业务关注点。2000 年代中期大量调查及新的政府立法之后，元数据已成为必须维护的关键企业资产，以确保股东透明度、企业安全与客户隐私。

NoSQL 数据库（宽松数据模式）的兴起与近期大数据趋势承诺从任何数据中释放价值，导致人们只关注建设采集、存储与分析数据的能力，很少投入元数据——常被视为无关紧要，或认为机器学习工具可自动获得。除市场趋势外，元数据管理在许多组织中仍是挑战，原因包括：

- **IT 复杂性**：遗留应用文档匮乏（参考数据缺失，数据在应用生命周期内含义变化）；并购扩大 IT 架构，需文档化的元数据范围随之变化；复制因子（某数据元素在信息系统中被复制的次数）越高，元数据文档化越难。
- **数据复杂性**：采集数据的多样性与速度（近实时社交媒体或日志、用于机器学习的文本与图像等）需要新技术采集相关元数据；动态模式使保持元数据文档最新变得困难。
- **IT 营销趋势**：微服务/微应用常挑战数据血缘并提高复制因子；“敏捷”交付被错误理解为不需要文档。
- **人工工作**：如何与业务和 IT 主题专家（SME）一起采集信息？正确的粒度与优先级标准是什么？元数据校验不自动，需要人工复核。
- **缺乏数据标准**：命名约定；数据类型与单位约定。

然而从业务视角看，元数据是良好了解和理解组织已有数据的关键。因此，对任何希望高效利用数据的组织而言，元数据是重要的基础数据管理能力。

在设计该能力时，我们聚焦有效交付元数据管理所需的最小功能集。随着组织实践成熟，可超越本框架定义的基线。我们还认为，数据的伦理使用对每个组织都越来越重要——这体现在 GDPR（《通用数据保护条例》，2018 年 5 月 25 日在欧盟生效）之后世界多地出台的法规中。比合规更重要的是，按设计记录数据使用、以实现对数据伦理使用的治理，可成为组织的竞争优势。因此，本基线框架在元数据管理业务功能中纳入了“数据使用文档”，并强调个人数据。

| 数据使用文档 | 维护数据使用方式清单，以满足监管要求。 |
| 规则与政策文档 | 记录应由数据治理执行的规则（数据质量规则、数据删除规则、归档与保留规则、数据转换规则等）与政策。 |
| 数据问题文档 | 记录任何相关业务数据问题（数据质量、主数据、参考数据等）。 |
| 业务资产与技术资产关联 | 为技术元数据提供业务语境。元数据关联提供对数据生命周期的第一层理解：从数据起源，到其在信息系统中经历的各种移动与转换。 |
| 元数据存储库设计 | 把业务需求转化为元数据需求：定义需在元数据存储库中捕获与存储的相关元数据集；定义元数据对象之间应实现的关系与约束；定义在存储库中创建与维护元数据的流程与工作流。 |
| 沟通与培训 | 围绕元数据存储库价值开展沟通；为最终用户（业务与技术）组织培训计划。 |

## 4. 过程与方法

### 4.1 面向元数据管理能力的 TOGAF 适配

本章综合元数据管理能力交付语境中应开展的、与 TOGAF ADM 各阶段（预备、A、B、C、D、E、F）相关的关键行动。

| TOGAF ADM 阶段 | 元数据管理建议 |
|---|---|
| 预备阶段 | 确保已识别数据所有者或具有明确元数据业务需求的业务利益相关者，以支持架构工作。确保架构治理委员会与数据治理及运营数据委员会良好整合，以保证架构决策与组织数据战略和数据管理活动一致。确保架构工作产出可在实施阶段通过设计权威机构落地。 |
| A——架构愿景 | 澄清记录元数据的业务驱动因素与将实现的业务目标。捕获元数据管理能力将支持的业务用例、优先级与业务参与者需求。评估组织在元数据管理实践方面的成熟度、现有痛点（如有）与期望改进。形成以下概览：组织内可用元数据源；每个元数据源周围的现有社区（业务与技术参与者）；每个数据源内的元数据生命周期（创建、修改、删除）及各社区相关的元数据管理流程。定义交付业务需求、并依据组织数据战略支持数据治理所需的元数据范围；澄清所需元数据层级、社区与元数据流程集成程度。创建包含概念元数据模型的企业元数据政策。结合业务用例、组织成熟度、现有痛点、可用元数据源与所需集成程度，制定目标元数据管理能力的价值主张。 |
| B——业务架构 | 利用已知监管要求、其他内外部合规要求、业务用例需求、业务数据问题与可用数据集，形式化元数据需求。定义支持业务需求需文档化的关键元数据资产。按元数据范围捕获所需元数据质量水平。识别元数据管理能力的现状（基线）与未来（目标）业务用户、相关角色与访问需求。在数据管理办公室支持下，形式化目标中应实施的组织与详细元数据管理流程。澄清交付业务需求所需的业务功能集，开展基线—目标差距分析；第 5 章的业务参考模型可作为指引（详见 4.2 节）。 |
| C——信息系统架构 | 把概念元数据模型扩展到逻辑层（规定属性与域），再把概念元数据实体/属性映射到逻辑数据模型实体、记录（元组/实例）或属性。定义元数据集成模型，澄清：目标元数据存储库（支持数据治理）所管理元数据范围；目标存储库与组织内现有元数据源之间的主/次角色；目标存储库与其他元数据源之间元数据交换的协作契约。定义目标中相关的元数据采集方式：手工摄取、从源推送、从源拉取。澄清元数据推断需求（如有）及推断复杂度——数据多样性（结构化、半结构化、非结构化）与 IT 架构是两大影响因素。数据文档化的关键挑战之一，是记录数据从其起源、到在信息系统中经历的移动与转换的生命周期；这通过元数据关联实现，通常需要人工投入，因此应基于业务需求澄清关联范围，集中精力。澄清交付业务需求所需的应用功能集，开展基线—目标差距分析（5.2 节应用参考模型可作指引，详见 4.3 节）。 |
| D——技术架构 | 元数据 IT 能力的完整覆盖可能需要多种技术组合：数据集成厂商通常提供优化连接器，从数据集成存储库、数据库字典及半结构化/非结构化数据模式中抽取技术与运营元数据；数据治理方案较少聚焦技术元数据抽取，但提供治理功能（元数据变更校验工作流、合规报表等）。定义交付元数据管理能力需要一种技术还是技术组合。确保信息交换平台服务在企业内外每次交换中都包含相关元数据——这对来自外部供应商和/或伙伴的入站数据尤为重要。 |
| E——机会与解决方案 | 使用 5.2 节应用参考模型挑战解决方案供应商。 |
| F——迁移规划 | 首先，在电子表格中开始记录元数据资产，聚焦小范围，以熟悉概念并在团队内培育文档文化。元数据文档需要人工投入：业务元数据由人管理，技术元数据存在于 IT 系统数据结构中，运营元数据在特定时点生成。这一阶段还应证明记录元数据的价值。下一步，迁移到集中式存储库，以执行元数据治理（管家职责、所有权、校验工作流等）、扩展文档规模、简化元数据访问与管理。集中式存储库有多项好处：把不同利益相关者（业务数据所有者、数据管家、内控人员、数据保护官、数据经理等）纳入同一存储库，便于知识共享与复用；所有资产已集中于一个存储库，便于元数据关联；集中式元数据管理支持元数据治理。但由数据管理办公室执行的强治理模型、以及各利益相关者的接纳可能颇具挑战，因为存储库未必针对其角色与特定需求。随着各方成熟，可能出现更高级需求（自动数据发现与编目、数据流可视化、数据模式自动逆向工程等）；此时可考虑为不同贡献者群体设立专用存储库，即按逻辑资产组定义专用系统（业务术语表库、数据字典库、数据质量规则文档与实施库等），从而为每类元数据文档功能提供高级特性，并为每个角色定制界面；但需投入专用精力做元数据集成，把资产关联起来、确保各库一致、避免孤岛，且不同利益相关者之间的协作可能受限。 |
| G——实施治理 | 与元数据管理项目（存储库实施、元数据集成）组织合规审查，检查其遵循原则与目标架构。 |

### 4.2 业务架构阶段的元数据管理指南（ADM 阶段 B）

元数据在组织内有多个来源（图 4-1）。主要挑战在于把不同种类、来自不同社区、具有不同流程与生命周期的元数据汇聚起来，以实现特定业务目标，如数据合规、数据质量监控与数据可访问性。

![图 4-1：元数据来源示意](../sources/retained/togaf-standard-10th-zh/figs/g234_fig4-1.svg)

我们的建议是采取循序渐进的方法建立元数据文档，而不是试图同时对现有元数据源中识别的所有资产进行文档化。

#### 4.2.1 收集元数据需求

定义元数据需求有不同方法（图 4-2）：

- **自上而下**：从合规或其他业务用例出发形式化元数据需求，例如：
  - 合规：法规（GDPR、偿付能力 II、IFRS 17）、内部（数字可持续性、安全规则）；
  - 业务用例：获取客户交互数据以改进向上销售。
- **自下而上**：基于业务数据问题或数据集需求，例如：
  - 数据集：为支持 BI 与分析用例，对现有客户信息文件（CIF）进行文档化；
  - 业务数据问题：客户被以错误频率开票，导致不满与投诉；调查根因以解决问题。

![图 4-2：元数据需求收集示意](../sources/retained/togaf-standard-10th-zh/figs/g234_fig4-2.svg)

自上而下方法（合规、业务用例）通常有强有力的业务支持，元数据一致性由校验流程与工作流要求并保障。自下而上方法更具机会主义色彩，未必有强业务支持；采用该方法时，重要的是在进一步自动化与治理前用具体例子展示价值。两种情况下，都应澄清元数据需求，包括期望的元数据质量水平。

#### 4.2.2 形式化元数据管理流程

元数据质量由流程与校验工作流保障，可因元数据范围而异。主要有两种方法（图 4-3）：

- **规范式**：旨在保证元数据的精确、准确、完整与一致。元数据由少数人创建、以只读方式发布、静态（随时间变化少），其生命周期通过校验工作流管理；适合受监管约束、集中管理的元数据。
- **协作式**：更适合数据民主化场景——需要多个贡献者维护技术元数据，并在需要时把技术元数据与业务元数据关联以提供业务语境；多人创建、多人编辑、动态、最终一致。

![图 4-3：元数据质量保障方法](../sources/retained/togaf-standard-10th-zh/figs/g234_fig4-3.svg)

确定要记录的元数据资产后，重要的是在属性层面利用都柏林核心™ 元数据元素集（Dublin Core™ Metadata Element Set，DCMES）[DCMES] 来有效描述每项资产。例如，subject（主题）字段对于确保元数据在整个企业内可被普遍发现至关重要。让标签与逻辑数据模型元素（尤其是泛化—特化构造，例如“轿车是一种汽车，汽车是一种交通工具”）相对应（映射）很有用，这样搜索（以及业务规则）就能为任何目的找到所有必需的数据。

一旦要收集的元数据资产范围确定，就需要澄清元数据集成模型，同时考虑现有元数据源的更大范围，以及业务架构产出（要接入的业务参与者、元数据校验流程、数据治理运营模式）。

如 ISO/IEC 19773 所述：“……它是一个适用于任何组织中任何种类数据、服务于任何目的的通用描述框架。ISO/IEC 19773 不涉及其他数据管理需求，例如数据模型、应用规格、程序代码、项目计划、业务计划和业务政策。”[ISO/IEC 19773]

此处提出的框架旨在超越 ISO/IEC 19773 模型，明确既与支持数据语义文档相关、又与数据管理需求相关的关键资产。

元数据交换可通过以下方式之一完成：

- **手工摄取（Manual ingestion）**：每个来源以约定格式导出元数据，再手工上传到存储库。
- **推送元数据（Pushing metadata）**：每个来源负责按协作契约（格式、数据结构、频率等）把约定范围内的元数据推送到元数据存储库。
- **拉取元数据（Pulling metadata）**：支撑元数据存储库的 IT 方案提供元数据代理，可直接部署在来源端以收集或推断元数据。

技术元数据与运营元数据通常采用拉取方式；业务元数据则需要人工投入。

每种方式都有一些需要考虑的影响：

- **手工摄取**：
  - 人工工作会影响运营效率；
  - 供应商对元数据集成的支持可能有限；
  - 需要初始投入，为每个元数据源构建抽取器。
- **推送元数据**：
  - 需要初始投入，为每个元数据源设置抽取器；
  - 可能需要额外工具来支持元数据集成。
- **拉取元数据**：
  - 元数据解决方案可能有权访问所有数据；事实上，工具有时需要访问数据文件才能推断技术元数据；
  - 元数据代理对关键应用而言可能是一个侵入性组件；
  - 由于元数据解决方案将拥有对信息系统全景中多个应用的读访问权限，因此需要开展安全审计，确保符合安全政策。

收集技术与运营元数据的复杂性取决于数据多样性和 IT 全景。主要差异在于：数据模式与运营元数据是“按设计”定义，还是事后借助分析技术（元数据推断、机器学习等）提取。

  在分析和治理之前，必须从非结构化数据中提取最低限度的结构（图像中的形状、文档中的电子邮件地址等）。这项工作需要扫描数据内容；如果要扫描数百万个文件，可能涉及密集的数据处理。

存在多种技术、库或工具可从数据中提取技术与运营元数据；工具选择取决于所需元数据的种类、提取信息的复杂性，以及待扫描数据的性能与数据量。

在某种程度上，管理非结构化数据的元数据意味着首先要捕获技术元数据；同一非结构化数据集可以随时间提取出多种结构。主要挑战在于维护与其他元数据的关联，从而把这部分非结构化数据置于语境中：

- **业务含义**：与业务术语、业务数据对象、业务数据元素关联；
- **使用语境**：与数据处理活动关联；
- **数据质量要求**：与业务数据质量规则、技术数据质量规则、数据质量异常关联；
- **隐私要求**：与数据删除规则等关联。

## 附录 A：元数据资产定义

本附录按原文附录 A 给出各类元数据资产的定义。

| 类别 | 名称 | 定义 |
|---|---|---|
| 业务 | 活动（Activity） | 业务为达成明确目标而开展的一项业务任务或一组业务任务。（来源：集成架构框架（IAF）） |
| 业务 | 业务数据删除规则（Business Data Deletion Rule） | 关于移除一组业务数据元素的业务规则，可执行以满足监管或业务要求。通常由业务数据所有者作为其数据治理职责的一部分，为其拥有的数据域定义数据删除规则。定义这些规则时应征求其他数据参与者（业务数据所有者、数据管家、内部控制人员、数据保护官、数据经理等）的意见。这些规则是合乎伦理地使用数据的关键组成部分，并能与数据提供方和消费方建立信任。 |
| 业务 | 业务数据域（Business Data Domain） | 一个主题域、一个业务领域以及（在相关时）其他维度（如地理区域、组织）的组合，构成用于数据治理目的的数据和/或元数据的一致分组。细粒度数据域通常聚焦数据治理（如负责理赔数据质量的数据域）或高度特定的元数据（如仅在受限语境中才有意义的一个数据元素或数据质量规则）。宏观层面定义的数据域通常聚焦共享元数据的治理（如在整个企业广泛使用的一个数据元素或数据质量规则）。 |
| 业务 | 业务数据元素（Business Data Element） | 基本的概念性数据单元。“变量”和“字段”常被同义使用，表示数据元素（如个人合同状态、理赔事件日期、员工名字）。数据元素由三个部分组成：数据对象——所关注并被描述的想法、人或事物（如客户）；属性——数据对象中令人关注的特性（如客户首选语言）；值域——确定可用于表示该数据元素的允许值。<br><br>值域具有数据类型（如布尔、十进制、整数），并可选地具有最小长度、最大长度和小数精度。值域可以是枚举的（通过至少两个单独允许值的列表指定）或非枚举的。例如，客户首选语言由语言代码列表 [ISO 639-1] 表示。数据元素可分为以下组之一：<br>• 输入型：若数据元素为输入型，表示数据基本上按采集时的样子使用或存储，未经重大修改；大多数数据元素属于此类<br>• 派生型：一个或多个数据元素以某种方式被修改；例如，多个数据元素可能为输出或逻辑目的聚合在一起<br><br>更多信息见表 5-1。 |
| 业务 | 业务数据问题（Business Data Issue） | 描述因数据问题而产生的业务问题及该问题的影响（定性或定量）。还描述业务影响的性质，如财务、监管、法律、声誉、运营等。 |
| 业务 | 业务数据对象（Business Data Object） | 为企业所采集数据提供语境的关键想法、人或事物。数据对象有助于理解，并可用于定义收集多个数据元素所针对的对象。例如，可将“联系”定义为数据对象，这有助于应用数据元素，包括联系日期、联系交付方式、联系客户在场状态。使用数据对象可减少在多个数据元素中重复大段文本。 |
| 业务 | 业务数据质量规则（Business Data Quality Rule） | 与一个业务数据元素或一组业务数据元素相关的业务规则，可通过测试确定这些业务数据元素是否满足数据质量要求。通常由业务数据所有者作为其数据治理职责的一部分，为其拥有的数据域定义数据质量规则。定义数据质量规则时应征求其他数据参与者（业务数据所有者、数据管家、内部控制人员、数据保护官、数据经理等）的意见。数据质量规则的定义、设计与实施是稳健数据质量管理计划的核心。示例：出生日期必须是有效日期；姓氏不得为空；电子邮件地址必须匹配 user@domain 模式。 |
| 业务 | 业务规则（Business Rule） | 可实施且属于业务管辖范围的规则。源自业务政策。（来源：对象管理组（OMG）） |
| 业务 | 业务术语（Business Term） | 用于描述事物、以语言或业务分支表达概念的词或短语。 |
| 业务 | 代码集（Code Set） | 定义一组值，枚举数据元素的可能值。例如，可为业务数据对象“人”的业务数据元素“性别”定义代码集，可能值为：男、女、未知。 |
| 业务 | 代码值（Code Value） | 代码集的一个实例或单个值。 |
| 业务 | 数据分类体系（Data Classification Taxonomies） | 数据文档化的一项重要活动，需要至少四类专业群体协作：信息安全、数据隐私、信息风险管理和数据管理。因此，它会影响安全措施、对个人与敏感数据的监管约束，以及数据管理与质量优先级。随着 GDPR 等监管要求的出现，其重要性日益提高。数据分类体系是应用于对每个数据元素分类的适用标签。尽管它们本质上是代码集与代码值，我们仍选择突出数据分类体系，因为它们需要多个利益相关者之间达成一致。 |
| 业务 | 数据政策（Data Policy） | 适用于数据的一组规则、指南、标准与模式。 |
| 业务 | 数据隐私评估（Data Privacy Assessment） | 一项旨在识别与个人数据使用相关风险、并定义缓解计划以符合监管要求的过程。 |
| 业务 | 数据处理活动（Data Processing Activity） | 为产生有意义的信息而对数据元素进行的收集与操作。它表示对数据或数据集执行的任何操作或系列操作，无论是否采用自动化手段，例如收集、记录、组织、结构化、存储、改编或变更、检索、咨询、使用、经传输披露、传播或以其他方式提供、对齐或组合、限制、擦除或销毁。在 GDPR 语境中，数据处理活动记录是收集和操作个人数据的那部分数据处理活动。 |
| 业务 | 组织（Organization） | 用于描述公司内由共同目的界定的利益相关者群体。通常描述分支机构、部门、团队等组织单元。用于驱动元数据存储库内的运营治理。在某些语境中，可能需要按组织单元细分业务数据域。 |
| 业务 | 流程（Process） | 一组相互关联或相互作用的活动，利用输入交付预期结果 [ISO 9000]。 |
| 业务 | 角色（Role） | 业务角色是执行特定行为的职责，可将参与者分配给该角色，或代表参与者在特定行动或事件中所扮演的部分。（来源：ArchiMate 规范） |
| 业务 | 服务水平协议（SLAs） | 运营数据治理的关键组成部分。它们在每个业务语境中描述支持业务用例所需的适用服务水平。例如，针对个人电子邮件地址的数据质量规则可能因业务运营模式（B2C 或 B2B2C）而有不同的可接受阈值。在第二种情形（B2B2C）中，如果公司与客户没有直接关系，电子邮件地址的质量可能无关紧要。 |
| 运营 | 数据访问事件（Data Access Event） | 信息系统中记录的、用于跟踪用户账户对某数据子集访问的任何事件。 |
| 运营 | 数据质量异常（Data Quality Anomaly） | 在信息系统内执行技术数据质量规则后检测到的问题。 |
| 运营 | 数据量（Data Volume） | 数据集或数据库中数据数量的度量。 |
| 运营 | 元数据活动日志（Metadata Activity Logs） | 与元数据存储库内开展的任何活动相关的一组事件。 |
| 技术 | 应用（Application） | 为执行特定任务（如文字处理、数据库管理或图形处理）而设计的一类计算机程序。 |
| 技术 | 数据流（Data Flow） | 描述应用之间的数据流。 |
| 技术 | 数据库（Database） | 有组织的数据集合，通常以电子方式从计算机系统存储和访问。数据库管理系统（DBMS）是与最终用户、应用及数据库本身交互以捕获和分析数据的软件。（来源：维基百科） |
| 技术 | 数据字段（Data Field） | 可存储数据的位置。通常指数据库中的列，或数据录入表单/Web 表单中的字段。（来源：维基百科） |
| 技术 | 数据集（Data Set） | 一组相关的离散数据项，可单独访问、组合访问或作为一个整体实体管理。（来源：TechTarget） |
| 技术 | 技术数据删除规则（Technical Data Deletion Rule） | 业务数据删除规则描述的物理可执行组件（多数情况下为 SQL SELECT 语句）。IT 负责设计并开发数据删除规则，之后可在全企业的批处理或近实时应用中实施、执行与监控。数据删除规则的输出是不符合该规则的所有业务引用列表（如合同引用/编号、员工引用/编号、供应商引用/编号等）（例如，不应保留在 BI 与分析平台中的所有客户联系详情列表）。 |
| 技术 | 技术数据质量规则（Technical Data Quality Rule） | 业务数据质量规则的物理可执行组件。IT 负责设计并开发数据质量规则，之后可在全企业的批处理或近实时应用中实施、执行与监控。数据质量规则的输出是不符合该规则的所有业务引用列表（如合同引用/编号、员工引用/编号、供应商引用/编号等）（例如，合同开始日期不是有效日期的所有合同引用列表）。 |
