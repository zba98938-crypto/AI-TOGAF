## 1. 引言

本文档描述使用**商业智能与分析**（BI & Analytics）支持架构工作的信息架构技术。

本文档包括：

- 用于评估与设计 BI 与分析能力的参考模型（见第 2 章、4.2 节、4.3 节）；
- 为支持 BI 与分析能力而对 TOGAF ADM 的适配（见 3.1 节、3.2 节）。

这些最佳实践基于项目经验，并经过归纳以支持在任何组织中的广泛使用，旨在：

- 加速架构交付，避免重复发明轮子，使其更高效；
- 澄清主题，提供培训数据架构师及其他数据专业人员的框架；
- 为数据专业人员（首席数据官 CDO、数据管理者、架构师、数据工程师、数据科学家等）提供描述 BI 与分析能力的共同语言。

### 1.1 ArchiMate® 建模记法

本文档的参考模型使用 ArchiMate 建模记法描述，该记法定义于 The Open Group 标准《ArchiMate 规范》[C226]。

本文档使用的 ArchiMate 元素见图 1-1，其定义如下：

**动机方面**

- **目标**（Goal）：对组织及其利益相关者而言，关于意图、方向或期望终态的高层陈述。原则上，目标可代表利益相关者期望的任何事物，如某种事态或所产生的价值。
- **利益相关者**（Stakeholder）：代表个人、团队或组织（或其类别）在架构影响方面的利益角色。利益相关者对组织及其企业架构有一个或多个利益或关注点；为把这些利益与关注点导向行动，利益相关者会改变、设定并强调目标，彼此之间也可能相互影响。

**业务层**

- **业务功能**（Business Function）：基于一组选定标准（通常是所需业务资源和/或胜任力）的业务行为集合，与组织紧密对齐，但不一定由组织显式治理。

**应用层**

- **应用功能**（Application Function）：可由应用组件执行的自动化行为。

## 2. BI 与分析能力

BI 与分析能力指为从组织相关决策数据中创造增值信息而组合起来的人员、流程、组织与系统。该能力打破应用数据孤岛，使数据能够按决策与分析用例进行结构化与利用；它涵盖业务价值、数据质量、可用性与安全性，以为相关报表或分析用例交付所需的共性数据。

该能力建立在参考业务功能与参考应用功能之上。本章给出高层功能参考模型及其定义；更详细的功能见本文档专门的参考模型部分（4.2 节与 4.3 节）。

## 3. 过程与方法

### 3.1 TOGAF ADM 对 BI 与分析能力的专门化

本章综合了在 BI 与分析能力交付语境中应开展的、与 TOGAF ADM 各阶段（预备、A、B、C、D、E、F、G）相关的关键行动。

**表 3-1：BI 与分析能力交付与 TOGAF ADM 阶段的对应**

| TOGAF ADM 阶段 | BI 与分析建议 |
|---|---|
| 预备阶段 | 确认实施模型所需的企业架构能力已就位：存储库、数据源、平台等。检查是否已组建具备所需技能的多学科团队，以架构有效的 BI 与分析能力。 |
| A——架构愿景 | 识别并定义 BI 与分析架构的相关原则。从 BI 与分析用户视角，梳理与报表、数据分析、数据科学及统计数据相关的现有痛点概览（可使用 TOGAF 业务场景技术 [G176]）。结合现有或新业务用途、期望改进（数据可用性、数据质量、数据文档、数据可访问性），制定目标 BI 与分析能力的价值主张。 |
| B——业务架构 | 识别 BI 与分析能力的现状与未来业务用户。列出该业务范围内的 BI 与分析用途：未来用途或待改进的现有用途。定义管理 BI 与分析用途的目标运营业务组织，覆盖从设计到持续部署与维护。定义每个用途的价值与优先级（例如基于复杂性与对组织的价值）。识别交付预期用例所需的关键数据——先在业务对象层面。评估现状能力的覆盖度，识别与未来需求的差距。第 2.2 节的业务功能可作为步骤指引。 |
| C——信息系统架构 | **数据**：规定数据建模方法及其在企业数据上的应用；根据业务期望的数据，定义每个数据结构的主要属性及彼此链接；定义用于覆盖不同业务需求的逻辑数据结构——原始数据结构、中间数据层（如企业/领域数据仓库）、末端数据层（数据集市/反规范化业务视图）；为每组数据定义生命周期管理（从平台集成到“生命周期结束/删除”）；对每组数据开展数据质量评估。**应用**：定义支持 BI 与分析采集、传输、存储与访问的目标应用架构；识别提供业务期望数据的源应用；定义支撑平台在数据量、多样性、重复度方面增长的流程；识别现状与目标架构在多样性、速度、容量方面的差距。第 2.3 节的应用功能可作为步骤指引。 |
| D——技术架构 | 识别支撑 BI 与分析运营的数据平台需求；规定数据建模的技术支持。 |
| E——机会与解决方案 | 使用本文档的应用参考模型，围绕 BI 与分析挑战解决方案供应商；参考模型可作为制定解决方案选择标准的依据。 |
| F——迁移规划 | 参见 3.2 节，处理从传统 BI 与分析技术方案向新一代方案的迁移。 |
| G——实施治理 | 与 BI 与分析项目组织合规性审查，检查其是否遵循 BI 与分析原则及目标架构。 |

### 3.2 参考 BI 与分析路线图步骤（ADM 阶段 F——迁移规划）

回顾市场上 BI 与分析的历史，曾使用不同的架构模式风格与技术方案。对特定组织而言，若未遵循 TOGAF 标准 [C220] 中引用的以下原则，多种 BI 与分析能力并存、技术各异且数据重复，将带来困难：

- **原则 11：数据是共享的。** 用户有权访问履行职责所需的数据，因此数据在企业职能与组织之间共享……在单一应用中维护及时、准确的数据再共享，比在多个应用中维护重复数据成本更低。对特定组织信息系统而言，先把数据保存在“信息中心”、再复制到“数据仓库”供其他分析使用，成本高且复杂。
- **原则 20：控制技术多样性。** 控制技术多样性，以最小化维护多种处理环境中的专业知识和连接性的非平凡成本。对特定组织信息系统而言，同时维护运行在关系数据库管理系统（RDBMS）上的数据仓库与基于 Hadoop 的数据湖，会带来 IT 成本与复杂性，应以业务价值证明其合理性。

本节描述一种方法，确保在为 BI 与分析引入新技术/模式时，用新架构替代传统架构。替换组织中已付费且运行中的能力从来都不简单，因为需要从业务角度不易论证的投资。该方法与技术方案无关。

以下示例处理从运行在关系数据库上的企业数据仓库，向新一代 BI 与分析数据平台的转变——后者可同时支持数据存储（结构化、非结构化、事件等）与数据处理（文件处理、SQL、图处理、流处理、机器学习等）在容量×多样性×速度方面的需求。

> **过渡架构**：对某一时点架构状态的正式描述，该时点对架构具有重大意义。注意：可使用一个或多个过渡架构描述从基线到目标架构的演进 [C220]。过渡架构被定义为在有限时间内存在的、相对稳定的架构状态；运营可正常运行，但过渡架构并不实现目标架构所覆盖的完整愿景。

- 新的 BI 与分析用例可利用新一代平台的历史数据与知识能力，在业务流程中改进决策。这些应用可通过人工界面或对数据应用算法产生新数据；新数据可经摄取过程进入新平台以保留历史。

| 项目 | 内容 |
|---|---|
| 收益 | 分析关系型与非关系型数据；可使用数据沙箱；支撑基于事件与历史数据组合的应用（“下一位最佳客户行动”“欺诈检测”等）。 |
| 缺失能力 | 历史数据双份存储：分析没有单一事实来源；新平台不存储来自数仓的原始数据；因原始数据缺失导致数据血缘困难。 |
| 进入步骤 3 的可能触发因素 | 需要分析的单一事实来源（要求打通全部数据）；技术路线图要求对现有方案做技术升级，可借机迁移到新一代平台；满足新分析需求或应用的敏捷性；数据血缘要求；减少影子 BI 与分析。 |

#### 3.2.3 步骤 3

［过渡步骤］新一代 BI 与分析数据平台向数据仓库提供新数据，并覆盖原始数据的完整范围。

- 对于历史上已导入数据仓库、同时也进入新平台的数据，首选做法不是让新平台向数据仓库供数，而是让数据集市直接进入步骤 4（但在某些情况下该做法也可能合理）；
- 在该步骤，数据集市与应用以机会驱动和/或分步方式从企业数据仓库切换到新一代平台（如原文 Figure 3-2 中的“数据集市 #3”）；部分可能同时由新平台与企业数仓供数（如原文 Figure 3-3 中的“交易应用 #1”）；
- 从交易应用到新平台的数据流与供给企业数仓的数据流不同，因为其抽取：交易应用的原始数据；交易应用的全部元数据（含外键、数据字典）——这类信息在供给数仓的流中很少显式存在，因为部分信息保留在数仓建模中；给定业务对象（如客户或合同）的全部可用数据——不限于分析用例所需范围；这是新平台的默认做法，因数据存储成本低而可行；
- 新平台充当持久的原始数据历史存储，并为数据仓库做信息与知识准备，替代暂存区或操作数据存储（ODS）；
- 需结合直接进入步骤 4 的可能性评估该过渡架构的价值。

| 缺失能力 | 历史数据双份存储：没有单一事实来源，且成本翻倍。 |
| 进入步骤 4 的可能触发因素 | 成本规避与优化（存储、项目：在建模前处理数据等）；需维护向数仓与新平台的双摄取流；双份历史存储带来的困难（无单一事实来源）；机会驱动：技术路线图或新业务要求对数据仓库架构做重大升级。 |

从结构上看，由于可存储更大容量、更多样、更高速度的数据，新平台可覆盖数据仓库的数据范围甚至更多。业界已形成共识：同时保留数据仓库与新一代平台两个历史数据存储库，不是可靠的目标愿景。这需要时间，但在目标状态下，新平台将覆盖数据仓库的完整范围，包括为回答分析需求而构建的统一企业数据模型。

现有数据集市接入新平台，新平台成为历史数据存储的单一事实来源。

**表 3-5：路线图步骤 4 细节**

| 项目 | 内容 |
|---|---|
| 沿用前步收益 | 关系型/非关系型分析；数据沙箱；事件组合应用；新平台存储原始/集成/加工数据；数据科学家可用数据；任何新应用可基于新平台；数据血缘更容易。 |
| 新增收益 | 无需再维护旧数据仓库基础设施；新平台存储原始数据及所有相关数据；新平台成为历史数据单一事实来源：历史原始数据存储的参考库，可随时为任何目的重新加工信息与知识；所有数据集中存储（原则上不应再有相关数据不在新平台的情况）；现有数据集市及相关工具的投资得以保留。 |
| 需考虑的风险 | 数据仓库架构满足的某些需求在该步骤可能不再被覆盖：为使这一重大转变可行，必须仔细识别当前由数仓覆盖的需求，并在需要时由基于新平台的架构覆盖；数据治理与元数据管理必须在新平台上谨慎推进，才能充分发挥“所有相关原始数据与信息集中存储并受保护”的全部价值。 |

步骤 4 是 BI 与分析能力建议的最终目标。步骤 2 与 3 是可能的过渡架构，但每个组织在设计路线图水平时都必须定义自己的过渡架构。

事实上，从步骤 1 到步骤 4 的旅程可能因组织现状而大不相同：

- 若现状已包含企业数据仓库，则从“数仓作为历史数据单一事实来源”转变的时间可能比没有企业数仓、可直接构建新一代目标架构的组织更长；
- 并非所有组织都能在三年内完成旅程，但在五年内，新一代 BI 与分析架构应在架构中占据重要位置，成为历史数据存储的单一事实来源。

> **信息**：由重大投资形成、并以可接受服务水平满足业务需求的现有系统，在需要技术迁移或出现新业务需求之前不会被替换。目标是先聚焦增值，并最大化利用过去投资。

### 4.4 BI 与分析参考模型——需求

作为本文档的补充，提供了包含 BI 与分析能力示例需求清单的电子表格文件。文件中的架构需求对参考架构所述应用功能给出了细节，不宜整体通读，可作为查找某些功能细节的参考。

**架构需求**

此处应用企业架构的系统化方法：整个工作范围是由子系统组成的系统，每个功能构成一个子系统；因此需求措辞中的“系统”指该需求对应的功能。需求在电子表格中按功能列出，本章按字母顺序提供。

架构需求代表利益相关者表达的、架构必须满足的正式需求陈述。架构需求捕获架构上重要的事项，即对架构决策有影响的事项；不应细到规格或测试需求的程度，但可作为编写它们的输入。

“正式陈述”意味着：

- 明确且可理解的需求；
- 不面向具体解决方案，不出现工具名称；
- 原子性；
- 唯一性；
- 可验证。

架构需求应足够综合且详细，以支持：

- 清晰理解所需与所交付的能力；
- 路线图排序；
- 保障 BI 与分析平台的实施——架构决策；精确理解 IT 供应商提供的能力。

需求形式化采用如下结构：“系统应［动词］［对象］［利益相关者］”。

**示例需求**

| R-16 | 面向工程与数据管理的数据访问——SQL 数据访问 | 系统应允许经授权的数据工程师直接对分析存储执行 SQL 查询，并记录查询审计。 |

| ODS | 操作数据存储（Operational Data Store）；一种设计用于整合多个来源的数据以便对数据做进一步操作的数据库。与主数据存储不同，数据不会被回传到运营系统；它可被传递用于进一步操作，并传递到数据仓库用于报表。由于数据来源于多个来源，集成通常涉及清洗、解决冗余以及按业务规则检查完整性。它通常设计为包含低层或原子（不可分割）数据（如交易与价格），历史有限，以“实时”或“近实时”方式捕获，而数据仓库通常以较低频率存储更大体量的数据。其总体目的是使用数据虚拟化、数据联邦或 ETL 等数据集成技术，把不同源系统的数据集成到单一结构中，从而支持对数据的运营访问，用于运营报表、主数据或参考数据管理。它不是数据仓库的替代品，但可以作为数据仓库的来源。 |
| P&L | 损益（Profit and Loss） |
| RACI | 负责、问责、咨询、知情（Responsible, Accountable, Consulted, Informed） |
| RDBMS | 关系数据库管理系统（Relational Database Management System） |
| ROI | 投资回报（Return on Investment） |
| SQL | 结构化查询语言（Structured Query Language）；一种用于管理关系数据库并对其数据执行各种操作的标准化编程语言。 |
| 暂存区或着陆区（Staging Area or Landing Zone） | ETL 过程中用于数据处理的中间存储区。数据暂存区位于数据源与数据目标之间，目标通常是数据仓库、数据集市、数据湖或其他数据存储库。数据暂存区通常是临时性的，其内容会在运行 ETL 过程之前或 ETL 过程成功完成后立即清除。 |
| TCO | 总拥有成本（Total Cost of Ownership） |
| UI | 用户界面（User Interface） |
