# togaf-artifact-review 判断规则

本文件是唯一需要人工撰写的部分：机器无法从注册表推出「什么情况选 A 不选 B」。

每条含判据、反例、影响。

## 判断 1：评审结论必须落到对象 ID，不能只给总体判断

- 判据：每条发现必须带「对象或关系 ID、依据、影响、修正建议」四项。只说「这张图有问题」不是评审结论。
- 反例：报告写「整体表达清晰，个别地方需完善」，作者无法定位要改什么，也无法复核是否改对。
- 影响：`architecture-acceptance-criteria`；`non-compliance-disposition` 的 `evidence_refs` 与 `follow_up`；评审记录的可用性。

## 判断 2：渲染成功不等于业务正确，也不等于视觉通过

- 判据：生成成功只证明文件产出；业务正确需要责任方判断；视觉通过需要**实际打开**原图与输出并记录观察。三者分别记录。
- 反例：把 `generate.py` 退出码 0 当作「图已通过评审」，结果图上对象重叠、箭头穿过卡片，从未有人看过。
- 影响：七维证据中的「生成」「评审」「视觉」三维必须分列；`opened_assets` 记录；`visual` 维度的 `not-applicable` 只允许在无独立图形本体时使用。

## 判断 3：来源结构等价与业务布局分别评

- 判据：`reference` 布局对英文原图评**来源结构等价**（对象、关系、方向、基数、层级）；`adaptive` 布局对同一模型评**业务可读性**。两者不互相替代。
- 反例：因为 adaptive 图好看，就判定来源结构已复刻；或因为 reference 布局整齐，就判定业务方可读。
- 影响：`profile-rendering.md` 的双布局约定；`coverage.json` 的未表示对象清单；模板的来源核实状态。

## 判断 4：跨视图同名不等于同义

- 判据：两张图里出现同名对象时，必须核对 `concept_id` 是否一致；不一致即不同对象，须报冲突而非合并。
- 反例：G211 图 3-2 与图 5-1 中少数能力名称不一致，直接按位置合并会造出原文没有的能力。
- 影响：`mixed-hierarchy` 与 `dangling-reference` 类检查；模型合并的正确性；评审记录的冲突登记。

## 判断 5：不一致时登记冲突，不择一覆盖

- 判据：原文、译文、图三者冲突时，按「哈希确认的英文原文 → 中文正文 → 中文图与 JSON → 历史审查」仲裁，并把冲突登记为带 ID 的记录，保留各方表述。
- 反例：发现中文重绘与英文原图不符，直接改图而不登记，导致后续无法追溯为何改动，也无法评估旧结论受影响范围。
- 影响：`evidence-registry.json` 的 `source_conflicts`；`non-compliance-disposition` 的 `original_value_basis`；历史记录的完整性。
