## 1. 引言

<a id="b00065"></a>
TOGAF标准是企业架构框架。希望开发供组织内部使用的企业架构的组织，可免费使用，见1.3.1使用条件。

<a id="b00066"></a>
本标准由The Open Group架构论坛成员开发维护。1995年TOGAF第1版基于美国国防部DoD的信息管理技术架构框架TAFIM；DoD明确授权并鼓励以TAFIM为基础创建TOGAF。TAFIM本身是多年开发及美国政府数百万美元投入的结果。

<a id="b00067"></a>
在此基础上，论坛成员开发后续各版，并在The Open Group公共网站发布。

<a id="b00068"></a>
本版继承前版并更新实践者资料，帮助建立可持续企业架构。关于与其他框架和架构风格集成使用的白皮书、指南工作，突出标准中的通用框架，以及行业、风格、目的特定的工具、技术和指导。这些工作体现于TOGAF资料库[1]。

<a id="b00069"></a>
全部文档虽共同发挥作用，组织采用时仍应有意选择、定制、排除或新建要素。例如可采用元模型，而因大量使用云服务，不采用自建内部技术架构的指导。

<a id="b00070"></a>
建议先读1.1高层概览，了解The Open Group对企业架构的理解及以下基本问题：

<a id="b00071"></a>
- 为什么需要企业架构？
- 为什么选择TOGAF作为企业架构框架？

<a id="sec-01_01"></a>
### 1.1. 高层概览

<a id="b00073"></a>
本节介绍企业架构是什么（并非仅为IT架构的另一名称）、为何需要，以及建立企业架构和采用TOGAF的收益。

<a id="b00074"></a>
什么是企业？

<a id="b00075"></a>
TOGAF将企业视为具有共同目标的任意组织集合，例如：

<a id="b00076"></a>
- 整个公司或其部门。
- 政府机构或单一政府部门。
- 因共同所有权连接的地理分散组织链。
- 共同创建通用或可共享交付物、基础设施的国家、政府或军队等政府组织群。
- 共同工作的商业伙伴和联盟，如联合体或供应链。

<a id="b00077"></a>
企业架构中的企业，可指涵盖全部业务活动、能力、信息、技术、基础设施和治理的整体，也可指一个或多个特定关注领域。企业可包括伙伴、供应商、客户及内部业务单元；所有情况下，架构都跨越多个系统和职能群体。

<a id="b00078"></a>
企业运营模型有助确定架构性质和范围。组织可能包含多个企业，并为其维护独立架构。这些企业常共享流程、职能和信息系统，因此共同框架有潜在广泛收益，如开发通用构建块、方案，以及共享储存库以集成和复用业务模型、设计、信息和数据。

<a id="b00079"></a>
为什么需要企业架构？

<a id="b00080"></a>
其目的是跨企业优化常常碎片化的遗留流程（手工及自动），形成可响应变化、支持交付业务战略的集成环境。

<a id="b00081"></a>
有效管理利用信息及数字化转型是业务成功关键，也是竞争优势的必要手段。企业架构为数字能力演进及覆盖范围提供战略语境，以响应不断变化的业务环境。

<a id="b00082"></a>
良好企业架构平衡业务转型与持续运营效率，使各业务单元能安全创新、追求目标和竞争优势，同时以集成战略满足组织需要，尽可能实现企业内外协同。

<a id="b00083"></a>
全球许多隐私法律还要求，以数据主体、法官、律师等未受专门培训读者易于理解的方式，完整记录个人数据流程；缺失文档可能受重大处罚，因此回应此类法律的文档至关重要。

<a id="b00084"></a>
企业架构有哪些收益？

<a id="b00085"></a>
有效企业架构可带来重要收益，潜在收益包括：

<a id="b00086"></a>
- 高管及业务领导更有效的战略决策：快速响应变化；与战略一致的敏捷性；采用业务技术新趋势的组织转型；支持数字化转型的组织变革；以组织及运营模型变更提升效率与效果。
- 更有效高效的业务运营：降低运营成本；提高敏捷性；跨组织共享能力；降低变更管理成本；更灵活人员；提高生产率；更好支持并购整合。
- 更有效高效的数字化转型及运营：用数字能力扩展企业覆盖；使各组件协调；降低开发、部署、运营、支持、维护成本；改善互操作、系统管理及全企业安全等关键问题处理；易于升级替换组件。
- 提高既有投资回报、降低未来风险：减少业务和IT复杂性；最大化既有投资回报；灵活自建、购买或外包方案；理解回报随时间变化。
- 更快、更简单、更经济的采购：连贯计划使采购信息易得、决策简单；兼顾速度灵活性及架构一致性；可采购异构多供应商开放系统；获得更经济的能力。

<a id="b00087"></a>
哪些事项会触发开发企业架构？

<a id="b00088"></a>
启动评审或开发的原因多样，包括：

<a id="b00089"></a>
- 业务驱动转型，例如以数字服务和产品作为收入资产。
- 技术驱动效率和降本，例如整合到物理、虚拟或混合环境。
- 并购，需先实现技术效率方能实现投资回报。
- 管理敏捷开发累积的技术债务。

<a id="b00090"></a>
当变革涉及相互依赖的多个系统，以上情形都需企业架构管理复杂性。识别为实现新业务目标所需变革的关键人员，通常称为利益相关者。架构师应通过以下方式处理关注点：

<a id="b00091"></a>
- 识别并细化需求。
- 开发显示如何处理关注点和需求的视图。
- 展示协调不同利益相关者潜在冲突时作出的取舍。

<a id="b00092"></a>
没有企业架构，所有关注点和需求都被考虑并满足的可能性很低。

<a id="b00093"></a>
什么是架构框架？

<a id="b00094"></a>
可用于开发广泛不同架构的基础结构集合。应包含方法，以构建块描述企业基线和目标、展示块如何组合，并规划基线到目标的演进。

<a id="b00095"></a>
通常按组织需要裁剪框架；裁剪应确立工具集及共同词汇。

<a id="b00096"></a>
为什么用TOGAF作为企业架构框架？

<a id="b00097"></a>
TOGAF由整个社区协作开发，使用它可形成一致、反映利益相关者需要、采用最佳实践并兼顾当前及预期未来需要的架构。

<a id="b00098"></a>
开发维护企业架构技术复杂，涉及众多利益相关者和决策过程。TOGAF使开发标准化、降低风险，提供增值最佳实践，使组织构建可运行且经济的方案，处理业务问题和需要。

<a id="b00099"></a>
其价值主张是以经过实践且认可的最佳实践，在企业整体和不同行业有效高效运营，处理具体业务技术趋势。

<a id="b00100"></a>
指导应适配不同需要和用例，因此可用于敏捷企业、数字化转型等广泛用例的可持续架构。

<a id="b00101"></a>
谁能从TOGAF获益？

<a id="b00102"></a>
正在或计划开发实施企业架构以支持业务转型的任何组织。

<a id="b00103"></a>
寻求无边界信息流的组织，可定义实施结构和流程，支持企业内外访问集成信息。

<a id="b00104"></a>
使用TOGAF设计实施架构的组织，可获得有利于开放系统实现的设计与采购规格，以较低风险取得开放系统收益。

<a id="b00105"></a>
需要适应新业务市场挑战、在数字化转型中改善客户价值主张的组织。

<a id="b00106"></a>
何时开展企业架构？

<a id="b00107"></a>
为最大化收益，应在变革早期及全程开展，帮助决策者理解影响。否则可能犯昂贵错误。决策之后才做架构，往往只是记录或执行既有决策，无法提前洞察其深远且可能不利的影响。

## 3. 核心概念

<a id="b00167"></a>

<a id="sec-03_01"></a>
### 3.1. 什么是TOGAF标准？

<a id="b00169"></a>
TOGAF是架构框架，提供帮助接受、产出、使用和维护企业架构的方法工具，基于迭代过程模型、最佳实践和可复用既有资产，见2.2。

<a id="sec-03_02"></a>
### 3.2. TOGAF语境中的架构是什么？

<a id="b00171"></a>
ISO/IEC/IEEE 42010:2022将架构定义为：

<a id="b00172"></a>
“实体在其环境中的基本概念或属性，以及支配该实体实现、演进和相关生命周期流程的原则。”

<a id="b00173"></a>
TOGAF采纳但不严格遵循其术语；除上述定义外，还依语境定义第二层含义：

<a id="b00174"></a>
“组件结构、相互关系，以及指导它们随时间设计和演进的原则与指导。”

<a id="b00175"></a>
TOGAF将企业视为系统，在相关标准概念术语与多数读者熟悉的通行术语之间取得平衡，见第4章及《架构内容》。

<a id="sec-03_03"></a>
### 3.3. TOGAF处理哪种架构？

<a id="b00177"></a>
通常认可整体企业架构的四个子域，TOGAF均支持：

<a id="b00178"></a>
- 业务架构：业务战略、治理、组织和关键业务流程。
- 数据架构：逻辑及物理数据资产、数据管理资源的结构。
- 应用架构：各待部署应用、交互及与核心业务流程关系的蓝图。
- 技术架构：数字架构，以及支持业务、数据、应用服务部署所需逻辑软硬件基础设施能力和标准，包括数字服务、物联网、社交媒体基础设施、云、IT基础设施、中间件、网络、通信、处理、标准等。

<a id="b00179"></a>
还可组合四域适当视图定义其他域，例如：

<a id="b00180"></a>
- 信息架构。
- 风险与安全架构。
- 数字架构。

<a id="b00181"></a>
TOGAF支持创建这些多维视图并分类为特定域，使企业考虑更广范围及能力。

<a id="b00183"></a>
ADM提供经过实践且可重复的开发过程，包括建立框架、开发内容、过渡并治理架构实现。

<a id="b00184"></a>
活动在持续定义及实现的迭代周期内进行，使组织按业务目标和机会受控转型，见图3-1。

<a id="b00185"></a>
![原图](../web-2025/volumes/01-introduction-and-core-concepts/assets/010-adm.png)

<a id="b00186"></a>
图3-1：架构开发周期

<a id="b00187"></a>
ADM阶段如下：

<a id="b00188"></a>
- 预备：创建架构能力的准备及启动，包括定制TOGAF、定义原则。
- A架构愿景：周期初始阶段，界定范围、识别利益相关者、创建愿景、获得继续开发的批准。
- B业务架构：开发支持商定愿景的业务架构。
- C信息系统架构：开发支持愿景的信息系统架构。
- D技术架构：开发支持愿景的技术架构。
- E机会与解决方案：初步实施规划、识别前序架构的交付载体。
- F迁移规划：最终确定详细实施与迁移计划，处理基线到目标的迁移。
- G实施治理：从架构角度监督实施。
- H架构变更管理：建立新架构变更管理程序。
- 需求管理：贯穿ADM管理架构需求。

<a id="b00189"></a>
《架构开发方法》的阶段描述重点建议为定义和部署企业架构可以做什么。

<a id="b00190"></a>
如何做见系列指南（2.2），引用指南完整清单见附录A。

<a id="b00191"></a>
建议适配ADM以满足企业需要、支持不同架构风格，见3.15。

<a id="b00192"></a>
特别是，ADM不：

<a id="b00193"></a>
- 强制按特定顺序执行阶段。
- 强制瀑布方法。

<a id="b00194"></a>
TOGAF描述迭代使用ADM开发全面架构全景。可将ADM图视为参考模型，定义以架构方式交付方案所需工作，并识别跨企业交互组件和关系，而不只将图看作流程模型。

<a id="b00208"></a>

#### 3.5.6. 企业架构实践发展支持服务

<a id="b00210"></a>

### 3.6. 交付物、制品与构建块

<a id="b00212"></a>
执行ADM产生流程、需求、计划、合规评估等输出。《架构内容》提供内容结构模型，使主要工作产品一致定义、组织和呈现。

<a id="b00213"></a>
内容框架按使用语境将工作产品分三类：

<a id="b00214"></a>
- 交付物：按契约规定，由利益相关者正式评审、批准、签署的工作产品。代表项目输出；文档交付物通常结项归档，或转入储存库成为参考模型、标准、某时点全景快照。
- 制品：描述架构某方面的工作产品，一般分目录、矩阵、图，如需求目录、应用交互矩阵、价值链图。交付物可含一个或多个制品，制品组成储存库内容；依契约规定，制品可能也是交付物，也可能不是。
- 构建块：可潜在复用的组件，可组合交付架构和方案。详细程度依开发阶段而异，早期可仅为名称概要，后续可分解为支撑块并附完整规格。可属于架构或方案。ABB通常描述所需能力并塑造SBB规格，例如客户服务能力由流程、数据、软件等SBB支持。SBB是实现能力的实际选择，例如网络ABB可由不同卫星网络实现：大量微卫星群或少数大卫星。

### 3.7. 架构抽象

<a id="b00224"></a>
为讨论、沟通及决策与利益相关者有关的系统某方面，创建简化视图的过程或技术。

<a id="b00225"></a>
抽象级别分层，从高层模型走向更详细模型。

<a id="b00226"></a>
跨业务、数据、应用、技术域，可划分四种抽象级别，回答基本问题：

<a id="b00227"></a>
- 为什么：为何需要架构？
- 什么：需满足哪些功能和其他需求？
- 如何：如何组织功能？
- 用什么：以哪些资产实施此结构？

<a id="b00228"></a>
此处为什么、什么、如何，与Zachman框架中对应词的用法无关。

<a id="sec-03_07_01"></a>
#### 3.7.1. 上下文抽象级别

<a id="b00230"></a>
理解企业运营环境和架构规划执行语境，回答为何开展工作、范围是什么，以及目标、驱动因素和具体目标形式的动机。

<a id="sec-03_07_02"></a>
#### 3.7.2. 概念抽象级别

<a id="b00232"></a>
分解需求以理解问题及所需内容，不应过早聚焦实现方式。回答实现需求需要什么，通常以业务、应用、技术服务模型表示期望行为。

<a id="b00233"></a>
也称服务抽象或行为抽象。

<a id="sec-03_07_03"></a>
#### 3.7.3. 逻辑抽象级别

<a id="b00235"></a>
识别实现概念级服务所需业务、数据、应用和技术组件种类，以实现无关方式组织架构。依原则和分组准则，可能有多种服务分组，形成不同逻辑方案。

<a id="sec-03_07_04"></a>
#### 3.7.4. 物理抽象级别

<a id="b00237"></a>
管理物理组件分配和实现，以满足逻辑组件；确定用哪些物理组件实现逻辑组件。依原则和分组准则，可有多种物理方案。

<a id="sec-03_08"></a>
### 3.8. 架构原则

<a id="b00239"></a>
原则是长期有效、很少修改的一般规则指导，告知并支持组织履行使命的方式。

<a id="b00240"></a>
可在不同域和层次建立原则；两个关键域影响架构开发使用：

<a id="b00241"></a>
- 企业原则：为全企业决策和使命履行提供基础，规定全部资源资产使用部署的基本规则，体现企业各部分共识，协调决策，是成功治理战略关键。下属业务或组织单元可有IT、HR、国内、海外运营等原则，为域内决策和架构开发提供依据；用于架构开发的原则必须与架构能力的组织语境一致。
- 架构原则：与架构工作有关，反映全企业共识、体现现有企业原则精神，支配架构流程，影响企业架构开发、维护和使用。

<a id="b00242"></a>
原则层级始于企业原则。下属分段原则必须处于上位原则边界内，各层继承并细化上层原则，不得越界。

<a id="b00243"></a>
架构原则可用适合指导开发的术语和形式重述其他企业指导。

<a id="b00244"></a>
架构如何实现响应驱动因素的具体目标，应能清楚关联到原则。

<a id="b00245"></a>
详见《ADM技术》。

<a id="sec-03_09"></a>
### 3.9. 互操作性

<a id="b00247"></a>
可定义为“共享信息和服务的能力”。明确哪些信息和服务在多大程度上共享或不共享，是有用需求，特别适于复杂或扩展企业。

<a id="b00248"></a>
互操作性确定贯穿ADM：

<a id="b00249"></a>
- A：业务场景初步揭示信息和服务交换性质及安全考虑。
- B：以业务术语进一步定义交换。
- C数据：用企业数据和/或信息交换模型细化内容。
- C应用：规定应用共享信息和服务的方式。
- D：规定实现交换的技术机制。
- E：选择实际方案，如COTS软件包。
- F：在逻辑上落实互操作性。

<a id="b00250"></a>
定义方式很多，目标是在企业及扩展企业一致应用，双方最好使用相同定义。

<a id="b00251"></a>
许多组织将其分为：

<a id="b00252"></a>
- 运营/业务互操作：企业各部分在业务层如何协作。
- 信息互操作：信息如何共享。
- 技术互操作：技术资源如何共享，至少相互连接。

<a id="b00253"></a>
从IT视角，也可类似企业应用集成EAI考虑：

<a id="b00254"></a>
- 表示集成/互操作：通过类似门户的共同界面和体验引导用户访问底层功能。
- 信息集成/互操作：企业应用无缝共享信息，如共同客户信息；通常基于公认企业本体，以及信息结构、质量、访问、安全/隐私的共享服务。
- 应用集成/互操作：集成并共享功能，避免每应用重复建设地址变更服务等，通过工作流无缝连接；影响业务与基础设施应用，紧密关联业务流程统一/互操作。
- 技术集成/互操作：主要在应用平台及通信基础设施域，提供通信、存储、处理、数据访问的通用方法和共享服务。

<a id="b00255"></a>
互操作性及需求详见《ADM技术》。

### 3.11. TOGAF内容框架与企业元模型

<a id="sec-03_12_01"></a>
#### 3.11.1. 概述

<a id="b00274"></a>
ADM提供企业架构创建管理的生命周期管理，各阶段输入、输出、步骤描述若干工作产品。

<a id="b00275"></a>
预备阶段建立企业特定架构能力时，一项基本任务是定义：

<a id="b00276"></a>
- 组织架构描述、工作产品及模型集合的分类框架，即内容框架。
- 创建描述时应捕获、存储、分析的实体类型及关系，以正式企业元模型表示。
- 应开发的具体制品，见3.6。

<a id="b00277"></a>
框架选择可能受以下因素影响：

<a id="b00278"></a>
- 架构能力所基于的架构框架。
- 支持架构能力的软件工具。

#### 3.11.3. 企业元模型

<a id="b00292"></a>

<a id="b00293"></a>

<a id="b00294"></a>

- 检查拟用建模语言或元模型的完整性：覆盖多少实体类型，是否管理所需属性和关系。

<a id="b00296"></a>
- 制品选择。
- 建模记法。可使用ArchiMate、BPMN、UML、实体关系图、流程图及其他能表达TOGAF思想的记法。

### 3.13. 将架构能力建立为运营实体

<a id="b00311"></a>
除纯粹支持变革项目群的能力外，成功EA实践必须有坚实运营基础，像其他业务单元一样作为业务运行。除ADM核心流程外，应建立：

<a id="b00312"></a>
- 财务、绩效、服务管理。
- 风险与机会管理（B.34）。
- 资源管理。
- 沟通和利益相关者管理（4.36）。
- 质量管理、供应商管理（B.40）。
- 配置管理（B.7）、环境管理。

<a id="b00313"></a>
持续架构运营的核心是明确有效的治理，在单一框架内控制并对齐所有具有架构意义的活动。

<a id="b00314"></a>
治理日益成为组织管理的显著要求；TOGAF纳入治理，符合业务最佳实践，并确保支持全部利益相关者要求与义务的可见性、指导和控制。

<a id="b00315"></a>
治理收益包括：

<a id="b00316"></a>
- 问责更透明，知情授权。
- 主动风险与机会管理。
- 最大复用既有组件，保护资产。
- 主动控制、监控及管理机制。
- 跨业务单元复用流程、概念和组件。
- 通过监控、测量、评价、反馈创造价值。
- 提高内部流程与外部要求可见性，尤其使可能有深远战略影响的低层决策受到适当层监督。
- 提高股东价值：EA越来越代表核心知识产权；文中指出良好治理与股东价值提高存在相关性。
- 集成现有流程方法，以控制能力补充其功能。

<a id="b00317"></a>
详见《EA能力与治理》。

<a id="sec-03_15"></a>
### 3.14. 与其他框架结合使用

<a id="b00319"></a>
任何EA框架的两个关键要素是：

<a id="b00320"></a>
- 架构活动应产出的交付物定义。
- 产生交付物的方法描述。

<a id="b00321"></a>
少数例外之外，多数框架侧重交付物，对生成方法说明较少，有些是有意如此。

<a id="b00322"></a>
TOGAF通用且适于广泛环境，提供灵活可扩展内容框架，支撑通用交付物。

<a id="b00323"></a>
可独立使用其通用交付物，也可用架构师认为相关的其他框架更具体交付物替换或扩展。

<a id="b00324"></a>
架构师应适配并扩展TOGAF，定义与企业流程和组织集成的裁剪方法；可采用其他框架要素，集成ITIL、CMMI、COBIT、PRINCE2、PMBOK、MSP等，采用资料库的IT4IT参考架构等。《ADM技术》提供相应适配指导。

<a id="b00325"></a>
TOGAF提供与其他框架集成的能力和协作环境，利用纵向业务域、横向技术领域（安全、可管理性）、电子商务等应用领域，形成最大化业务机会的竞争性框架。

<a id="sec-03_16"></a>
### 3.15. 与不同架构风格结合使用

<a id="b00327"></a>
TOGAF设计灵活，适于各种风格。

<a id="b00328"></a>
风格在重点、形式、技术、材料、主题、时间跨度上不同；通用可扩展TOGAF可方便适配。

<a id="b00329"></a>
架构全景可能含多种风格，TOGAF确保每个利益相关者需要在其他利益相关者及基线语境下得到处理。

<a id="b00330"></a>
支持特定风格时，首先必须识别架构执行或表达中的独特特征组合。

<a id="b00331"></a>
其次确定如何处理这些特征。通常不应大改框架，而应调整模型、视点及工具。

<a id="b00332"></a>
B、C、D中应选择相关模型、视点和工具描述域并证明关注点被处理。不同风格可增加需描述要素、突出已有要素、调整记法、聚焦特定利益相关者或关注点。

<a id="b00333"></a>
通常包括内容元模型扩展、特定记法或技术及视点识别。主导风格可能使实践者重访预备阶段调整能力，或在单周期预期范围内处理独特特征。

<a id="b00334"></a>
风格特定参考模型和成熟度模型是常用工具。

<a id="b00335"></a>
TOGAF发展中出现多种风格，以处理实践关键问题并提高特定语境相关性。

<a id="b00336"></a>
部分由The Open Group论坛和工作组开发，以指南、白皮书或标准发布，例如：

<a id="b00337"></a>
- 《使用TOGAF定义和治理面向服务架构》。
- 《在TOGAF企业架构中集成风险与安全》。

<a id="b00338"></a>
部分与其他机构协作，例如：

<a id="b00339"></a>
- TOGAF与SABSA集成。
- Archi Banking：结合BIAN参考模型、ArchiMate记法及TOGAF。
- 探索TOGAF与Frameworx协同。
- TOGAF 9与DoDAF 2.0。

<a id="b00340"></a>
TOGAF资料库www.opengroup.org/togaf-library提供支持标准的结构化资源。

### 3.17. 企业敏捷性

<a id="b00347"></a>
实践者定义有所不同，但它使企业更以客户和产品为中心、更有效率、更能确保法规遵从，从而更好响应变化。

<a id="b00348"></a>
Agile常与敏捷软件开发宣言相关流程相联系。

<a id="b00349"></a>
敏捷原则和技术可用于适配TOGAF，但企业敏捷范围更广，需额外技术。

<a id="b00350"></a>
EA将变革与战略方向、业务价值关联，提供足够组织视图来管理复杂性、持续变革和意外后果风险。

<a id="b00351"></a>
TOGAF以分区和层级及时响应企业需要：分区将工作分成多个架构举措；层级支持不同粒度和详细程度开发。

<a id="b00352"></a>
ADM还支持多个迭代概念。

<a id="b00353"></a>
详细适配描述见：

<a id="b00354"></a>
- 《使用敏捷Sprint应用TOGAF ADM》。
- 《使能企业敏捷性》。
- 《开放敏捷架构标准》。

<a id="sec-03_19"></a>
### 3.18. 风险管理

<a id="b00356"></a>
任何架构/业务转型都有风险；应事先识别、分类、缓解，并全程跟踪。

<a id="b00357"></a>
缓解持续进行。并购等风险触发因素可能超出规划者范围，因此必须持续监控语境。

<a id="b00358"></a>
架构师可识别并缓解部分风险，但风险必须在治理框架内先接受、后管理。

<a id="b00359"></a>
应考虑两级风险：

<a id="b00360"></a>
- 初始风险：确定和实施缓解行动前的分类。
- 剩余风险：实施缓解行动（若有）后的分类。

<a id="b00361"></a>
过程包括：

<a id="b00362"></a>
- 分类、识别、初始评估、缓解及剩余风险评估、监控。

<a id="b00363"></a>
定性方法见《ADM技术》。

<a id="b00364"></a>
企业安全架构中的风险概念见：

<a id="b00365"></a>
- 《在TOGAF企业架构中集成风险与安全》。

<a id="b00366"></a>
更严格的定量方法见Open FAIR知识体系，包含开放风险分类法O-RT和开放风险分析O-RA两项标准。

## 4. 定义

<a id="b00368"></a>
下列术语定义适用于本标准。补充定义见附录B；两处均未定义的术语参照Merriam-Webster Collegiate Dictionary。

<a id="sec-04_01"></a>
### 4.1. 抽象

<a id="b00370"></a>
对详细复杂内容提供摘要或一般化描述的技术。

<a id="b00371"></a>
注：“抽象层次”也可指为分析聚焦一致、共同的细节或抽象程度。在架构各领域达成一致定义和理解，支持有效沟通决策；尤其有助在复杂大型架构深入细节前识别相关问题。

<a id="sec-04_02"></a>
### 4.2. 参与者

<a id="b00373"></a>
具有一个或多个角色、发起或参与活动的人、组织或系统，如外出访客的销售代表，可为组织内部或外部。

<a id="b00374"></a>
注：汽车经销商可将参与供应链活动的原始设备制造商视为参与者。

<a id="sec-04_03"></a>
### 4.3. 应用架构

<a id="b00376"></a>

<a id="b00377"></a>
注：应用架构见《架构开发方法》。

<a id="sec-04_04"></a>
### 4.4. 应用组件

<a id="b00379"></a>
与实现结构对齐、模块化且可替换的应用功能封装；封装行为和数据，提供服务并通过接口开放。

<a id="b00380"></a>
注：如会计、薪资、CRM系统；通常维护数据组件，由技术组件提供的技术服务使能。

<a id="sec-04_05"></a>
### 4.5. 应用平台

<a id="b00382"></a>
提供应用支撑服务的软硬件技术组件集合。

<a id="sec-04_06"></a>
### 4.6. 应用服务

<a id="b00384"></a>
可向应用请求的独立行为；支持或交付一个或多个业务服务部分或全部的自动化要素。

<a id="sec-04_07"></a>
### 4.7. 架构风格

<a id="b00386"></a>
与架构执行或表达的特定语境有关的独特特征组合；引导或约束架构形成的原则和特征集合。

<a id="sec-04_08"></a>
### 4.8. 架构

<a id="b00388"></a>
1. 实体在环境中的基本概念或属性，以及支配其实现、演进和相关生命周期流程的原则（ISO/IEC/IEEE 42010:2022）。
2. 组件结构、相互关系及支配其随时间设计演进的原则和指导。

<a id="sec-04_09"></a>
### 4.9. 架构构建块ABB

<a id="b00390"></a>

注：也可看作该类视图定义或模式，规定构建、解释、使用视图以处理关注系统特定关注点集合的约定。部分章节用viewpoint作同义词。

<a id="b00427"></a>
另见B.25元视图。

<a id="sec-04_22"></a>
### 4.22. 架构愿景

<a id="b00429"></a>
简洁描述目标架构、业务价值及成功部署对企业的变化；作为期望愿景和详细开发边界。

<a id="b00430"></a>
注：A阶段见《架构开发方法》。

<a id="sec-04_23"></a>
### 4.23. 制品

<a id="b00432"></a>
描述架构某方面的工作产品。

<a id="b00433"></a>
另见4.26构建块。

<a id="sec-04_24"></a>
### 4.24. 基线

<a id="b00435"></a>
已正式评审商定的规格，作为后续开发或变更基础，只能通过正式变更控制或配置管理等程序改变。

<a id="sec-04_25"></a>
### 4.25. 无边界信息流

<a id="b00437"></a>
“访问集成信息以支持业务流程改进”的简称，代表符合组织业务需要的基础设施期望状态。

<a id="b00438"></a>
注：无边界信息流是The Open Group商标，相关需要见III-RM系列指南。

<a id="sec-04_26"></a>
### 4.26. 构建块

<a id="b00440"></a>
可潜在复用的组件，与其他构建块组合交付架构和方案。

<a id="b00441"></a>
注：详细程度依阶段而异，早期可为名称概要，后续可分解并附完整规格；可属于架构或方案。见《架构内容》及4.23制品。

<a id="sec-04_27"></a>
### 4.27. 业务架构

<a id="b00443"></a>
能力、端到端价值交付、信息和组织结构的整体多维业务视图，以及这些视图同战略、产品、政策、流程、举措、利益相关者关系的表示。

<a id="b00444"></a>
注：将业务要素关联到业务目标及其他域要素，见《架构开发方法》。

<a id="sec-04_28"></a>
### 4.28. 业务能力

<a id="b00446"></a>
业务为实现特定目的可能拥有或交换的特定能力。

<a id="sec-04_29"></a>
### 4.29. 业务职能

<a id="b00448"></a>
按所选准则形成、紧密对应组织的业务行为集合。

<a id="sec-04_30"></a>
### 4.30. 业务治理

<a id="b00450"></a>
确保业务流程、政策及其运作交付业务结果，遵守相关业务法规。

<a id="sec-04_31"></a>
### 4.31. 业务模型

<a id="b00452"></a>
描述企业如何创造、交付、获取价值的原理的模型。

<a id="sec-04_32"></a>
### 4.32. 业务服务

<a id="b00454"></a>
封装独特业务行为要素以支持业务。

<a id="b00455"></a>
注：企业外部服务可由业务服务支撑。

<a id="sec-04_33"></a>
### 4.33. 能力

<a id="b00457"></a>
组织、人员或系统拥有的能力。

<a id="b00458"></a>
注：通用定义，业务架构细化见4.28业务能力。

<a id="sec-04_34"></a>
### 4.34. 能力架构

<a id="b00460"></a>
描述企业所拥有能力的架构。

<a id="b00461"></a>
另见《遵循TOGAF ADM开发企业架构的实践者方法》。

<a id="sec-04_35"></a>
### 4.35. 能力增量

<a id="b00463"></a>
交付特定价值的能力架构独立部分；全部增量完成时，该能力实现。

<a id="sec-04_36"></a>
### 4.36. 沟通与利益相关者管理

<a id="b00465"></a>
管理EA实践利益相关者需要，以及实践与利益相关者、服务消费者之间的沟通执行。

<a id="b00466"></a>
注：利益相关者管理见《ADM技术》。

<a id="sec-04_37"></a>
### 4.37. 关注点

<a id="b00468"></a>
与一个或多个利益相关者有关的系统利益。

<a id="b00469"></a>
注：可涉及功能、开发、运营任何方面，如性能、可靠、安全、分布、可演进性，并可能决定系统可接受性。

<a id="b00470"></a>
另见4.76利益相关者。

<a id="sec-04_38"></a>
### 4.38. 行动方案

<a id="b00472"></a>
战略目标和具体目标提供的方向及重点，通常用于交付业务模型的价值主张。

<a id="sec-04_39"></a>
### 4.39. 数据架构

<a id="b00474"></a>
描述企业主要数据类型与来源、逻辑及物理数据资产、数据管理资源的结构。

<a id="b00475"></a>
注：本地原文指向《Architecture Method》。

<a id="sec-04_40"></a>
### 4.40. 交付物

<a id="b00477"></a>
契约规定、由利益相关者正式评审商定并签署的架构工作产品。

<a id="b00478"></a>
注：代表项目输出；文档交付物通常结项归档，或转入储存库作为参考模型、标准、某时点全景快照。

<a id="sec-04_41"></a>
### 4.41. 数字架构

<a id="b00480"></a>
结合EA、数据科学、电信与物联网、安全、AI、认知科学、神经科学、机器人、社交媒体，以交付运营服务的包容性架构。

<a id="sec-04_42"></a>
### 4.42. EA全景

<a id="b00482"></a>
见4.15架构全景。

<a id="sec-04_43"></a>
### 4.43. 企业

<a id="b00484"></a>
通常为组织最高层描述，涵盖全部使命和职能，常跨多个组织。

<a id="sec-04_44"></a>
### 4.44. 企业架构服务

<a id="b00486"></a>
交付特定EA功能的、经封装的EA能力要素。

<a id="sec-04_45"></a>
### 4.45. 企业连续系列

<a id="b00488"></a>
对架构及SBB从通用走向特定适用性或反向演进进行分类的机制。

<a id="b00489"></a>
另见4.10架构连续系列及4.75解决方案连续系列。

<a id="sec-04_46"></a>
### 4.46. 基础架构

<a id="b00491"></a>
通用构建块、相互关系及原则指导的组合，作为构建更特定架构的基础。

<a id="sec-04_47"></a>
### 4.47. 框架

<a id="b00493"></a>
用于组织思考、确保一致完整的内容或流程结构。

<a id="sec-04_48"></a>
### 4.48. 差距

<a id="b00495"></a>
两个状态差异的陈述，用于差距分析中识别基线和目标的差异。

<a id="b00496"></a>
注：见《ADM技术》。

<a id="sec-04_49"></a>
### 4.49. 治理

<a id="b00498"></a>
监控和指导业务或IS/IT全景管理，以交付所需业务结果的纪律。

<a id="b00499"></a>
另见4.14架构治理、4.30业务治理、B.27运营治理及附录B。

<a id="sec-04_50"></a>
### 4.50. 信息

<a id="b00501"></a>
以文字、数字、图形、地图、叙述、视听等任何媒介形式，沟通或表示事实、数据、意见。

<a id="sec-04_51"></a>
### 4.51. 信息技术IT

<a id="b00503"></a>
组织所用信息及相关技术的生命周期管理。

<a id="sec-04_52"></a>
### 4.52. 互操作性

<a id="b00505"></a>
1. 共享信息和服务的能力。
2. 两个或多个系统、组件交换并使用信息的能力。
3. 系统相互提供和接收服务，并使用交换服务有效共同运行的能力。

<a id="sec-04_53"></a>
### 4.53. 逻辑

<a id="b00507"></a>
独立于实现。

<a id="b00508"></a>
注：逻辑架构是实现无关的架构定义。

<a id="sec-04_54"></a>
### 4.54. 元数据

<a id="b00510"></a>
任何媒介中的任何类型“关于数据的数据”，描述实体特征。

<a id="sec-04_55"></a>
### 4.55. 元模型

<a id="b00512"></a>
描述构建架构描述所用实体、其特征及关键关系的模型。

<a id="sec-04_56"></a>
### 4.56. 方法

<a id="b00514"></a>
解决特定问题类型的已定义、可重复途径。

<a id="sec-04_57"></a>
### 4.57. 建模

<a id="b00516"></a>
通过构建模型，以可推理、洞察和澄清主题本质的形式表示主题的技术。

<a id="sec-04_58"></a>
### 4.58. 模型种类

<a id="b00518"></a>
一类建模的约定。

<a id="b00519"></a>
注：视点引用一个或多个模型种类；视图包含一个或多个模型。

<a id="sec-04_59"></a>
### 4.59. 具体目标

<a id="b00521"></a>
以具体、可度量、可行动、现实、有时限SMART方式陈述的组织目的，如“年底前容量利用率提高30%，支持计划市场份额增长”。

<a id="sec-04_60"></a>
### 4.60. 模式

<a id="b00523"></a>
将构建块置于语境中的技术，例如描述问题的可复用解决方案。

<a id="b00524"></a>
注：构建块是用什么，模式可说明如何、何时、为何使用及相应取舍。

<a id="b00525"></a>
另见4.26构建块。

<a id="sec-04_61"></a>
### 4.61. 物理

<a id="b00527"></a>
现实世界、可触及的。

<a id="b00528"></a>
注：逻辑架构通过物理架构实现。

<a id="sec-04_62"></a>
### 4.62. 原则

<a id="b00530"></a>
见4.19架构原则。

<a id="sec-04_63"></a>
### 4.63. 产品

<a id="b00532"></a>
业务产生、提供给客户的结果，包括材料和/或服务。

<a id="sec-04_64"></a>
### 4.64. 参考模型RM

<a id="b00534"></a>
用于理解环境实体的重要关系，并开发支持环境的一致标准或规格的抽象框架。

<a id="b00535"></a>
注：基于少量统一概念，可用于教育、向非专家讲解标准；不直接绑定标准、技术或具体实现，而寻求跨实现无歧义的共同语义。来源OASIS：www.oasis-open.org/committees/soa-rm/faq.php。

<a id="sec-04_65"></a>
### 4.65. 需求

<a id="b00537"></a>
无歧义、可测试或度量，且是可接受性必要条件的需要陈述。

<a id="sec-04_66"></a>
### 4.66. 路线图

<a id="b00539"></a>
业务或技术变革的抽象计划，通常跨学科、跨多年，常见于技术路线图、架构路线图等用语。

<a id="sec-04_67"></a>
### 4.67. 角色

<a id="b00541"></a>
1. 参与者通常或预期的行为，或某人、某物在流程事件中的作用；一个参与者可有多个角色。
2. 个人在组织中所起作用，以及应用技能、知识、经验和能力作出的贡献。

<a id="b00542"></a>
另见4.2参与者。

<a id="sec-04_68"></a>
### 4.68. 分段架构

<a id="b00544"></a>
企业内某领域的详细正式描述，用于项目群或组合层组织、对齐变革活动。

<a id="b00545"></a>
另见4.78战略架构。

<a id="sec-04_69"></a>
### 4.69. 服务

<a id="b00547"></a>
响应参与者或其他服务请求、提供特定功能的封装行为要素。

<a id="b00548"></a>
注：服务有接口和描述。

<a id="sec-04_70"></a>
### 4.70. 服务导向

<a id="b00550"></a>
以提供和消费的服务看待企业、系统或构建块。

<a id="b00551"></a>
另见4.71面向服务架构。

<a id="sec-04_71"></a>
### 4.71. 面向服务架构SOA

<a id="b00553"></a>
支持服务导向的架构风格。

<a id="b00554"></a>
另见4.7架构风格、4.70服务导向。

<a id="sec-04_72"></a>
### 4.72. 服务组合

<a id="b00556"></a>
服务集合，可能是接口定义。

<a id="b00557"></a>
注：在TOGAF中用于定义构建块或系统需求。

<a id="sec-04_73"></a>
### 4.73. 解决方案架构

<a id="b00559"></a>
描述一项离散聚焦的业务运营或活动，以及IS/IT如何支持它。

<a id="sec-04_74"></a>
### 4.74. 解决方案构建块SBB

<a id="b00561"></a>
实现一个或多个逻辑ABB部分或全部的物理或实施特定组件。

<a id="b00562"></a>
注：有业务、应用、技术SBB。

<a id="sec-04_75"></a>
### 4.75. 解决方案连续系列

<a id="b00564"></a>
按不断增加的细节和特化程度，对解决方案全景或参考库（储存库一部分）内组件制品分类的机制。

<a id="b00565"></a>
另见4.45企业连续系列、4.10架构连续系列。

<a id="sec-04_76"></a>
### 4.76. 利益相关者

<a id="b00567"></a>
对系统有利益关联的个人、团队、组织或其类别。

<a id="sec-04_77"></a>
### 4.77. 标准库

<a id="b00569"></a>
可用于定义组织特定架构的特定服务及其他组件的标准库。

<a id="b00570"></a>
注：见《架构内容》。

<a id="sec-04_78"></a>
### 4.78. 战略架构

<a id="b00572"></a>
企业的概要正式描述，提供组织运营和变革活动的框架，以及用于方向设定的高管级长期视图。

<a id="sec-04_79"></a>
### 4.79. 目标架构

<a id="b00574"></a>
为组织开发的架构未来状态描述。

<a id="b00575"></a>
注：可有多个未来状态，作为路线图展示向目标演进。

<a id="sec-04_80"></a>
### 4.80. 架构视图分类体系

<a id="b00577"></a>
与架构有关的全部视图的有序集合。

<a id="sec-04_81"></a>
### 4.81. 技术架构

<a id="b00579"></a>
描述技术服务和组件的结构与交互。

<a id="b00580"></a>
注：见《架构开发方法》。

<a id="sec-04_82"></a>
### 4.82. 技术组件

<a id="b00582"></a>
1. 技术构建块：提供技术服务，直接或间接使能、支持应用或数据组件的通用基础设施技术。
2. 代表某类或特定技术产品的基础设施封装。

<a id="sec-04_83"></a>
### 4.83. 技术服务

<a id="b00584"></a>
提供使能基础设施、支持应用交付所需的技术能力。

<a id="sec-04_84"></a>
### 4.84. 过渡架构

<a id="b00586"></a>
在具有架构意义的时点，对一个架构状态的正式描述。

<a id="b00587"></a>
注：一个或多个过渡架构可描述从基线到目标的时间推进，详见《架构内容》。

<a id="sec-04_85"></a>
### 4.85. 价值流

<a id="b00589"></a>
为客户、利益相关者或最终用户创造整体结果的端到端活动集合的表示。

<a id="sec-04_86"></a>
### 4.86. 视图

<a id="b00591"></a>
见4.20架构视图。

<a id="sec-04_87"></a>
### 4.87. 视点

<a id="b00593"></a>
见4.21架构视点。

<a id="sec-04_88"></a>
### 4.88. 视点库

<a id="b00595"></a>
储存库参考库中保存的视点规格集合。

<a id="sec-04_89"></a>
### 4.89. 工作包

<a id="b00597"></a>
为实现一个或多个业务具体目标而识别的行动集合，可为项目一部分、完整项目或项目群。

## B：补充定义词汇表

<a id="b00607"></a>
本附录补充第4章定义。

<a id="sec-06_01"></a>
### B.1. 应用软件

<a id="b00609"></a>
具有特定业务目的的软件实体。

<a id="sec-06_02"></a>
### B.2. 可用性

<a id="b00611"></a>
IT系统中，用户在任意时点可使用系统功能的概率，考虑运营、修复、管理及后勤等全部时间；按系统类别进一步定义常规及优先操作可用性。

<a id="sec-06_03"></a>
### B.3. 业务系统

<a id="b00613"></a>
共同实现业务能力的硬件、软件、政策声明、流程、活动、标准和人员。

<a id="sec-06_04"></a>
### B.4. 目录

<a id="b00615"></a>
用于参考的同类架构输出结构化清单，如技术标准目录或应用组合。

<a id="sec-06_05"></a>
### B.5. 客户端

<a id="b00617"></a>
向服务器请求服务的应用组件。

<a id="sec-06_06"></a>
### B.6. COBIT控制目标

<a id="b00619"></a>
“信息及相关技术控制目标”的缩写，由ISACA及ITGI创建，为信息系统与技术治理/管理提供最佳实践建议。

<a id="sec-06_07"></a>
### B.7. 配置管理

<a id="b00621"></a>
以技术和行政指导及监督开展以下工作的纪律：

<a id="b00622"></a>
- 识别并记录配置项功能及物理特征。
- 控制特征变更。
- 记录报告处理及实施状态变化。

<a id="b00623"></a>
也指管理EA实践知识产权资产和基线配置，并控制其变更。

<a id="sec-06_08"></a>
### B.8. CxO高管

<a id="b00625"></a>
特定业务职能最高负责人，如CEO、CFO、CIO、CTO。

<a id="sec-06_09"></a>
### B.9. 数据字典

<a id="b00627"></a>
含元数据的专门数据库；保存数据特征信息，用于设计、监控、记录、保护和控制信息系统及数据库数据；支持元数据定义管理的应用系统。

<a id="sec-06_10"></a>
### B.10. 数据元素

<a id="b00629"></a>
具有意义的信息基本单位，可包含有独立单位和值的数据项子类。

<a id="sec-06_11"></a>
### B.11. 数据库

<a id="b00631"></a>
供计算机访问的、结构化或有组织的数据实体集合。

<a id="sec-06_12"></a>
### B.12. 数据库管理系统

<a id="b00633"></a>
访问或操作数据库的计算机应用程序。

<a id="sec-06_13"></a>
### B.13. 最终用户

<a id="b00635"></a>
最终使用计算机应用或输出的人。

<a id="sec-06_14"></a>
### B.14. 企业资源规划ERP系统

<a id="b00637"></a>
支持主要业务支撑职能的完整集成应用套件，例如财务（应付、应收、总账）、人力、薪资、库存、订单及开票、采购、物流、制造等。

<a id="sec-06_15"></a>
### B.15. 硬件

<a id="b00639"></a>
运行软件所需物理基础设施，如服务器、工作站、网络设备。

<a id="sec-06_16"></a>
### B.16. 信息域

<a id="b00641"></a>
按安全分类、所有权、位置等准则分组的信息或实体。安全语境中指一组用户、其信息对象和安全政策。

<a id="sec-06_17"></a>
### B.17. 信息系统IS

<a id="b00643"></a>
业务系统中基于计算机或IT的部分。

<a id="sec-06_18"></a>
### B.18. 交互

<a id="b00645"></a>
体现通信或使用的架构构建块（服务或组件）关系。

<a id="sec-06_19"></a>
### B.19. 交互模型

<a id="b00647"></a>
展示特定交互类型的视图、目录或矩阵，例如应用集成图。

<a id="sec-06_20"></a>
### B.20. 接口

<a id="b00649"></a>
人与人、系统、设备、应用，或用户与应用/设备之间的互连及相互关系。

<a id="sec-06_21"></a>
### B.21. 关键绩效指标KPI

<a id="b00651"></a>
量化业务或项目绩效的方式。

<a id="sec-06_22"></a>
### B.22. 生命周期

<a id="b00653"></a>
从系统构思开始到不再可用结束的时间段。

<a id="sec-06_23"></a>
### B.23. 成功项目群管理MSP

<a id="b00655"></a>
英国政府商务办公室OGC开发的项目群管理最佳实践方法。

<a id="sec-06_24"></a>
### B.24. 矩阵

<a id="b00657"></a>
以网格展示两个或多个架构要素关系的形式。

<a id="sec-06_25"></a>
### B.25. 元视图

<a id="b00659"></a>
用于开发个别视图的模式或模板，确立目的、受众、记录方式（如可视建模）及使用方式（如分析）。

<a id="b00660"></a>
另见第4章4.21架构视点。

<a id="sec-06_26"></a>
### B.26. 开放系统

<a id="b00662"></a>
实现足够开放的接口、服务和支撑格式规格，使正确工程化的应用软件能够：

<a id="b00663"></a>
- 在广泛系统间以最小改动移植。
- 与本地、远程应用互操作。
- 以有利于用户迁移的方式交互。

<a id="sec-06_27"></a>
### B.27. 运营治理

<a id="b00665"></a>
按契约绩效水平管理系统运营表现、定义运营水平并实施确保有效运行的系统。

<a id="b00666"></a>
另见4.49治理。

<a id="sec-06_28"></a>
### B.28. 套装服务

<a id="b00668"></a>
从COTS供应商市场采购、而非编码自建的服务。

<a id="sec-06_29"></a>
### B.29. 可迁移性

<a id="b00670"></a>
1. 系统、组件、数据或用户在软硬件环境间转移的容易程度。
2. 衡量将软件迁至另一环境，或转换至另一操作环境、硬件配置、软件系统环境所需相对工作量的质量指标。

<a id="sec-06_30"></a>
### B.30. 组合

<a id="b00672"></a>
为实现战略具体目标而作为一组管理的项目群、项目和/或运营集合，如项目、应用、技术或服务组合。

<a id="b00673"></a>
注：组合管理即管理组合的行为。

<a id="sec-06_31"></a>
### B.31. PRINCE2方法

<a id="b00675"></a>
“受控环境中的项目”的缩写，是标准项目管理方法。

<a id="sec-06_32"></a>
### B.32. 项目群

<a id="b00677"></a>
向组织交付业务收益的、经协调的变革项目集合。

<a id="sec-06_33"></a>
### B.33. 项目

<a id="b00679"></a>
向组织交付业务收益的单个变革项目。

<a id="sec-06_34"></a>
### B.34. 风险管理

<a id="b00681"></a>
管理可能威胁EA实践成功、愿景、目标及具体目标实现、尤其服务提供的风险和问题。

<a id="b00682"></a>
注：本地原文指向《架构内容》。

<a id="sec-06_35"></a>
### B.35. 可伸缩性

<a id="b00684"></a>
同一应用用于PC到超级计算机等不同软硬件平台的能力，扩展可迁移概念；以及增长以承载增加负载的能力。

<a id="sec-06_36"></a>
### B.36. 安全

<a id="b00686"></a>
保护数据、确保机密性、可用性和完整性的服务。

<a id="sec-06_37"></a>
### B.37. 服务器

<a id="b00688"></a>
响应客户端请求的应用组件。

<a id="sec-06_38"></a>
### B.38. 服务质量

<a id="b00690"></a>
可分配给服务或契约的非功能属性预设配置。

<a id="sec-06_39"></a>
### B.39. SMART准则

<a id="b00692"></a>
具体、可度量、可行动、现实、有时限的缩写，用于确保目标和具体目标可实现、可测量。

<a id="sec-06_40"></a>
### B.40. 供应商管理

<a id="b00694"></a>
配合公司整体采购，管理向EA实践提供产品和服务的供应商。

<a id="sec-06_41"></a>
### B.41. 系统

<a id="b00696"></a>
为实现一个或多个规定目的而组织的交互要素组合，来源ISO/IEC/IEEE 15288:2015。

<a id="sec-06_42"></a>
### B.42. 时间段

<a id="b00698"></a>
测量潜在影响的时间跨度。

<a id="sec-06_43"></a>
### B.43. 用例

<a id="b00700"></a>
将能力置于使用者语境、展示组织、应用或产品功能的视图。

<a id="sec-06_44"></a>
### B.44. 用户

<a id="b00702"></a>
1. 使用信息处理系统服务的个人、组织或职能单元。
2. 概念模式语言中，可能向系统发出或接收命令消息的任何人或事物。
