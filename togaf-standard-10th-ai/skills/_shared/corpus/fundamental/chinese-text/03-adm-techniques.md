## 2. 架构原则

<a id="b00043"></a>
本章描述开发EA所用原则。

<a id="tag_02_01"></a>
### 2.1. 引言

<a id="b00045"></a>
原则是长期有效、很少修改的一般规则指导，告知并支持组织履行使命。

<a id="b00046"></a>
它可为从价值观到行动结果、共同定义指导组织的结构化思想集的一部分。

<a id="b00047"></a>
依组织情况，可在不同域及层次建立原则。两个关键域影响架构开发使用：

<a id="b00048"></a>
- 企业原则：全企业决策与使命履行的基础，协调组织决策，是成功架构治理战略关键；下属业务或组织单元可有IT、HR、国内、海外运营原则。需确保用于架构开发的原则符合架构能力的组织语境。
- 架构原则：与架构工作有关，体现企业共识和上位原则精神，治理开发、维护、使用流程。

<a id="b00049"></a>
原则集常形成层级，分段原则依据并细化企业原则；架构原则受企业原则告知和约束。

<a id="b00050"></a>
可用适于指导架构开发的术语形式重述其他企业指导。

<a id="b00051"></a>
本节其余部分专论架构原则。

<a id="tag_02_02"></a>
### 2.2. 架构原则特征

<a id="b00053"></a>
定义全企业IT资源资产使用部署的基本规则，反映企业各部分共识，作为未来IT决策基础。

<a id="b00054"></a>
各原则应清楚关联业务具体目标及关键架构驱动因素。

<a id="tag_02_03"></a>
### 2.3. 架构原则组成

<a id="b00056"></a>
宜以标准方式定义，除陈述外还含理由和影响，以促进理解接受，并解释论证具体决策。

<a id="b00057"></a>
建议模板见表2-1。

<a id="b00058"></a>
表2-1：原则定义建议格式

|要素|指导|
|---|---|
|名称|体现规则本质且易记。名称和陈述不应提具体技术平台；避免“支持、开放、考虑”等歧义词，谨慎使用“避免、管理”，去除无必要形容词和副词。|
|陈述|简洁、无歧义传达基本规则。组织间信息管理原则通常类似，但陈述无歧义至关重要。|
|理由|用业务术语突出收益，说明信息技术原则与业务运营原则相似性、同其他原则关系及平衡解释意图；说明何时某原则优先或权重更大。|
|影响|说明执行所需业务及IT资源、成本、活动任务。现有系统标准实践可能不符，但范围程度由语境决定。清楚回答“如何影响我”，不要过度简化、轻视或评判影响价值。有些仅为潜在影响，可能属推测、未充分分析。|

<a id="b00059"></a>
按模板的示例集见2.6。

<a id="tag_02_04"></a>
### 2.4. 开发架构原则

<a id="b00061"></a>
通常由企业架构师与关键利益相关者共同开发，架构委员会批准。

<a id="b00062"></a>
若有企业级原则，应以其为依据。

<a id="b00063"></a>
必须明确可追溯、表达清晰，以指导决策，确保架构及目标实施与战略愿景一致。

<a id="b00064"></a>
开发通常受以下因素影响：

<a id="b00065"></a>
- 企业使命、计划、组织基础设施。
- 战略举措：优势、弱点、机会、威胁及流程改进、质量管理等全企业举措。
- 外部约束：上市时间、客户期望等市场因素及现行、潜在法律。
- 当前系统技术：文档、设备清单、网络图、政策程序等信息资源。
- 新兴行业趋势：影响环境的经济、政治、技术、市场预测。

<a id="tag_02_04_01"></a>
#### 2.4.1. 原则质量

<a id="b00067"></a>
即使人人同意，有一份名为原则的文字，也不代表原则良好。

<a id="b00068"></a>
良好原则集根植组织信念价值，用业务理解的语言表达，数量少、面向未来、由高层认可倡导；为架构规划、政策程序标准、矛盾解决奠基。糟糕原则很快弃用，导致架构政策标准显得武断、自利、不可信。本质上原则驱动行为。

<a id="b00069"></a>
良好原则集有五项判据：

<a id="b00070"></a>
- 易懂：全组织迅速理解，意图明确无歧义，减少有意无意违规。
- 强健：支持高质量决策及可执行政策标准；在复杂争议情形足够明确精确。
- 完整：定义所有潜在重要信息技术管理原则，覆盖预见情形。
- 一致：严格遵循某原则可能需灵活解释另一原则，表达应允许平衡，不应违背其他原则精神；措辞支持一致且灵活解释。
- 稳定：长期有效而能适应变化；首次批准后有增删修改流程。

<a id="tag_02_05"></a>
### 2.5. 应用架构原则

<a id="b00072"></a>
捕获企业使用部署IT资源资产的基本真理。

<a id="b00073"></a>
使用方式包括：

<a id="b00074"></a>
1. 为EA及目标实施项目的有意识决策提供框架。
2. 指导评价准则，影响后期产品、方案、解决方案架构选择及符合性管理。
3. 驱动功能需求。
4. 评估现有实现和战略组合的符合性，为按业务目标优先级实施过渡提供洞察。
5. 理由说明符合原则的业务价值，指导驱动因素冲突时的困难决策。
6. 影响说明关键任务、资源、潜在成本，输入未来过渡规划。
7. 支持治理：在标准合规评估允许或需要解释时提供兜底；当架构修改影响不能在本地程序内解决时，支持发起豁免请求。

<a id="b00075"></a>
原则可能相互关联，须成套应用。

<a id="b00076"></a>
可相互竞争，如可访问性与安全性；每项需在“其他条件相同”语境下考虑。

<a id="b00077"></a>
有时需决定哪个原则优先，理由应始终记录。

<a id="b00078"></a>
“显然、不必记录”是常见反应，但显然不代表遵循；记录有助确保决策达到期望结果。

<a id="b00079"></a>
原则声明不规定具体处罚，但违反通常导致运营问题，妨碍使命。

<a id="tag_02_06"></a>
### 2.6. 原则示例集

<a id="b00081"></a>
过多原则降低灵活性，许多组织仅定义10—20条高层原则。

<a id="b00082"></a>
以下展示典型内容及上述建议格式。

<a id="tag_02_06_01"></a>
#### 2.6.1. 业务原则

<a id="tag_02_06_01_01"></a>
##### 2.6.1.1. 原则1：原则优先

<a id="b00085"></a>
陈述：

<a id="b00086"></a>
信息管理原则适用于企业内全部组织。

<a id="b00087"></a>
理由：

<a id="b00088"></a>
只有全部组织遵循，才能向决策者提供一致、可度量的高质量信息。

<a id="b00089"></a>
影响：

<a id="b00090"></a>
- 否则例外、偏袒、不一致会快速破坏信息管理。
- 未经原则符合性检查，不启动信息管理举措。
- 与原则冲突，应改变举措框架解决。

<a id="tag_02_06_01_02"></a>
##### 2.6.1.2. 原则2：最大化企业整体收益

<a id="b00092"></a>
陈述：

<a id="b00093"></a>
信息管理决策为企业整体提供最大收益。

<a id="b00094"></a>
理由：

<a id="b00095"></a>
体现服务高于自我；企业整体视角比局部长期价值更大。最大投资回报要求遵循全企业驱动因素和优先级，少数群体不得损害整体，但也不阻碍其完成工作。

<a id="b00096"></a>
影响：

<a id="b00097"></a>
- 需改变信息规划管理，技术本身不能完成。
- 局部可能需让步。
- 可行时由全企业为全企业确定开发优先级。
- 跨组织共享应用组件；按企业计划开展举措。
- 各组织遵循企业蓝图优先级，必要时改计划；需要变化时由有全面代表性的论坛调整优先级。

<a id="tag_02_06_01_03"></a>
##### 2.6.1.3. 原则3：信息管理人人有责

<a id="b00099"></a>
陈述：

<a id="b00100"></a>
全部组织参与实现业务具体目标所需的信息管理决策。

<a id="b00101"></a>
理由：

<a id="b00102"></a>
信息用户是以技术解决业务需要的关键客户。全部组织必须参与信息环境各方面，使之与业务一致；业务专家与开发维护技术人员应组队共同定义IT目标。

<a id="b00103"></a>
影响：

<a id="b00104"></a>
- 各利益相关者或客户须承担开发信息环境责任。
- 实施需要承诺资源。

<a id="tag_02_06_01_04"></a>
##### 2.6.1.4. 原则4：业务连续性

<a id="b00106"></a>
陈述：

<a id="b00107"></a>
即使系统中断，企业运营仍维持。

<a id="b00108"></a>
理由：

<a id="b00109"></a>
系统越普及依赖越深，设计使用全过程需考虑可靠性。各业务场所应能不受外部事件影响持续运营，硬件故障、自然灾害、数据损坏不应中止活动，企业必须能以替代信息交付机制运行。

<a id="b00110"></a>
影响：

<a id="b00111"></a>
- 共享应用依赖要求事先识别管理中断风险，包括定期评审、脆弱性暴露测试、以冗余或替代能力保证关键服务连续。
- 设计时考虑恢复、冗余、维护。
- 按应用关键性及使命影响，确定连续性级别和恢复计划。

<a id="tag_02_06_01_05"></a>
##### 2.6.1.5. 原则5：通用应用

<a id="b00113"></a>
陈述：

<a id="b00114"></a>
优先开发全企业共用应用，而非仅供特定组织的类似重复应用。

<a id="b00115"></a>
理由：

<a id="b00116"></a>
重复能力昂贵且导致数据冲突扩散。

<a id="b00117"></a>
影响：

<a id="b00118"></a>
- 依赖局部能力的组织须转向替代的全企业能力，建立并遵循相应政策。
- 不允许自建与企业能力重复的局部能力，减少稀缺资源重复支出。
- 决策数据将更标准化，因为原来不共享、产生不同数据的局部能力被替代。局部组织可论证原数据价值，促成新增企业能力，但最终成为企业系统一部分、全企业共享数据。

<a id="tag_02_06_01_06"></a>
##### 2.6.1.6. 原则6：服务导向

<a id="b00120"></a>
陈述：

<a id="b00121"></a>
架构基于反映企业内外业务流程中真实业务活动的服务设计。

<a id="b00122"></a>
理由：

<a id="b00123"></a>
服务导向交付企业敏捷和无边界信息流。

<a id="b00124"></a>
影响：

<a id="b00125"></a>
- 用流程、目标、规则、政策、接口、组件等业务描述提供语境，以服务编排实现。
- 基础设施有特定要求，应以开放标准实现互操作和位置透明。
- 实现受环境语境约束或使能，必须在语境内描述。
- 强治理表示及实现，建立判断良好服务的试金石。

<a id="tag_02_06_01_07"></a>
##### 2.6.1.7. 原则7：遵守法律

<a id="b00127"></a>
陈述：

<a id="b00128"></a>
信息管理流程遵循全部相关法律、政策和法规。

<a id="b00129"></a>
理由：

<a id="b00130"></a>
企业政策要求遵从，但不排除促成政策法规变化的流程改进。

<a id="b00131"></a>
影响：

<a id="b00132"></a>
- 注意收集、保留、管理数据的法律法规及外部政策。
- 提供教育和规则访问。
- 效率、需要、常识并非唯一驱动，法律法规变化可驱动流程或应用变更。

<a id="tag_02_06_01_08"></a>
##### 2.6.1.8. 原则8：IT责任

<a id="b00134"></a>
陈述：

<a id="b00135"></a>
IT组织负责拥有、实施IT流程和基础设施，使方案满足用户定义的功能、服务水平、成本、交付时间需求。

<a id="b00136"></a>
理由：

<a id="b00137"></a>
有效对齐期望、能力和成本，确保项目成本有效；高效有效方案应成本合理、收益清晰。

<a id="b00138"></a>
影响：

<a id="b00139"></a>
- 创建项目优先级流程。
- IT定义管理业务单元期望的流程。
- 创建数据、应用、技术模型，以集成质量方案并最大化结果。

<a id="tag_02_06_01_09"></a>
##### 2.6.1.9. 原则9：保护知识产权

<a id="b00141"></a>
陈述：

<a id="b00142"></a>
必须保护企业IP，并体现于IT架构、实施及治理流程。

<a id="b00143"></a>
理由：

<a id="b00144"></a>
企业大部分IP托管于IT域。

<a id="b00145"></a>
影响：

<a id="b00146"></a>
- 保护IP人人有责，但实际保护多在IT实现，非IT流程的信任也可用邮件、必填备注等IT流程管理。
- 需管理人员及IT参与者的安全政策，避免泄露并减少责任。
- 政策资源可参阅SANS：www.sans.org/security-resources/policies。

<a id="tag_02_06_02"></a>
#### 2.6.2. 数据原则

<a id="tag_02_06_02_01"></a>
##### 2.6.2.1. 原则10：数据是资产

<a id="b00149"></a>
陈述：

<a id="b00150"></a>
数据具有企业价值，应按资产管理。

<a id="b00151"></a>
理由：

<a id="b00152"></a>
数据有真实可度量价值，用于帮助决策；准确及时数据对准确及时决策关键。应像其他资产一样精心管理，知道位置、可信精度，并在需要的时间地点获取。

<a id="b00153"></a>
影响：

<a id="b00154"></a>
- 与共享、可访问原则密切关联，需教育全组织理解三者价值关系。
- 数据管理人须有管理问责数据的权限和手段，文化从所有权转向管理责任。
- 过时、错误、不一致数据损害企业决策，管理人须确保质量，建立防错纠错、改善缺陷信息产生流程的程序，测量并提升质量，可能需政策程序。
- 全企业代表论坛决定管理人建议的流程变更。
- 应在企业级分配管理人，对正确管理共同资产问责。

<a id="tag_02_06_02_02"></a>
##### 2.6.2.2. 原则11：数据共享

<a id="b00156"></a>
陈述：

<a id="b00157"></a>
用户可访问履职所需数据，因此跨职能、组织共享。

<a id="b00158"></a>
理由：

<a id="b00159"></a>
及时访问准确数据提升决策质量效率。单应用维护再共享比多处重复维护便宜。企业数据丰富却散落不兼容孤岛，共享能力决定收集、创建、传输、吸收速度。

<a id="b00160"></a>
依赖更少、最终一个虚拟来源的准确及时受管理数据可改善决策；复用现有实体创建新实体、无需重复录入，可提高效率。

<a id="b00161"></a>
影响：

<a id="b00162"></a>
- 与资产、可访问原则关联，需教育。
- 制定遵循短长期数据管理访问共同政策、程序、标准。
- 短期为保护遗留投资，投入迁移到共享环境的软件；开发标准模型、元素及元数据，建库以便访问。
- 长期替换遗留时，对新开发者实施共同访问政策，确保新应用数据可共享、新应用可使用共享数据。
- 长短期均采用共同创建、维护、访问方法工具。
- 需要重大文化变化；共享与安全会冲突，但绝不应损害机密数据。
- 用户应依赖共享的准确及时数据履职，形成全企业“虚拟单一来源”。

<a id="tag_02_06_02_03"></a>
##### 2.6.2.3. 原则12：数据可访问

<a id="b00164"></a>
陈述：

<a id="b00165"></a>
用户可访问数据以执行职能。

<a id="b00166"></a>
理由：

<a id="b00167"></a>
广泛访问提升决策效率效果、及时回应信息和服务请求。应从企业视角支持各种用户，节省时间、改善一致性。

<a id="b00168"></a>
影响：

<a id="b00169"></a>
- 与资产、共享原则关联，需教育全组织。
- 可访问性指获取信息的容易程度；访问及显示方式应适应广泛用户及方式。
- 可访问不等于理解，须防止误解；也不意味着可修改或披露。
- 需要教育及文化变化，改变职能单元拥有数据的观念。

<a id="tag_02_06_02_04"></a>
##### 2.6.2.4. 原则13：数据受托责任人

<a id="b00171"></a>
陈述：

<a id="b00172"></a>
每个数据元素有对质量问责的受托责任人Trustee。

<a id="b00173"></a>
理由：

<a id="b00174"></a>
架构化环境可共享文字、视频、声音等数据。共享及共同信息依赖增长时，必须由受托责任人决定内容；其对录入负唯一责任，避免多次录入损坏完整性、减少人工与存储冗余。

<a id="b00175"></a>
注：Trustee负责准确性和时效性；Steward职责可能更广，包括标准化和定义，两者不同。

<a id="b00176"></a>
影响：

<a id="b00177"></a>
- 受托管理化解所有权问题，满足用户需要，可能需文化转变。
- 负责满足所问责数据的质量要求，能以来源等属性建立信任。
- 必须识别真实来源，才能向数据权威分配责任；不意味着披露保密来源，也不意味着来源就是责任人。
- 尽可能在源头附近一次电子捕获、立即验证，以质量控制确保完整性。
- 跨企业共享后，须认识对指定元素准确及时性承担的问责和责任。

<a id="tag_02_06_02_05"></a>
##### 2.6.2.5. 原则14：共同词汇与数据定义

<a id="b00179"></a>
陈述：

<a id="b00180"></a>
全企业一致定义数据，所有用户均可获取并理解定义。

<a id="b00181"></a>
理由：

<a id="b00182"></a>
开发应用的数据须在整个总部有共同定义以共享；共同词汇促进有效对话，也是接口和交换所需。

<a id="b00183"></a>
影响：

<a id="b00184"></a>
- 有数据管理员岗位或论坛不代表已解决；必须额外投入，这是改善环境关键，与广泛社区处理的数据元素定义相关但不同，更像共同词汇定义。
- 建立初始业务词汇，全企业统一使用。
- 新定义应由企业数据管理员协调，与企业词汇表协调一致。
- 局部多义应让位于企业认可定义，协调多项标准化举措，分配职能数据管理责任。

<a id="tag_02_06_02_06"></a>
##### 2.6.2.6. 原则15：数据安全

<a id="b00186"></a>
陈述：

<a id="b00187"></a>
保护数据免受未授权使用披露，包括但不限于国家安全分类、决策前、敏感、采购来源选择敏感及专有信息。

<a id="b00188"></a>
理由：

<a id="b00189"></a>
开放共享及依法公开，应与限制机密专有敏感信息相平衡。

<a id="b00190"></a>
法律要求在允许开放访问的同时保护国家安全和数据隐私；未授权发布的在制决策前信息应防止无根据推测、误解和不当使用。

<a id="b00191"></a>
影响：

<a id="b00192"></a>
- 保密与非保密数据汇聚需评审、解密程序；所有者/职能用户判断是否提高密级，以政策程序处理；按需知访问需定期评审。
- 重新考虑不同密级分系统方式：软件能否隔离？硬件分离笨重低效昂贵，在涉密系统管理非涉密数据更贵。
- 为同时开放和保密，在数据层而非应用层定义安全需要，可限制只读或不可见。
- 确定各类敏感标签，从数据元素设计之初纳入安全，不能事后附加。
- 防止系统、数据、技术未授权访问操纵及总部信息意外或未授权修改、破坏、灾害、披露。
- 结合内容时效制定决策前和在制信息保护期限政策。

<a id="tag_02_06_03"></a>
#### 2.6.3. 应用原则

<a id="tag_02_06_03_01"></a>
##### 2.6.3.1. 原则16：技术独立

<a id="b00195"></a>
陈述：

<a id="b00196"></a>
应用独立于具体技术选择，可在多种平台运行。

<a id="b00197"></a>
理由：

<a id="b00198"></a>
可使开发、升级和运营及时且成本有效，否则不断过时、依赖供应商的技术会取代用户需求成为驱动。

<a id="b00199"></a>
任何IT决策都带来技术依赖，本原则旨在避免应用软件绑定特定硬件和操作系统。

<a id="b00200"></a>
影响：

<a id="b00201"></a>
- 需支持可迁移标准；COTS/GOTS当前选择可能有限，许多绑定平台。
- 为遗留与新环境互操作开发子系统接口。
- 用中间件解耦具体软件方案，例如优先平台独立的Java及未来类似协议。

<a id="tag_02_06_03_02"></a>
##### 2.6.3.2. 原则17：易用

<a id="b00203"></a>
陈述：

<a id="b00204"></a>
应用易用，底层技术对用户透明，使其聚焦任务。

<a id="b00205"></a>
理由：

<a id="b00206"></a>
理解底层越多、生产率越低。易用激励用户在集成环境工作，避免自建孤岛；系统操作知识相似，减少培训和误用风险。

<a id="b00207"></a>
使用应用应像换车驾驶一样直观。

<a id="b00208"></a>
影响：

<a id="b00209"></a>
- 需共同界面体验及人体工学要求，设计标准和可用性测试准则。
- 界面指导不应狭隘假定位置、语言、培训或身体能力；语言、视力、键鼠能力、技术熟练度均影响易用性。

<a id="tag_02_06_04"></a>
#### 2.6.4. 技术原则

<a id="tag_02_06_04_01"></a>
##### 2.6.4.1. 原则18：基于需求的变更

<a id="b00212"></a>
陈述：

<a id="b00213"></a>
仅为响应业务需要而变更应用和技术。

<a id="b00214"></a>
理由：

<a id="b00215"></a>
使信息环境响应业务，而非业务被动响应IT；以业务交易这一信息支持目的为拟议变更基础。

<a id="b00216"></a>
尽量减少IT变更的意外业务影响。

<a id="b00217"></a>
技术变化也可提供流程改进机会，进而改变业务需要。

<a id="b00218"></a>
影响：

<a id="b00219"></a>
- 用EA全面检查后才变更实施。
- 无记录的业务需要，不资助技术改进或系统开发。
- 建立符合原则的变更管理。
- 可能与及时变更冲突；文档流程不应妨碍合理需要的及时响应。聚焦业务而非技术需要，及时响应也是业务需要。

<a id="tag_02_06_04_02"></a>
##### 2.6.4.2. 原则19：响应式变更管理

<a id="b00221"></a>
陈述：

<a id="b00222"></a>
及时实施企业信息环境变更。

<a id="b00223"></a>
理由：

<a id="b00224"></a>
期望人员在环境中工作，就必须响应其需要。

<a id="b00225"></a>
影响：

<a id="b00226"></a>
- 变更管理实施流程不应制造延迟。
- 用户应联系业务专家帮助解释并实施需要。
- 变更时保持架构更新；可能需额外资源。
- 可与企业整体收益、共用应用等原则冲突。

<a id="tag_02_06_04_03"></a>
##### 2.6.4.3. 原则20：控制技术多样性

<a id="b00228"></a>
陈述：

<a id="b00229"></a>
控制多样性，减少维护多处理环境专业知识及互连的可观成本。

<a id="b00230"></a>
理由：

<a id="b00231"></a>
支持替代技术的基础设施、维持多处理器结构互连维护，均有实质成本。

<a id="b00232"></a>
限制支撑组件数量，可简化维护降本。

<a id="b00233"></a>
较少多样性带来标准封装、可预测实施影响和估值回报、重新定义测试、公用设施属性及适应技术进步的灵活性。共用技术带来规模经济，有限资源聚焦共享技术可控制管理支持成本。

<a id="b00234"></a>
影响：

<a id="b00235"></a>
- 技术采购政策标准程序直接关联本原则。
- 选择受技术蓝图约束；建立扩展认可技术集以满足新需要的程序，基线并非冻结。
- 欢迎进步，在证明兼容、效率改善或所需能力后更新蓝图。

<a id="tag_02_06_04_04"></a>
##### 2.6.4.4. 原则21：互操作性

<a id="b00237"></a>
陈述：

<a id="b00238"></a>
软硬件应符合促进数据、应用、技术互操作的规定标准。

<a id="b00239"></a>
理由：

<a id="b00240"></a>
标准确保一致、便于管理、提高满意度、保护投资并降本；互操作标准还支持多供应商产品和供应链集成。

<a id="b00241"></a>
影响：

<a id="b00242"></a>
- 遵循互操作与行业标准，除非有充分业务理由使用非标准方案。
- 建立标准制定、定期评审修订及例外批准流程。
- 识别并记录现有IT平台。

## 3. 利益相关者管理

<a id="tag_03_01"></a>
### 3.1. 引言

<a id="b00245"></a>
利益相关者管理帮助架构实践者赢得他人支持，在其他项目失败之处取得成功。

<a id="b00246"></a>
成功管理的收益包括：

<a id="b00247"></a>
- 及早识别有影响力者，用其输入塑造架构、确保支持、提高模型质量。
- 获得更多资源，提高成功可能。
- 及早频繁沟通，使其理解过程和EA收益，必要时更主动支持。
- 预判对模型报告的反应，在计划中利用积极反应、避免或处理消极反应。
- 及早识别冲突目标并制定解决策略。

<a id="b00248"></a>
应识别对开发有贡献、从引入架构中获益或受损的个人群体，并制定应对策略。

<a id="tag_03_02"></a>
### 3.2. 管理途径

<a id="b00250"></a>
A阶段分析关键参与者，各阶段更新。推进到E、F、H时可能发现新利益相关者。

<a id="b00251"></a>
复杂架构不仅开发难，获得众多受影响方同意也难。

<a id="b00252"></a>
如建筑师为电工、业主、规划官员分别绘布线、平面、立面，企业架构师也应为不同关注点创建业务、信息系统、技术视图。

<a id="b00253"></a>
ADM通过以下概念处理此问题，见《架构内容》：

<a id="b00254"></a>
- 视图、视点、关注点、利益相关者。

<a id="tag_03_03"></a>
### 3.3. 管理步骤

<a id="b00256"></a>
以下详细描述建议活动。

<a id="tag_03_03_01"></a>
#### 3.3.1. 识别利益相关者

<a id="b00258"></a>
识别EA关键利益相关者。

<a id="b00259"></a>
先考虑所有受影响、有权力影响或对成功失败有利益的人。

<a id="b00260"></a>
可包括高管、项目及客户组织角色、开发者、伙伴、供应商、IT运营、客户等。

<a id="b00261"></a>
不要过度聚焦正式结构；非正式群体可能同样强大。

<a id="b00262"></a>
多数个人属于多个群体，群体常因具体事件形成。

<a id="b00263"></a>
考虑谁受项目影响：

<a id="b00264"></a>
- 谁获益、谁受损？谁控制流程变更？谁设计系统？谁决策？
- 谁采购、决定买什么？谁控制资源？谁有专业技能？谁有影响力？

<a id="b00265"></a>
尤其识别受尊重、在上升、参加重要会议委员会、熟悉动态、被同事上级重视的影响者；不一定有正式权力，可查会议记录。

<a id="b00266"></a>
利益相关者可为组织和人，但最终要与人沟通，因此需正式识别组织内正确个人。

## 4. 架构模式

<a id="b00292"></a>
本章指导使用架构模式。

<a id="tag_04_01"></a>
### 4.1. 引言

<a id="b00294"></a>
EA描述模式日益重要，多样、多学科特征要求在不同学科、域和详细层次开发模式。

<a id="b00295"></a>
旧版因成熟度不足未全面采用；如今组织广泛用于软件设计到业务层。仍无单一描述标准，但存在描述模式的模式。

<a id="tag_04_01_01"></a>
#### 4.1.1. 背景

<a id="b00297"></a>
Fowler将模式定义为“在一个实际语境有用，并可能在其他语境有用的思想”，见《分析模式》。

<a id="b00298"></a>
TOGAF以模式将构建块放入语境，描述可复用方案。构建块是用什么，模式说明如何、何时、为何用及取舍，帮助识别过去有效、未来可能有效的ABB/SBB组合。

<a id="b00299"></a>
建筑师Christopher Alexander以1979年《永恒的建造之道》确立模式技术价值，并以《模式语言》《俄勒冈实验》扩展特征和收益。

<a id="b00300"></a>
建筑和软件问题相似，软件架构师因而关注模式；之后大量出版，著名如Gamma等1994年《设计模式》，描述面向对象设计具体问题的简洁优雅方案。

<a id="tag_04_01_02"></a>
#### 4.1.2. 模式内容

<a id="b00302"></a>
格式众多，无单一广泛接受格式，但对内容类型有共识。以下标题来自Buschmann等1996年《面向模式的软件架构》，多数模式包含这些要素，即使标题不同。

<a id="b00303"></a>
- 名称：有意义、易记，通常一词或短语。
- 问题：应用意图，在以下语境及作用力中要达到的目标，可能含优先级。
- 语境：适用前提和应用前初始状态。
- 作用力：相关力量、约束及彼此和目标的交互冲突，明确复杂性及取舍。可包括安全、强健、可靠、容错；可管理；效率性能吞吐带宽空间；按需伸缩；扩展演进维护；模块独立复用开放组合即插即用及可迁移；完整正确；易构建、易用等。这些往往就是架构师优化的质量及关注点。
- 方案：用文字图形说明如何达目标，含静态结构、动态行为、人员计算参与者及协作，可含实施指导和变体特化。
- 结果语境：应用后状态，解释哪些作用力如何解决、哪些未解决，并可指出新语境适用其他模式，在相关模式中详述。
- 示例：具体问题、语境、作用力、应用及结果。
- 理由：论证整体或组件如何运作、为何有效、如何解决力量达目标。方案描述外部结构行为，理由解释内部机理。
- 相关模式：前驱（其结果为本初始）、后继（本结果为其初始）、同题不同力量的备选、需共同应用的依赖模式。
- 已知使用：现有系统实际应用，验证确是重复问题的已证实方案，也可作示例。

<a id="b00304"></a>
也可先有摘要，概览模式和问题类型，说明受众及对读者假设。

<a id="tag_04_01_03"></a>
#### 4.1.3. 术语

<a id="b00306"></a>
软件尤其面向对象、组件领域多年关注设计模式，近来更多将其原则概念扩展到架构。

<a id="b00307"></a>
不少作者以架构指软件，所谓架构模式实为高层软件设计模式，因此精确用语更重要。

<a id="tag_04_01_03_01"></a>
##### 4.1.3.1. 架构模式与设计模式

<a id="b00309"></a>
设计模式常泛指软件架构、设计或编程实现模式。《面向模式的软件架构》区分：

<a id="b00310"></a>
- 架构模式：软件基本结构或模式，预定义子系统、责任及关系组织规则。
- 设计模式：细化子系统、组件及关系，描述在特定语境解决一般设计问题的重复通信结构。
- 惯用法：特定语言的低层模式，以语言特性实现组件或关系特定方面。

<a id="b00311"></a>
区分有用，但此处架构仍仅指软件；软件是TOGAF重要方面，却非唯一。

<a id="b00312"></a>
本节关注企业系统架构模式，借鉴软件模式概念术语，专为含软件、硬件、网络和人员的信息系统提供可复用模型方法。

<a id="tag_04_01_03_02"></a>
##### 4.1.3.2. 模式与架构连续系列

<a id="b00314"></a>
本段指出模式尚未完全集成到标准，但A—D各阶段说明何时考虑连续系列中的可复用资产，模式是其中一种。

<a id="b00315"></a>
正式采用复用模式的企业，通常将其集成到连续系列。

<a id="tag_04_01_03_03"></a>
##### 4.1.3.3. 模式与视图

<a id="b00317"></a>
视图是完整系统模型的选定部分，聚焦利益相关者关注点；模式帮助设计模型及组合视图。

<a id="tag_04_01_03_04"></a>
##### 4.1.3.4. 模式与业务场景

<a id="b00319"></a>
业务场景工作中可能识别相关模式。

## 5. 差距分析

<a id="b00321"></a>
ADM广泛用差距分析验证架构，突出基线与目标之间不足，即有意省略、意外遗漏或尚未定义项目。

<a id="tag_05_01"></a>
### 5.1. 引言

<a id="b00323"></a>
验证关键是考虑忘了什么，架构必须支持全部基本信息处理需要。最重要来源是以往未处理的利益相关者关注点。

<a id="b00324"></a>
潜在差距包括：

<a id="b00325"></a>
- 业务：人员（交叉培训）、流程（低效）、工具（重复缺失）、信息、度量、财务、设施（建筑办公空间）。
- 数据：不够及时、地点不对、内容不对、时间不对、未创建、未消费、关系缺口。
- 应用及技术：受影响、删除或新建。

<a id="tag_05_02"></a>
### 5.2. 建议步骤

<a id="b00327"></a>
建议如下：

<a id="b00328"></a>
- 矩阵纵轴为基线全部ABB，横轴为目标全部ABB。
- 基线轴加“新建”行，目标轴加“删除”列。
- 两者均有的交叉格标“包含”。
- 基线有而目标无的逐项评审：正确删除则标明；意外遗漏则在删除格标明，并在下轮恢复。
- 目标有而基线无的，在新建行标需开发或采购填补的差距。

<a id="b00329"></a>
完成后，删除及新建项都是差距，须解释为正确删除，或标明需恢复、开发、采购。

## 6. 互操作性需求

<a id="b00335"></a>
本章指导定义、建立互操作性需求。

<a id="tag_07_01"></a>
### 6.1. 概述

<a id="b00337"></a>
互操作性可定义为共享信息和服务的能力。明确共享程度是有用架构需求，尤其适于复杂或扩展企业。

<a id="b00338"></a>
贯穿ADM确定：

<a id="b00339"></a>
- A：业务场景揭示交换性质及安全考虑。
- B：以业务术语细化。
- C数据：用企业数据/交换模型细化内容。
- C应用：规定共享方式。
- D：规定技术机制。
- E：选择COTS等实际方案。
- F：在逻辑上落实互操作性。

<a id="tag_07_02"></a>
### 6.2. 定义互操作性

<a id="b00341"></a>
方式很多，目标是企业及扩展企业一致应用，最好使用共同定义。

<a id="b00342"></a>
许多组织分类为：

<a id="b00343"></a>
- 运营/业务：如何共享流程。
- 信息：如何共享信息。
- 技术：如何共享技术服务，至少连接。

<a id="b00344"></a>
也可按IT的EAI视角考虑：

<a id="b00345"></a>
- 表示：共同门户式界面体验引导底层功能。
- 信息：企业应用无缝共享，如共同客户信息，通常基于共同本体及结构、质量、访问、安全/隐私共享服务。
- 应用：集成共享功能，避免每应用重复地址变更等能力，通过工作流无缝连接，与业务流程统一紧密相关。
- 技术：主要在应用平台、通信域共享通信、存储、处理、访问方法服务，取决于标准及共同平台的基础设施合理化程度，如多应用共用平台、一万个网站共用内容管理和服务器，而非遍布各地的服务器管理员。

<a id="b00346"></a>
组织可自建模型。加拿大政府按电子政务使能因素定义三类，明确共享内容：

<a id="b00347"></a>
- 信息：知识管理、商业智能、信息管理、可信身份。
- 业务：交付网络、电子民主、电子商务、企业资源管理、关系与案例管理。
- 技术：IT基础设施。

<a id="b00348"></a>
系统之系统或联邦模型等方法强烈建议互操作，决定系统交互；关键考虑为运营模型。

<a id="tag_07_03"></a>
### 6.3. 企业运营模型

<a id="b00350"></a>
确立互操作的关键是运营模型，即“向客户交付货物服务所需的业务流程集成和标准化程度”。它描述公司如何繁荣增长，比战略提供更稳定可行动视图，驱动执行基础设计。[1]

<a id="b00351"></a>
只共享文档所需ABB/SBB可能比共享结构化交易数据简单。若愿景含共享服务，应定义服务共享层次。

<a id="b00352"></a>
运营模型通常指示适当途径，应在A阶段或B阶段确定，最迟E阶段。

<a id="b00353"></a>
复杂/扩展企业可有多种模型，例如内部与供应链外部不同。

<a id="tag_07_04"></a>
### 6.4. 细化互操作性

<a id="b00355"></a>
实现互操作需要创建、管理、接受并执行现实的SMART标准：具体（Specific）、可度量（Measurable）、可行动（Actionable）、现实（Realistic）、有时限（Time-bound）。清楚的互操作性度量是成功的关键。

<a id="b00356"></a>
架构识别标准，促进式讨论检查符合当前或新兴文化的务实途径。

<a id="b00357"></a>
细化至无歧义满足企业内外需要；程度、类型和高层目标应成为EA战略方向的一部分或被其引用。

<a id="b00358"></a>
以转型战略实例化，纳入目标定义、在过渡架构务实实施；更新汇总差距及依赖，捕获研讨全部输出。

<a id="b00359"></a>
加拿大国防部及北约为共享信息制定四个程度示例：

<a id="b00360"></a>
- 1非结构化交换：人可理解的自由文本，如运营估算、分析和文稿。
- 2结构化交换：人可理解、供手工和/或自动处理，但仍需手工编制、接收和/或分发消息。
- 3无缝共享数据：基于共同交换模型在系统间自动共享。
- 4无缝共享信息：扩展3，通过协作应用的数据处理普遍解释信息。

<a id="b00361"></a>
各程度应技术性细化。例如3可分：

<a id="b00362"></a>
- 3A正式消息交换。
- 3B共同数据交换。
- 3C完整数据交换。
- 3D实时数据交换。

<a id="b00363"></a>
意图是细到技术上有意义的所需程度。

<a id="b00364"></a>
这些程度规定系统交换方式，为实施项目提供关键方向。

<a id="b00365"></a>
服务/业务及技术互操作也应有类似度量。

<a id="tag_07_05"></a>
### 6.5. 确定需求

<a id="b00367"></a>

<a id="b00368"></a>

<a id="b00369"></a>
以差距和业务场景为基础讨论处理IT问题，确保全部差距明确处理并验证组织需求。

<a id="b00370"></a>
后续开发必须识别职能依赖和边界，考虑市场产品，示例见《架构内容》构建块。

## 7. 业务转型准备度评估

<a id="b00387"></a>
评估量化组织接受变革准备程度的技术。

<a id="b00388"></a>
基于加拿大政府BTEP工作。

<a id="tag_08_01"></a>
### 7.1. 引言

<a id="b00390"></a>
创新愿景和B—D定义常意味着重大变革，其中人员最重要。例如信息整合、转向服务导向有重大人力影响；抗拒变化文化和狭窄技能可能使优秀架构无法推进。

<a id="b00391"></a>
理解准备程度、识别问题并纳入E/F实施迁移计划，是成功关键，需公司尤其HR、业务线和IT规划者合作。

<a id="b00392"></a>
建议活动：

<a id="b00393"></a>
- 确定准备因素。
- 用成熟度模型呈现。
- 评估及评级。
- 评估各因素风险并识别缓解改进行动。
- 将行动纳入E/F计划。

<a id="tag_08_01_01"></a>
#### 7.1.1. 业务转型使能项目BTEP

<a id="b00395"></a>
提供识别转型问题的指导。

<a id="b00396"></a>
建议全部项目至少开展准备评估，确定、分析、评级一组因素，深入理解挑战机会。许多挑战直接转为需处理监控、可能缓解的风险。

<a id="b00397"></a>
以下按BTEP及经验教训描述。各组织因素准则独特，但多数相似。

<a id="tag_08_02"></a>
### 7.2. 确定准备因素

<a id="b00399"></a>
先确定影响基线至目标转型的因素。

<a id="b00400"></a>
最好由跨组织人员参加促进式工作坊，兼顾各种视角；以暂定清单让参与者复用、拒绝、增补、替换。BTEP示例：

<a id="b00401"></a>
- 愿景：清楚定义沟通成果，管理者明确战略和具体目标，业务牵头、IT输入，有可预测且证明有效的愿景到需求流程；驱动、范围、途径全组织明确。
- 愿望、意愿与决心：想达结果、愿接受工作影响、坚持完成；积极讨论影响并明确接受，分配财务人力，高管清楚传达努力和收益；有善始善终、及时结案记录，大家认为正确。
- 需要：有迫切理由，明确不做将不能做什么、做成能做什么；失败后果可见且理解，成功准则明确沟通。
- 商业论证：聚焦必须实现的具体收入或节省，形成成功动力，明确组织承诺目标。
- 资金：明确资金来源，满足潜在支出。
- 赞助与领导：广泛共享但不稀释问责，使各方聚焦战略；适当高管能在高层阐明捍卫需要，持续参与。
- 治理：让有利益或责任者参与支持，服务公司利益和目标；明确利益责任，鼓励整体非局部目标，有跨领域管理记录、实质而非象征参与，持续评审挑战并接受外部建议。
- 问责：分配具体适当责任、认可可度量期望，决策与责任及影响所在一致，也与成功收益、失败后果承受者一致。
- 可行途径与执行模型：任务途径合理、环境支持、基于已证方法；客户与承建/总包关系明确，已有经验、流程纪律技能治理，角色成熟稳定；沟通覆盖意识到技术细节，奖励良好变更、规划预防危机及新行为；实施监控纠偏明确，全程资源充分。
- IT执行容量：具备全部IT任务所需技能、工具、流程和管理；近期成功做过类似规模复杂度工作，有适当流程纪律技能及外采技能活动的合理决策模型。
- 企业执行容量：具备非IT任务及紧时限决策能力，近期成功做过至少一半规模复杂度工作；有相关流程纪律技能、持续项目组合管理能力，认识新技能知识与正式行为技能差距分析价值。
- 企业实施与运营能力：能实施转型要素及流程、吸收变化、持续在新环境运营；近期已证实能处理新系统流程变更，且有扎实、纪律化、流程驱动服务管理，运营维护支持既有系统。

<a id="b00402"></a>
定义后再开工作坊详细评估影响风险，以下说明准备方法。

<a id="tag_08_03"></a>
### 7.3. 呈现因素

<a id="b00404"></a>
以清楚、能最大化参与价值的方式呈现。

<a id="b00405"></a>
可将各因素转为成熟度模型，也作为复用治理资产，配标准表记录信息与推论。

<a id="b00406"></a>
模型应支持：

<a id="b00407"></a>
- 评估基线成熟度。
- 确定实现目标所需成熟度。
- 确定较短时间可达中间目标。

<a id="b00408"></a>
精心准备投入不小，但聚焦工作坊可快速处理大量因素，收回投入。

<a id="b00409"></a>
因素定义清晰、模型反映初步规划范围，使讨论聚焦有效。

<a id="b00410"></a>
提前传阅供评论，确保完整并让人员准备；图示含架构师建议目标状态，也发挥治理作用。

BTEP某因素示例见图7-1。

### 7.4. 评估因素

<a id="b00415"></a>
理想为多学科工作坊，用成熟度模型等在短时间覆盖大量内容。

<a id="b00416"></a>
逐因素模板加速评估并保持一致。

<a id="b00417"></a>
应处理三项：

<a id="b00418"></a>
- 因素愿景、评级、风险与行动。

<a id="tag_08_04_01"></a>
#### 7.4.1. 因素愿景

<a id="b00420"></a>
确定需演进到何处，先评基线再评目标。

<a id="b00421"></a>
如IT执行容量低，为实现愿景理想应高；可设中间目标，成熟度模型可指导。

<a id="tag_08_04_02"></a>
#### 7.4.2. 因素评级

<a id="b00423"></a>
愿景确定后，判断重要性及达到可接受状态的挑战。

<a id="b00424"></a>
BTEP评级可作为任何行业组织起点，按以下维度：

<a id="b00425"></a>
- 紧迫：转型开始前需行动。
- 准备状态：低（需大量工作）、一般（需一些工作）、可接受（有问题但无阻断）、良好（仅小问题）、高（无问题）。
- 修复难度：无需行动、容易、中等、困难。

详细表之外宜有管理汇总，见图7-2。

<a id="tag_08_04_03"></a>
#### 7.4.3. 风险与行动

<a id="b00430"></a>
评级后导出使因素转为有利状态的行动。

<a id="b00431"></a>
本地原文指向第9章流程，评风险并估影响、频率。

<a id="b00432"></a>
逐项评估、列改进，先查架构已有行动，再新增。

<a id="b00433"></a>
新行动正式纳入形成中的实施迁移计划。

<a id="b00434"></a>
行动旨在缓解风险、形成可接受剩余风险，纳入风险管理并在实施中密切监控。

<a id="tag_08_05"></a>
### 7.5. 准备度与迁移规划

<a id="b00436"></a>
现实评估是E启动、F完成战略迁移规划的关键输入。判断转型行动是否在关键路径及影响；员工不会用、支持未准备好时，部署新IT能力没有意义。

<a id="b00437"></a>
G阶段持续监控，通过IT治理快速纠偏，确保可实施。

<a id="b00438"></a>
评估为动态文档，在规划执行过渡架构时发挥关键作用。

<a id="tag_08_06"></a>
### 7.6. 推介实施计划

<a id="b00440"></a>
在识别缓解转型问题、将行动纳入愿景和计划的整体推介方案前，不应广泛传播架构定义。

<a id="b00441"></a>
如信息整合可能导致数百岗位流失，应先有人力转型计划、再培训或求职支持，后宣布。

<a id="b00442"></a>
转型工作坊是沟通计划关键，使组织关键人员评估影响、理解愿景定义，形成主人翁意识，认可架构师为有价值的管理人。

<a id="b00443"></a>
因素判断形成跨企业理解，为实施迁移计划提供洞察。

<a id="b00444"></a>
该计划应含沟通，尤其让受影响员工知情；与工会及职工代表合作，可支持人性化、平稳过渡。

<a id="tag_08_07"></a>
### 7.7. 结论

<a id="b00446"></a>
实施须深入了解影响目标迁移的全部转型因素。随IT演进，关键常为文化而非技术；计划须兼顾。忽视人员文化、只看技术，会使实施无法兑现愿景承诺。

## 8. 风险管理

<a id="b00448"></a>
本章描述实施架构项目时缓解风险的技术。

<a id="tag_09_01"></a>
### 8.1. 引言

<a id="b00450"></a>
架构/业务转型总有风险，应事先识别、分类、缓解，以便全程跟踪。

<a id="b00451"></a>
缓解持续进行，触发因素（如并购）可能超出规划者范围，需持续监控语境。

<a id="b00452"></a>
架构师可识别缓解部分风险，但必须在治理框架内先接受、后管理。

<a id="b00453"></a>
考虑两个级别：

<a id="b00454"></a>
1. 初始风险：确定实施缓解前。
2. 剩余风险：实施缓解（若有）后。

<a id="b00455"></a>
过程如下各节，活动包括：

<a id="b00456"></a>
- 分类、识别、初始评估、缓解与剩余评估、监控。

<a id="tag_09_02"></a>
### 8.2. 风险分类

<a id="b00458"></a>
风险遍布EA及全部ADM阶段，分类使管理和缓解更迅速。

<a id="b00459"></a>
常按组织影响分类，使特定影响由特定治理层处理，见8.4。

<a id="b00460"></a>
常分进度、预算、范围，也可有客户转型关系、契约、技术、范围复杂性、公司环境、人员、客户接受风险。

<a id="b00461"></a>
也可按业务、信息、应用、技术域委派；若组织已有特定表达，EA部门应采用扩展，而非修改。

<a id="b00462"></a>
EA风险最终是公司风险，应同样或扩展分类，适当管理。

<a id="tag_09_03"></a>
### 8.3. 风险识别

<a id="b00464"></a>
成熟度和准备评估产生大量风险，需确定全程应对策略。

<a id="b00465"></a>
CMM可针对交付因素先识别基线目标，再识别行动；达不到目标的影响可揭示风险。本段原文交叉引用仍指第8章。

<a id="b00466"></a>
在风险管理计划语境记录，可用PMBOK、PRINCE2及政府方法模板。

<a id="b00467"></a>
通常含应急规划、跟踪评价风险级别、响应因素变化，以及记录报告沟通。

<a id="tag_09_04"></a>
### 8.4. 初始评估

<a id="b00469"></a>
按组织量表评效果和频率，组合形成初评。

<a id="b00470"></a>
测量无固定规则，以下基于现有最佳实践。

<a id="b00471"></a>
效果示例：

<a id="b00472"></a>
- 灾难性：关键财务损失，可能破产。
- 严重：多业务线重大损失，生产率下降、IT投资无回报。
- 边际：单业务线小损失，IT回报下降。
- 可忽略：对交付产品服务影响极小。

<a id="b00473"></a>
频率示例：

<a id="b00474"></a>
- 频繁：经常和/或持续。
- 很可能：一个转型周期数次。
- 偶尔：零星发生。
- 罕见：可能性很低，一周期大概不超过一次。
- 不太可能：一周期大概不发生。

<a id="b00475"></a>
以启发式但一致规则组合，企业影响可分：

<a id="b00476"></a>
- 极高E：转型很可能失败，后果严重。
- 高H：重要部分失败，某些目标未达。
- 中M：明显局部失败，威胁某些目标。
- 低L：某些目标不能完全成功。

<a id="b00477"></a>
分类推导见图8-1。

<a id="b00478"></a>
![原图](../web-2025/volumes/03-adm-techniques/assets/003-31_riskclass.png)

<a id="b00479"></a>
图8-1：风险分类方案

<a id="tag_09_05"></a>
### 8.5. 缓解与剩余评估

<a id="b00481"></a>
识别、规划、执行使风险降至可接受水平的行动。

<a id="b00482"></a>
从简单监控/接受，到业务连续性计划内完全冗余的全面应急，均可能，须考虑范围成本时间。

<a id="b00483"></a>
务实而系统进行，优先高频高影响，逐项缓解。

<a id="tag_09_06"></a>
### 8.6. 开展剩余风险评估

<a id="b00485"></a>
确定每项风险的缓解行动后，重新评估效果与发生频率，再计算影响，检查缓解是否真正带来可接受的差异。缓解往往耗费大量资源；为使剩余风险很小或不存在而付出的重大支出，应受到质疑。这里不把原文改写为“缓解改善很小”，也不据此自动决定接受风险。

<a id="b00486"></a>
缓解后剩余称剩余风险。必须真正降低企业影响，不能仅移至同样高的象限。例如频繁/灾难改为频繁/严重，仍极高，需重新考虑行动。

<a id="tag_09_07"></a>
### 8.7. 监控与治理（G阶段）

<a id="b00491"></a>
剩余风险须经IT治理批准，若需业务接受，也可能进入公司治理。

<a id="b00492"></a>
接受后仔细监控缓解执行，确保面对剩余而非初始风险；工作表作为治理制品，在G阶段保持更新并监控。

<a id="b00493"></a>
可识别未缓解关键风险，可能触发全部或部分ADM周期。

<a id="tag_09_08"></a>
### 8.8. 小结

<a id="b00495"></a>
风险管理是EA组成部分，鼓励采用公司方法或据本章扩展；没有正式方法时，可作最佳实践。

## 9. 架构备选方案与取舍

<a id="b00497"></a>
本章描述识别目标备选及其取舍的技术。

<a id="tag_10_01"></a>
### 9.1. 概念

<a id="b00499"></a>
往往多个目标方案均符合愿景、原则和需求。应识别并理解可能性和取舍；架构通常要平衡竞争力量。向利益相关者展示备选，可揭示影响最终目标的隐藏议程、原则、需求。

<a id="tag_10_02"></a>
### 9.2. 方法

<a id="b00501"></a>
通常没有单一方案满足全部关注点，可调查并讨论。为简化常逐域定义，再合并整体分析。

<a id="tag_10_02_01"></a>
#### 9.2.1. 准则

<a id="b00509"></a>
来自多种架构输入，考虑原则、需求、愿景、关注点影响。

<a id="b00510"></a>
各方案优缺点需讨论商定，可能需额外视点视图探索依赖、风险、不确定性。

<a id="b00511"></a>
按准则的典型类型包括：

<a id="b00512"></a>
- 灵活方案。
- 实现时间成本，含过渡和稳定平台期。
- 估计收益实现时间。
- 遵循风格或指导。
- 交付方式：复用、开发、购买。
- 实施对业务能力影响最小。
- 风险及所需缓解最小等。

<a id="tag_10_02_02"></a>
#### 9.2.2. 识别备选

<a id="b00514"></a>
用愿景、原则、需求识别可能方案集。

<a id="b00515"></a>
对每项：

<a id="b00516"></a>
1. 定义概览准则，来自愿景原则需求，可用于不同抽象层及阶段。
2. 描述架构，创建足够理解影响的视图及信息，不宜过细，但须良好影响评估，明确与其他方案、现有全景依赖，完整理解实施影响。
3. 估基线差距；基线未定义时为非正式分析，见第5章。
4. 理解跨全景影响和取舍：对现有及过渡架构、在行或计划项目的影响；项目对本方案约束；同项目其他阶段影响；约束其他架构的需求/变更请求；最终价值、填补未来差距程度及迭代目的。

<a id="tag_10_02_03"></a>
#### 9.2.3. 选择并详细定义

<a id="b00518"></a>
从备选选择或定义另一方案，用取舍分析解决冲突：

<a id="b00519"></a>
1. 理解优缺点。
2. 按准则一致程度比较。
3. 与利益相关者协作，选最适合或组合特征。
4. 组装方案：最终描述；处理全部视点；细节足以决策；解决全景影响；正式评审决定方案及资金。

<a id="b00520"></a>
影响分析仅做到足以在方案间选择。
