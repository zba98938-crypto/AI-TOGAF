## 2. 建立架构能力

<a id="b00041"></a>
本章指导如何运用ADM建立架构能力。

<a id="tag_02_01"></a>
### 2.1. 概述

<a id="b00043"></a>
与其他业务能力一样，企业架构能力的建立可以得到TOGAF架构开发方法（ADM）的支持。成功应用ADM将形成以客户为中心、增加价值且可持续的架构实践：使能业务、帮助最大化投资价值，并主动识别获取业务收益及管理风险的机会。

<a id="b00044"></a>
在组织内建立可持续的架构实践，可以遵循建立其他能力（例如业务流程管理BPM能力）的相同方法。ADM是设计此类能力并治理其实施的理想方法。以“在组织内建立架构实践”为特定架构愿景来应用ADM，就能实现这一目标。

<a id="b00045"></a>
不应把建立架构实践看作架构项目中的一个阶段，或一次性项目。它是一项持续的工作纪律，为治理并使能组织的架构交付提供语境、环境和资源。在该环境中执行的架构项目，可能要求改变架构实践，从而触发另一轮ADM以扩展架构实践。

<a id="b00046"></a>
组织实施任何能力都需要设计业务、数据、应用和技术四个领域架构。因此，在组织内建立架构实践需要设计：

<a id="b00047"></a>
- 架构实践的业务架构：突出架构治理、架构过程、架构组织结构、架构信息要求、架构产品等。
- 数据架构：定义组织的企业连续体和架构存储库的结构。
- 应用架构：规定使能架构实践所需的功能和/或应用服务。
- 技术架构：描述架构实践的基础设施要求及部署，以支持架构应用和企业连续体。

<a id="b00048"></a>
下文在ADM各阶段的语境中解释建立架构实践的步骤。读者应参考《TOGAF标准——架构开发方法》的相应阶段，以理解各步骤的完整范围。本节突出各阶段中建立架构实践时特有且应考虑的关键方面；目的不是重复各阶段描述，而是指导在建立架构实践的语境中应用每个阶段。

<a id="tag_02_02"></a>
### 2.2. A阶段：架构愿景

<a id="b00050"></a>
在建立架构实践的语境中，本阶段旨在定义或复核架构实践的愿景、利益相关者和原则。本阶段关注整个架构实践，而非某个具体架构项目。

<a id="b00051"></a>
在此语境下理解各步骤时，应考虑：

<a id="b00052"></a>
- **建立项目**：着重履行必要程序，使项目得到认可，获得公司管理层的赞同以及必要业务线管理者的支持和承诺。应引用企业已采用的其他管理框架，说明本项目与这些框架的关系。
- **识别利益相关者与关注点、业务需求及架构愿景**：从业务信息系统和技术的角度，对架构实践的基线与目标环境给出最初的高层定义。
- **识别业务目标和业务驱动因素**：理解这些目标与驱动，是使架构实践与业务对齐的必要条件。
- **定义范围**：架构实践范围的定义，是下一时期计划解决哪些架构事项的高层项目计划。
- **定义约束**：着重识别影响全部架构项目的企业范围约束。
- **复核架构原则，包括业务原则**：旨在定义治理和指导架构实践运行的原则。架构原则通常治理架构交付物，而架构实践原则关注架构实践的组织、内容、工具和过程。
- **制定架构工作说明并获得批准**：本步骤形成架构实践的愿景和范围。

<a id="b00053"></a>
本阶段还可以考虑进行架构成熟度评估，相关指导见《TOGAF系列指南：架构成熟度模型》。

<a id="tag_02_03"></a>
### 2.3. B阶段：业务架构

<a id="b00055"></a>
在建立或细化架构实践的业务架构时，本阶段的关键关注领域包括：

<a id="b00056"></a>
- **架构本体**：定义组织使用的架构术语及其定义，建立共同理解。
- **架构过程**：以ADM为基础，根据组织要求及架构实践愿景进行定制；开发指导见《TOGAF标准——架构开发方法》。所需的架构治理过程应纳入整体架构过程。
- **架构视点与视图**：列出架构实践应处理的全部视点和视图；由已识别的架构实践利益相关者指导定义。其中应包含架构治理视点，输出指导见《TOGAF标准——架构内容》。
- **架构框架**：描述架构实践将产生的各种交付物、它们之间的关系和依赖，以及治理其设计的规则和指导。已定义的视点与视图应用于指导框架定义；《架构开发方法》和《架构内容》可辅助描述该框架。
- **架构问责矩阵**：定义架构实践中的角色，将角色对架构交付物和过程的问责责任分配清楚；包括所需治理结构和角色。指导见《架构开发方法》、本卷第4章“架构委员会”、第3章“架构治理”及《TOGAF系列指南：架构技能框架》。
- **架构绩效度量**：识别和描述用于按既定愿景与目标监控架构实践绩效的度量。
- **架构治理框架**：是已定义架构过程及架构问责矩阵的一个特定视图。

<a id="tag_02_04"></a>
### 2.4. C阶段：数据架构

<a id="b00058"></a>
架构实践的数据架构规定并治理组织的企业连续体和架构存储库的结构。应依据架构框架定义该数据架构。有时它也称为架构实践的元模型。

<a id="tag_02_05"></a>
### 2.5. C阶段：应用架构

<a id="b00060"></a>
架构实践的应用架构定义：为生成、维护、发布、分发和治理架构框架规定的交付物，需要哪些功能。建模工具集应是重点，但不应是唯一重点；选择工具集的指导见《TOGAF标准——架构开发方法》。为回应框架中特定视图而发布架构交付物，有时需要专用或定制功能，这一点不应忽略。

<a id="tag_02_06"></a>
### 2.6. D阶段：技术架构

<a id="b00062"></a>
架构实践的技术架构应定义支持该实践的技术基础设施。

<a id="tag_02_07"></a>
### 2.7. E阶段：机会与解决方案

<a id="b00064"></a>
在规划建立架构实践的这一阶段，必须重点考虑所需的组织变革以及怎样实现该变革。

<a id="tag_02_08"></a>
### 2.8. F阶段：迁移规划

<a id="b00066"></a>
本阶段不应只关注信息系统架构组件，也应包括业务架构。架构过程和框架的采用，将显著影响组织内架构实践的整体建立。

<a id="tag_02_09"></a>
### 2.9. G阶段：实施治理

<a id="b00068"></a>
本阶段应关注架构实践业务架构的实施。改变组织实践，使其采用更结构化、更有纪律的方法是一项挑战，应运用适当的组织变革技术处理。

<a id="tag_02_10"></a>
### 2.10. H阶段：架构变更管理

<a id="b00070"></a>
本阶段管理架构实践自身架构的变化。这些变化通常由架构项目的执行触发。典型变化是需要一种新的架构交付物，它会影响架构实践的所有领域架构。

<a id="tag_02_11"></a>
### 2.11. 需求管理

<a id="b00072"></a>
理解和管理架构实践的需求至关重要。需求应清楚表述，并与架构实践愿景对齐。

<a id="b00073"></a>
构建企业架构能力的补充指导，见《TOGAF系列指南：TOGAF领导者指南——建立并演进EA能力》。

<a id="chap03"></a>
## 3. 架构治理

<a id="b00075"></a>
本章提供架构治理的框架和指导。

<a id="tag_03_01"></a>
### 3.1. 引言

<a id="b00077"></a>
本节描述治理的性质及治理层次。

<a id="tag_03_01_01"></a>
#### 3.1.1. 企业内的治理层次

<a id="b00079"></a>
架构治理是在企业范围管理和控制企业架构及其他架构的实践与取向。

<a id="b00080"></a>
架构治理通常在治理结构的层次体系中运行，而非孤立运行。尤其在大型企业中，下列各项都可能作为具有自身纪律和过程的独立治理领域存在：

<a id="b00081"></a>
- 公司治理。
- 技术治理。
- IT治理。
- 架构治理。

<a id="b00082"></a>
在整个企业内，每个治理领域都可能存在于全球、区域和本地等多个地理层次。

<a id="b00083"></a>
因此，公司治理是一个广泛主题，超出了TOGAF这类企业架构框架的范围。

<a id="b00084"></a>
本小节及相关小节关注架构治理；由于它通常在前述治理结构层次体系中运行，文中会结合企业整体治理语境进行说明。

<a id="b00085"></a>
具体而言，本节及后续各节旨在：

<a id="b00086"></a>
- 概述治理作为独立纪律的性质。
- 描述企业内架构治理通常发挥作用的治理语境。
- 描述一个可以裁剪应用的实用架构治理框架，既可用于企业架构，也可用于其他IT架构。

<a id="tag_03_01_02"></a>
#### 3.1.2. 治理的性质

<a id="tag_03_01_02_01"></a>
##### 3.1.2.1. 治理的一般视角

<a id="b00089"></a>
治理的实质是确保业务适当地开展。其重点更多是指导以及有效、公平地使用资源，以确保组织战略目标的可持续性，而较少是显式控制和严格遵守规则。

<a id="b00090"></a>
以下概述经济合作与发展组织（OECD）识别的公司治理基本原则：

<a id="b00091"></a>
- 关注股东的权利、角色及公平待遇。
- 信息披露、透明度以及董事会的职责。
- 确保对组织的可靠战略指导、董事会对管理层的有效监督，以及董事会对公司和股东承担问责责任。
- 董事会负责复核和指导公司战略，设定管理绩效目标并监控实现情况。

<a id="b00092"></a>
OECD据此描述了对治理的传统理解：“……指导和控制商业公司的制度。公司治理结构规定公司中不同参与者之间权利与职责的分配，例如董事会、管理者、股东及其他利益相关者，并明确公司事务决策的规则与程序。由此，它也提供设定公司目标、实现目标以及监控绩效的结构。”（来源：OECD，2001年。）

<a id="tag_03_01_02_02"></a>
##### 3.1.2.2. 治理的特征

<a id="b00094"></a>
以下特征改编自Naidoo（2002年）的《公司治理》，用以突出组织及其与各相关方交往时采用治理的价值与必要性：

<a id="b00095"></a>
纪律（Discipline）

<a id="b00096"></a>
所有相关方承诺遵循组织确立的程序、过程和权限结构。

<a id="b00097"></a>
透明度（Transparency）

<a id="b00098"></a>
全部已执行行动及其决策支持信息，均可供获得授权的组织方和供应方检查。

<a id="b00099"></a>
独立性（Independence）

<a id="b00100"></a>
确立全部过程、决策方式及机制时，应使潜在利益冲突最小化或避免其发生。

<a id="b00101"></a>
问责性（Accountability）

<a id="b00102"></a>
组织内可识别的群体，例如采取行动或作出决定的治理委员会，应获得授权并对其行动负责。

<a id="b00103"></a>
责任（Responsibility）

<a id="b00104"></a>
每个缔约方都必须对组织及其利益相关者负责任地行事。

<a id="b00105"></a>
公平性（Fairness）

<a id="b00106"></a>
所作决定、所用过程及其实施，均不得让某个特定方获得不公平优势。

<a id="tag_03_01_03"></a>
#### 3.1.3. 技术治理

<a id="b00108"></a>
技术治理控制组织怎样在商品及服务的研究、开发和生产中运用技术。它可能包含IT治理活动，但范围往往更广。

<a id="b00109"></a>
由于技术遍布组织各方面，技术治理是多数组织的关键能力、要求及资源。

<a id="b00110"></a>
近期研究显示，许多组织需要管理的无形资产比有形资产占比更大。多数此类无形资产是信息和数字资产，说明业务愈加依赖IT，因此IT的治理，即IT治理，正成为技术治理中更重要的一部分。

<a id="b00111"></a>
这些趋势也凸显：业务不仅依赖信息本身，还依赖创造、交付和消费信息的过程、系统及结构。许多行业日益通过无形资产增加价值，风险管理因而必须被视为理解和调节新挑战、威胁与机会的关键。

<a id="b00112"></a>
组织日益依赖IT的不只是运营和盈利能力，其声誉、品牌乃至价值观，也依赖同样的信息及支撑技术。

<a id="tag_03_01_04"></a>
#### 3.1.4. IT治理

<a id="b00114"></a>
IT治理提供连接IT资源、信息与企业目标及战略的框架和结构。它还把规划、获取、实施及监控IT绩效的最佳实践制度化，以确保企业IT资产支持业务目标。

<a id="b00115"></a>
近年来，IT治理已成为现代企业有效治理不可分割的一部分。业务日益依赖IT支持关键职能与流程；要成功获取竞争优势，企业需要有效管理遍布组织的复杂技术，以快速、安全地响应业务需求。

<a id="b00116"></a>
此外，信息系统灾难与电子欺诈事件的报告增多，推动全球监管环境日益要求企业更严格地控制信息。管理IT相关风险，现已被广泛接受为企业治理的关键部分。

<a id="b00117"></a>
因此，必须在高层管理支持下确立IT治理战略及实施该战略的适当组织，明确谁拥有企业IT资源，尤其是谁最终负责其企业范围的集成。

<a id="tag_03_01_04_01"></a>
##### 3.1.4.1. IT控制框架——COBIT

<a id="b00119"></a>
与公司治理一样，IT治理主题广泛，超出TOGAF这类企业架构框架的范围。COBIT框架（Control OBjectives for Information and related Technology，信息及相关技术控制目标）是IT治理详细信息的良好来源。它是用于控制IT的开放标准，由IT治理协会（ITGI）开发和推广，由信息系统审计与控制协会（ISACA）出版。COBIT控制措施可为运行符合性策略提供有用辅助。

<a id="tag_03_01_05"></a>
#### 3.1.5. 架构治理概述

<a id="tag_03_01_05_01"></a>
##### 3.1.5.1. 架构治理特征

<a id="b00122"></a>
架构治理是在企业范围管理和控制企业架构及其他架构的实践与取向，包括：

<a id="b00123"></a>
- 对所有架构组件和活动的创建及监控实施一套控制机制，确保在组织内有效引入、实施并演进架构。
- 实施一套机制，确保符合内部与外部标准以及监管义务。
- 建立过程，支持在约定参数内有效管理上述过程。
- 发展相应实践，确保向组织内外清楚识别的利益相关者群体承担问责责任。

<a id="tag_03_01_05_02"></a>
##### 3.1.5.2. 架构治理作为董事会层面的职责

<a id="b00125"></a>
本节旨在推动IT与架构治理的开放，使与架构活动及制品有关的业务职责能够得到阐明和管理。

<a id="tag_03_01_05_03"></a>
##### 3.1.5.3. TOGAF标准与架构治理

<a id="b00127"></a>
TOGAF ADM的G阶段（见《TOGAF标准——架构开发方法》）专门处理实施治理，即通过变革项目实现架构。实施治理只是架构治理的一个方面；架构治理涵盖企业内企业架构及其他架构开发和演进各方面的管理与控制。

<a id="b00128"></a>
架构治理需要架构治理框架的支持，见§3.2。该框架辅助识别有效过程，使架构治理相关的业务职责能够得到有效阐明、沟通和管理。

<a id="tag_03_02"></a>
### 3.2. 架构治理框架

<a id="b00130"></a>
本节描述架构治理的概念框架和组织框架。

<a id="b00131"></a>
如前所述，TOGAF ADM的G阶段（见《TOGAF标准——架构开发方法》）专门处理实施治理，即通过变革项目实现架构。

<a id="b00132"></a>
实施治理只是架构治理的一个方面；架构治理涵盖企业内企业架构及其他架构开发和演进各方面的管理与控制。

<a id="b00133"></a>
架构治理需要下述架构治理框架的支持。它是可根据企业现有治理环境裁剪的一般框架，旨在辅助识别有效过程与组织结构，使架构治理相关业务职责能够得到有效阐明、沟通和管理。

<a id="tag_03_02_01"></a>
#### 3.2.1. 架构治理框架——概念结构

<a id="tag_03_02_01_01"></a>
##### 3.2.1.1. 关键概念

<a id="b00136"></a>
从概念上说，架构治理是一种方法、一系列过程、一种文化取向，以及一组有明确承担者的职责，共同确保组织架构的完整性和有效性。

<a id="b00137"></a>
关键概念见图3-1。

<a id="b00138"></a>
![原图](../web-2025/volumes/06-ea-capability-and-governance/assets/004-50_concepts.png)

<a id="b00139"></a>
图3-1：架构治理框架——概念结构

<a id="b00140"></a>
把过程、内容和语境分开，是支持架构治理举措的关键：它允许引入新的治理材料，例如法律、监管、标准或立法材料，而不过度影响过程。这种与内容无关的方法确保框架具有灵活性。过程通常独立于内容，并采用经过验证的最佳实践方法开展主动治理。

<a id="b00141"></a>
架构治理框架是企业连续体不可分割的组成部分，管理与架构本身及架构治理过程有关的全部内容。

<a id="tag_03_02_01_02"></a>
##### 3.2.1.2. 关键架构治理过程

<a id="b00143"></a>
需要治理过程来识别、管理、审计和传播与架构管理、契约及实施有关的全部信息。这些过程确保持续监控全部架构制品和契约、原则及运营级别协议（OLA），并清楚审计所作的全部决定。

<a id="b00144"></a>
政策管理与纳管（Policy Management and Take-On）

<a id="b00145"></a>
全部架构修订、契约及支撑信息必须通过正式过程纳入治理，以登记、验证、确认、管理和发布新增或更新内容。这些过程确保其与既有治理内容有序整合，使所有相关方、文档、契约及支撑信息得到管理和审计。

<a id="b00146"></a>
符合性（Compliance）

<a id="b00147"></a>
应持续按照服务级别协议（SLA）、运营级别协议（OLA）、标准及监管要求进行符合性评估，以确保稳定性、遵循性及绩效监控。评估结果须经过复核，并根据治理框架定义的判据接受或拒绝。

<a id="b00148"></a>
豁免（Dispensation，也称Waiver）

<a id="b00149"></a>
当所评估领域——设计、运营、服务级别或技术——不符合要求时，可以拒绝该符合性评估。在这种情况下，该领域可以：

<a id="b00150"></a>
1. 调整或重新对齐，以满足符合性要求。
2. 请求豁免。

<a id="b00151"></a>
当符合性评估被拒绝时，可通过豁免提供达到临时遵循要求的替代途径。豁免针对特定期限及一组明确的服务与运营判据授予，这些判据必须在豁免有效期内得到执行。豁免不能无限期授予；其作用是在实施方式和时点上提供一定灵活性，同时确保达到服务级别和运营级别。豁免具有期限，因此成为符合性周期的重要触发因素。

<a id="b00152"></a>
监控与报告

<a id="b00153"></a>
需要绩效管理，确保按约定判据管理运营和服务要素，包括依据SLA和OLA进行监控、为调整提供反馈以及报告。

<a id="b00154"></a>
内部管理信息在“环境管理”中考虑。

<a id="b00155"></a>
业务控制

<a id="b00156"></a>
业务控制是为确保遵循组织业务政策而启动的过程。

<a id="b00157"></a>
环境管理

<a id="b00158"></a>
环境管理识别确保治理框架所依托的存储库环境有效、高效所需的全部服务，包括物理及逻辑存储库管理、访问、沟通，以及所有用户的培训和认可。

<a id="b00159"></a>
全部架构制品、服务协议、契约及支撑信息必须通过正式过程纳入治理，以登记、验证、确认、管理和发布新增或更新内容。这些过程确保其与既有治理内容有序整合，使所有相关方、文档、契约及支撑信息得到管理和审计。

<a id="b00160"></a>
应在治理环境中定义若干管理过程，以实现对服务和过程环境的管理，包括用户管理、为控制自身过程而定义的内部SLA，以及管理信息报告。

<a id="b00165"></a>
- 全球治理委员会。
- 本地治理委员会。
- 设计权威机构。
- 工作组。

##### 3.2.2.3. 运营收益

<a id="b00174"></a>
如图3-2所示，对组织架构的治理，不仅直接控制和指导开发与实施，还延伸到已实施架构的运营。

<a id="b00175"></a>
持续治理架构已被发现能带来下列收益：

<a id="b00176"></a>
- 将IT过程、资源和信息与组织战略及目标相连。
- 整合并制度化IT最佳实践。
- 与COBIT等行业框架对齐，包括规划与组织、获取与实施、交付与支持，以及监控IT绩效。
- 使组织充分利用信息、基础设施、硬件和软件资产。
- 保护组织底层数字资产。
- 支持监管与最佳实践要求，如可审计性、安全性、责任和问责性。
- 推动可见的风险管理。

<a id="b00177"></a>
这些收益表明：TOGAF架构治理框架是一种方法、一系列过程、一种文化取向及一组有明确承担者的职责，共同确保组织架构的完整性和有效性。

<a id="tag_03_03"></a>
### 3.3. 架构治理实践

<a id="b00179"></a>
本节提供有效实施架构治理的实用指导。

<a id="tag_03_03_01"></a>
#### 3.3.1. 架构治理的关键成功因素

<a id="b00181"></a>
要成功开展架构治理并有效管理架构契约，应考虑：

<a id="b00182"></a>
- 对架构政策、程序、角色、技能、组织结构和支持服务的提交、采用、复用、报告及退役采用最佳实践。
- 具备支持架构治理过程及报告要求的组织职责和结构。
- 整合工具与过程，从程序及文化两方面促进这些过程的采用。
- 规定控制架构治理过程、豁免、符合性评估、SLA及OLA的判据。
- 识别对全部架构治理相关信息、服务和过程的有效性、效率、保密性、完整性、可用性、符合性及可靠性的内部和外部要求。

<a id="tag_03_03_02"></a>
#### 3.3.2. 有效架构治理战略的要素

<a id="tag_03_03_02_01"></a>
##### 3.3.2.1. 架构治理与公司政治环境

<a id="b00185"></a>
缺乏适当高层支持及公司政治环境对齐而强推的企业架构必然失败。要取得成功，企业架构必须反映组织需要。企业架构师若未参与业务战略制定，至少必须从根本上理解该战略及组织当前面对的业务问题。他们甚至可能需要参与系统部署过程，并最终承担技术架构实施所产生的投资和产品选择决定。

<a id="b00186"></a>
架构治理战略有三个重要要素，尤其关系到架构在企业内的接受与成功。它们本身也有独立意义，因此分别描述，同时构成任何有效架构治理战略不可分割的部分。

<a id="b00187"></a>
- 必须在高层管理支持下建立跨组织架构委员会，监督企业架构治理战略的实施，见第4章。
- 应建立完整的一组架构原则，指导、说明并支持组织通过IT完成使命的方式，见《TOGAF标准——ADM技术》。
- 应采用架构符合性策略，见第6章：采取具体措施，而不只是政策声明，确保符合架构，包括项目影响评估、正式架构符合性评审过程，还可能包括架构团队参与产品采购。

<a id="chap04"></a>
## 4. 架构委员会

<a id="b00189"></a>
本章指导如何建立和运行企业架构委员会。

<a id="tag_04_01"></a>
### 4.1. 角色

<a id="b00191"></a>
成功的架构治理战略中，一个关键要素是建立跨组织架构委员会，监督该战略实施，见第3章。该机构应代表架构的所有关键利益相关者，通常由负责复核及维护整体架构的一组高管组成。

<a id="b00192"></a>
架构委员会的范围可以是全球、区域或业务线。尤其在大型企业中，委员会通常至少包含组织内两个层次的代表：

<a id="b00193"></a>
- 本地层次：领域专家，承担业务线责任。
- 全球层次：承担整个组织的责任。

<a id="b00194"></a>
在这些情况下，每个委员会都应有清楚识别及表述的：

<a id="b00195"></a>
- 职责及决策能力。
- 职权范围及权限边界。

<a id="tag_04_02"></a>
### 4.2. 职责

<a id="b00197"></a>
通常，架构委员会负责并就实现下列部分或全部目标承担问责责任：

<a id="b00198"></a>
- 为全部架构相关决策提供基础。
- 保证各子架构之间的一致性。
- 建立组件复用目标。
- 保持企业架构灵活性，以适应变化的业务需要并利用新技术。
- 执行架构符合性要求。
- 提高组织架构纪律的成熟度。
- 确保采用以架构为基础的开发方式。
- 为超出权限范围的决定提供可见的升级处理能力。

<a id="b00199"></a>
从运营角度，还应承担：

<a id="b00200"></a>
- 对架构契约进行各方面的监控与控制。
- 定期召开会议。
- 确保有效且一致地管理和实施架构。
- 解决上报的歧义、问题和冲突。
- 提供建议、指导和信息。
- 确保符合架构，并授予符合技术战略及目标的豁免。
- 当相似豁免反复被请求并授予时，考虑改变政策，例如排期、SLA或新型服务要求。
- 确保与架构契约实施有关的全部信息在受控条件下发布，并可供授权方获取。
- 验证报告的服务级别、成本节约等。

<a id="b00201"></a>
从治理角度，架构委员会还负责：

<a id="b00202"></a>
- 产生可用的治理材料与活动。
- 通过共识及授权发布，提供正式接受和批准架构的机制。
- 提供基本控制机制，确保架构有效实施。
- 建立和维护架构实施、企业架构所体现的架构战略与目标、以及业务战略目标之间的联系。
- 识别偏离架构的情况，并通过豁免或政策更新规划重新对齐的活动。

<a id="tag_04_03"></a>
### 4.3. 建立架构委员会

<a id="tag_04_03_01"></a>
#### 4.3.1. 企业架构发起支持

<a id="b00205"></a>
在许多公司中，最初架构工作的高层发起人是CIO或其他高管。然而，要获得广泛公司支持，发起机构比个人更有影响力。本文称该机构为“架构委员会”，但名称并不重要；无论如何命名，它都是负责复核和维护战略架构及全部子架构的高层群体。

<a id="b00206"></a>
架构委员会是企业内架构工作的发起支持者，但委员会自身也需要来自公司最高层的高管发起支持。这种承诺必须贯穿规划过程，并延续到架构项目维护阶段。许多架构规划失败的公司，都明显缺乏高层参与及对项目的鼓励。

<a id="b00207"></a>
公司董事会是经常被忽略的架构委员会成员来源。这些成员通常具有关于业务及竞争的多样知识。由于他们显著影响业务愿景和目标，他们可能有效验证IT战略与业务目标的对齐。

<a id="tag_04_03_02"></a>
#### 4.3.2. 委员会规模

<a id="b00209"></a>
建议架构委员会设四至五名常任成员，不超过十名。为在保持合理规模的同时长期确保企业范围代表性，可以轮换成员，把决策权和责任交给不同高管。部分成员可能因时间限制无法长期积极参与，这本身也可能要求轮换。

<a id="b00210"></a>
组织可采取代表制建立架构委员会，为每位成员分配其在会议上代表的利益相关者。成员因而有责任与这些利益相关者会面，获取他们对议程各项的意见。

<a id="b00211"></a>
但委员会必须保持一定连续性，避免公司架构从一套理念摇摆到另一套理念。一种兼顾轮换与连续性的方法，是为成员规定任期，并使任期在不同时间到期。

<a id="b00212"></a>
最初架构工作结束后的持续架构过程中，可以重新规定委员会职权。高层发起人通常复核委员会工作并评价有效性；必要时更新或改变架构符合性评审过程。

<a id="tag_04_03_03"></a>
#### 4.3.3. 委员会结构

<a id="b00214"></a>
TOGAF架构治理框架（§3.2）提供一般组织框架，把架构委员会放在企业更广泛治理结构中定位。该结构识别主要组织群体、职责及群体间关系。它是最佳实践结构，可因组织形式及既有结构而改变。

<a id="b00215"></a>
必须考虑组织规模、形式以及IT职能的实施方式，以此为基础，在整体治理环境中设计委员会结构。尤其应考虑全球所有权与本地实施的概念，以及整合来自所有架构实施领域的新概念和新技术。

<a id="b00216"></a>
委员会结构应反映组织形式。所需架构治理结构完全可能超出TOGAF架构治理框架（§3.2）的一般结构。组织可能需要结合现有IT治理过程、组织结构及能力，通常包括以下机构类型：

<a id="b00217"></a>
- 全球治理委员会。
- 本地治理委员会。
- 设计权威机构。
- 工作组。

<a id="tag_04_04"></a>
### 4.4. 架构委员会的运行

<a id="b00219"></a>
本节尤其从治理角度描述架构委员会的运行。

<a id="tag_04_04_01"></a>
#### 4.4.1. 概述

<a id="b00221"></a>
委员会会议应有清楚的议程，明确目标、内容范围及规定行动。一般应遵循最佳实践，例如COBIT框架所述实践，见§3.1.4.1。

<a id="b00222"></a>
这些会议将在以下方面提供关键方向：

<a id="b00223"></a>
- 支持产生高质量治理材料与活动。
- 通过共识和授权发布，提供正式接受的机制。
- 提供基本控制机制，确保架构有效实施。
- 建立并维护架构实施与组织既定业务及IT战略和目标之间的联系。
- 识别偏离契约之处，并通过豁免或政策更新规划重新对齐契约的活动。

<a id="tag_04_04_02"></a>
#### 4.4.2. 准备

<a id="b00225"></a>
每位参与者将收到议程及全部支撑文档，例如豁免请求、绩效管理报告等，并应熟悉其内容。

<a id="b00226"></a>
已向个人分配行动时，该个人负责报告行动进展。

<a id="b00227"></a>
每位参与者必须确认能否及是否出席委员会会议。

<a id="tag_04_04_03"></a>
#### 4.4.3. 议程

<a id="b00229"></a>
本节概述委员会会议议程的内容，仅描述各议程项的内容。

<a id="tag_04_04_03_01"></a>
##### 4.4.3.1. 前次会议纪要

<a id="b00231"></a>
纪要按组织标准规程记录以往委员会会议的详情。

<a id="tag_04_04_03_02"></a>
##### 4.4.3.2. 变更请求

<a id="b00233"></a>
本项通常是修订架构、原则等的变更请求，也可包含架构契约有关的业务控制，例如确保禁止拨打天气预报等高收费电话号码，并控制访问某些网站的数据流量。

<a id="b00234"></a>
任何变更请求都应在架构契约定义的约定权限层次及参数内提出。

<a id="tag_04_04_03_03"></a>
##### 4.4.3.3. 豁免

<a id="b00236"></a>
豁免是在正常运营参数之外请求改变既有架构、契约、原则等的机制。例如，不向某子公司提供服务；因特定业务原因请求不同寻常的服务级别；部署非标准技术或产品支持某项业务举措。

<a id="b00237"></a>
豁免针对特定期限及一组明确的服务和运营判据授予；这些判据必须在有效期内执行。豁免不能无限期授予，而是在实施方式与时点提供一定灵活性，同时确保达到服务及运营级别等要求。豁免具有期限，因此会触发架构符合性活动。

<a id="tag_04_04_03_04"></a>
##### 4.4.3.4. 符合性评估

<a id="b00239"></a>
依据SLA、运营级别协议（OLA）、成本目标及必要架构更新进行符合性评估。根据治理框架规定的判据，复核后接受或拒绝评估结果。架构符合性评估报告将包含所述详情。

<a id="tag_04_04_03_05"></a>
##### 4.4.3.5. 争议解决

<a id="b00241"></a>
本项识别经过符合性及豁免过程仍未解决、需进一步行动的争议；这些争议记录在符合性评估和豁免文档中。

<a id="tag_04_04_03_06"></a>
##### 4.4.3.6. 架构战略与方向文档

<a id="b00243"></a>
本项描述架构战略、方向和优先级，仅由全球架构委员会制定，应采用标准架构文档形式。

<a id="tag_04_04_03_07"></a>
##### 4.4.3.7. 已分配行动

<a id="b00245"></a>
本项报告以往会议分配的行动。使用行动跟踪器记录和维护所有已分配行动的状态，至少应包含：

<a id="b00246"></a>
- 引用编号。
- 优先级。
- 行动描述。
- 行动责任人。
- 行动详情。
- 提出日期。
- 到期日期。
- 状态。
- 类型。
- 解决日期。

<a id="tag_04_04_03_08"></a>
##### 4.4.3.8. 契约文档管理

<a id="b00248"></a>
本项正式接受架构文档的更新和变化，以便后续发布。

<a id="tag_04_04_03_09"></a>
##### 4.4.3.9. 其他事项（AOB）

<a id="b00250"></a>
描述上述各项未直接覆盖的问题。可以不在议程中预先描述，但应在会议开始时提出。全部支撑文档必须按照其他架构治理文档的相同方式管理。

<a id="tag_04_04_03_10"></a>
##### 4.4.3.10. 会议安排

<a id="b00252"></a>
应详细列出并公布全部会议日期。

<a id="chap05"></a>
## 5. 架构契约

<a id="b00254"></a>
本章指导如何定义和使用架构契约。

<a id="tag_05_01"></a>
### 5.1. 角色

<a id="b00256"></a>
架构契约是开发合作方与发起支持者就架构交付物、质量及适用性达成的共同协议。通过有效架构治理实现这些协议的成功实施，见第3章。对契约管理采用受治理的方法，可确保：

<a id="b00257"></a>
- 持续监控机制，检查组织内全部架构相关活动的完整性、变化、决策和审计。
- 遵循既有或开发中架构的原则、标准和要求。
- 识别架构开发和实施各方面风险，既包括内部开发对已接受标准、政策、技术和产品的遵循，也包括架构运营方面的风险，使组织能在有韧性的环境中持续开展业务。
- 具备一组过程和实践，确保全部架构制品开发及使用中的问责性、责任和纪律。
- 正式理解负责契约的治理组织、其权限层次，以及该机构治理的架构范围。

<a id="b00258"></a>
传统架构契约由发起支持者与架构职能或信息系统（IS）部门达成。然而，越来越多服务由系统集成商、应用提供商和服务提供商提供，并由架构职能或IS部门协调。因此，需要架构契约在架构开发和交付的所有参与方之间建立共同协议。

<a id="b00259"></a>
架构契约可出现在ADM不同阶段，例如：

<a id="b00260"></a>
- A阶段产生的架构工作说明（见《TOGAF标准——架构开发方法》），实际上是架构组织与企业架构发起支持者或IT治理职能之间的架构契约。
- 一个或多个领域架构——业务、数据、应用、技术——的开发，有时连同整体企业架构监督，也可以外包给系统集成商、应用提供商和/或服务提供商。每项安排通常由架构契约治理，规定交付物、质量、所开发架构的适用性，以及各合作方的协作过程。
- G阶段（实施治理）开始时，架构职能与负责实施前几个ADM阶段所定义企业架构的职能之间建立契约；实施方通常为内部系统开发职能或承担外包工作的主要承包方。G阶段“实施”的是整体企业架构，通常包括D阶段技术基础设施，以及C阶段应用与数据架构定义的企业应用和数据管理能力；这些能力具有企业范围，或具有战略业务意义，因而对整个企业重要且可见。通常不包括业务单元随后在企业架构所实施技术基础设施之上部署的非战略业务应用。在大型实施中，一个实施项目群可按实施团队分别订立架构契约。
- F阶段结束、最终架构定义文档可用时，架构职能或包含该职能的IT治理职能，通常与随后将在架构环境中构建和部署系统的业务用户订立架构契约。

<a id="b00261"></a>
在上述所有情况下，都应牢记最终目标不仅是企业架构，而且是动态企业架构，即可以灵活响应技术与业务驱动变化而演进，避免不必要约束。架构契约对于使能动态企业架构至关重要，也是治理实施的关键。

<a id="b00262"></a>
下文解释这三类架构契约的典型内容。

<a id="tag_05_02"></a>
### 5.2. 内容

<a id="tag_05_02_01"></a>
#### 5.2.1. 架构工作说明

<a id="b00265"></a>
架构工作说明是A阶段交付物，实际上是架构组织与企业架构发起支持者，或代表企业的IT治理职能之间的架构契约。

<a id="b00266"></a>
典型内容见《TOGAF标准——架构内容》。

<a id="tag_05_02_02"></a>
#### 5.2.2. 架构设计与开发合作方之间的契约

<a id="b00268"></a>
这是合作组织——包括系统集成商、应用提供商及服务提供商——就设计和开发企业架构或其中重要部分签署的意向声明。

<a id="b00269"></a>
一个或多个领域架构的开发日益可能外包，由企业架构职能监督整体企业架构，并协调和控制整体工作。有时连监督角色也可能外包，但多数企业倾向于内部保留这一核心责任。

<a id="b00270"></a>
无论外包安排的具体形式如何，通常都由架构契约治理，规定交付物、质量、所开发架构的适用性，以及合作方开展架构开发时共同工作的过程。

<a id="b00271"></a>
架构设计与开发契约的典型内容包括：

<a id="b00272"></a>
- 引言与背景。
- 协议性质。
- 架构范围。
- 架构及战略原则与要求。
- 遵循性要求。
- 架构开发及管理过程和角色。
- 目标架构度量。
- 已定义的交付物阶段。
- 按优先级排序的共同工作计划。
- 时间窗口。
- 架构交付及业务度量。

<a id="b00273"></a>
若尚无模板，通常在ADM的Preliminary阶段定义该契约模板；再根据外包工作的性质，在适当ADM阶段定义具体契约。

<a id="tag_05_02_03"></a>
#### 5.2.3. 架构职能与业务利益相关者之间的契约

<a id="b00275"></a>
实施与迁移计划在F阶段末达成一致后，可由架构职能与随后在架构环境中构建和部署系统的业务利益相关者订立架构契约。

<a id="b00276"></a>
业务利益相关者架构契约可包含：

<a id="b00277"></a>
- 引言与背景。
- 协议性质。
- 范围。
- 战略要求。
- 满足业务需求的架构交付物。
- 遵循性要求。
- 架构采用者。
- 时间窗口。
- 架构业务度量。
- SLA。

<a id="b00278"></a>
该契约也用于在H阶段管理企业架构变化。

<a id="tag_05_03"></a>
### 5.3. 与架构治理的关系

<a id="b00280"></a>
ADM的G阶段产生的架构契约文档，在架构治理中具有突出地位，见第3章。

<a id="b00281"></a>
在架构治理语境中，架构契约经常用作驱动架构变化的手段。

<a id="b00282"></a>
要确保架构契约有效、高效，可能需要在G阶段引入治理框架的下列方面：

<a id="b00283"></a>
- 简单的过程。
- 以人为中心的权威。
- 有力的沟通。
- 及时响应及有效升级处理过程。
- 支撑性组织结构。
- 架构实施状态跟踪。

<a id="chap06"></a>
## 6. 架构符合性

<a id="b00285"></a>
本章指导如何确保项目符合架构。

<a id="tag_06_01"></a>
### 6.1. 引言

<a id="b00287"></a>
确保各项目符合企业架构，是架构治理的重要方面，见第3章。为此，企业IT治理职能通常定义两个互补过程：

<a id="b00288"></a>
- 要求架构职能准备一系列项目架构，即企业架构针对项目的视图，说明企业架构如何影响组织中的主要项目，见ADM的A至F阶段。
- 企业治理及IT治理职能定义正式架构符合性评审过程，评审所有项目是否符合企业架构，见§6.3。

<a id="b00289"></a>
除定义正式过程外，架构治理职能还可能规定：架构职能不应只定义架构和选择标准，还应参与技术选择，乃至参与外部服务和产品采购的商业关系。这有助于减少误解企业架构的机会，并最大化集中商业谈判的价值。

<a id="tag_06_02"></a>
### 6.2. 术语：架构符合性的含义

<a id="b00291"></a>
架构与实施之间的关键关系之一，在于“conformant”“compliant”等术语的定义。不同组织用语可能不同，但图6-1所示的遵循程度概念，有助于制定IT符合性策略。

<a id="b00292"></a>
![原图](../web-2025/volumes/06-ea-capability-and-governance/assets/002-48_conformance.png)

<a id="b00293"></a>
图6-1：架构遵循程度（Levels of Architecture Conformance）

<a id="b00294"></a>
图6-1中的“in accordance with”（与之相符）表示：

<a id="b00295"></a>
- 支持既定战略及未来方向。
- 遵循既定标准，包括规定的语法与语义规则。
- 提供既定功能。
- 遵循既定原则，例如：在可能且适当时采用开放方式；在可能且适当时复用组件构建块。

<a id="tag_06_03"></a>
### 6.3. 架构符合性评审

<a id="b00297"></a>
架构符合性评审，是根据已确立的架构判据、精神和业务目标，对具体项目符合性进行的仔细审查。此类正式评审过程通常构成企业架构符合性策略的核心。

<a id="tag_06_03_01"></a>
#### 6.3.1. 目的

<a id="b00299"></a>
架构符合性评审目标包括下列部分或全部内容：

<a id="b00300"></a>
- 首先，尽早发现项目架构错误，从而降低生命周期后期所需变更的成本与风险。这也缩短整体项目时间，使业务更快获得架构开发带来的实际效益。
- 确保架构工作应用最佳实践。
- 概述架构对企业强制标准的符合情况。
- 识别标准本身可能需要修改之处（原文此处带有星号）。
- 识别当前为应用专用、但可能作为企业基础设施一部分提供的服务。
- 记录跨多个架构团队的协作、资源共享及其他协同策略。
- 利用技术进步。
- 向管理层沟通项目的业务及技术就绪状态。
- 识别采购活动的关键判据，例如纳入商用现成（COTS）产品信息征询书（RFI）或建议征询书（RFP）。
- 识别重大架构差距，并向产品和服务提供商沟通。

<a id="b00301"></a>
除上述质量保证的一般目标外，还有一些更偏组织政治层面的评审动机，在特定情况下可能适用：

<a id="b00302"></a>
- 评审是比较架构备选方案的良好方式：通常参与的业务决策者可从业务最有利的角度指导决定，而不只追求技术上的美观或优雅。
- 评审输出是少数可供高层管理决策的可度量交付物之一。
- 评审可使架构组织参与那些原本可能没有架构职能介入的开发项目。
- 评审可向企业业务群体展示迅速且积极的支持：企业架构与架构符合性有助于确保IT项目与业务目标对齐；架构师有时会被认为深陷技术基础设施而远离核心业务。
- 评审往往主要关注系统关键风险领域，因此经常能为系统所有者突出主要风险。

<a id="b00303"></a>
虽然开发和实施要求符合架构，但不符合情况也提供了一种机制，用以突出：

<a id="b00304"></a>
- 需要处理以重新对齐的领域。
- 符合性过程中发现、值得考虑纳入架构的领域。

<a id="b00305"></a>
后一点表明架构应持续变化并适应需求。这些需求可能由不守纪律引起，也可能来自运营环境更快的变化。通常使用豁免（见“Dispensation”）突出这些变化，并启动过程登记、监控和评价所需变化的适宜性。

<a id="tag_06_03_02"></a>
#### 6.3.2. 时机

<a id="b00307"></a>
安排符合性活动时，应考虑架构自身的开发进展。

<a id="b00308"></a>
在项目生命周期中适当的里程碑或检查点开展符合性评审，具体应包括：

<a id="b00309"></a>
- 架构本身的开发，即ADM符合性。
- 架构的实施，即架构符合性。

<a id="b00310"></a>
架构项目评估的时点应包括：

<a id="b00311"></a>
- 项目启动。
- 初始设计。
- 重大设计变化。
- 临时需要时。

<a id="b00312"></a>
评审通常安排在业务需求与企业架构已相对稳定、项目架构正在成形但远未完成时。

<a id="b00313"></a>
目标是在实际可行的情况下尽早评审，此时仍有时间纠正重大错误或缺陷；但显然也必须已经有足够的项目架构进展，才有可供评审的内容。

<a id="b00314"></a>
评审输入可能来自标准项目生命周期的其他部分，这会影响评审时点。

<a id="tag_06_03_03"></a>
#### 6.3.3. 治理与人员情景

<a id="b00316"></a>
在评审的治理、开展方式及参与人员方面，存在多种可能情景：

<a id="b00317"></a>
- 小型项目可以采用项目架构师或项目负责人用下述检查表自问的一系列问题，或将答案汇成提交管理层的项目报告。开展此过程的要求通常纳入企业整体治理政策。
- 如果项目迄今没有实践型或全职架构师参与，例如应用级项目，评审目的通常是引入企业架构职能的专业能力。此时由企业架构职能组织、领导并开展评审，业务领域专家参与。评审不能替代架构师参与项目，但可以补充或指导其参与。分析大型系统或系统集时，可能需要数据库管理产生的大量数据。
- 多数情况下，尤其大型项目，架构职能已深入参与、甚至领导被评审的开发项目，这是典型TOGAF情景。评审由牵头企业架构师协调，召集业务及技术领域专家，并把问题答案汇总成报告；问题通常由这些专家提出。也可由架构委员会或类似企业范围责任机构的代表领导评审。

<a id="b00318"></a>
所有情况下，架构符合性评审都需要高层管理支持，通常由公司架构治理政策强制规定，见第3章。通常由企业CIO或企业架构委员会（第4章）要求所有重大项目接受架构评审，之后每年复核。

<a id="tag_06_06"></a>
### 6.5. 架构符合性评审指导

<a id="b00332"></a>
本节提供架构符合性评审的指导。

<a id="tag_06_06_01"></a>
#### 6.5.1. 裁剪检查表

<a id="b00334"></a>
- 聚焦高风险领域以及预期或新出现的差异化因素。
- 对检查表中的每个问题，理解问题本身、背后原则，以及应在回答中寻找什么。
- 征询主题专家的意见。
- 为自身使用情境调整检查表问题。
- 牢记向架构委员会反馈的需要。

<a id="tag_06_06_02"></a>
#### 6.5.2. 开展架构符合性评审

<a id="b00336"></a>
- 清楚理解请求评审者的目标，保持范围，交付对方请求的内容。例如，对方通常想知道所设计系统的优缺点，而非开发方法或其管理结构的优缺点。讨论容易偏向有趣、可能有价值、却不属于请求范围的事项。若能提供技术洞见但对评审并非必要，可主动提出评审后提供。
- 若讨论明显暴露出请求范围之外的其他待处理问题，会后向会议主席提出，并按严重程度制定处理计划。
- 保持“科学”态度。例如，不说“我们喜欢把大型数据库放在ABC而非XYZ上”，而是说明“XYZ数据库环境的停机时间远大于ABC，因此不建议在XYZ环境中托管M和N类型系统”。
- 提开放式问题，即不预设特定答案的问题。
- 请求评审者之间往往存在你事先不知道的“隐含议程”或争议。采用不针对个人的讨论方式，有助于弥合而非扩大分歧。
- 尊重被访谈者。他们也许没有以“应该的方式”构建系统，但很可能已在当时条件下尽力。
- 使这次活动成为你与呈现者共同学习的经历。
- 评审应包括针对架构的详细评估，并确保结果存入企业连续体。
