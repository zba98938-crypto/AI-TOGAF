# G249 全渠道订单履约改造：虚构贯通案例

这个案例将架构工作依据、四类角色的决策任务、技能要求、观察证据、任务配置和发展复评接到同一组架构对象上。业务、人员、日期和候选方案均为教学虚构，不代表实际业务批准。方案比较由显式案例分析编写，不宣称程序能从任意自然语言自动推导正确架构。

先阅读 [原始业务材料](raw-business-materials.md)，再检查 [任务与人员证据输入](role-skill-inputs.json)和[可重复构建脚本](build.py)。方法说明见 [G249 工作流](../../references/g249-operational-workflow.md)及[运行时契约](../../references/g249/runtime-contract.md)。

从仓库根目录运行：

```sh
python3 -B skills/_shared/examples/g249-omnichannel/build.py --out output/g249-omnichannel --render
python3 -B -m unittest discover -s tests -p 'test_g249*.py' -q
```

构建生成 `baseline` 和 `offline-change` 两个独立版本，分别有 12 和 13 个视图。每版包含模型、索引、结构化制品、可编辑 Mermaid/SVG、PNG、覆盖检查、验证结果及角色配置分析。两版共用稳定对象 ID。`change-impact.json` 遍历新增离线要求的完整可达对象，作为人工排查候选；可达不等于已证明业务影响。

基线同时保留同步预占和异步处理候选，库存一致性与承诺要求不足时不排名。离线版增加本地持久记录、恢复接口、中央对账边界、异常处理、过渡与验证场景，并更新技能行为要求、发展动作和复评标准；人员原有观察不随要求变更而提升。

四类角色分别围绕经营取舍、跨分段责任、库存边界和可实施方案形成待决问题。首席角色的经营决策材料保存在 `delivery-notebook`，实际决策人与风险承诺仍待确认。订单受理、最终确认、异常与物流交接分开表示，未确认订单不能直接进入物流履约。

预期结果不是“全部通过业务验收”：两版模型结构校验无错误或警告，但分析仍明确返回证据、工作量、角色配置和业务接受条件的缺口。独立评审应从原始材料检查输出是否改变了实际判断，而不能用图形渲染成功替代内容审查。
