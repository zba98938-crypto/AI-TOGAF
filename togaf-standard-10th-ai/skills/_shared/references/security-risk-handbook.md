# 风险与安全的跨域工作方法

依据本地 G152 第 4、5.1—5.12 节的中文正文与图表解释。这里转述方法，不声称已经核实 C220 的全部正式定义。正文依据、图示解释和项目建模约定分别注明；按任务选取成果，不能用制品数量证明安全有效。

## 从业务价值到可验证控制

**正文依据（G152 §5.1、5.2、5.10）**：先确定业务目标、业务属性、利益相关者和风险偏好。业务影响分析描述应避免的影响类型与后果，不负责给出发生可能性。业务属性画像将目标转化为业务语言表达的要求，并支持目标绩效度量。控制目标是期望达到的安全状态，与安全需求不必一一相同。

**项目操作约定**：先访谈目标与资产的业务所有者，记录范围、时点和证据，再建立以下独立对象：

| 对象 | 必须回答的问题 | 不应混用 |
|---|---|---|
| 业务目标与属性画像 | 谁希望实现什么结果？在本语境如何定义、度量该属性？ | 属性名称不能代替阈值或业务定义 |
| 业务影响分析 | 中断、泄露、失真等情景会损害什么价值？影响随时间怎样变化？ | 不能据影响等级推断可能性 |
| 风险偏好 | 哪类风险可接受到什么边界，谁有授权？ | 不能把当前残余风险当作已被接受 |
| 风险情景 | 什么威胁利用什么脆弱性，影响哪个资产或目标？ | 风险、威胁、脆弱性分别记录 |
| 控制目标 | 需要达到什么安全状态，与哪项业务属性相关？ | 不能把产品名称当作控制目标 |
| 需求与控制措施 | 哪项可验证约束由哪些措施实现？ | 需求不是措施实施成功的证据 |
| 安全服务与构建块 | 谁提供什么安全功能，在哪个范围内运行？ | 服务存在不代表它在本范围内有效 |
| 评估证据与风险决定 | 谁在何时通过什么测试，证明什么结论；谁处理剩余风险？ | 未测、未决定分别保留状态 |

将影响、可能性和置信度分开；只有明确规则和尺度证据时运行风险计算器。定性序数不可随意相乘；多个后果不应在未定义权重时平均。对实施前、实施后和过渡状态分别评估，保留评估日期。

## 域、信任、分类与权限

**正文依据（§5.3、5.4）**：安全域把受相同安全策略管辖、具有类似安全属性的资产分组，并指定策略权威；它有助于明确外部责任交接。信任关系有单向、双向或不存在三种情况；数字证书只能传递已有业务、法律和策略关系所支持的信任，不能创造信任。安全分类适用于业务服务、能力、信息、系统与技术组件等各类资产。

**项目操作约定**：安全域模型记录域、边界、策略、策略权威、资产成员和责任交接。信任框架记录方向、依赖目的、信任依据、范围、期限和撤销条件，不能从网络连通推导信任。分类方案记录标签定义、所有者、适用范围与保护要求；用户角色使用某应用不等于其获得数据访问权限。授权需独立需求和控制证据。

跨域图至少能追溯：业务风险→安全目标/需求→控制→安全服务或 ABB→候选/已选 SBB→应用、数据或技术部署→验证证据。图示中的关联线不得自行强化为因果或实现关系。

## 各阶段的差异

| ADM 工作位置 | 应开展的分析与成果 | 阶段边界 |
|---|---|---|
| 预备 | 安全原则、风险偏好、关键风险领域、业务影响分析、安全资源和授权 | 复用现有企业政策须核对范围与有效期 |
| A | 安全利益相关者、关注点、属性画像、价值论证及安全蓝图范围 | 应足以支持愿景决策；不要求完成全部详细设计 |
| B | 安全策略架构、安全域、信任框架、风险登记册、法规与控制框架适用性 | 法规适用须记录业务功能、数据、司法辖区、依据和确认者 |
| C | 安全服务目录、安全分类、数据质量责任与度量 | 控制框架记录要求；服务目录记录实现功能及运营信息 |
| D | 控制落到平台与技术组件，论证风险缓解与资源约束 | G152 未要求所有项目另造专用技术安全制品；按利益相关者关注点建视图 |
| E | 复用验证、SBB 规格、风险缓解计划、工作包的风险收益 | 现有认证或服务不能免除当前范围下的有效性验证 |
| F | 过渡风险、安全影响、回退规划与迁移活动 | 与 E 的总体缓解计划区分，必须考虑生产迁移本身的风险 |
| G | 安全设计/代码/配置评审、测试、培训和纠正行动证据 | 合规声明需有证据；生成审计计划不等于完成审计 |
| H | 风险环境和价值持续监控、变更分流及新迭代触发 | 正文强调过程，未声称存在专属有形安全交付物 |
| 需求管理 | 属性画像、安全目标、安全标准适用性与需求追溯 | 目标、需求、标准及控制各保留身份与关系 |

## 可操作的评审顺序

1. 检查范围、资产所有者、业务目标和风险偏好是否有证据；缺失则登记问题及对决策的影响。
2. 从情景逐项核查威胁、脆弱性、资产、后果、可能性与评估尺度。检查业务影响是否与画像使用相同含义。
3. 核查每个处理决定的责任、期限、成本和剩余风险。接受、规避、转移、缓解不可用同一状态代替。
4. 检查需求、目标、控制框架、安全服务、构建块是否被错误合并；逐项验证实现与测试链。
5. 对迁移工作包增加过渡风险、回退触发条件、恢复责任、数据对账和可运营性检查。
6. 报告已知证据、未验证控制、未批准风险接受和法规核实缺口。图和文档保留同一稳定标识。

## 明确标记的虚构示例

虚构图书馆目标：借阅记录只能由获授权的馆员按工作职责读取。业务影响分析先记录隐私泄露后果；未经评估不填写发生概率。风险情景 R-1 是被盗凭据导致未经授权查询，风险所有者为馆务负责人。控制目标 O-1 是仅允许授权访问；需求 Q-1 指定身份验证和权限撤销时限。控制 C-1 是统一身份与最小权限，ABB-1 描述身份服务所需能力，SBB-1 是候选实施方案，状态为 candidate。测试 T-1 验证撤销后查询被拒绝；未实际执行时保持 planned。风险 R-1 的残余风险接受仍待授权人决定。迁移阶段另列旧新系统并行、权限同步和回退时的风险，不复用目标状态的评估结论。以上时限与等级须由实际项目补充。
