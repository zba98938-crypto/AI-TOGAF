# 元数据应用功能覆盖评估

本能力扩展既有工作产品 `metadata-asset-coverage`，新增表格规范 `metadata-application-function-coverage` 与方法 `metadata-application-coverage-review`。默认的三类元数据×管理维度矩阵保留。`metadata-application-function-map` 描述参考功能，不能证明项目实现。

决策用途：在一个明确范围、架构状态及日期，哪些元数据应用功能已具备可核对的项目证据，哪些只有计划，哪些未知，哪些经授权不适用。利益相关者为数据治理负责人、资产所有者、工具负责人、平台测试与审查人员；适用ADM C及E/F方案和迁移规划、G实施审查。结果不代替治理批准。

## 来源、语义和界限

本地G234 §5.2图5-2、表5-2 L641–664定义六组、24项功能。运行时从[随包来源表](../source-tables/metadata-functions.json)核对[审查清单](../source-tables/metadata-application-coverage-requirements.json)的全集、名称和完整定义；源表改变而清单未同步时拒绝运行。数量仅是当前版本观察，不是覆盖上限。源定义已读本地译文；官方定义认证单独记录。

清单把完整源语义拆成可观察的方面，例如搜索的多条件、全文和自动补全。它是项目的操作表示法，允许有依据的范围裁剪，不声称每项目必须实现所有参考功能或所有示例算法/格式。元数据推断的机器学习、模式、字典等是示例，不要求全部实现；查询的SQL/API和导入导出的格式也不要求全部实现。

641行明确区分八类创建对象：术语表、数据字典、数据使用、数据分类、规则与政策、问题、治理资产、技术质量规则。选定资产保留原定义的子项，例如治理角色和组合数据域；只有工具CRUD不证明这八类对象均有覆盖。659行分别核查事件、修改历史、来源与作者，不把历史一项代替其他三项。

模型复用稳定工具ID和版本、元数据资产ID、来源功能ID。`g234:function-coverage` 是特定范围的审查记录，`g234:metadata-tool` 是项目工具。`g234:coverage-of-asset` 从审查记录指向所需资产，`g234:tool-coverage-claim` 从工具指向审查记录，后者仅表达声明。关系、表格相邻、工具存在都不代表实现。批准和部署/生产状态独立记录。

## 输入与缺口处理

必要输入：范围、架构状态、观察日期、责任人及其证据；工具ID/版本/责任人；资产ID/来源类别/责任人；源功能对应的要求范围与资产列表；每条实现或计划声明中的资产和功能方面；带种类的证据清单。证据种类区分观察、计划、裁剪、范围、工具/资产清单、项目规则、未核实信息和参考资料。

缺少某项源功能评估时仍输出该功能并标 `unknown`；缺资产范围、观察、工具版本、计划或裁剪依据时输出带ID缺口，不填零、不推定不存在、不默认通过。未知来源ID、重复稳定ID、未知功能、越界资产/方面或版本不一致属输入错误。重名但不同ID保持为不同工具或资产。

输入中的规则是项目自声明的审查契约，并非TOGAF规定的成熟度模型或认证标准：

| 状态 | 证据要求 |
|---|---|
| `implemented` | 在明确工具版本、环境、日期，对所列每个资产×方面有通过观察；观察说明实际行为并引用 observation 类证据。仅在该范围成立。 |
| `planned` | 每个尚未实现的资产×方面有责任人、目标日期、里程碑、准确范围和 plan 类证据；逾期显示缺口，不能提升为实现。 |
| `unknown` | 无评估、范围不足、缺证据、结果不通过或冲突。已有部分实现仍逐格保留，不提升整个功能。 |
| `not-applicable` | 整项功能在所述范围有理由、授权人和 tailoring 类证据；不能同时挂实现/计划声明。范围变化必须重审。 |

同一格可以由多个工具支持；按资产/方面合并后再得到功能状态，不重复计算功能。若保留的声明中有失败观察，保守列为冲突待审；如某工具仅为已淘汰备选，应明确调整当前审查范围并保留历史，而不是把失败证据隐藏。一个绑定记录覆盖多格时，观察不完整会使该绑定不具备“已实现”支撑；可按不同验证范围拆分绑定。

## 实际操作

1. 读取原始访谈、工具配置、资产清单、观察日志、实施计划和裁剪决定，保留每条材料ID和定位。识别事实、产品介绍、计划及假设；不要将参考功能复制为项目现状。
2. 从来源全集建立逐功能处置清单。为每项明确资产和方面范围。641行若少一类资产，必须补范围或记录该类别的授权裁剪。源完整定义一直可见。
3. 以稳定ID整理工具和资产。在绑定记录中指明工具版本、涉及资产、涉及方面和声明状态。观察记录逐资产/方面写实际行为，不用“工具已买”作为实现证据。
4. 执行方法，得到逐格结果、整项四态、分组清点和带ID缺口。任一格未知使整项未知；无未知但存在计划使整项计划中；全部有通过观察才为已实现。此结论只属于当前审查范围。
5. 评审全部缺口与裁剪。需要更细功能或组织特定要求时显式扩展来源/项目清单，不能冒充源指南要求。输出不计算加权分数、合格线或默认覆盖百分比。

输出是可检索的逐记录表、模型JSON、分析结果、关系方向、证据引用、`coverage.json`表达位置和生成manifest。此规范属于表格，SVG/PNG视觉验收不适用；参考功能地图的两布局图形验收仍是独立能力。

## 完整案例、修改与评审

原始材料（历史材料已清理）使用独立虚构五馆联盟案例，包含八类资产、四个工具、项目规则、逐项观察、计划、未知以及两项裁剪。所有观察为虚构业务材料，不声称已实际测试真实产品。

初始模型（历史材料已清理）覆盖全部源功能。两个工具共同查询A2仍只形成一项源功能结论。来源/作者尚未知的事件日志功能保留部分实现格；修改模型（历史材料已清理）只加入这两个方面的观察，日志结论随之改变；数据库版本仍为计划。每个版本附 `transformation.json`，列出原料→审查记录的对应关系。

在已登记此addendum的技能副本中：

```sh
python skills/_shared/scripts/analyze.py skills/_shared/examples/addenda/metadata-application-function-coverage/baseline-model.json --evaluate metadata-coverage-analysis
python skills/_shared/scripts/generate.py skills/_shared/examples/addenda/metadata-application-function-coverage/baseline-model.json --out skills/_shared/examples/addenda/metadata-application-function-coverage/baseline-output --profile metadata-application-function-coverage
python skills/_shared/tests/test_metadata_coverage.py
```

标准验证、分析和生成入口都会把分析快照与当前模型按稳定ID绑定：工具版本、资产属性、审查范围/状态/日期、声明关系、所选视图及复算结果必须一致。仅修改主模型工具版本而保留旧分析快照会返回带ID的 `metadata-binding-field` 错误，不能继续输出旧结论。原料改变后应重新审查并同步两者，不通过自动覆盖消除冲突。

审查应复算模型中的分析并比较显示值、追溯全部ID、核对表中确实表达了所选对象/关系/属性。反例测试包括：漏功能、少641类别、659语义遗漏、只有参考资料、缺观察、缺计划范围、缺裁剪授权、工具升级、重名/重复ID、未知引用、错误日期、失败证据、多个工具复用和局部修改。技术检查只能验证结构与审查规则，不能证明原材料真实或治理已批准。

交付物可把此具体 `view_id` 与 `metadata-coverage-analysis` 装入架构定义文档、架构需求规格；部署缺口可追溯工作包。不能用仅链接原料或填预写章节替代实际组装，本补丁本身不声明新交付物实例已组装。
