# 业务周期与工作产品时点

架构工作产品何时必须可用以影响业务决定？

依据：G184 §4.3.2、§10.3、§11.4；G186 §4、§8.1、§11.2、§14。源文提供方法与参考，字段和状态编码为项目操作规范。公开官方核验以覆盖索引为准。

## 必要输入与缺口

范围和五维语境；原始访谈/计划/测量及定位；授权角色和适用目标版本。逐项登记缺口；未知不等于否或零。缺授权、原口径、时点或关键证据时只能候选，不自动批准、通过或核算。

## 字段与语义

| 字段 | 含义 |
|---|---|
| name | 交付时点安排 |
| business_event | 业务/预算/发布/运营事件 |
| decision | 该事件需要作出的决定 |
| consumer | 消费架构成果的责任人 |
| required_by | 消费方需要日期 |
| planned | 计划提供日期 |
| actual | 实际交付日期或未知 |
| product_view_refs | 具体工作产品及view_id |
| dependency | 前置输入/工作 |
| status | 准时/迟到/未知 |
| recovery_action | 晚交付时如何修正或披露决策缺口 |
| rule_source | 项目日历与日期依据 |

## 从原料到结论

1. 访谈消费方确认业务事件、决定和最迟输入日期
2. 将目的与所需工作产品/实际视图绑定
3. 以输入依赖倒排完成与评审
4. 比较计划/实际和消费期限，指出错过决策的后果
5. 重排范围资源或显式告知未满足条件，不改原业务事实

## 修改与反例

修改：组合选项计划从11月16改为11月12。预期：迟3天变提前1天；实际仍unknown。

反例：无消费方期限，只写“阶段F完成”。应有结果：missing-consumer-deadline拒绝准时判定。

## 评审与追溯

- ADM阶段顺序不决定业务消费时点
- 30天/季度是G186的实践建议，项目日期必须由实际日历确认
- 计划早于期限不证明实际已按时交付
