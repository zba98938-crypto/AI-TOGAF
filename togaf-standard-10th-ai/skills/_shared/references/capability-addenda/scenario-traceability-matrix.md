# 业务场景关联矩阵：原料转换与问题成果追溯

本增量依据 G176 §3.2.3、§11.4，英文 PDF 第22–23、45–46页。指南要求保留原始数据、拆分复合陈述、逐次记录规范化变更，并以流程连接利益群体、人的参与者、计算机参与者、问题和目标。每个痛点至少有一个成果。证据摘要（历史材料已清理） 可随技能包携带。

## 调用与输入

[规范](../../capability-addenda/scenario-traceability-matrix.json) 对应原制品和默认视图 `scenario-traceability-matrix` / `scenario-traceability-matrix-default`。单项请求仅需原始业务材料及相关场景范围，不应迫使使用者先填全套架构目录。

来源没有规定统一矩阵版式或加权公式。本实现采用流程为行、五类对象分组列，是显式项目表示约定。单元格表示有证据的场景关联；不自动表示CRUD、流程顺序或责任分工。没有关系证据时显示“待确认”，不能用空白暗示已证明无关联。

## 分析步骤与语义

先锁定原始材料和定位。把复合陈述按单点拆分，统一术语并分类；每次转换记录输入ID、输出ID、操作、理由和证据。重名对象使用不同ID与语境区分；确为同一人的参与角色或系统复用同一ID。

逐流程确认五类要素的关联，避免将所有对象连到每一行。再独立建立“问题→期望成果”追溯，验证每个痛点至少一个成果。流程同时关联问题和目标，并不能自动证明两者存在改善关系。

从已支持的场景结果形成业务需求；技术实现推断仍应标候选。完成评审和实际批准后，才进入需求存储库。六项总体任务、五个迭代步骤、三个场景阶段属于不同分解，不能拼成单一流程图。

## 完整业务案例

原料（历史材料已清理） S-R1描述电话和网页重复占名额、目标唯一预约，以及预约员在受理预约中使用课程预约系统。S-R2描述取消后退款漏记、次一工作日登记退款，以及预约员使用退款队列、财务组关注退款记录。

S-N1至S-N13逐条保存拆分结果，S-T1至S-T3记录转换。由这些记录形成两条流程行、五类列、11条已支持的矩阵关联和2条问题成果关系。两个流程复用同一预约员和读者群体；课程预约系统只关联受理预约，退款队列只关联取消退款。

初始模型（历史材料已清理） 使用明确关联标签，扩展数据位于 `togaf-addenda:g176-scenario`。从目标推导出的“向退款系统传送取消记录并回传结果”是技术候选需求，材料没有确认具体传输实现。

S-R3明确将取消退款改为统一支付台。修改模型（历史材料已清理） 只替换 `s-refund-computer` 的计算机端点；受理预约关系、预约员ID、读者群体ID保持不变。旧模型与原材料保留，新转换S-T4和新条目S-N14记录变更。目标模型的演进状态同时更新，不能只改对象而留下基线视图状态。

三个反例分别删除退款问题的成果关系、擅自将计算机关联编码为C、移除规范化记录所引用的S-R2。应分别输出 SCN-003、SCN-004、SCN-001，而不是绘出看似完整的矩阵。

## 表示、输出与评审

矩阵必须呈现五类列头、流程ID、关系ID及其含义、未确认格和证据入口。问题成果关系应在矩阵旁的追溯表或独立可达视图表达；不能因为它不是流程行关联而静默丢弃。转换日志和原料映射可作为关联矩阵的证据附录，需通过稳定引用可达。

执行记录（历史材料已清理） 已验证两版v2模型、只有一条关联变化，以及三个反例。渲染器仍需证明非流程关系和转换引用的表达；当前结果不计图形或视觉通过。
