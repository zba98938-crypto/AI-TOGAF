# 如何通读并讲清楚TOGAF：ADM、架构内容、流程与层次

适用于讲解TOGAF、规划完整架构工作、核对阶段与制品关系时。以下中文是项目解释，源定义与限定以本包保存的C220和指南原文为准。逐节语义分析、完整中文正文与真实组织批准各有独立状态，不能互相代替。

## 从工作问题理解整体

TOGAF提供可裁剪的企业架构方法及内容、治理与能力指导。先确定要支持的业务决定：例如“能否在不断店营业的条件下改变库存承诺机制”。再明确范围、约束、利益相关者、时间与证据，而后选择ADM工作和表达制品。下载完整资料、填满模板、绘图成功分别解决不同问题，都不足以证明已经作出可信架构判断。

六卷分别回答：核心概念是什么；ADM怎样开展工作；用哪些分析技术；如何在组织和不同范围中应用ADM；怎样组织架构内容；谁授权、治理并持续建设EA能力。系列指南在特定语境细化这些方法。白皮书、Playbook和基础标准的出版物类型及版本分别保留；跨文档的建议不自动升级为标准强制要求。

## ADM是反复形成和检验决定的过程

详细输入、原始步骤、输出与来源在[阶段契约](adm-phases.json)。[执行记录](adm-cycle.md)把实际对象、决定和证据绑定到迭代。以下表格是理解用途的项目解释，不是官方步骤的替代品。

[完整流程图生成入口](../examples/adm-flow/README.md)可从当前合同生成总览、内容关系、预备阶段、A–H、持续需求管理和实际周期迭代。附带94来源步骤、全部23交付物及196制品族的映射和来源定位；支持可编辑Mermaid、SVG和PNG。

```sh
python3 -B _shared/scripts/adm.py flow --out work/adm-flow --render
# 展示实际记录时同时传入 --cycle <周期JSON> --model <架构模型JSON>
```

|工作|要解决的决定|常见输入与分析|应形成的变化及可查证据|
|---|---|---|---|
|Preliminary|组织为什么需要EA、提供什么服务、谁授权及如何治理？|组织环境、战略、已有治理和能力；裁剪框架、原则、角色及工作方式|组织模型、裁剪框架、原则、资料库和治理边界；职责与权限依据|
|A Architecture Vision|这项架构工作要达到什么、服务谁、范围是否可接受？|架构工作请求、驱动、目标、利益相关者、现有能力、风险及价值|愿景、架构工作说明、沟通安排和范围；实际启动及范围决定|
|B Business Architecture|业务能力、服务、价值交付和组织过程需要怎样改变？|同一范围的基线与目标、关注点和视点、差距及跨域影响|业务架构、需求、差距、候选路线图组件；利益相关者对业务影响的评审|
|C Information Systems Architectures|数据和应用如何共同支撑业务变化？|数据权威与生命周期、应用服务、接口、依赖；分别开展数据/应用分析并协调|数据及应用架构、接口约束、需求、差距和候选组件；所有者及互操作证据|
|D Technology Architecture|什么技术服务和平台能够支撑上面的约束？|业务/数据/应用需求、技术基线、平台标准、非功能需求、成本和风险|技术架构、平台约束、差距和候选组件；容量、保护及运营判断的依据|
|E Opportunities and Solutions|哪些候选工作包与过渡状态能把跨域变化落地？|合并B/C/D差距、候选方案、依赖、实施因素、现有项目与能力|工作包、候选SBB、过渡架构、路线图及实施迁移计划草稿；组合与可运营性论证|
|F Migration Planning|以什么顺序、资源和投资安排实施？|E的候选路线图/过渡状态、项目管理与投资准则、价值风险和资源依据|细化并完成路线图及实施迁移计划；源要求的批准须由真实证据证明；适用时的实施治理模型|
|G Implementation Governance|实际交付是否遵循架构约束，偏离怎样处理？|架构契约、实施计划、已批准要求、实施及测试证据、治理安排|符合性评估、偏离处置、变更请求与实施交接；不能由设计图推断实际符合|
|H Architecture Change Management|运行和环境变化是否要求修改架构或启动新周期？|效果与价值观察、运行问题、业务/技术变化、变更请求及治理记录|变更决定、后续架构工作请求、更新约束及经验反馈；不能把上线或培训完成直接当收益实现|
|Requirements Management|各阶段依赖的是哪版需求，变化影响谁，谁作决定？|持续捕获、基线、优先级、冲突、变化及影响|需求存储库、需求规格、版本化影响评估、决定与各阶段复核；贯穿整个周期|

源定位：[ADM卷各阶段](../corpus/fundamental/analysis/02-architecture-development-method.md)，尤其各章Objectives/Inputs/Steps/Outputs；[应用ADM卷第2—4章](../corpus/fundamental/analysis/04-applying-the-adm.md#chap02)。

Preliminary管理实践能力，项目可以复用有效组织安排。A明确本次工作范围。B/C/D之间有信息依赖，也可并行和迭代；先研究数据约束可能迫使业务目标或范围调整。E整合可实施变化，F协调迁移和投资安排；两者不是同一个排期表的不同标题。G核查实际实施，H根据效果和变化决定进一步工作。需求管理位于这些工作的共同反馈循环中，标准没有“Phase I”。

阶段关系要表达输入的版本与决定依据。例如B-1提出承诺规则，C-1发现离线无法获得中心预占，B-2便重新区分“受理”与“确认”；不是因为B编号较小就禁止返回。一个周期还可在不同范围中重复应用。复用、不适用和阶段退出均记录理由及适用证据；工具不自动推进，也不代签批准。

## 交付物、制品和构建块各回答什么

源定义：[核心概念§3.6](../corpus/fundamental/analysis/01-introduction-and-core-concepts.md#sec-03_06)；[架构内容卷第3—5章](../corpus/fundamental/analysis/05-architecture-content.md#chap03)。

|对象|含义及用途|全渠道履约示例|不能据此推断|
|---|---|---|---|
|Deliverable 交付物|有工作约定、正式评审和利益相关者接受语境的工作产品；可包含多个制品|架构定义文档把业务、数据、应用和技术判断连同范围、依据组织起来|文件存在、组装通过不等于已接受|
|Artifact 制品|从特定视点描述架构的一方面，通常以目录、矩阵或图表达|能力目录、应用通信图、数据生命周期图、工作包/过渡架构增量表|一个视图不等于整个架构；矩阵空白不自动代表无关系|
|Building Block 构建块|能组合形成架构和解决方案的可复用能力或组成部分，可有不同粒度|库存预占能力及其服务约束；具体实现组件|不能把每个方框、文档章节都自动认定为构建块|
|ABB Architecture Building Block|表达架构所需的功能与能力，指导和约束SBB的选择|需要幂等的库存预占服务，明确责任及接口语义|ABB不自动指定产品，也不保证满足所有要求|
|SBB Solution Building Block|实现所要求能力的具体解决方案组成，需和ABB及约束建立可检查关系|某预占服务实现、消息组件及运维配置|选定或购买产品不等于已实施、已符合或已有收益|

交付物可以包含制品；制品描述构建块；构建块彼此组合并提供能力。应分别保存这些关系。项目ID `architecture-building-blocks`是一种交付物登记入口，模型中的单个`abb`对象是它描述的对象，二者身份不同。制品和交付物可跨阶段复用、补充和升版；“阶段输出”不是互斥的一次性文件归属。

目录适于识别对象、属性与责任；矩阵适于检查两组对象间的关系与覆盖；图适于表达结构、行为、交互或演进。选择取决于关注点。若问题是哪些应用实现哪些能力，不能用孤立应用清单代替关系矩阵；若问题是失败时怎样补偿，静态组件图不能代替状态/交互与运营场景。所有表达复用稳定ID、范围和状态，修改共享对象后检查各视图的同一含义。

E/F的五项新增制品各有不同用途：实施因素目录需要从因素推导行动/约束；合并差距、方案和依赖矩阵连接跨域差距与候选方案；架构定义增量表把项目增量分配到过渡架构；状态演进表描述服务及SBB在过渡中的变化；价值风险矩阵依据预先制定的准则分别评价价值与风险。缺少权重、容量或观察时保留未知。来源示例颜色不是通用必用配色，指数也不能由渲染器填写。

## “上下级”需要先区分哪一种关系

源定位：[架构全景与不同层次](../corpus/fundamental/analysis/04-applying-the-adm.md#chap03)、[分区](../corpus/fundamental/analysis/04-applying-the-adm.md#chap04)、[内容框架](../corpus/fundamental/analysis/05-architecture-content.md#chap02)及[G249角色解析](../corpus/chapters/G249.json)。

|维度|关系和判别问题|需要保留的区别|
|---|---|---|
|架构全景粒度|Strategic、Segment、Capability：关注范围和细节怎样组织？|战略提供方向、分段组织连贯能力、能力层提供更具体的变化；不是三个岗位等级|
|架构域|Business、Data、Application、Technology：从哪类内容分析？|同一分段通常跨多个域；Segment不能固定等同某个域或部门|
|抽象程度|Contextual、Conceptual、Logical、Physical：描述具体到哪一层？|抽象程度与全景粒度、角色层级和ADM阶段分别记录；逻辑架构不自动等同企业级|
|时间/演进|Baseline、Target、Transition：哪个时间与状态？|多个过渡状态各有可运营条件；Target不是批准状态，批准也不是实现状态|
|组成/分解|contains/decomposes：整体由什么构成？|能力分解不等于流程先后；图中嵌套不自动补为原图没有的连线或基数|
|类型/实例|instance_of：这是哪种能力的具体实例？|某地实际能力实例不应被混成能力类型的下级分解|
|实现/支撑|realizes/enables/uses：什么实现、使能或使用什么？|实现、使用、包含的方向和含义不同；ABB/SBB映射须有依据|
|治理与协作|guidance/constraint/coordinates：谁约束或协调什么范围？|同级可在有依据的专项内协调；不能自动变成人事汇报|
|人事关系|reports_to：哪项实际组织授权证明汇报关系？|Chief是EA特殊角色，不是把所有技能升为4；角色名称和技能熟练度都不授予权限|

上层架构通过目标、原则、约束、共享服务和治理指导具体变化；下层通过可行性、风险、实施与运营反馈修正上层判断。相互关系需要明确适用范围及接口。不能只画一棵树就宣称已说明架构全景、组织汇报、业务分解和实现关系。

Enterprise Continuum用于组织从通用到组织特有的架构与解决方案资产，帮助分类和复用；它不是ADM时间线、项目成熟度或审批链。Architecture Repository保存有版本与状态的架构资产；Reference Library、Standards Information Base、Governance Log等内容有不同用途，不能把来源资料库中的参考示例当成本企业批准标准。见[内容卷§6](../corpus/fundamental/analysis/05-architecture-content.md#chap06)与[§7](../corpus/fundamental/analysis/05-architecture-content.md#chap07)。

## 用变化证明理解，而不是背诵阶段

以明确虚构的全渠道履约任务练习：先缺失库存一致性要求时，比较同步预占与异步处理并列出决定所缺依据。提供充分情景输入后，才根据声明的受理/确认、超卖边界、离线条件和恢复目标评价候选；保留专家及真实批准待办。

新增“离线门店持续销售”时，应检查受理和确认状态、持久化、重放幂等、冲突与补偿、库存风险、运营人工介入、过渡安排和测试。未确认订单不能直接进入物流。相反，只把“库存预占”重命名为“库存锁定”且语义不变，应沿稳定ID更新目录、矩阵和图的显示，不凭文字变化重造业务政策。

讲解或评审应能从材料指出：为何选择该阶段工作；哪个证据支撑方案判断；哪些制品表达同一对象；哪个变化会使旧决定失效；谁有权决定；哪些事实仍未知。若无法回答，应回到对应来源和实际业务材料补充，而非增加模板数量。

## 阅读来源有疑点时怎样处理

本地《架构内容》表2-3有若干相反方向使用相同被动标签的行，例如应用服务与数据实体双向均标为Used by。中文对照保留源、目标和英文标签，当前[来源问题清单](../corpus/quality/extended-source-issues.json)记录差异。实际业务模型应依证据说明谁使用、访问或更新什么；不能从这类表行自动制造互逆关系、方向或多重性。核心卷SMART写Specific，内容卷实体表写Simple，均按来源保留，项目采纳的目标标准需另记依据。
