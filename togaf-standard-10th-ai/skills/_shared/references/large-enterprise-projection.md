# 大规模企业数据到架构模型

本工作流用于百万级交易、事件和运营台账。交易记录为度量与现状证据，架构对象另按业务含义建立；不能把每条交易当成一个架构节点。

## 输入与可复算事实

1. 保存原始数据快照、schema、来源时间、记录数、单位、时区、主外键和 SHA-256。模拟数据明确标注虚构；职责、目标、预算、候选方案和批准不得从交易行自动推导。
2. 独立检查金额、数量、时间先后、跨表一致性、状态及边界。保留失败输入和异常注入结果；生成器成功退出不等于数据正确。
3. 在只读快照上聚合。每个事实保留 SQL、参数、期间、返回行、查询 ID 与快照哈希；查询前后再次核对哈希。不要把事件晚到天数解释为毫秒级 API 延迟。
4. 按基地、产品、客户分层、能力、价值流阶段及系统边界选择关注点。聚合粒度与分母必须能解释，未知或未采集不替换为零。

可复跑示例：[百万企业输入与独立核算](../examples/million-enterprise/README.md)。大型 SQLite 是可重建验收数据，核心包保留生成器、契约与SQL，运行后另存当前清单；使用百万案例前重建数据库，常规技能无需加载它。

## 共享模型与 ADM

用稳定 ID 关联组织、能力、流程、应用、信息、技术、需求和工作包。同一企业的多个视图复用这些对象；不要把 266 个独立表示法案例简单拼接后称为一套企业架构。

从业务说明和证据建立企业边界、利益相关者、原则和愿景；B/C/D 描述基线、候选目标及质量需求；E/F 明确差距、依赖、优先级和可运营过渡状态；G/H 需要实际实施与价值观察。通过 [ADM 周期](adm-cycle.md) 保留每阶段裁剪、输入、输出、退出条件与迭代，通过 [持续需求追溯](requirements-trace.md) 检查目标、设计、工作包和验收链。

模型中交易度量引用查询来源，架构决策引用访谈、契约或显式假设。目标值不当作已实现值。交付物章节绑定实际模型对象与分析记录，每章说明结论、依据、决策边界及待解决事项。

## 输出与验收

- 数据层：保存实际百万级扫描、独立核算、损坏反例和确定性复建证据。
- 企业层：从同一模型生成所需目录、矩阵、图和交付物；检查跨制品一致性、查询溯源与章节内容。
- 表示层：逐 profile 运行正例、修改例和缺字段/缺结构反例。独立表示法测试不能冒充百万交易事实。
- 方法层：逐方法列明实际入口、输入来源、规则、结果和边界。区分百万数据绑定、模拟治理输入及独立方法案例。
- 来源层：打开原图与当前整图，核对层级、方向、归属、类型、坐标轴、单位和例外。目录行不是正文证据，缩略图筛查和 SVG 成功不等同语义验收。

最后冻结源码和模型指纹，再运行全量回归与输出完整性校验。运行期间有相关输入变化则保留该批次作为诊断，重新执行受影响检查，不手工刷新旧报告的指纹。

## 已编码的来源误读防护

G212 因素递进使用 `dtra-factor-progression` 或 `adoption-factor-progression-default`：基础、影响、持续三层与类型 1/2/3 是定性就绪情形，不是三个排期步骤；外层必须具备内层前提。实施计划另外建工作包。

G233 应用变化使用 `application-gap-dependency`：分别建应用、数据副本、差距、退役事件、交付物与显式工作包关系；退役事件不能替换为差距。工作包依赖是项目陈述，不从参考图位置推断。
