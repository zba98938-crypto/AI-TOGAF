# 冲刺 DORP 记录：没达成就写没达成

虚构跨馆借阅试点的 SP-01 结束了。演示做了一半，演示也做成了几项，但整体没达成。本案例演练 DORP 四项活动（演示、成果整理、回顾、下轮规划）如何留下可核对记录，以及为什么"未完成项回流"和"顺延已获准"是两件完全不同的事。

所有业务材料、人物、承诺与结果均为虚构教学材料（`BR-01`–`BR-20`）。指南只提供方法依据，项目规则不冒充 TOGAF 规定。

方法：`dorp-record-method`。来源方法：G210 §3.3.2、§5.5。
入口：[dorp-record-method](../analysis-methods/dorp-record-method.md)。
素材：原料（历史材料已清理）、模型（历史材料已清理）。

## 决策与原始业务资料

要回答：**SP-01 到底达成没有？没达成的部分去哪了？回顾得出什么、下轮打算做什么、谁批的？**

| 证据 ID | 原始材料 |
|---|---|
| `BR-06` | SP-01 目标是"形成可供两馆审阅的身份与预约契约包，包含审计事件"；这些是待评审设计结果，不能声称已投产。 |
| `BR-07` | 11 月 6 日演示：身份规则正确分开两名同名测试读者，`DEMO-01` 记录人工复核分支；审计清单 `AUD-01` 已形成。预约契约仍缺乙馆"取消后重新预约"状态约束，**未完成**。**总体冲刺目标未达成。** 未完成项应回到业务变革待办，**不能直接宣称顺延已获准**。 |
| `BR-08` | 回顾发现乙馆接口负责人直到最后一天才参与。下一次先邀请该负责人澄清取消规则，并评审旧系统状态取值；记录行动 `ACT-01`，负责人接口负责人，目标日期 11 月 9 日。11 月 6 日还收到"短信通知模板"新需求，记为**待澄清，尚无估算，不自动承诺下个冲刺**。 |

## 来源规则与项目规则

1. **来源方法（G210 §3.3.2、§5.5）**：DORP 是冲刺结束的四项活动——演示（Demo）、成果整理（Outcomes）、回顾（Retrospective）、下轮规划（Planning）。四项缺一，冲刺就没有真正的结束点。
2. **来源方法**：成果以**冲刺目标**为基准判断，不以"完成了几个事项"为基准。三个事项完成两个，目标仍可能未达成。
3. **来源方法**：未完成项回到业务变革待办，保留原标识，不因结束而删除。
4. **项目规则**：目标未达成时 `goal_result` 必须写 `not-achieved`，不得写"部分达成"这类模糊值（`BR-07` 原文即"未达成"）。
5. **项目规则**：下轮规划中的行动是 `proposed`；**"顺延"本身需要批准**，未获批准即不得写成已安排（`BR-07`）。
6. **项目规则**：新需求在无估算、未澄清时只能标 `needs-clarification`，`estimate` 写 `null`（`BR-08`）。

## 转换与推理

1. **演示段逐项记事实，不记评价**。`DORP-01.demo` 三条：`BL-01` 证据 `DEMO-01`，观察"同名异证分开且有人工复核分支"；`BL-03` 证据 `AUD-01`，观察"审计清单已形成"；`BL-02` 证据 `BR-07`，观察"取消后重约约束缺失，未完成"。**演示记录只写看到了什么**，不写"效果良好"。

2. **成果段以目标为基准**。`outcomes.goal_result=not-achieved`；`completed=[BL-01, BL-03]`；`incomplete=[BL-02]`；`reason` 写"API 契约关键状态缺失，整体包不满足目标"。这里的关键推理是：**"包含审计事件"这一半满足了，但"可供两馆审阅的契约包"这一半没有**，所以整体判为未达成。不能因为 2/3 事项完成就判"基本达成"。

3. **回流是明确字段，不是口头承诺**。`returned_to_business_backlog=[BL-02]`。`BL-02` 回到业务待办后仍是同一个 ID，其 `status` 从 `selected` 回到 `open`，`history` 追加一条带日期的记录。

4. **回顾写机制而不是写情绪**。`retrospective` 写"乙馆接口负责人介入过晚，状态语义直到最后一天才暴露"。这是一条**可检验的机制性观察**；写"沟通不畅"则无法据此改动任何东西。

5. **下轮规划只到 `proposed`**。`next_plan=[{ACT-01, 邀请乙馆负责人澄清取消规则并评审取值, 接口负责人, 2026-11-09, proposed}]`。负责人与目标日期都有，但状态是提案。**"有人负责 + 有日期"不等于"已批准"**。

6. **新需求单独通道**。`new_backlog_requests=[{REQ-SMS, 短信通知模板, needs-clarification, estimate: null}]`。它没有进 `next_plan`——因为 `BR-08` 明确它尚无估算、不自动承诺下个冲刺。若把它塞进 `next_plan`，就是把"收到一个想法"当成"承诺一件事"。

7. **记录时点**。`review_at=2026-11-06`，`history` 追加 `{at: 2026-11-06, goal_result: not-achieved, evidence: BR-07}`。历史条目只追加不覆盖，后续若有人主张"其实达成了"，必须以新增更正条目处理，不能改旧条目。

## DORP 四项活动的产出对照

四项活动各有独立产出，缺一项冲刺就没有真正的结束点：

| 活动 | 产出 | 判据 | 本案记录位置 |
| --- | --- | --- | --- |
| Demo（演示） | 逐项观察到的结果 | 有证据编号，含未达成的项 | `DORP-01.demo` |
| Outcomes（成果整理） | 以目标为基准的达成判定 | `goal_result` + 完成/未完成集 | `DORP-01.outcomes` |
| Retrospective（回顾） | 机制性观察 | 可据以改动流程，非评价 | `retrospective` |
| Planning（下轮规划） | 提案级行动 | 含负责人与目标日期，状态 `proposed` | `next_plan` |

**"演示"必须是逐项的**。三项演示里有一项未完成，也要写进 `demo` 并附证据——**只报成功的项，`outcomes` 就无法解释为何未达成**。

**"达成判定"以目标为基准，不以事项数为基准**：

| 情形 | 正确判定 | 错误判定 |
| --- | --- | --- |
| 3 项中 2 项完成，但目标要求的组合不完整 | `not-achieved` | "基本达成 67%" |
| 3 项中 1 项完成，但目标只要求这一项 | `achieved` | "只完成 33%" |

判断依据是**目标是否被满足**，不是完成比例。

## 三个不可混淆的集合

| 集合 | 含义 | 本案内容 |
| --- | --- | --- |
| `completed` | 演示中已观察到的结果 | `BL-01`、`BL-03` |
| `incomplete` | 已识别但未完成 | `BL-02` |
| `returned_to_business_backlog` | 回到上游待办的事项 | `BL-02` |

**`incomplete` 与 `returned` 通常重叠但不必然相等**：未完成项可能因为范围取消而不回流，也可能因为依赖未满足而回流。本案 `BL-02` 两者皆有。

**历史条目只追加**。`history` 是时间序列，后续补上的证据以新条目记录，**不改旧条目**。这一条使"当时确实未达成"成为可考证的事实。

## 修改演练

改动一处输入：假设 11 月 9 日乙馆给出取消规则，`DEMO-02` 验证了 API 的取消与重新预约（即 `BR-18` 的情形）。

**不能做的事**：把 `DORP-01.outcomes.goal_result` 改成 `achieved`。理由：`BR-18` 明确"新证据**不改变**原冲刺目标未达成的历史记录"。冲刺是有时间盒的，时间盒结束时未达成，就是未达成；后来补上了，属于下一轮的事实。

**可以做的事**：
- `BL-02` 的状态可从 `open` 推进到"设计完成"（**不是投产**）。
- `ACT-01` 从 `proposed` 可推进为已完成，附 `DEMO-02` 为证据。
- `DORP-01.history` **追加**一条 `{at: 2026-11-09, note: BL-02 取消语义补齐并验证, evidence: BR-18}`，原有 `{at: 2026-11-06, goal_result: not-achieved}` 保持不变。

影响视图：`v-dorp-record-default` 的 `history` 与 `next_plan` 字段变化；`outcomes` 不变。这体现了"历史只追加、结论不回写"的规则。

反向演练：若把 `REQ-SMS` 的 `estimate` 从 `null` 改为 `1` 并加入 `next_plan`，则违反 `BR-08` 的"尚无估算、不自动承诺"。正确做法是先澄清（谁发起、模板内容、是否涉及个人数据），澄清后再估算，估算后再由有权限的人决定是否入下轮。

## 反例与输入不足

- **错误做法**：`outcomes.goal_result` 写 `achieved`，理由是"三项里两项完成，且第三项已排计划"。计划不是结果。预期 `dorp-goal-conflict`。
- **错误做法**：未完成项不写入 `returned_to_business_backlog`，让它在冲刺视图里消失。冲刺结束不等于事项结束。预期 `dorp-return-missing`。
- **错误做法**：`next_plan` 中 `ACT-01` 状态写 `approved`，但没有任何批准记录。预期 `fictional-approval`。
- **错误做法**：把 `REQ-SMS` 直接放入 `next_plan` 并给 `estimate: 0.5`。无估算依据的承诺。预期 `fictional-approval`。
- **错误做法**：DORP 记录只有 `demo` 与 `outcomes`，省略 `retrospective` 与 `next_plan`。四项活动不可裁剪。预期 `dorp-boundary-missing`。
- **错误做法**：修改后把 `history` 的旧条目改写为 `achieved`，而不是追加新条目。历史被覆盖。预期 `dorp-goal-conflict`。

**输入不足**：`BR-08` 没有给出 `REQ-SMS` 的发起人、模板内容、涉及的数据范围。因此本案例只能把它登记为待澄清，不能判断它是否涉及个人数据、是否需要安全评审。`BR-07` 也没有说明"顺延"由谁批准——所以 `DORP-R5` 只能停在 `proposed`，审批路径列为未决。

## 评审记录

- 核对演示三项均有证据引用，且含一项明确的负向观察。
- 核对 `goal_result` 以目标为基准判定，未用事项完成比例替代。
- 核对未完成项在 `returned_to_business_backlog` 中显式出现，且 ID 未变。
- 核对回顾为机制性观察，可据以改动流程。
- 核对 `ACT-01` 停在 `proposed`，未出现"已顺延/已批准"字样。
- 核对 `REQ-SMS` 未进入下轮承诺，估算为 `null`。
- 核对修改演练中历史只追加、旧结论不被回写。
- 核对 DORP 四项活动齐全。
