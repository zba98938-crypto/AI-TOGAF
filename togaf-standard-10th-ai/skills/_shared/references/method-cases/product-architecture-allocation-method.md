# 产品架构分配：功能、组件、接口三层不能混

## 决策与原始业务资料

养老金申报产品的功能、组件与接口如何分配？哪些已获批？

| 证据 ID | 原始材料 |
|---|---|
| `R09` | 产品 `PR-PENSION` 需功能 `F-SUBMIT`（提交受理）、`F-STATUS`（查状态）。 |
| `R09` | 前台组件 `C-PORTAL` 承接两项交互；`C-CASE` 处理受理，`C-STATUS` 提供查询。 |
| `R09` | 接口 `I-SUBMIT`：`C-PORTAL`→`C-CASE`，提交申请 ID 与必要字段，返回受理编号。接口 `I-STATUS`：`C-PORTAL`→`C-STATUS`，查申请 ID，返回状态与更新时间。 |
| `R09` | 均为 **1.0 候选**，需认证与授权，**未获批上线**。 |
| `R10` | 技术组件 `TC-API` 为受控 API 运行环境，两个后端依赖它；无真实厂商与 SLA。 |

## 来源规则与项目规则

1. 来源方法（G21H）：产品架构分功能（做什么）、组件（谁做）、接口（怎么连）三层，各层有独立身份。
2. 来源方法：接口必须声明方向、载荷与返回，不能只有一条连线。
3. 项目规则：**候选不等于获批**（`R09`）；未获批前不得称"已上线"或"已交付"。
4. 项目规则：`TC-API` 无真实厂商与 SLA（`R10`），因此不得引用具体性能承诺。

## 转换与推理

1. **三层分配表**：

| 功能 | 承接组件 | 接口 | 方向 | 载荷 |
| --- | --- | --- | --- | --- |
| `F-SUBMIT` | `C-CASE`（经 `C-PORTAL`） | `I-SUBMIT` | `C-PORTAL` → `C-CASE` | 申请 ID + 必要字段 → 受理编号 |
| `F-STATUS` | `C-STATUS`（经 `C-PORTAL`） | `I-STATUS` | `C-PORTAL` → `C-STATUS` | 申请 ID → 状态 + 更新时间 |

2. **`C-PORTAL` 的角色**：它承接两项交互但不实现业务逻辑，是交互层。若把它当作业务组件，会把展示逻辑误当受理逻辑。
3. **`TC-API` 的位置**：技术组件，被两个后端依赖。它属技术层，不在功能-组件-接口三层的主体分配中，但需独立记录其依赖关系。
4. **候选状态贯穿**：所有对象标 `1.0 candidate`，需认证与授权。因此结论是候选架构设计；候选设计本身可作为草稿交付物，不等于运营系统已交付。

5. **三层各有独立身份，不能合并登记**：

| 层 | 回答什么 | 本案对象 | 若合并会怎样 |
| --- | --- | --- | --- |
| 功能 | 做什么 | `F-SUBMIT`、`F-STATUS` | 与组件混谈，无法判断是否有人实现 |
| 组件 | 谁做 | `C-PORTAL`、`C-CASE`、`C-STATUS` | 与功能混谈，一个组件承载多功能时归属不清 |
| 接口 | 怎么连 | `I-SUBMIT`、`I-STATUS` | 只有连线没有方向载荷，无法验证契约 |

   合并的实际后果：**无法回答"这个功能由谁实现、通过什么契约暴露"**——而这正是产品架构要回答的问题。

6. **交互层不是业务层**。`C-PORTAL` 承接两项交互，但**不实现业务逻辑**。因此 `F-SUBMIT` 的承接组件是 `C-CASE`，`C-PORTAL` 只是入口。若把 `C-PORTAL` 当作承接组件：
   - 受理逻辑的归属消失
   - `C-CASE` 变成"内部细节"，无法单独评估
   - 出问题时无法判断是展示错还是受理错

7. **接口必须有方向、载荷、返回三要素**。只有一条连线的"接口"不是接口：
   - **方向**：`C-PORTAL` → `C-CASE`（谁调谁）
   - **载荷**：申请 ID + 必要字段
   - **返回**：受理编号

   缺任一项，契约无法被实现方与调用方分别验证。

8. **技术组件单列，不混入三层**。`TC-API` 是技术组件，被两个后端依赖。它不属于"功能—组件—接口"的主体分配，但需记录依赖关系。理由：技术组件的选型与 SLA 是另一类决策，混进产品架构会让"业务能力"与"基础设施"界限模糊。

9. **候选状态贯穿全部对象**。`R09` 明确所有对象为 1.0 候选，需认证与授权，**未获批上线**。因此：
   - 可以说"架构设计已完成到候选程度"
   - **不能说**"已上线""已交付""可对外服务"

   候选状态不是上线许可；只证明本案尚未获上线批准，不能扩大为任何设计活动都无授权。

10. **无厂商无 SLA 时不给性能承诺**。`R10` 说 `TC-API` 无真实厂商与 SLA。因此不能写"P99 50ms"这类指标——那是把设想写成事实。

## 修改演练

**情景一：新增 `F-ASSIST`（人工协助提交）**。需新增 `C-DESK` 组件与 `I-ASSIST` 1.1 候选接口，且**必须记录代理操作依据**——人工代替申请人提交，授权链与自助提交不同。这条差别不是技术细节，是合规前提。

**情景二：`C-CASE` 与 `C-STATUS` 合并**。组件合并不要求接口合并；可保留 I-SUBMIT 与 I-STATUS 两个契约及稳定标识。若另决定共用进程/资源，需评估故障耦合，但查询故障并非必然拖垮受理，取决于隔离实现。

**情景三：`TC-API` 确定厂商与 SLA**。可写入具体性能指标，但**需区分"厂商承诺的 SLA"与"本项目实测的能力"**——两者可以不同，实测未做时只能引用前者并注明来源。

**情景四：某功能被认定"不需要接口"**。例如纯离线批处理。此时该功能仍属功能层，但接口层留空并说明理由；**不能因为没接口就把功能也删掉**。

**影响范围**：情景一新增组件与接口并引入授权差异；情景二重评组件实现、契约保留与故障隔离；情景三使性能指标可引用；情景四改变接口层而非功能层。四种情形下"候选未获批"的状态不变。

## 反例与输入不足

- **错误做法**：因接口已定义即宣布"申报功能已上线"。候选未获批。预期 `approval-without-evidence`。
- **错误做法**：把 `TC-API` 写成"某厂商 API 网关，P99 50ms"。无厂商与 SLA 依据。预期 `missing-evidence`。
- **错误做法**：把 `C-PORTAL` 当作业务组件并让 `F-SUBMIT` 直接归属它。交互层不等于业务实现。预期 `relation-endpoint-type`。
- **错误做法**：把 `I-SUBMIT` 画成一条无向线。接口须有方向、载荷、返回。预期 `relation-endpoint-type`。
- **错误做法**：合并登记功能与组件，写成"`C-CASE` = 提交受理功能"。功能与组件是两个身份。预期 `core-vocabulary-override`。
- **错误做法**：把 `TC-API` 列为业务组件并参与功能分配。技术组件单列。预期 `undefined-entity-type`。
- **错误做法**：候选状态下写"系统已可对外受理申报"。未获批上线。预期 `approval-without-evidence`。
- **错误做法**：给 `TC-API` 标注具体延迟指标。无厂商无 SLA。预期 `measurement-evidence-gap`。
- **错误做法**：因合并 `C-CASE`/`C-STATUS` 后接口更少，就判定架构"更简洁更优"。组件/接口数量不能直接证明故障隔离或整体优劣。预期 `missing-evidence`。

**输入不足**：`PRA-GAP-1` 的认证授权方案缺失，因此无法判断候选架构是否可进入实现。`R10` 未给 `TC-API` 的厂商与 SLA，`PRA-4` 只能声明"不作性能承诺"。材料未给 `C-DESK`（情景一）的现有能力，故该情景只列需求不评可行性。
