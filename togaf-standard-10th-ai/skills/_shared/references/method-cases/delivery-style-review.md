# 交付风格逐范围比较：同一组织可以同时有三种节奏

虚构市民图书馆在做一个跨 47 个服务点的计划。有人主张"全馆一律敏捷"，有人说"档案迁移必须瀑布"。本案例演练：交付风格不是组织级标签，而是**按范围**判定，且必须解释冲突特征而不是投票。

所有业务材料、人物、实验数据与规则均为虚构教学材料（`RAW-01`–`RAW-24`、`LAB-1`–`LAB-3`）。G20F §4.7.1 表 4-1 只提供三种风格的一般画像，**不是组织成熟度等级**。

方法：`delivery-style-review`。来源方法：G20F §4.7.1 表 4-1。
入口：[delivery-style-review](../analysis-methods/delivery-style-review.md)。
素材：原料（历史材料已清理）、执行审计（历史材料已清理）。

## 决策与原始业务资料

要回答：**每个范围该用哪种交付节奏？当 24 条特征彼此冲突时怎么办？**

| 证据 ID | 原始材料 |
|---|---|
| `RAW-01` | 通知组件只影响预约回执 |
| `RAW-02` | 总计划涉及 47 个服务点和中央档案 |
| `RAW-03` | 回执复用既有短信接口 |
| `RAW-04` | 跨点身份与历史档案同步复杂 |
| `RAW-05` | 数据库与消息队列已稳定运行 |
| `RAW-06` | 团队拟采用未在本馆使用的事件流技术 |
| `RAW-08` | 线上预约和退款流程正在重新定义 |
| `RAW-15` | 节庆通知组件目标两周交付 |
| `RAW-16` | 全馆迁移预计跨一个年度 |
| `RAW-17` | 节庆通知上线窗口两周不可延 |
| `RAW-18` | 档案迁移必须跨年度保存窗口 |
| `RAW-20` | 馆藏与收费记录不得丢失且需审计 |
| `RAW-23` | 只读短信模板修改影响有限 |
| `RAW-24` | 个人数据和收费迁移失败后果高 |
| `LAB-3` | 修改实验：变更扩大到 47 馆并发，A 延迟 800 毫秒超出项目 500 毫秒要求；同时短信组件新增个人收费信息 |

## 来源规则与项目规则

1. **来源方法（G20F §4.7.1 表 4-1）**：三种风格（rapid / agile / robust）是**一般画像**，由特征组合描述，不构成成熟度阶梯。
2. **来源方法**：风格按**范围**判定；同一组织内不同范围可以有不同风格，且可以嵌套。
3. **来源方法**：当特征指向不同风格时，应**解释冲突**，而不是数匹配项做多数表决。
4. **项目规则**：24 条特征逐条提取为 `feature_id`，无证据的保留 `unknown`，不补默认值。
5. **项目规则**：`weighted_score` 必须为 `null`，`automatic_approval` 必须为 `false`——本方法不产生分数，也不自动批准。
6. **项目规则**：范围间的风格**不自动传播**（`RAW-23` 明示"rapid 只适用于只读通知组件，不继承到收费或数据迁移"）。

## 转换与推理

1. **按范围切分，而不是按组织切分**。两个范围：`archive-program`（全馆迁移 + 有界预约功能）与 `sms-component`（节庆通知组件）。**同一份 24 条特征在两个范围上得出不同结论**，这本身不是矛盾。

2. **`archive-program`：robust + agile 嵌套**。证据 `RAW-02`（47 点 + 中央档案）、`RAW-04`（跨点身份与档案同步复杂）、`RAW-16`（跨一个年度）、`RAW-24`（个人数据与收费迁移失败后果高）指向 robust；`RAW-08`（线上预约与退款流程正在重新定义）指向需要迭代。结论：**全馆迁移用 robust 控制，预约功能子项目用 agile 试验**。`tailoring` 写"全馆迁移 robust；预约功能子项目 agile；按过渡出口复核运行和恢复条件"。

3. **`sms-component` 基线：rapid**。证据 `RAW-01`（只影响预约回执）、`RAW-03`（复用既有短信接口）、`RAW-15`（两周交付）、`RAW-23`（只读模板影响有限）。四条一致指向 rapid，冲突特征 `F02`、`F24` 被**记录但不推翻结论**——理由是它们描述的是"潜在扩展方向"，当前范围不含。`tailoring` 明确写"rapid 只适用于只读通知组件，不继承到收费或数据迁移"。

4. **冲突特征必须显式列出**。`conflicting_features=["F02","F24"]` 表示这两条特征与选定风格不符。**列出的作用是让读者看到判断的边界**，不是"待消除的异常"。若把它们删掉，结论看起来更干净，但审查者就无法知道判断在哪儿最脆弱。

5. **`weighted_score=null`、`automatic_approval=false`**。这两个字段不是占位符，而是**否定性结论**：本方法不提供分数，不代替批准。`notice` 字段写明"不能以匹配项多数决定交付风格"。

6. **修改：短信组件的风格翻转**。`LAB-3` 加入"个人收费信息" ⇒ `RAW-23` 的"只读、影响有限"前提失效 ⇒ `sms-component.styles` 从 `["rapid"]` 变为 `["agile","robust"]`。`rationale` 改写为"新增个人收费信息使原快速交付假设失效"；`tailoring` 写"功能迭代用 agile；跨馆敏感数据契约与恢复门禁用 robust"。**注意 archive-program 的风格标签可不变，但 LAB-3 的47馆容量证据仍须进入其运营/容量复评**——范围隔离生效。

7. **为什么不是投票**：短信组件有 4 条特征支持 rapid、2 条冲突。若投票，rapid 胜。但 `LAB-3` 之后，那 2 条冲突特征变成了**决定性**的——一条"涉及个人收费数据"足以压过 4 条"影响小/复用/快速"的描述。这说明特征不是等权票，冲突的解释权高于计数。

本方法采用定性判断与追溯演练，没有适用的统一计算器。**`weighted_score` 恒为 `null`**：本案例不给特征赋权、不做加总、不设及格线。三风格比较的产物是**带冲突说明的范围级判断**，不是排名。

## 修改演练

改动一处输入：`LAB-3` 声明短信组件新增个人收费信息。

- `sms-component.styles`：`["rapid"]` → `["agile","robust"]`。
- `sms-component.rationale`：改为"新增个人收费信息使原快速交付假设失效"。
- `sms-component.evidence_refs`：从 `["RAW-01","RAW-03","RAW-15","RAW-23"]` 改为 `["LAB-3"]`。**旧证据不再单独成立**，因为 `RAW-23` 的"只读"前提已被推翻；保留旧引用会让读者以为判断仍基于"只读"。
- `sms-component.tailoring`：改为"功能迭代采用 agile；跨馆敏感数据契约与恢复门禁采用 robust"。
- archive-program 的既有风格理由仍可保留，但此次 LAB-3 也直接涉及47馆负载，需补容量风险和证据；不能借范围隔离宣称所有字段全部不变。
- 影响视图：`delivery-style-assessment` 的两个范围行，第二个范围的 `styles`、`rationale`、`evidence_refs`、`tailoring` 变化。

反向演练：若 `LAB-3` 只给"47 馆并发下 A 延迟 800ms"，而短信组件不变，则 `sms-component` 应保持 rapid，只有 `archive-program` 的恢复/容量判断受影响。**修改必须落在它真正触及的范围上**，不能因为同一次实验就全表机械翻转风格，也不能遗漏实验直接触及的容量判断。

## 三风格的适用范围

- rapid/agile/robust 是一般画像，不是等级阶梯
- 风格按范围判定，同一组织可有多种
- 特征冲突时解释冲突，不做多数表决
- weighted_score 恒为 null，不做加权
- 风格不跨范围自动传播

## 反例与输入不足

- **错误做法**：只提取 20 条特征，漏掉 4 条与结论冲突的。特征覆盖不全。预期 `style-feature-coverage`。
- **错误做法**：`sms-component.rationale` 留空，只在 `styles` 里写 `["rapid"]`。判断无依据。预期 `style-decision-evidence-gap`。
- **错误做法**：`archive-program.conflicting_features=[]`，把 robust 与 agile 的张力隐去。冲突必须显式。预期 `style-conflict`。
- **错误做法**：给 24 条特征各赋权重，算出 `sms-component` 得分 72 分判 rapid。禁止加权评分。预期 `unsourced-maturity-rating`。
- **错误做法**：把三种风格标为"成熟度 1/2/3 级"，并称组织"处于 2 级"。风格不是等级。预期 `unsourced-maturity-rating`。
- **错误做法**：把 `sms-component` 的 rapid 直接继承给 `archive-program` 的收费迁移部分，理由是"同属一个项目"。风格不自动传播。预期 `missing-evidence`。

**输入不足**：`RAW-06`（拟采用未在本馆使用的事件流技术）与 `RAW-10`（事件流设计与恢复演练需培训）指向能力缺口，但材料**未给培训完成情况**。因此 `archive-program` 的 robust 判断中，"团队是否具备事件流恢复能力"仍为未知，未作为支撑证据使用。`RAW-19`（志愿者和 IT 预算限制）未给具体数额，本案例不据此做任何资源结论。

## 评审记录

- 核对 24 条特征逐条有 `feature_id` 与来源引用，无遗漏、无补填。
- 核对两个范围风格不同且各自有独立证据组，未互相继承。
- 核对 `conflicting_features` 在两个范围均非空并逐条列出。
- 核对 `weighted_score` 为 `null`、`automatic_approval` 为 `false`，全表无分值。
- 核对 `tailoring` 明确写出风格的作用边界（"不继承到收费或数据迁移"）。
- 核对修改演练中只有被触及的范围变化，另一范围字段完全不变。
- 核对 `evidence_refs` 在前提被推翻后同步替换，未保留失效引用。
- 核对三风格未被表述为成熟度阶梯。
