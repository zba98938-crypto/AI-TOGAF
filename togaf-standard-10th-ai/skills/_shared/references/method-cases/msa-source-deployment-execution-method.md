# 微服务源与部署：一个部署包只装一个服务

所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充 TOGAF 规定。案例完整演练不等于独立业务评审通过。

## 决策与原始业务资料

资格服务的源、部署与执行单元边界在哪？两个实例是否算两个服务？

| 证据 ID | 原始材料 |
|---|---|
| `msa-s1` | 资格服务有独立源单元。 |
| `msa-s2` | 可复用不含业务逻辑的脱敏日志库。 |
| `msa-s3` | 单一部署包只包含资格服务代码。 |
| `msa-s4` | 在节点 A/B 运行**同代码实例**，数据有效且健康后才接流量。 |
| `msa-s5` | 没有把两个服务打成一个部署包。 |

## 来源规则与项目规则

1. 来源方法（G21I）：源单元、部署单元、执行单元是三个不同层级，需分别追溯。
2. 来源方法：共享库不等于共享业务代码；无业务逻辑的通用库可以复用。
3. 项目规则：**一个部署包只含一个服务的业务代码**（`msa-s3`/`msa-s5`）；否则失去独立部署能力。
4. 项目规则：多实例是同一服务的执行单元复制（`msa-s4`），不是多个服务。

## 转换与推理

1. **三层切分**：

| 层 | 内容 | 说明 |
| --- | --- | --- |
| 源单元 | 资格服务独立逻辑源单元（物理仓库是否独立未给） | 独立，不含他服务代码 |
| 依赖库 | 脱敏日志库 | 无业务逻辑，可跨服务复用 |
| 部署单元 | 单一部署包 | 只含资格服务 |
| 执行单元 | 节点 A、节点 B 两个实例 | 同代码实例，具体进程/容器布局待证 |

2. **实例不等于服务**：`msa-s4` 的两个实例是同一服务的水平扩展。若把它们当作两个服务，会错误地产生"服务间调用"关系。
3. **接流量条件**：数据有效 + 健康检查通过才接流量，两者缺一不可。仅健康不足以说明数据可用。
4. **共享库判定**：日志库不含业务逻辑，可作为复用候选；仍需核版本、依赖、访问与脱敏控制，不能仅凭无业务逻辑证明不影响数据边界。若复用库中含有资格判定逻辑，则两个服务实际耦合。

5. **三层各自的"一个"含义不同**：

| 层 | "一"指什么 | 本案证据 |
| --- | --- | --- |
| 源单元 | 可追溯的逻辑源单元只承载本服务；不把独立源单元强等同独占物理仓库 | `msa-s1` |
| 部署单元 | 一个部署包只含本服务代码 | `msa-s3` |
| 执行单元 | 本案运行实例；进程/容器实现未给，不强制一实例一进程 | `msa-s4`（两节点） |

   三者可以数量不同：**一个源 → 一个部署包 → 两个执行实例**。若把"一个"理解为"全局只有一个"，就会把 A/B 两节点误判为两个服务。

6. **实例不等于服务，这条区分决定架构图的对错**。`msa-s4` 说节点 A/B 运行同代码实例。若把它们画成两个服务并连一条调用关系：
   - 凭空产生一条不存在的服务间契约
   - 后续会有人为这条"契约"设计重试、超时、幂等——全是无中生有
   - 真实的服务边界被掩盖

7. **接流量需要两个条件，且第二个更难**。`msa-s4` 要求"数据有效 + 健康"才接流量：
   - **健康**：进程活着、端口可达（技术上容易验证）
   - **数据有效**：依赖的数据已就绪且可用（业务上常被忽略）

   只做健康检查就接流量，会让实例返回"活着但答错"的结果。

8. **共享库的判据是"有无业务逻辑"，不是"是否共享"**。`msa-s2` 的脱敏日志库无业务逻辑，可跨服务复用。判据：
   - 无业务逻辑 ⇒ 不引入共享业务规则；技术依赖与数据访问影响仍须核查
   - 含业务逻辑 ⇒ 复用的两方实际耦合（改一处影响两方）

   若日志库里塞进了"资格判定"规则，它就变成了隐式的共享业务代码。

9. **退化信号：两个服务一个部署包**。`msa-s5` 明确没有把两个服务打成一个部署包。若出现这种情形，独立部署能力即失效：
   - 任一服务变更需整体发布
   - 无法按服务独立回滚
   - **不应再称"微服务"**

## 修改演练

**情景一：两个服务打进一个部署包**。`MSA-S1` 的独立部署失效，任一服务变更需整体发布，**退化为分布式单体**。此时不得再称"微服务"——名称与能力不符。

**情景二：A/B 运行不同版本**。不再是同代码实例，需按发布策略处理版本兼容。**不能简单视为水平扩展**——不同版本的实例对同一请求可能给出不同结果。

**情景三：脱敏日志库被加入资格判定规则**。该库从"通用库"变为"含业务逻辑的共享代码"，两个服务的边界被侵蚀。此时应把判定逻辑抽回资格服务，或承认两者已耦合。

**情景四：节点 B 健康但数据未就绪**。按 `msa-s4` 不应接流量。若已接入，会返回"活着但答错"的结果——这类故障比进程宕机更难发现。

**影响范围**：情景一改变部署独立性；情景二改变实例版本与发布兼容评估，但不自动变为两个服务身份；情景三改变库的性质与边界；情景四关系到接流量条件。四种情形下"三层分别追溯"的要求不变。

## 反例与输入不足

- **错误做法**：把节点 A、节点 B 画成两个微服务并连一条调用关系。它们是同一服务的实例。预期 `relation-endpoint-type`。
- **错误做法**：两服务共用一个部署包但声称独立部署。违反 `msa-s3`。预期 `missing-evidence`。
- **错误做法**：仅凭健康检查通过就接流量，未验证数据有效性。预期 `missing-evidence`。
- **错误做法**：把节点 A/B 画成两个微服务并连调用关系。同代码实例是执行单元复制。预期 `relation-endpoint-type`。
- **错误做法**：两服务共用一个部署包但声称独立部署。预期 `missing-evidence`。
- **错误做法**：仅凭健康检查通过就接流量，未验证数据有效性。预期 `missing-evidence`。
- **错误做法**：因两服务共用脱敏日志库就判定它们耦合。无业务逻辑的库可复用。预期 `missing-evidence`。
- **错误做法**：把含资格判定逻辑的库当作"通用库"继续复用。含业务逻辑即耦合。预期 `relation-endpoint-type`。
- **错误做法**：两个服务强制同版本、同构建发布，却声称独立演进。单纯共用代码仓库（monorepo）本身不证明演进耦合。预期 `missing-evidence`。

**输入不足**：`MSA-SGAP-1` 的数据有效性标准未定义，因此无法判断节点 B 何时可接流量。`msa-s4` 未给健康检查的具体项（存活、就绪、依赖探针），接流量条件无法细化。材料未给发布策略，情景二的版本兼容处置只能定性描述。
