# 工作包依赖拓扑排序：五批还是六批，取决于一条依赖边

虚构集团的迁移计划有六个核心工作包及一个培训工作包：建模型、清洗主数据、部署新平台、迁移数据、应用切换、旧系统下线。本案例演练如何用依赖边排出可执行的批次、如何处理硬依赖与软依赖的区别、以及为什么发现环就必须停下而不是硬给一个顺序。

所有业务材料、依赖关系与工期影响均为虚构教学材料。指南只提供方法依据，项目规则不冒充 TOGAF 规定。

方法：`dependency-topological-order`。来源方法：G186 §8、G188 §3.2。
入口：[dependency-topological-order](../analysis-methods/dependency-topological-order.md)。

## 决策与原始业务资料

要回答：**这七个节点最早能分几批做完？哪一批会卡住后面的全部工作？有没有不能排的环？**

| 证据 ID | 原始材料 |
|---|---|
| `DEP-1` | `W1` 建立目标数据模型，无前置。 |
| `DEP-2` | `W2` 主数据清洗，硬依赖 `W1`。 |
| `DEP-3` | `W3` 部署新平台，无前置。 |
| `DEP-4` | `W4` 数据迁移，硬依赖 `W2`、`W3`。 |
| `DEP-5` | `W5` 应用切换，硬依赖 `W4`。 |
| `DEP-6` | `W6` 旧系统下线，硬依赖 `W5`。 |
| `DEP-7` | 软依赖：`W5` 之前最好完成"运维培训"（`W7`），但**它不阻塞切换**。 |

## 来源规则与项目规则

1. **来源方法（G186 §8、G188 §3.2）**：用工作包清单建节点、依赖边建有向图；拓扑分批给出的是**可执行顺序**，不是授权结论。
2. **来源方法**：**存在环时立即返回环清单（`cycle`），不输出顺序**——不可执行的顺序比没有顺序更危险。
3. **来源方法**：硬依赖决定批次，**软依赖不阻塞批次**，但必须登记为"被跨越的软边"。
4. **来源方法**：缺 `hard`/`soft` 标记时，只能输出**候选序**并登记缺口，不能声称关键路径。
5. **项目规则**：批次编号从 1 起，同批内节点可并行，但**并行须另受资源约束**（本案例未给并发上限，故不判断并行可行性）。
6. **项目规则**：本方法**不证明任何工作包已获授权**；排序结果不等于批准。

## 转换与推理

1. **建图**：节点 `W1`–`W7`；硬边 `W1→W2`、`W2→W4`、`W3→W4`、`W4→W5`、`W5→W6`；软边 `W7⇢W5`。

2. **检测环**：沿硬边走一圈，回到起点即环。本图无环，继续。

3. **拓扑分批（每步把"前置已全部完成"的节点放入当前批）**：
   - **批次 1**：`W1`、`W3`、`W7`（均无硬前置）
   - **批次 2**：`W2`（`W1` 已完成）
   - **批次 3**：`W4`（`W2`、`W3` 均完成）
   - **批次 4**：`W5`（`W4` 完成）
   - **批次 5**：`W6`（`W5` 完成）

4. **软边处理**：`W7` 在批次 1，`W5` 在批次 4，故此候选分批中软边顺序已满足，`crossed_soft_edges=[]`。软边不参与硬边入度计算；若资源排程把培训推迟至切换之后，才登记该软边被跨越，不能仅因它是软边就记跨越。

5. **为什么批次 1 有三个节点**：`W1`、`W3`、`W7` 互无硬依赖，可同批启动。**但"可同批"不等于"应同批"**——若团队只有一组人，两件事仍要串行。本案例未给资源约束，故只报逻辑上的最早分批，`blocked=[]`。

6. **"五批"不是工期**。批次是**逻辑层次**，不是日历周期。若 `W4` 需要 3 个月，批次 3 就比批次 2 长得多。**把批次数当工期是常见误读。**

| 结果 ID | 结论 | 追溯 | 状态 |
|---|---|---|---|

| `DTO-2` | 最早可行分批为 5 批：[[W1,W3,W7],[W2],[W4],[W5],[W6]] | `DEP-1`–`DEP-6` | 已计算 |
| `DTO-3` | 候选分批满足 `W7⇢W5` 的先后，`crossed_soft_edges=[]`；资源排程后须重核 | `DEP-7` | 已登记 |
| `DTO-4` | `blocked=[]`，无被阻塞节点 | `DEP-1`–`DEP-6` | 已判定 |
| `DTO-5` | 硬/软标记完整，可报告拓扑分批；缺工期，不能声称关键路径 | `DEP-7` | 已核对 |
| `DTO-GAP-1` | 未给资源约束与并发上限，并行可行性未判 | 项目规则 | 未决 |
| `DTO-GAP-2` | `W7` 的工期与责任人未给 | `DEP-7` | 未决 |

批次划分与环检测为可复核的图算法（任何人用同样输入可得同样分批）；**但"是否该同批并行""软边跨越是否可接受"属于判断，不由算法给出**。本案例不计算关键路径长度（缺工期数据），不折算工期。

本方法采用定性判断与追溯演练，没有适用的统一计算器。**方法输出的边界**：给出与 `dependency-topological-order` 相关的判定与缺口清单，**不给出**达标结论、覆盖率或成熟度评分——材料未提供相应度量依据，任何比率都会失真。

## 修改演练

改动一处输入：`W3` 改为依赖 `W2`（新平台需在主数据清洗后部署）。

- 硬边变为：`W1→W2`、`W2→W3`、`W2→W4`、`W3→W4`、`W4→W5`、`W5→W6`。
- 重新分批：
  - 批次 1：`W1`、`W7`
  - 批次 2：`W2`
  - 批次 3：`W3`
  - 批次 4：`W4`
  - 批次 5：`W5`
  - 批次 6：`W6`
- **批次数从 5 增至 6**，且批次 1 从三个节点减为两个——原本可并行的 `W1`/`W3` 现在必须串行。
- 影响：`W4` 及其后节点的逻辑层次后移；原"最早五批"失效，必须重出。缺工期和资源日历，不能据此断言实际日期或总工期必然后移。
- **不能做的事**：保留旧的 5 批结果并注明"仅供参考"。依赖变了，旧顺序就是错的。

反向演练：若把 `W7⇢W5` 的软边改为硬边，则新增硬边 `W7→W5`；本案 `W7` 原已在批次 1，因此仍为 5 批，`crossed_soft_edges` 仍为空。**软硬标记的变更等同于依赖变更**，不能只改标记不改分批。

## 反例与输入不足

- **错误做法**：依赖图 `A→B→C→A` 成环，仍输出 A、B、C 顺序。存在环却未报告，给出的顺序不可能执行。预期 `cycle`。正确处置：立即返回 `cycles`，不输出 `batches`，并要求先裁决环上的依赖是否真实。
- **错误做法**：把软依赖 `W7⇢W5` 当硬依赖，并声称必然推迟 `W5`。软边不应计入硬入度；本案改硬也不增加批次数。预期 `missing-evidence`（依赖类型误判）。
- **错误做法**：删除 `hard`/`soft` 标记后仍声称"以下为关键路径"。缺标记只能给候选序。预期 `missing-evidence`。
- **错误做法**：把批次 3 的 `W4` 与批次 4 的 `W5` 合并为一批，理由是"看起来差不多能一起做"。`W5` 硬依赖 `W4`，同批不可能。预期 `dependency-order-violation`（依赖顺序被违反，不是图中存在环）。
- **错误做法**：输出顺序后声明"因此 `W1` 已获批准启动"。排序不是授权。预期 `approval-without-evidence`。
- **错误做法**：把"5 批"写成"5 周"。批次是逻辑层次，不是日历。预期 `measurement-basis-gap`。

**输入不足**：材料未给各工作包工期，因此**无法计算关键路径长度**，也无法判断哪一批是瓶颈（工期缺口，非环检测结果）。`W7` 只有名称"运维培训"，无工期、无责任人、无完成标准（`DTO-GAP-2`）。未给并发上限，故"批次 1 的 `W1` 与 `W3` 可并行"只是逻辑可能，不是资源可行。

## 评审记录

- 核对节点与依赖边逐条可追到 `DEP-1`–`DEP-7`。
- 核对硬/软标记完整，软边单独检查顺序，本候选未跨越。
- 核对环检测在分批之前执行，且无环结论有依据。
- 核对分批严格按"前置全部完成"规则，无跨批违反依赖。
- 核对批次 1 含三个无硬前置节点，且未声称其并行在资源上可行。
- 核对 `blocked` 为空与无环、无缺失前置一致。
- 核对未把批次数表述为工期。
- 核对排序结果未升级为授权结论。
- 核对修改演练中依赖变化导致重新分批，未保留旧顺序。
