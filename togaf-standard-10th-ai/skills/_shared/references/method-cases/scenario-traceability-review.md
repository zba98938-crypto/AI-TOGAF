# 业务场景关联矩阵：两行流程凭什么复用一个参与者角色

虚构图书馆有两个流程——受理预约与取消退款。业务材料把它们混在一段话里说完。本案例演练如何把原始叙述拆成"五类列 × 流程行"的关联矩阵、如何区分同一个人与两个对象、以及为什么表格里相邻不代表它们有关系。

所有业务材料、人物与修订均为虚构教学材料（`S-R1`–`S-R3`）。指南只提供方法依据，项目规则不冒充 TOGAF 规定。

方法：`scenario-traceability-review`。来源方法：G176 §3.2.3；English PDF 22–23；G176 §11.4；English PDF 45–46。
入口：[scenario-traceability-review](../analysis-methods/scenario-traceability-review.md)。
素材：案例（历史材料已清理）、基线结果（历史材料已清理）。

## 决策与原始业务资料

要回答：**哪些实体真的参与哪个流程？哪些关系是我们自己猜出来的？**

| 证据 ID | 原始材料 |
|---|---|
| `S-R1` | 读者群体说：电话和网页重复报名让同一人占两个名额，希望每个读者每场课程只有一个有效预约。预约员在受理预约流程中使用课程预约系统处理两条渠道。 |
| `S-R2` | 读者群体说：取消后退款经常漏记，希望次一工作日内登记退款。预约员在取消退款流程里与退款队列系统交互；财务组关注这个流程的退款记录。 |
| `S-R3` | **修订**：取消退款改由**统一支付台**处理，**原退款队列退役**。受理预约仍使用课程预约系统。 |

## 来源规则与项目规则

1. **来源方法（G176 §3.2.3）**：业务场景矩阵以**流程**为行、以**五类实体**（利益群体、人参与者、计算机参与者、问题、目标）为列，单元格表示参与关系。
2. **来源方法**：矩阵中的关联表示"参与"，**不是 CRUD、不是控制流、不是数据流**。
3. **来源方法**：同一实体出现在两行时，**复用同一 ID**，不因出现在不同流程而新建对象。
4. **项目规则**：每个"痛点"必须有对应的"结果"，否则矩阵只记录抱怨而无改进目标（`SCN-003`）。
5. **项目规则**：不得把技术候选需求标为已批准（`review.unresolved` 明示）。
6. **项目规则**：空白格表示"尚未确认无关联"，**不等于已确认无关**。

## 转换与推理

1. **拆分复合句，保留全部子句**。`S-R1` 一句里含六件事：读者群体（`st-patrons`）、重复报名问题（`p-duplicate`）、唯一预约目标（`g-unique`）、受理预约流程（`proc-book`）、预约员（`actor-booking`）、课程预约系统（`app-booking`）。拆成 `S-N1`–`S-N6`，**每条都注明来自 `S-R1`**。

2. **同一参与者角色不建两个对象；材料未证明是同一自然人**。`S-R2` 里又出现"预约员"，`S-N10` 的说明写"复用预约员，不生成第二个对象"，`entity_id` 仍是 `actor-booking`。`S-N13` 同理复用 `st-patrons`。财务组是**新的**利益群体（`st-finance`），因为它此前没出现。

3. **转型日志显式记录"为什么这么拆"**。`S-T2` 的 `reason` 写"拆分第二流程；**项目将预约员解释为同一参与者角色、读者解释为同一群体并复用ID，实际个人身份未证实**，财务组独立"。"已知"二字很重要：复用不是自动去重算法猜的，是分析者基于材料判断的，因此必须可审查。

4. **五类列 × 两行 = 11 个关联**。基线：`proc-book` 行 5 个（`st-patrons`、`actor-booking`、`app-booking`、`p-duplicate`、`g-unique`），`proc-refund` 行 6 个（`st-patrons`、`st-finance`、`actor-booking`、`app-refund-old`、`p-refund`、`g-refund`）。合计 11。**`shared_human_actor_count = 1`**——两个流程复用一个参与者角色，不能据此统计自然人人数，这是矩阵能表达而清单不能表达的信息。

5. **痛点—结果配对**。`p-duplicate → g-unique`、`p-refund → g-refund`，两条 `painpoint_outcome_links`。若某条痛点没有配对结果，矩阵就在记录抱怨。`review.questions` 里"每个痛点有结果吗？"正是这条检查。

6. **关联类型不能升级为 CRUD**。`s-book-computer` 表示预约流程**使用**课程预约系统，不是"创建/读取/更新/删除"。若标 `codes=['C']`，就引入了材料里没有的技术语义（`SCN-004`）。

7. **修订只改一格，保留其余**。`S-R3` 说退款改由统一支付台处理。修改：`s-refund-computer` 的 `old_target=app-refund-old` → `new_target=app-payment`（`new_name=统一支付台`）。`must_keep=["s-book-computer","actor-booking","st-patrons"]`——受理预约侧完全不变，两个流程共用的预约员与读者群体保留。`expected_changed_cells=2`（旧关系消失、新关系出现）。关联总数仍 11。

## 矩阵结构

**五类列的定义与判据**：

| 列类 | 收录什么 | 本案实例 | 常见误收 |
| --- | --- | --- | --- |
| 利益群体 | 关注结果的组织或个人 | `st-patrons`、`st-finance` | 把"系统"收进来 |
| 人参与者 | 执行流程的人 | `actor-booking` | 把岗位名称当人 |
| 计算机参与者 | 支撑流程的系统 | `app-booking`、`app-refund-old` | 把模块当系统 |
| 问题 | 阻碍价值的现状 | `p-duplicate`、`p-refund` | 把解决方案当问题 |
| 目标 | 期望的改善结果 | `g-unique`、`g-refund` | 把指标当目标 |

**"把解决方案当问题"是最常见的误收**：如果写成"缺少统一支付台"，那是方案；问题是"退款漏记"。

**关联的三条纪律**：

| 纪律 | 说明 | 违反后果 |
| --- | --- | --- |
| 关联=参与 | 只表示"该实体参与该流程" | 引入 CRUD 会带来材料没有的技术语义 |
| 同实体同 ID | 跨流程复用同一标识 | 新建 ID 会丢失"同一参与者角色"这一建模事实 |
| 空白≠无关 | 未确认的格子保持空白并标注 | 填"无关联"会让后续无法区分"查过"与"没查" |

**痛点—结果的配对要求**。每个 `problem` 必须至少关联一个 `objective`。没有配对的问题只是抱怨，无法驱动改进。本案两条问题各有配对（`p-duplicate → g-unique`、`p-refund → g-refund`）。

**转型日志的作用**。`transformation_log` 记录"原始子句 → 规范条目"的每一步，含操作类型与理由。它使**归一化过程可复核**——读者能看到"为什么这一句被拆成六条"，而不是只看到最后的结果。

## 修改演练

改动一处输入：`S-R3` 声明退款改由统一支付台处理、原退款队列退役。

- `associations` 中 `s-refund-computer`：`target` 从 `app-refund-old` 改为 `app-payment`，名称改为"统一支付台"。
- `categories.computer_actor`：移除 `app-refund-old`，加入 `app-payment`。
- 关联总数**仍为 11**（一进一出）。
- `s-book-computer`、`actor-booking`、`st-patrons` **必须保留**（`must_keep`），因为它们不涉及退款系统变更。
- 影响视图：业务场景关联矩阵的 `proc-refund` 行计算机参与者列；`proc-book` 行不变。

**最危险的错误**：因为"退款队列退役"就把 `proc-refund` 整行删掉。退役的是一个**系统**，不是整个**流程**——退款流程仍存在，只是换了执行系统。`expected.old_refund_link_absent=true` 与 `new_payment_link_present=true` 必须**同时**成立，只满足前者意味着流程被误删。

反向演练：若 `S-R3` 说"取消退款流程并入受理预约流程"，则应是**行合并**：两个流程并为一个，`proc-refund` 行消失，其关联并入 `proc-book` 行，`actor-booking` 与 `st-patrons` 仍复用。此时关联数应减少（重复项合并），与"换系统"情形（数量不变）不同。

## 反例与输入不足

- **错误做法**：删掉 `p-refund` 的结果配对，矩阵只剩痛点。痛点必须有对应结果。预期 `SCN-003`。
- **错误做法**：给 `s-book-computer` 标 `codes=['C']`，材料里没有任何"创建"语义。关联不是 CRUD。预期 `SCN-004`。
- **错误做法**：从原始记录清单里删掉 `S-R2`，但规范条目仍引用它。来源链断裂。预期 `SCN-001`。
- **错误做法**：把 `actor-booking` 在 `proc-refund` 行新建为 `actor-booking-2`。同一角色被拆成两个对象；不声称两条叙述必为同一自然人，跨流程共享信息丢失。预期 `duplicate-id`。
- **错误做法**：把 `app-refund-old` 与 `app-booking` 都用"系统"合并为一个实体。两个不同系统不能因同属一类而合并。预期 `relation-endpoint-type`。
- **错误做法**：把技术候选需求（如"改用事件驱动"）直接写成矩阵中的已批准目标。候选不是批准。预期 `approval-without-evidence`。

**输入不足**：`S-R1`、`S-R2` 未说明两个流程的**先后顺序**与**触发条件**，因此矩阵不表达时序与控制流——这是方法的边界，不是遗漏。`S-R2` 未给"次一工作日"的具体计时起点（取消时刻还是确认时刻），`g-refund` 的表述保持原文而不细化。空白格（如 `proc-book` 行是否有财务组参与）材料未提，标为未确认而非"无关联"。
