# 微服务就绪：没人管退役就是没就绪

所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充 TOGAF 规定。案例完整演练不等于独立业务评审通过。

方法：`msa-readiness-evidence-method`。来源方法：G21I。
入口：[msa-readiness-evidence-method](../analysis-methods/msa-readiness-evidence-method.md)。
素材：原料（历史材料已清理）。

## 决策与原始业务资料

把预约判断拆成服务，组织与生命周期条件是否具备？

| 证据 ID | 原始材料 |
|---|---|
| `msa-r1` | 预约团队负责开发、部署与值班，**无人负责退役**。 |
| `msa-r2` | 两开发一轮值运维，未完成恢复演练。 |
| `msa-r3` | 团队可自选框架，但须满足生产最小权限与可追溯变更。 |
| `msa-r4` | 有自动构建与测试；发布前复核与变化监控**仍是手工**。 |
| `msa-r5` | 先在一城试点，复盘组织影响后再扩第二城。 |
| `msa-r6` | 没有 OSIMM 模型或评估结果，不能给总分。 |

## 来源规则与项目规则

1. 来源方法（G21I）：微服务就绪不仅是技术条件，还包括组织责任、生命周期与运维能力。
2. 来源方法：服务的完整生命周期含开发、部署、运行、**退役**；缺退役责任即为不完整。
3. 项目规则：**不给总分**（`msa-r6`）——无 OSIMM 模型时不合成评级。
4. 项目规则：手工环节不阻止试点（`msa-r5` 的一城试点），但必须被识别为扩展前的待改进项。

## 转换与推理

1. **逐项判定，条件不合并**。八项就绪条件各自作答，答案取"是 / 部分 / 否"，一项为"否"不因其他项为"是"而被平均掉。
2. **区分"职责有人"与"职责内容完整"**。`msa-r1` 说明开发、部署与值班均有归属，却**明确无人负责退役**——同一责任主体在三项上成立、在第四项上不成立，须分项判定。
3. **"有机制"与"机制已验证"分开**。`msa-r4` 有自动构建与测试（可判"是"），但发布前复核与变化监控仍手工，只能判"部分"；`msa-r2` 有轮值运维（可判"是"），但恢复演练未完成，运行能力**未验证**。
4. **要求明确 ≠ 已满足**。`msa-r3` 只规定"须满足生产最小权限与可追溯变更"，这是约束的存在，不等于已达成；故记为"部分（要求已明确、未验证）"而非"是（已满足）"。
5. **不合成总分**。因 `msa-r6` 明确没有 OSIMM 模型或评估结果，八项结果不折算为"就绪度百分比"，也不设通过线。
6. **扩展范围受试点约束**。`msa-r5` 限定先一城试点、复盘后再扩，因此上述判定只对该城成立，不外推到第二城。

7. **八项条件的判定口径必须逐项固定**，否则同一份材料会得出不同结论：

| 条件 | 判"是"的口径 | 判"否"的口径 | 判"部分"的口径 |
| --- | --- | --- | --- |
| 开发责任 | 有明确团队且承担 | 无人负责 | 有人但不明确 |
| 部署责任 | 同上 | 同上 | 同上 |
| 运行值班 | 有排班且可执行 | 无值班 | 排班未定 |
| 退役责任 | 有指定责任方 | **无人负责** | 责任待定 |
| 恢复演练 | 已演练并可查证 | **未完成** | 演练计划中 |
| 最小权限与可追溯变更 | 要求已满足 | 无要求 | **要求已明确未验证** |
| 自动构建测试 | 已存在并运行 | 无 | 部分手工 |
| 发布复核与变化监控 | 全自动或人工但有记录 | 无 | 手工已知，但执行记录未提供；不推定实际无记录 |

   本案的"部分"有两处：要求未验证，以及发布复核/监控虽有手工环节但记录未提供；手工本身不等于无效。

8. **退役责任为什么是硬缺口，而手工复核不是**。`msa-r1` 无人负责退役；`msa-r4` 发布复核仍手工。两者都可改进，但性质不同：
   - **退役责任缺失**：服务生命周期不完整，**无法处理"不用了怎么办"**
   - **手工复核**：能力已有，只是效率低

   前者是结构缺陷，后者是执行机制差异，不能仅由手工推断成熟度低。因此 `MSA-R2` 阻断扩展，`MSA-R4` 只约束扩展节奏。

9. **"要求已明确"不是"已满足"**。`msa-r3` 说团队须满足最小权限与可追溯变更。这是**约束的存在**，不是**达成的事实**。因此记"部分（要求已明确、未验证）"——括号里的限定语是结论的一部分，去掉它就变成了错误结论。

10. **试点范围限制结论的适用范围**。`msa-r5` 说先一城试点、复盘后再扩。因此上述八项判定：
    - 对第一城成立
    - **对第二城尚未验证，不能说条件已被证实不成立**（尚未评估）
    
    把一城的结论写进"全部城市的就绪度"，是最容易犯的范围错误。

| 条件 | 判定 | 依据 |
| --- | --- | --- |
| 开发责任 | 是 | 预约团队（`msa-r1`） |
| 部署责任 | 是 | 同上 |
| 运行值班 | 是 | 一轮值运维（`msa-r2`） |
| **退役责任** | **否** | 无人负责（`msa-r1`） |
| 恢复演练 | 否 | 未完成（`msa-r2`） |
| 最小权限与可追溯变更 | 部分（要求已明确、未验证） | `msa-r3` |
| 自动构建测试 | 是 | `msa-r4` |
| 发布复核与变化监控 | 部分 | 手工（`msa-r4`） |

**不合成总分**：因 `msa-r6`，上述判定保持逐项，不折算"就绪度 75%"。

|---|---|---|---|
| `MSA-R1` | 8 项条件中 4 是 / 2 部分 / 2 否 | `msa-r1`–`msa-r4` | 已登记 |

| `MSA-R4` | 试点范围限定一城，扩展需复盘 | `msa-r5` | 约束 |
| `MSA-RGAP-1` | 退役责任未指派 | `msa-r1` | 未决 |

本方法采用定性判断与追溯演练，没有适用的统一计算器。**方法输出的边界**：给出与 `msa-readiness-evidence-method` 相关的判定与缺口清单，**不给出**达标结论、覆盖率或成熟度评分——材料未提供相应度量依据，任何比率都会失真。

## 修改演练

**情景一：指派退役责任人**。`MSA-RGAP-1` 关闭，八项变为 5 是 / 2 部分 / 1 否，`MSA-R2` 的阻断解除。**但退役责任人的具体职责（何时启动、如何通知消费者）仍需定义**——有人不等于有流程。

**情景二：完成一次恢复演练并留记录**。`MSA-RGAP-2` 关闭，运行值班从"有排班"升级为"已验证"。此时 `MSA-R3` 的状态从"缺口"转为"已核"。

**情景三：发布复核自动化并有执行证据**。仅该项可从部分转是。若独立于情景一、二，分布为5是/1部分/2否；即使累计补任命及演练后，最小权限仍待验证，不能称八项全绿。**但 `msa-r6` 仍禁止合成总分**——八项全绿不等于"就绪度 100%"。

**情景四：扩展到第二城**。需重新评估八项条件，**不能沿用第一城的结论**。第二城的团队、值班、演练情况可能完全不同。

**影响范围**：情景一、二、三分别改变单项判定与阻断状态；情景四重置评估范围。四种情形下"不合成总分"与"试点范围限制结论"两条规则不变。

## 反例与输入不足

- **错误做法**：8 项中 6 项满足即报"就绪度 75%，可以通过"。违反 `msa-r6` 不给总分。预期 `unsourced-maturity-rating`。
- **错误做法**：认为"团队负责服务"已覆盖退役。生命周期明确包含退役。预期 `missing-evidence`。
- **错误做法**：有自动测试即判"发布监控完备"。手工环节仍在。预期 `missing-evidence`。
- **错误做法**：把"要求已明确"记为"已满足"。括号里的限定语是结论的一部分。预期 `missing-evidence`。
- **错误做法**：用第一城的判定结果支持第二城扩展决定。试点范围限制结论适用域。预期 `missing-evidence`。
- **错误做法**：手工发布复核与退役责任缺失当作同等程度的问题。手工与自动的差别不是本案可评定的成熟度等级；需看执行效果，后者是结构缺陷。预期 `core-vocabulary-override`。
- **错误做法**：指派退役责任人后即认为退役流程就绪。有人不等于有流程。预期 `missing-evidence`。

**输入不足**：`msa-r1`（退役责任）与 `msa-r2`（恢复演练）两项缺失，扩展前无法关闭。`msa-r4` 未给手工复核的具体环节与频次，无法判断其风险水平。材料未给第二城的团队与运维安排，故不评估扩展条件。
