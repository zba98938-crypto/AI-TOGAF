# 过渡架构可运营性判定：65% 完成度不能证明这个状态能跑

虚构制造企业分两期替换旧 ERP。过渡一（T1）的状态是：旧 ERP 财务模块继续运行，新平台接管库存与采购，两系统每晚批量对账。原始材料只给了一句"T1 完成度约 65%"。本案例演练五项运营条件逐项核查，以及为什么进度百分比与可运营性是两件完全不同的事。

所有业务材料、组织安排、对账规则与回退条款均为虚构教学材料。指南只提供方法依据，项目规则不冒充 TOGAF 规定。

方法：`transition-operability-check`。来源方法：G248 §2、G186 §9。
入口：[transition-operability-check](../analysis-methods/transition-operability-check.md)。

## 决策与原始业务资料

要回答：**T1 这个中间状态能不能真的运行？如果不能，缺的是哪一项？**

| 证据 ID | 原始材料 |
|---|---|
| `TRN-1` | T1 期设**双系统运维组**，组长**已任命**。 |
| `TRN-2` | 旧 ERP **财务只读**；新平台**库存与采购可写**；**边界清晰**。 |
| `TRN-3` | 每晚 **23:00 批量对账**，差异**次日 10:00 前处置**。 |
| `TRN-4` | 新平台**沿用旧审批流**，访问控制**按岗位映射**。 |
| `TRN-5` | 回退：只说"**必要时回退**"，**无触发条件、无责任人、无验证方法**。 |
| `TRN-6` | 原始材料只给"T1 完成度约 **65%**"。 |

## 来源规则与项目规则

1. **来源方法（G248 §2、G186 §9）**：判定的是"这个中间状态能不能真的运行"，**不是"项目完成了多少"**。
2. **项目实施规则（来源核验未完成）**：本案细化的五项运营条件为**人员、系统、数据、控制、回退**，逐项给出答案。
3. **项目规则**：**按本案保守工程闸门，任一必需项缺失即不放行，不能由此证明技术上绝不可能运行**，并输出缺失项 ID。
4. **项目规则**：五项齐备时，还须检查回退方案是否有**可验证的触发条件**。
5. **项目规则**：进度百分比**不是可运营性证据**（`TRN-6` 只是完成度，未说明任何运营条件）。
6. **项目规则**：回退的"可验证"须含三要素——**触发条件、责任人、验证方法**；缺一即不可验证。

## 转换与推理

1. **逐项检查五项，只记有答案的**：
   - **人员**：有。双系统运维组，组长已任命（`TRN-1`）。
   - **系统**：有。旧 ERP 财务只读、新平台库存与采购可写，边界清晰（`TRN-2`）。
   - **数据**：有。每晚 23:00 批量对账，差异次日 10:00 前处置（`TRN-3`）。
   - **控制**：有。沿用旧审批流，访问控制按岗位映射（`TRN-4`）。
   - **回退**：**缺**。只说"必要时回退"，三要素全无（`TRN-5`）。

2. **判定：不可运营**。五项缺一 ⇒ `operable=false`，`missing_conditions=[{condition: "回退", gap_id: "GAP-T1-ROLLBACK"}]`。这是本项目保守清单闸门的结论，不是对真实运行结果的事实断言。

3. **为什么回退是五项里最不能省的一项**。前四项保证"能跑"，回退保证"跑错了能停"。一个能跑但不能停的过渡状态，在出问题时没有出口——目标架构同样需要失败处置；不是只有过渡架构才需要回退或恢复。

4. **"65%" 不进入判定**。`notes` 写"「完成度 65%」不是可运营性证据"。**65% 完成度既不能证明可运营，也不能证明不可运营**——它是另一个维度（进度）的度量，与本方法要回答的问题无关。若把它折算成"基本可用"，就是用进度代替能力。

5. **补齐回退后的复判**：三项要素齐备后，工程清单可记 `operable=true`、`rollback_verifiable=true`，但仅表示规则可检查，不证明真实运营安全或回退有效。
   - 触发（新增候选项目规则）：差错订单数/同窗对账订单数连续3日 > 0.5%，分母为0则未知，不能当0差异
   - 责任人：双系统运维组长
   - 验证：回退后核对 2 笔历史订单与库存

6. **注意触发条件的形状**。"连续 3 日超过 0.5%"包含三个可判定的成分：连续性（连续）、阈值（0.5%）、时长（3 日）。若只写"差异较大时回退"，则不可验证——"较大"是谁的判断？**可验证的触发条件必须能被第三方按同一标准复现判定。**

五项条件的"是否齐备"为可复核的检查（每项有/无），**但"触发条件是否足够严格""验证方法是否有效"属于判断**，不由计算得出。本案例**不把完成度折算为可运营概率**，不给"可运营度 80%"这类输出。

本方法采用定性判断与追溯演练，没有适用的统一计算器。**方法输出的边界**：给出与 `transition-operability-check` 相关的判定与缺口清单，**不给出**达标结论、覆盖率或成熟度评分——材料未提供相应度量依据，任何比率都会失真。

## 修改演练

改动一处输入：补入回退条款。触发"差错订单数/同窗对账订单数连续3日 > 0.5%（空分母为未知）"，责任人双系统运维组长，验证"回退后核对 2 笔历史订单与库存"。

- `operable`：工程清单闸门 false→true，非业务已接受或运行成效已证实。
- `missing_conditions`：`[GAP-T1-ROLLBACK]` → `[]`。
- `rollback_verifiable`：`false` → **`true`**（三要素齐备）。
- 影响：`transition-architecture-model` 的 `operating_conditions` 字段、迁移路线图中 T1 的**发布门槛**、切换演练的范围（演练须覆盖回退路径）。
- **仍不能做的事**：因 `operable=true` 就宣布 T1 已发布。可运营是**必要条件**，发布还须授权与演练证据。

反向演练：若补齐了触发条件与责任人，但**验证方法写"回退后观察一段时间"**，则 `rollback_verifiable` 仍为 `false`——"一段时间"不可判定。此时 `operable` 应按方法第 4 步判为**不可运营**（回退不可验证）。**三要素缺一不可**，这是本方法最容易放水的地方。

第三种演练：若把 `TRN-3` 的对账改为"每周对账"，数据条件仍"有答案"，但一致性保障强度显著下降。本方法只判"有没有答案"，不判"答案够不够好"——**后者需要业务与审计判断，超出本方法范围**，应在评审记录中列为待业务确认项。

## 反例与输入不足

- **错误做法**：过渡架构仅给"完成 70%"，未说明人员、系统、数据、控制与回退。进度百分比不能证明中间状态可运行。预期 `transition-operability-gap`。正确处置：返回 `operable=false` 并列出五项缺失，**不按百分比折算为"基本可用"**。
- **错误做法**：回退只写"必要时回退"，仍判 `operable=true`。回退三要素不全。预期 `transition-operability-gap`。
- **错误做法**：把 `rollback_verifiable` 设为 `true` 但触发条件为"差异较大时"。不可复现判定。预期 `measurement-basis-gap`。
- **错误做法**：五项中"控制"一项写"沿用现有控制"，未说明是哪些控制。空泛回答不算答案。预期 `missing-evidence`。
- **错误做法**：因四项齐备、仅回退缺失，就判"基本可运营（4/5）"。五项是**与**关系，不是计分。预期 `transition-operability-gap`。
- **错误做法**：把 T1 与 T2 合并判定，用一个"整体可运营"结论。每个过渡状态须独立判定。预期 `measurement-basis-gap`。

**输入不足**：只读旧财务如何新增凭证未说明，补回退不自动关闭此业务缺口。材料未给过渡期时长与服务水平要求（方法列为可选输入），因此本案例不判断对账窗口（23:00 至次日 10:00）是否满足业务时效。`TRN-2` 未说明旧 ERP 财务只读期间**如何新增财务凭证**，这是系统边界的潜在缺口，列为待确认项。

## 评审记录

- 核对五项条件逐项给出"有/无"结论，无一项含糊。
- 核对缺失项以 `gap_id` 形式输出，可被后续跟踪。
- 核对 `operable=false` 由"任一项缺失"规则直接推出。
- 核对回退三要素（触发/责任人/验证）逐项检查，未因"写了回退"就放行。
- 核对"完成度 65%"被明确排除在判定依据外。
- 核对补齐后 `operable=true` 与 `rollback_verifiable=true` 分别判定，未混为一谈。
- 核对 `operable=true` 未被升级为"已发布/已批准"。
- 核对未出现"4/5 基本可运营"这类计分式结论。
- 核对方法边界（只判有/无，不判好坏）写入输出。
