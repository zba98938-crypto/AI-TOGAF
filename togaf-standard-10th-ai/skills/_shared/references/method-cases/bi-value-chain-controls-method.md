# BI 数据价值链：五层是设计，不是标准

## 决策与原始业务资料

从库存应用的一张表到调度主管看到的"缺件候选"，中间每一层各自负责什么、出错时谁来定位？

| 证据 ID | 原始材料 |
|---|---|
| `bic-1` | U1 读取库存应用。每批原始库存保存不变，不做就地修改。 |
| `bic-2` | 技术层 TECH-1 只统一日期类型；异常记录被隔离，不丢弃。 |
| `bic-3` | 业务层 BUS-1 以"需求量大于可用量"识别候选缺件。 |
| `bic-4` | 语义层 SEM-1 解释"时点"与"站点"的口径，避免同一字段两种含义。 |
| `bic-5` | 调度人复核后才调拨；看板只做提示，不自动下单。 |
| `bic-6` | 库存源及时性未测；看板显示观测时间，数据过期转人工。 |
| `bic-7` | 每层保留批次、规则、用途血缘与负责人；客户联系方式不进入链路。 |

## 来源规则与项目规则

1. 来源方法（G238）：数据从源到消费应可解释为价值链，每层有明确变换与责任。
2. 来源方法：血缘需记录到**规则**与**批次**，不只是表名到表名。
3. 项目规则：五层（原始／技术／业务／语义／消费）是**本项目设计**，不是所有项目必须相同的层数。
4. 项目规则：`bic-1` 的原始批不可变是硬约束，任何变换都必须生成新层。
5. 项目规则：`bic-6` 的时效未测不阻碍出提示，但必须显示观测时间；过期不静默。

## 转换与推理

1. **逐层定义变换**：

| 层 | 输入 | 变换 | 输出 | 负责人 |
|---|---|---|---|---|
| 原始 | 库存应用导出 | 无（只落盘） | 原始批次 | 平台 |
| 技术 TECH-1 | 原始批次 | 统一日期类型，异常隔离 | 技术批次 | 数据工程 |
| 业务 BUS-1 | 技术批次 | 需求量 > 可用量 → 候选 | 候选清单 | 业务分析 |
| 语义 SEM-1 | 候选清单 | 解释时点／站点口径 | 可读候选 | 业务分析 |
| 消费 | 可读候选 | 人复核后调拨 | 决策 | 调度主管 |

2. **血缘记录**：每层输出的每条记录携带 `batch_id`、`rule_id`、`purpose`、`owner`。缺任一项即无法定位问题来源。
3. **异常处理**：TECH-1 隔离异常而非丢弃，因此异常数量本身可被监控；丢弃会让问题消失得无影无踪。
4. **时效表达**：因 `bic-6` 未测及时性，看板必须显示"观测时刻"，并按项目规则在超期时转人工。不得用"实时"描述未测量的能力。
5. **隐私边界**：链路各层字段清单校验不含联系方式（`bic-7`）。

6. **五层是项目设计，不是通用标准**。项目规则明说五层（原始／技术／业务／语义／消费）是**本项目设计**。层数可多可少，关键是每层有：
   - 明确的输入与输出
   - 可命名的变换规则
   - 单一负责人

   若某项目只有三层，只要能回答"这一层做了什么、谁负责"，同样成立。**不能因为指南没规定五层就说五层错，也不能说五层是唯一解。**

7. **原始层不可变，是全部可追溯性的地基**。`bic-1` 要求每批原始库存保存不变、不做就地修改。推论：
   - 任何清洗、转换都必须**生成新层**，不能改原件
   - 出错时可回到原始批次复现
   
   若允许就地修改，一旦下游结论异常，将无法判断是数据本身有问题还是变换有问题。

8. **异常隔离 ≠ 异常丢弃**。`bic-2` 说异常记录被隔离而不丢弃。区别在于：
   - 隔离：异常**可计数、可查看、可回补**
   - 丢弃：问题消失，且无人知道消失过

   隔离让"异常率"成为可监控指标；丢弃会让数据质量问题静默累积。

9. **语义层存在的理由**。`bic-4` 说 SEM-1 解释"时点"与"站点"的口径。若没有这一层，同一字段在不同报表可能含义不同——**技术层只能统一类型，不能统一含义**。这是语义层不可省略的原因。

10. **看板只提示，不自动下单**。`bic-5` 明确调度人复核后才调拨。这条把系统定位为**决策辅助**而非执行者。若看板直接下单，出错时责任无法界定——是规则错了还是数据错了？

11. **时效未测的表达方式**。`bic-6` 说源及时性未测。可接受做法：
    - 显示"观测时刻"，让使用者自行判断新鲜度
    - 超期转人工
    
    不可接受：用"实时"描述未测能力，或不显示时间让使用者误以为是最新值。

本方法采用定性判断与追溯演练，没有适用的统一计算器。**方法输出的边界**：给出逐层变换、责任与血缘记录要求，**不给出**数据质量评分、时效达标结论或异常率阈值——源及时性未测、异常量级未给，任何比率都缺依据。

## 修改演练

**情景一：源数据及时性实测为"每 4 小时"**。`bic-6` 的未知被填补，只能说明观测到约 4 小时更新频率，不能直接保证端到端延迟 ≤ 4 小时；还须测源记录时刻、导出/处理耗时与失败间隔。但**仍不能标"实时"**——4 小时不是实时。此时可在业务上评估 4 小时是否满足调度需求。

**情景二：某层负责人空缺**。该层的输出**不可信以为已交付**——无人负责意味着出问题无人定位。此时应登记缺口并阻断该层下游的正式使用，而非"先跑起来再说"。

**情景三：业务规则变更（如"需求量 > 可用量"改为含在途库存）**。BUS-1 的 `rule_id` 必须更新，且下游所有依赖该规则的历史结论需标注适用版本。**不能只改规则不留痕**——否则历史报表无法解释。

**情景四：隐私审查要求去掉某字段**。该字段若在链路中间层被使用（如站点编码用于聚合），删除会影响下游。需先评估用途，**不能各层各删一遍**。

**影响范围**：情景一填补时效数据；情景二阻断某层；情景三改变规则版本与历史适用性；情景四影响跨层字段用途。四种情形下"原始层不可变"的硬约束不变。

## 反例与输入不足

- **错误做法**：在原始层就地修改异常记录以"清洗数据"。原始批必须不可变。预期 `missing-evidence`。
- **错误做法**：技术层把异常记录直接丢弃。丢弃使问题静默消失，无法计数。预期 `missing-evidence`。
- **错误做法**：只在技术层统一了日期类型，就认为"时点"含义已统一。类型统一不等于语义统一。预期 `core-vocabulary-override`。
- **错误做法**：让看板在识别到缺件时自动下单调拨。`bic-5` 要求人工复核。预期 `approval-without-evidence`。
- **错误做法**：在看板上标注"实时库存"。`bic-6` 明说及时性未测。预期 `measurement-evidence-gap`。
- **错误做法**：链路各层都未记录 `rule_id`，只记表名到表名。血缘需记到规则，否则无法定位变换来源。预期 `missing-evidence`。
- **错误做法**：声称"五层是 G238 规定的标准分层"。五层是本项目设计。预期 `core-vocabulary-override`。

**输入不足**：`bic-6` 未给库存源的实际更新频率，因此本案例不判断 4 小时类延迟是否可接受。`bic-1`/`bic-2` 未给异常记录的数量级，故不评价异常率是否正常。材料未给 `bic-7` 的具体字段清单，隐私校验只能落在"字段清单不含客户联系方式"这一要求上。

## 评审记录

- 核对五层逐层有输入、变换、输出与负责人，无空层。
- 核对每层记录 `batch_id`、`rule_id`、`purpose`、`owner` 四项，缺任一项即标为无法定位。
- 核对原始层不可变被表述为硬约束，任何变换生成新层。
- 核对异常为隔离而非丢弃，且异常数量可监控。
- 核对技术层只统一类型，语义口径由语义层承担，两层职责未混。
- 核对看板为提示而非自动执行，人工复核环节保留。
- 核对时效未测时显示观测时刻并按规则转人工，未标"实时"。
- 核对五层被标注为项目设计，未声称为通用标准。
- 核对隐私约束落在字段清单层校验。
- 核对四项修改情景分别说明影响范围与不变项。
