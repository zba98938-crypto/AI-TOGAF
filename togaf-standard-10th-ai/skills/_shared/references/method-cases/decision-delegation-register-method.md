# 决策授权与可逆性登记：可逆才敢下放，不可逆必须共决

虚构跨馆借阅试点里有三件事等着定"谁说了算"：试点 API 的内部命名、读者关联证据的保留期限、脱敏日志的展示样式。本案例演练如何用**可逆性**而不是"重要性"来决定授权层级，以及为什么"拟采用"必须与"已批准"分开记。

所有业务材料、人物、授权与对话均为虚构教学材料（`BR-01`–`BR-20`）；Management 3.0 的七级名称仅为 G210 §5.4 转引的外部参考词汇，本项目并未据此默认授权任何事项。指南只提供方法依据，项目规则不冒充 TOGAF 规定。

方法：`decision-delegation-register-method`。来源方法：G210 §5.4。
入口：[decision-delegation-register-method](../analysis-methods/decision-delegation-register-method.md)。
素材：原料（历史材料已清理）、模型（历史材料已清理）。

## 决策与原始业务资料

要回答：**这三件事分别由谁定？依据是什么？如果不确定会怎样？**

| 证据 ID | 原始材料 |
|---|---|
| `BR-09` | 对试点 API 的内部命名，项目提出采用 **consult**：架构负责人先听取开发团队意见，再由架构负责人做出记录化决策。可逆性依据是**当前无外部消费者**，保留旧别名并能恢复路由；**一旦有外部消费者即重新评估**。此为拟定授权安排，**尚未获正式批准**。 |
| `BR-10` | **删除读者关联的历史证据无法以普通回滚恢复。** 因此保留期限变更应由数据治理、借阅业务与安全负责人共同达成一致（**agree**）；在依据和共同决策完成前**不执行**。其他例中的 tell/sell/advise/inquire/delegate 仅为 G210 引用的外部 Management 3.0 名称，本项目并未默认授权所有事项。 |
| `BR-11` | 试点日志展示样式由开发团队在**既定脱敏与访问护栏内**提出 **delegate**；更改不触及保留期限或审计字段，**能切回旧模板**。没有正式授权证明，因此仍为 **proposed**。 |
| `BR-19` | **修改试验**：API 命名现在已有一名外部消费者，旧别名不能完全恢复其缓存状态；把 `BR-09` 的可逆性改为 **unknown**，原自治安排必须保持 **proposed** 并补更广利益相关者评审，**不能把未知当可逆**。 |

## 来源规则与项目规则

1. **来源方法（G210 §5.4）**：授权层级是一组外部框架词汇（tell/sell/consult/agree/advise/inquire/delegate），其含义来自该框架，不是 TOGAF 规定的默认授权矩阵。
2. **来源方法**：授权决策必须记录决策范围、决策者、参与者、护栏与**复核触发条件**；范围之外的事项不受该授权影响。
3. **来源方法**：可逆性可作为授权判断的重要依据；本案不可逆事项要求 agree 是 BR-10 的项目规则，不是 TOGAF 通用授权上限。
4. **项目规则**：可逆性必须附**具体依据**（`BR-09` 的"无外部消费者"、`BR-11` 的"能切回旧模板"），不能只写"可逆"两个字。
5. **项目规则**：`auth_status` 只有 `proposed` 与 `approved` 两态；**没有正式授权证明时一律 `proposed`**（`BR-09`、`BR-11` 均如此）。
6. **项目规则**：不可逆且无回滚方案时，`rollback_plan` 写 `not-available`，且**决策完成前不得执行**（`BR-10`）。

## 转换与推理

1. **先判可逆性，再判层级**。这个顺序不能颠倒：如果先想"这事谁管"，就会退化成按职级分配。`BR-09` 的可逆性来自"保留旧别名 + 可恢复路由"这一条**可验证的技术事实**；`BR-10` 的不可逆性来自"删除历史证据无法普通回滚"这一条**可验证的操作事实**。

2. **DEC-01 试点 API 内部命名**：范围限"仅无外部消费者的试点 API 内部命名"——范围写窄，是授权能够成立的前提。层级 `consult`（听取开发团队意见、架构负责人决定）；可逆性 `reversible`，依据 `BR-09` 原文；护栏两条（不改契约业务语义、不涉及读者证据删除）；`auth_status=proposed`；复核触发"新增外部消费者或无法恢复路由"。

3. **DEC-02 读者关联证据保留期限**：不可逆。层级 `agree`，参与者三人（数据治理、借阅业务、安全）。`rollback_plan` 写 `not-available；决策完成前不得执行删除`。这一条是本案例最关键的推理：**不可逆 + 无回滚 ⇒ 不能由单一角色决定，也不能在依据未齐时先执行后补**。

4. **DEC-03 脱敏日志展示样式**：可逆（能切回旧模板），层级 `delegate`，但护栏必须写全"不改保留期限、不改审计字段、保持访问与脱敏规则"。护栏的作用是把委派范围**围起来**——超出护栏即触发复核，而不是"委派了就都可以改"。

5. **三者的权责安排来自BR-09至BR-11的项目提议，可逆性是其中一项依据**：DEC-03 看起来最"技术琐碎"，却给了最深的委派，因为它可逆且护栏明确；DEC-02 看起来只是一项参数调整，却要求三人共决，因为删掉就回不来。

6. **框架来源必须标注**：`framework_origin` 写"Management 3.0，G210 §5.4 转引；具体权责为本例项目规则"。这样读者不会误以为这七个词是 TOGAF 规定的授权级别。

7. **修改后的重判**：`BR-19` 加入外部消费者后，`DEC-01.reversibility` 从 `reversible` 改为 `unknown`（不是 `irreversible`——材料只说"不能完全恢复缓存状态"，没有说完全不可逆）。`rollback_plan`、`reversibility_evidence`、`decision_result` 同步改写，`participants` 扩为更广群体，`auth_status` **保持 proposed**。

## 判定细则

**可逆性的三档口径**（本案例的项目规则）：

| 档位 | 判据 | 本案实例 |
| --- | --- | --- |
| `reversible` | 有明确回退路径且已验证可执行 | `DEC-01`（保留旧别名、可恢复路由）、`DEC-03`（可切回旧模板） |
| `irreversible` | 已证明无法回退 | `DEC-02`（删除历史证据无法普通回滚） |
| `unknown` | 回退能力未证实，或证明不完整 | `BR-19` 后的 `DEC-01`（不能**完全**恢复缓存状态） |

**"不能完全恢复"属于 `unknown`，不是 `irreversible`。** 这一条是本案例最容易出错的地方：材料只说"旧别名不能完全恢复其缓存状态"，没说"完全不能恢复"。把部分恢复能力缺失读成完全不可逆，会让授权层级不必要地升高。

**授权层级与可逆性的对应关系**（项目规则，非 TOGAF 规定）：

| 可逆性 | 可采用的层级上限 | 理由 |
| --- | --- | --- |
| `reversible` | `delegate`（有护栏时） | 错了能退，团队可自主 |
| `unknown` | `consult` 或 `agree` | 回退不确定，需多方知情 |
| `irreversible` | `agree`（多人共决） | 错了不能退，必须共同承担 |

这张表是**上限**，不是要求。`DEC-02` 选 `agree` 而非更强的形式，因为材料明确"共同达成一致"。

**三种状态不是递进关系**。`proposed → approved` 是状态迁移，但 `unknown` 不是"可逆与不可逆之间的中间态"——它是**信息不足**的独立标记。

## 修改演练

改动一处输入：`BR-19` 声明 API 命名已有一名外部消费者，旧别名无法完全恢复其缓存状态。

- `DEC-01.reversibility`：`reversible` → `unknown`。**关键点：不能写 `irreversible`**。材料只证明"不能完全恢复"，未证明"完全不能恢复"；把未知写成不可逆，与把未知当可逆，是同一类越界。
- `DEC-01.reversibility_evidence`：改为"已有一名外部消费者；旧别名不能完全恢复其缓存状态（`BR-19`）"。
- `DEC-01.rollback_plan`：从"恢复旧别名与路由"改为需说明缓存状态无法回退的部分。
- `DEC-01.participants`：从 `["架构负责人","开发团队"]` 扩为含外部消费者代表。
- `DEC-01.authorization_status`：**仍为 `proposed`**。这是最容易被改错的一处——有了新证据不等于有了批准。
- 影响视图：仅 `v-decision-delegation-register-default`。`DEC-02`、`DEC-03` 不变。

反向演练：若 `BR-11` 补充"展示样式变更需同步修改审计字段"，则 DEC-03 的原委派范围被突破，需暂停超范围变更并重评。改审计字段不必然等于删除历史证据；只有确认触及 BR-10 的不可逆删除范围时，才按该项目规则提请 agree。这说明护栏不是装饰：护栏被突破时，授权层级必须连带重判。

## 反例与输入不足

- **错误做法**：DEC-01 写"可逆，因为可以改回来"，不给任何技术依据。可逆性必须有证据。预期 `reversibility-without-evidence`。
- **错误做法**：DEC-02 因"效率考虑"标记为 `approved`，但没有任何批准记录。预期 `fictional-approval`。
- **错误做法**：把 DEC-02 的层级改为 `delegate`，理由是"数据治理负责人足够专业"。不可逆决策不得按可逆决策下放。预期 `approval-without-evidence`。
- **错误做法**：把 `BR-19` 的 `unknown` 直接写成 `reversible`，理由是"目前没出问题"。未知不得当可逆。预期 `reversibility-without-evidence`。
- **错误做法**：DEC-03 的 `decision_scope` 写成"日志相关全部变更"，把保留期限也括进去。授权范围必须窄于护栏。预期 `core-vocabulary-override`。
- **错误做法**：登记表只写 `delegation_level` 与 `authority`，省略 `guardrails` 与 `review_trigger`。没有复核触发的委派等于永久授权。预期 `unrepresented-attribute`。

**输入不足**：三项决策都没有正式授权文件（`DDR-GAP-1`）。因此本案例**不能**给出"已获授权"的结论，也不能反推"既然没人反对就是默许"。`BR-10` 明确"在依据和共同决策完成前不执行"——这一条使 DEC-02 处于执行阻断态，而不是"待办中"。
