# 按变革画像核查：社区预约服务上线前的 59 条检查

虚构社区服务中心要让居民能在线上预约、同时保留线下窗口。项目初拟按 **Rapid** 画像快速试点，但运营方尚未提交过渡 A 的部署演练结果。本案例演练如何用 G248 的变革画像检查表逐项核查：哪些项建议纳入、哪些项必须回答、以及为什么"未回答"既不是通过也不是不适用。

所有业务材料、访谈记录、部署状态与授权均为虚构教学材料（`INT-01` 及其衍生输入）；**源表含 59 条检查，"Y"表示建议纳入，空白既不是通过也不是不适用**。指南只提供方法依据，项目规则不冒充 TOGAF 规定。

方法：`change-profile-governance-review`。来源方法：G248 §3、§9 表 9-1、§11 表 11-1。
入口：[change-profile-governance-review](../analysis-methods/change-profile-governance-review.md)。
素材：原始输入（历史材料已清理）、实际结果（历史材料已清理）、[源表](../source-tables/change-profile-checks.json)。

## 决策与原始业务资料

要回答：**这次变革按哪个画像推进？该画像建议的检查项里，哪些已答、哪些没答、哪些必须等演练？**

| 证据 ID | 原始材料 |
|---|---|
| `INT-01` | 社区服务负责人要求居民可线上预约，**线下窗口仍保留**。初步拟采用 **Rapid 画像**快速试点；运营方**还没有提交过渡 A 部署演练结果**。项目负责人要求所有结果**按具体过渡状态记录**。 |
| `INT-01`（需求项） | `INT-01` 仅支持"需求是否理解并达成一致"这一条检查的示例回答；**不能据一次访谈推定所有功能/非功能需求完整**。 |
| `INT-01`（部署项） | 部署检查记录为 **`deferred`**，责任人为运营负责人，下一步等待演练。 |
| `INT-01`（其余项） | 其余未回答项保留 **`unreviewed`**，**不填零、不算合格率、不批准上线**。 |
| 源表 | 59 条检查各有 `check_id`、ADM 标签、建议画像、纳入理由。**`Y` = 建议纳入；空白 ≠ 通过 ≠ 不适用。** |

## 来源规则与项目规则

1. **来源方法（G248 §3、§9 表 9-1、§11 表 11-1）**：变革画像（Rapid / Functional / 等）用于**裁剪**检查范围，不用于给变革评级。
2. **来源方法**：每条检查有 `check_id`、ADM 标签、建议画像与纳入理由；纳入与否须有理由，不是默认全部纳入或默认全部忽略。
3. **项目记录约定**：检查的三种回答状态——`pass`、`deferred`（已识别但待证据）、`unreviewed`（尚未处理）——必须分开；**空白不是任何一种**。
4. **项目规则**：回答 `pass` **必须附证据**；无证据的 `pass` 一律拒绝。
5. **项目规则**：排除一条建议纳入项时，须**同时给出** `include=false`、理由与证据。
6. **项目规则**：结果**按具体过渡状态记录**（`transition_id`），不合并为"整体进度"。
7. **项目规则**：`unreviewed` 不填零、不算合格率、不批准上线。

## 转换与推理

1. **先识别共同客户需求与过渡 A 的范围**，再谈画像。`INT-01` 的核心需求是"线上预约 + 线下窗口保留"，过渡 A 是 Rapid 试点的目标状态。范围没定就选画像，等于先选尺子再量东西。

2. **按 Rapid 读取源表中的建议项**。59 条里标 `Y` 的进入本次核查范围；未标 `Y` 的留作参考，但**若要排除某条建议项，必须给出理由与证据**。这一步的输出是"应查清单"，不是"合格清单"。

3. **只填有证据的那一条**。`INT-01` 支持"需求是否理解并达成一致"这一条 → 该条可填 `pass`，证据为 `INT-01`。**其余条目不能因为"看起来也会通过"而填 pass**。一次访谈不能推定全部功能与非功能需求完整。

4. **部署项标 `deferred`，不是 `unreviewed`**。区别在于：`deferred` 表示**已识别、已知需要、在等具体证据（演练结果）**，并有责任人（运营负责人）与下一步；`unreviewed` 表示**还没处理**。把"等演练"写成"未处理"会丢失责任人与触发条件；把"未处理"写成"等演练"会伪造计划。

5. **`unreviewed` 的语义边界**。它**不是 0 分**，也**不参与合格率计算**。若把 59 条中 1 条 pass、1 条 deferred、57 条 unreviewed 算成"1/59 ≈ 1.7% 合格"，就把"没查"当成了"不合格"——这是最常见的口径污染。

6. **结构化结果逐行保留来源字段**。每行含 `check_id`、ADM 标签、建议画像、纳入理由、回答、证据、`transition_id`。**保留源 `check_id` 是为了让结果能被源表核验**；自行重编号会使追溯断裂。

7. **修改：画像从 Rapid 改为 Functional**。客户进一步要求"稳定业务可运营能力" ⇒ 项目改为 Functional。重新执行后：
   - **建议纳入项增加**（Functional 覆盖更多运营稳定性检查）。
   - **新增项保持 `unreviewed`**——画像变了不等于检查做完了。
   - **原有 `check_id` 与证据不因画像变化而重新编号**。
   - **只有实际完成相应检查才能更新结果**。

本方法只**整理显式回答**，不核实证据内容是否可信。检查项的 `pass` 计数可以数，但**"合格率""成熟度""就绪度"不在本方法输出内**——`unreviewed` 项无法参与任何比率的分母。其余判断（画像是否合适、裁剪是否合理）本方法采用定性判断与追溯演练，没有适用的统一计算器。

## 修改演练

改动一处输入：客户追加"稳定业务可运营能力"要求，画像从 Rapid 改为 Functional。

- 应查清单扩大：Functional 建议纳入的运营稳定性检查项进入范围。
- **新增项一律 `unreviewed`**。不能因为"画像升了"就给它们填 `pass`，也不能因为"原来 Rapid 没要求"就标"不适用"。
- 原有 `check_id` 与证据引用**保持不变**——重编号会让上一轮结果无法核对。
- `transition_id` 仍指向过渡 A；**画像变更不改变过渡状态**。
- 影响：完整结果表仍为 59 行，纳入项从 12 增至 33；`profile`/`included` 变化，但现有记录的 57 unreviewed、1 pass、1 deferred 计数不变。

反向演练：若客户撤销"稳定运营"要求，画像退回 Rapid，则新增项应标为 `include=false` 并**附排除理由与证据**（项目规则 5），而不是直接从表中删除。删除会让读者以为它们从未被考虑过。

## 四种回答状态与比率禁令

- pass：有证据的通过
- deferred：已识别、等具体证据，需责任人与下一步
- unreviewed：尚未处理
- 空白：既不是通过也不是不适用
- unreviewed 不填零、不进分母、不算合格率

## 反例与输入不足

- **错误做法**：把 `planning-01` 标为 `pass` 却删除证据。无证据的通过不成立。预期 `missing-evidence`（由 `tests/test_source_addenda.py` 实际拒绝）。
- **错误做法**：排除一条建议纳入项，只写 `include=false`，不给理由与证据。预期 `missing-evidence`。
- **错误做法**：把 59 条中未处理的 57 条及待证据的 1 条均当不合格计入分母，算出"合格率 1.7%"。`unreviewed` 不参与比率。预期 `measurement-basis-gap`。
- **错误做法**：把 `deferred` 写成 `pass`，理由"演练迟早会过"。待证据不是通过。预期 `approval-without-evidence`。
- **错误做法**：画像从 Rapid 改 Functional 时，把新增项批量填 `pass`。"画像变化不会偷偷给新增项填通过"。预期 `fictional-approval`。
- **错误做法**：把所有过渡状态合并成一个"整体完成度 65%"。结果须按具体过渡状态记录。预期 `measurement-basis-gap`。
- **错误做法**：把源 `check_id` 重编为 1–59 连续序号，导致无法回溯源表。预期 `dangling-reference`。

**输入不足**：`INT-01` 未说明线下窗口与线上预约的**数据一致性要求**（同一时段会不会双订），相关检查项只能保持 `unreviewed`。过渡 A 的部署演练结果未提交，`CPG-GAP-1` 无预计日期。项目未说明 Rapid → Functional 的切换由谁批准，因此 `CPG-7` 只能记为候选。

**方法的边界**：该计算器**不能核实证据内容是否可信**，也**不能替代 G 阶段实施合规检查或 H 阶段价值实现评估**。因此本案例的任何 `pass` 都只表示"按项目规则提交了证据"，不表示"事实上合格"。

- 核对过渡 A 范围与共同需求先于画像选择确定。
- 核对 59 条检查逐行保留源 `check_id`、ADM 标签、建议画像与纳入理由。
- 核对仅 1 条填 `pass` 且附证据，其余未推定通过。
- 核对部署项为 `deferred`（含责任人与下一步），与 `unreviewed` 明确区分。
