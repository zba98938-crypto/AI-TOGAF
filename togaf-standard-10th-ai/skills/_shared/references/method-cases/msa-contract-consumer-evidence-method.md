# 微服务契约：版本未获批就不能算消费者

## 决策与原始业务资料

借阅资格服务从 1.0 升 1.1 新增原因码，能否安全上线？

| 证据 ID | 原始材料 |
|---|---|
| `msa-c1` | 服务只判断一个 ABF（借阅资格），职责单一。 |
| `msa-c2` | 1.0 有两个试点消费者：预约服务、馆员台。 |
| `msa-c3` | 移动端拟用 1.1，但**未获批**。 |
| `msa-c4` | 契约要求身份令牌、最小返回。 |
| `msa-c5` | 项目候选目标：P95 ≤ 200ms、月可用 99.5%，**尚未测试**。 |
| `msa-c6` | 新增原因码须检查旧消费者映射。 |

## 来源规则与项目规则

1. 来源方法（G21I）：服务契约须有明确消费者清单；消费者增加或契约变更须评估兼容。
2. 来源方法：独立部署、单一职责、数据边界是微服务的必要条件，缺一即为分布式单体。
3. 项目规则：**"拟用"不等于消费者**（`msa-c3`）；未获批的拟用方不计为已批准消费者，但应列待定和风险调查范围；若发现实际调用，不得因未授权就忽略兼容与安全影响。
4. 项目规则：`msa-c5` 的 200ms/99.5% 是**候选目标**，未测试前不得称"满足"。

## 转换与推理

1. **先把"消费者"这个词钉死**。材料里出现三种身份：

   | 说法 | 是否消费者 | 依据 |
   | --- | --- | --- |
   | 预约服务、馆员台（已在 1.0 运行） | **是** | `msa-c2` |
   | 移动端"拟用"1.1 | **否**（待定） | `msa-c3` 未获批 |
   | 未来的其他调用方 | **未知** | 材料未提 |

   有效消费者 **2 个**。移动端单列为待定，不计入已批准消费者数，但保留拟用方的版本、需求和潜在调用调查，不能把未批准当作不存在。

2. **判定变更性质，先看"增加"还是"改语义"**。新增原因码属于**增加**类：既有取值不变，只多一个。理论上向后兼容。但 `msa-c6` 提示了关键前提：**要看消费者怎么处理未知取值**。

3. **兼容性的真正风险在消费者侧，不在提供方**：
   | 消费者实现方式 | 新增原因码的后果 |
   | --- | --- |
   | 忽略未知值 / 有默认分支 | 兼容，无需改动 |
   | `switch` 穷举全部原因码，无默认分支 | **抛异常或走空分支**，运行失败 |
   | 把原因码持久化为枚举列 | 写入被拒或截断 |

   因此 `MSA-C2` 的结论是"**需核旧消费者枚举处理**"，而不是"增加类变更所以安全"。**"通常兼容"不等于"本次兼容"**。

4. **职责单一与数据边界**。`msa-c1` 说服务只判断一个 ABF（借阅资格）。这是独立性的一项证据，但不是全部——独立部署、数据边界仍需分别确认。相邻数据分布案例给出了只读快照设计，但本案 msa-c1–c6 没有该事实证据，不能直接借用为已确认的数据边界；需核实是否为同一服务、版本与范围。

5. **性能目标是候选，不是承诺**。`msa-c5` 的 P95 ≤ 200ms、月可用 99.5% **尚未测试**。因此：
   - 可以写进"设计目标"
   - **不能**写进契约的服务水平条款
   
   把未测目标写进契约，等于对外承诺一个自己没验证过的数。

6. **两项缺口性质不同，不能都自动阻断不含移动端的发布**：
   - `MSA-CGAP-1`（旧消费者枚举处理未确认）：**技术阻断**——可能导致运行时失败
   - `MSA-CGAP-2`（移动端明确尚未获批，后续审批结果未知）：**范围待决**——若发布包含移动端则阻断该范围；排除其上线不必自动阻断旧消费者发布

## 契约变更的三类判定

- 增加类：既有取值不变，只多新值。对忽略未知值的消费者兼容，对穷举枚举的消费者不兼容
- 修改语义：同一取值含义变化。对全部消费者不兼容，须升主版本
- 删除类：去掉取值。对使用该值的消费者不兼容，须给迁移窗口
- 判定顺序：先看消费者实现方式，再看变更形式；消费者的实现决定兼容结论
- 契约中的性能数值：未测目标只能写为设计目标，不得写入服务水平条款
- 待定消费者不计为已批准消费者，但保留风险调查与未来兼容需求

## 修改演练

**情景一：移动端获批使用 1.1**。消费者从 2 增至 3。此时需重评其容错：移动端更新节奏尚无证据；若旧版本仍使用1.0，需评估双版本或其他迁移策略，不能先断言必须双版本（1.0 与 1.1 同时可用一段时间），而不是"全部升到 1.1"。

**情景二：旧消费者对原因码做穷举（无默认分支）**。新增原因码从"增加类"翻转为**破坏性变更**：需按明确的项目版本策略决定主版本、并行接口或消费者先升级，并提供适用迁移窗口，**不能按增加处理**。这一个发现会让整份评估结论反转。

**情景三：性能测试完成，P95 实测 180ms**。仅能确认该负载和窗口下延迟满足候选目标，月可用性99.5%仍未验证；不能把MSA-C3两项整体升级，但仍不等于契约里的对外承诺——**承诺需要与服务对象协商并写入条款**，测试通过只是必要条件。

**影响范围**：情景一改变消费者数量与版本策略；情景二改变变更性质与发布方式；情景三改变 `MSA-C3` 的状态。三种情形下"未获批不计入"的规则不变。

## 反例与输入不足

- **错误做法**：把移动端计入 1.1 的消费者。未获批。预期 `missing-evidence`。
- **错误做法**：在契约中写"P95 ≤ 200ms"作为承诺。未测试。预期 `measurement-evidence-gap`。
- **错误做法**：只核新增原因码不核旧消费者枚举。可能触发默认分支异常。预期 `missing-evidence`。
- **错误做法**：因"增加类变更通常向后兼容"就直接放行上线。兼容性取决于消费者实现。预期 `approval-without-evidence`。
- **错误做法**：把"服务只判断一个 ABF"当作独立性已完全满足的结论。单一职责是必要条件之一，独立部署与数据边界需分别确认。预期 `missing-evidence`。
- **错误做法**：移动端获批后直接改为"全部消费者升级到 1.1"。移动端更新策略未知，需要核实旧版调用与兼容迁移，不能假设全部立即升级。预期 `missing-evidence`。

**输入不足**：`msa-c3`（移动端审批状态）与 `msa-c6`（旧消费者枚举处理）两项证据缺失，本轮无法关闭。材料未给两个消费者的技术栈与版本号，因此无法判断其处理未知取值的方式。`msa-c5` 未给测试计划，性能验证的时间点未定。

## 评审记录

- 核对消费者清单只含已获批的两方，移动端单列待定。
- 核对"拟用"与"已获批"被区分，未混为一谈。
- 核对"新增"与"破坏性"变更被区分，且区分依据是消费者实现而非变更形式。
- 核对性能目标标注为候选、未测，未写入契约承诺。
- 核对职责单一有依据；数据边界未借相邻案例冒充本案已验证事实。
- 核对数据边界符合"不直接访问他库"。
- 核对两项缺口的性质（技术 vs 范围）被区分，移动端范围待决不自动阻断排除移动端的发布。
- 核对三项修改情景分别说明结论如何在何处翻转。
- 核对性能目标未写入服务水平条款，仅作设计目标。
- 核对移动端作为待定消费者被单列，未被计入也未被视为不存在。
