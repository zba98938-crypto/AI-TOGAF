# 从月结数仓演进到新数据平台并保持可运营

所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充TOGAF规定。案例完整演练不等于独立业务评审通过。

方法：`bi-transition-method`。来源方法：G238 §3。
入口：[bi-transition-method](../analysis-methods/bi-transition-method.md)。

## 决策与原始业务资料

在不停止月结报表的条件下引入小时级库存分析。

|证据 ID|原始材料|
|---|---|
|bi-1|现状：订单数据库夜间导入EDW，EDW提供财务月结和渠道集市。月结结果必须继续可重现。|
|bi-2|目标：新增事件流用于小时级库存分析；财务业务不能接受新旧口径不一致；目标平台厂商尚未选择。|
|bi-3|项目迁移门槛：试点连续7个工作日按订单ID、记录数和金额完全对账；任何差异阻止扩大。保留旧夜批及可重放事件。门槛是本项目约定。|

## 来源规则与项目规则

1. **来源方法（G238）**：BI 演进按基线、过渡与目标组织状态，每个状态需说明运营、数据一致性与退出条件。
2. **来源方法**：过渡状态的可运营性以其自身条件判定，不以"目标态已设计"代替。
3. **项目规则**：G238 示例按明确角色处理为基线、两个过渡与目标；**不把"四个过渡架构"的泛称强加给本案**。
4. **项目规则**：入站、出站与回写方向分开记录，状态颜色不承载方向语义；本项目迁移门槛（连续 7 个工作日按订单 ID、记录数与金额对账（不是全部字段））为本例项目约定。

**来源依据**：`references/capability-addenda/bi-transition.md`。

## 转换与推理

1. **先把四个状态的身份钉死**。`B0`、`T1`、`T2`、`T3` 是**四个命名状态**，各自对象版本用稳定 `concept_id` 关联。**`T1` 与 `T2` 不能合成一个"过渡态"**——它们的运营主体、一致性依据与退出条件都不同：

   | 状态 | 承担什么 | 是否回写订单库 | 退出条件 |
   | --- | --- | --- | --- |
   | `B0` | EDW 月结 + 渠道集市 | — | 基线，不退出 |
   | `T1` | 事件平台**仅**支撑库存试点 | **否** | 7 日对账通过 |
   | `T2` | 新平台覆盖原订单数据范围并向 EDW 供数 | 否（供数方向） | 同口径月结验证通过 |
   | `T3` | 新平台服务全部已验收用例 | 视需求 | 全部用例验收 |

2. **`T1` 的关键约束是"不回写"**。事件平台在 `T1` 只读订单事件、只支撑库存看板，**不回写订单库**。这一条决定了 `T1` 的风险边界：新平台出问题不会污染交易数据。若在 `T1` 就加回写，风险性质立刻改变，需要额外的写入审批与幂等/回滚设计（见修改演练）。

3. **每个状态都要给五项条件**（`bi-3` 的门槛 + `bi-1` 的运营事实）：
   | 项 | `T1` | `T2` |
   | --- | --- | --- |
   | 运营 | 数据团队值班 | EDW 月结继续 |
   | 一致性 | 按 `bi-3` 每日对账 | 新旧供数对比、同口径月结 |
   | 依赖 | 事件 ID 与重放能力 | 历史补载 |
   | 控制 | 试点读取权限隔离 | 双轨审计 |
   | 回退 | 关闭新看板，回旧库存报告 | 重新启用旧夜批 |

4. **"月结结果必须继续可重现"是硬约束**。`bi-1` 明说月结结果必须继续可重现。这意味着 `T1`、`T2` 期间**旧夜批不能停**——本项目明确要求保留旧夜批作为回退；历史复算还取决于历史数据、规则版本和重放能力，不能仅由停跑一个批任务断言不可能复算。`bi-3` 的"保留旧夜批及可重放事件"正是为此。

5. **门槛不可跳，且失败要重置窗口**。`bi-3`：连续 **7 个工作日**按订单 ID、记录数、金额**完全对账**，任何差异阻止扩大。"连续"意味着**中途失败要重新计数**，不是累计 7 天。

6. **`T3` 不等于 EDW 退役**。`T3` 说 EDW "可作为保留组件纳入平台边界"。是否退役是**单独决策**，不能从"新框覆盖旧框"的图面推断已退役。这与 `bi-1` 的月结可重现约束直接相关——退役前必须证明月结已在新平台可重现。

7. **方向语义不靠颜色**。入站（订单 → 平台）、出站（平台 → EDW）、回写（平台 → 订单库）三个方向分开记录。**状态颜色不承载方向语义**——同一状态里可能同时有入站与出站，靠颜色区分会丢失信息。

## 修改演练

**情景一：`T1` 第 5 日对账失败**。处置：保持 `T1`，定位事件重放问题，**重新开始"连续 7 个工作日"窗口**。`T2` **不得因日期到达自动进入**——门槛是证据条件，不是时间条件。日期到了但证据没到，就是没到。

**情景二：运营要求增加回写（平台 → 订单库）**。这不是"把供数箭头反过来"就行：需要新增**写入审批**与**幂等/回滚设计**，并把 `T1` 的风险边界从只读侧扩展到写入侧。**只反转箭头会让读者以为风险没变**。

**情景三：`T2` 完成后决定 EDW 是否退役**。需先证明月结在新平台可完整重现（含历史期），再评估监管留存要求（`GAP-BI`）。**退役是独立决策，不是 `T3` 的自动结果**。

**情景四：连续对账通过但存在"可解释差异"**。`bi-3` 要求"完全对账"，**"可解释"不等于"无差异"**。若要允许可解释差异，属于修改项目门槛，需明确批准并记录，不能由执行者自行放宽。

**影响范围**：情景一重置门槛计数但不改变状态定义；情景二扩展 `T1` 的风险边界与所需控制；情景三关闭或保留 `GAP-BI`；情景四变更项目门槛本身。四种情形下"月结结果必须可重现"这一硬约束不变。

## 状态划分与五项条件

- B0/T1/T2/T3 是四个命名状态，各有 concept_id
- 每状态列运营、一致性、依赖、控制、回退五项
- T1 不回写订单库，风险限于只读侧
- 7 个工作日对账为连续窗口，失败重算
- T3 不等于 EDW 退役，退役为独立决策

## 反例与输入不足

- **错误做法**：只有四张不同颜色的演进图，就宣称迁移可行。图示本身不证明可迁移。预期 `missing-evidence`。
- **错误做法**：把 G238 的参考目标当作"必然采购某厂商"或"必然退役 EDW"的决定。参考目标不是决定。预期 `approval-without-evidence`。
- **错误做法**：跳过 7 个工作日对账门槛就直接扩大试点。门槛是项目约定，不可跳。预期 `approval-without-evidence`。
- **错误做法**：把 `T1` 与 `T2` 合并成一个"过渡架构"节点。两者运营主体与退出条件不同。预期 `core-vocabulary-override`。
- **错误做法**：在 `T1` 停掉旧夜批以"简化双轨"。月结结果必须可重现，旧夜批不可停。预期 `missing-evidence`。
- **错误做法**：对账出现差异但标注"可解释"就继续扩大试点。门槛要求完全对账。预期 `approval-without-evidence`。
- **错误做法**：因 `T3` 图里新平台覆盖了 EDW 的位置，就宣布 EDW 已退役。图面覆盖不是退役决定。预期 `approval-without-evidence`。

**输入不足**：目标平台厂商尚未选择，因此不比较具体产品能力（`GAP-BI2`）。`bi-3` 未给"完全对账"的容差定义（金额精度、时间窗），故本例按"零差异"理解，若项目另有容差需显式声明。`GAP-BI` 的监管留存期限未给。
