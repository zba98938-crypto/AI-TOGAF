# BI 业务功能覆盖：采购了软件不等于具备功能

## 决策与原始业务资料

参考模型的 54 条业务功能，本企业实际具备哪些？哪些只是"买了软件"？

| 证据 ID | 原始材料 |
|---|---|
| `bif-1` | 只出示 U1/U2 两个用途待办，以及"拟每周复核模型"的计划。 |
| `bif-2` | 其余业务功能没有访谈或运行证据。 |
| `bif-3` | 软件已采购不构成覆盖证据。 |
| `bif-4` | 54 条源表行含宏观参考行与子功能，粒度不一。 |

## 来源规则与项目规则

1. 来源方法（G238）：按参考功能逐条评估现状，结果分为已见、计划、未知、有理由不适用四类。
2. 来源方法：宏观参考行与子功能粒度不同，不能以宏观行推断其下子项已覆盖。
3. 项目规则：**软件采购 ≠ 功能具备**（`bif-3`）；覆盖证据必须是组织活动或实际运行记录。
4. 项目规则：无访谈或运行证据的条目一律记 `unknown`，不记"部分覆盖"——部分覆盖是未定义的中间态。

## 转换与推理

1. **先确认源表的粒度问题**。`bif-4` 说 54 条源表行**含宏观参考行与子功能，粒度不一**。这决定了判定规则：不能对 54 条一视同仁地判，必须先识别哪些是宏观行、哪些是子功能。

   | 行类型 | 判据 | 判定约束 |
   | --- | --- | --- |
   | 宏观参考行 | 概括一个功能组 | 不可单独判"已见"，须看子功能 |
   | 子功能行 | 描述具体动作 | 可单独判定，须逐条有证据 |

2. **四类判定规则待逐行落下**。`bif-1`/`bif-2` 给出事实基础：

   | 判定 | 条数 | 依据 |
   | --- | --- | --- |
   | 已见 | 未确定 | U1/U2 待办只证明用途已记录，不能自动映射成两条已具备功能 |
   | 计划 | 未确定 | 拟每周复核是计划意图，参考行 ID 与执行安排待补 |
   | 未知 | 未逐行计数 | 缺 54 条逐行映射；不得倒减得到 51 |
   | 有理由不适用 | 0 | 未提出不适用理由 |
   | **应登记总数** | **54** | 待取得逐行清单后校验闭合，当前不是完成声明 |

3. **"已见"的证据门槛**。`bif-3` 明说软件采购不构成覆盖证据。因此"已见"必须是**组织活动或实际运行记录**。U1/U2 是"用途待办"——这是业务侧的用途定义，不是运行记录。因此**不能把两个用途数当成已见功能数**。若将来某参考行专门要求用途管理，待办可作为该行组织活动的候选证据，但须核查定义与适用范围。

4. **为什么不设"部分覆盖"**。项目规则明确：无访谈或运行证据一律记 `unknown`，不记"部分覆盖"。理由：**"部分覆盖"没有定义**——是覆盖了 50% 的功能点？还是覆盖了主要场景？没有统一口径的中间态会让统计失去意义。

5. **粒度校验的反向约束**。宏观行若被判"已见"，其下子功能**不得自动继承**。反过来也成立：若宏观行的子功能全部未知，宏观行本身也不能判"已见"。**继承在两个方向都被禁止。**

6. **缺口行动要排序，不能批量**。未证实条目若统一写"待补证"，等于没有行动。应按用途优先级排序：先补与 U1/U2 直接相关的条目——因为这些是本项目已声明的用途，其余条目是否纳入范围尚未确认。

## 修改演练

**情景一：补入 U1 相关的 8 条访谈证据**。先定位这 8 条证据对应的参考行、排除重叠并按功能定义核实；已见数最多新增 8，不能从未经证实的 2 直接加到 10。关键限制：
- "最多"意味着这 8 条中可能有条目访谈后仍无运行证据，此时仍是未知
- 复核意图**仍需核查是否形成计划**，不得因为同一批次补充就并入已见
- 总数仍为 54，四类之和必须恒等于 54

**情景二：某宏观行被判已见，但其子功能未逐条核**。`BIF-3` 触发：该宏观行的判定**降为未知**，直至其下子功能逐条有证据。这是粒度规则的反向应用——上层的"已见"不能向下传递，同样也不能在上层单独成立。

**情景三：业务方提出"这 3 条我们不适用"**。必须给出理由（法规不要求、业务模式不涉及等），才能记"有理由不适用"。**"暂时没做"不属于不适用**，那是未知。若理由是"我们不做这块业务"，需与 `bif-1` 的用途范围核对。

**影响范围**：情景一改变四类计数但总数不变；情景二使某条从已见退回未知；情景三使用既有第四类取值。三种情形下"采购不作证据"的规则不变。

## 粒度与继承的两向禁令

- 行类型判据：宏观参考行概括功能组，子功能行描述具体动作
- 宏观行已见 ⇏ 子功能已见（不能向下继承）
- 子功能全未知 ⇏ 宏观行已见（不能向上推断）
- 采购事实不构成任何一类的覆盖证据

## 反例与输入不足

- **错误做法**：因已采购某 BI 产品，就把参考表中的功能判为"已具备"。采购是能力交付的前提，不是证据。预期 `missing-evidence`。
- **错误做法**：宏观参考行判为已见后，其下所有子功能自动继承"已见"。粒度不同，不可继承。预期 `core-vocabulary-override`。
- **错误做法**：把无访谈证据的条目记作"部分覆盖 50%"。部分覆盖是未定义的中间态，四类里没有它。预期 `measurement-basis-gap`。
- **错误做法**：把"计划每周复核模型"计入已见。计划尚未执行，不是已见。预期 `approval-without-evidence`。
- **错误做法**：四类计数之和为 55（多于 54）。逐条判定必须恰好覆盖全部源表行。预期 `measurement-basis-gap`。
- **错误做法**：把"暂时没做"记为"有理由不适用"。不适用需要理由，缺做只是未知。预期 `missing-evidence`。
- **错误做法**：算出"覆盖率 3.7%（2/54）"并据此判断 BI 建设水平。用途数不是参考功能已见数；证据覆盖比例若定义，也不能直接代表建设水平。预期 `measurement-basis-gap`。

**输入不足**：`bif-2` 只说其余功能无访谈或运行证据，未支持精确 51 条，因此本案例不给覆盖率、不给达标结论。`bif-1` 只给 U1/U2 两个用途待办的具体内容未展开，故不认定它们对应两条已见参考功能。`bif-4` 未给 54 条中宏观行与子功能的具体分布数量，因此无法计算粒度校验的覆盖比例。

- 核对未计算覆盖率或任何以 54 为分母的完成度比率。
