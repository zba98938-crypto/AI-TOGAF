# 以事务一致性和团队能力选择服务边界

所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充TOGAF规定。案例完整演练不等于独立业务评审通过。

方法：`microservice-boundary-method`。来源方法：G21I §6–7。
入口：[microservice-boundary-method](../analysis-methods/microservice-boundary-method.md)。

## 决策与原始业务资料

订单应用是否应按页面功能拆成七个微服务。

|证据 ID|原始材料|
|---|---|
|ms-1|订单与库存预约在当前单库事务内保持一致；支付由外部支付机构提供；通知失败可重试。前端有下单、地址、查询、取消等七个页面。|
|ms-2|两个开发小组都可维护订单代码，但只有一个轮值运维组；当前无跨服务事务和分布式追踪经验。|
|ms-3|业务目标是促销期间订单写入可扩展、支付集成独立更新；不能接受扣款成功而订单长期未知。未给出具体容量目标。|

## 来源规则与项目规则

1. **来源方法**：从业务功能、质量目标、数据所有权、资源与价值分析分解服务边界；更多更小不自动更优。
2. **来源方法**：独立部署、单一职责与数据边界是微服务的必要条件，缺一即为分布式单体。
3. **项目规则**：不凭页面数量或代码行数定边界——这是本案例的项目约定。
4. **项目规则**：事务拆分前必须明确状态恢复、幂等、补偿与运营责任；缺任一项不得宣称边界可用。

**来源依据**：`references/capability-addenda/microservice-boundary.md`。

## 转换与推理

1. **三个候选方案，先按业务与数据归属筛**：

   | 方案 | 边界划分 | 数据所有权 | 判定 |
   | --- | --- | --- | --- |
   | A | 七个页面 → 七个服务 | 模糊：地址、取消、订单状态跨多服务 | 否 |
   | B | 订单核心 + 支付适配 + 通知 | 清晰：订单核心主控状态 | **候选** |
   | C | 保持模块化单体 | 单库事务，天然一致 | 备选 |

   **A 被否不是因为"服务太多"，而是因为数据所有权说不清**。七个页面里，下单、地址、查询、取消都要读写订单状态，拆开后没有单一主控方。

2. **B 的边界理由逐条给**：
   - **订单核心**：订单与库存预约在**当前单库事务内保持一致**（`ms-1`）。这两者的事务边界不能拆——拆开就要引入跨服务事务，而 `ms-2` 明说团队**无跨服务事务经验**。
   - **支付适配**：支付由外部机构提供（`ms-1`），天然是独立边界；它持有外部交易映射与幂等请求。
   - **通知**：通知失败可重试（`ms-1`），与主流程松耦合，重试不影响订单写入。

   **三个理由各自对应一条材料事实**，不是"业界通常这样分"。

3. **数据写权必须唯一**。单库事务并不能单独证明写权归属；本候选设计选择把订单与库存预约写权保留在订单核心，须由业务与数据负责人确认。若把库存拆成独立服务并让它直接写订单表，就破坏了声明的所有权——这正是"共享数据库却称独立服务"的错误形态。

4. **失败方向决定边界质量**。`ms-3` 说不接受"扣款成功而订单长期未知"。这要求可靠的结果确认、幂等、超时核对与恢复机制。本候选选择事件回传，不让适配器直接写订单表；受控轮询也可能满足要求，不能由业务目标推出唯有事件可行。

5. **运营能力是边界的现实约束**。`ms-2`：两个开发小组都能维护订单代码，但**只有一个轮值运维组**，且无分布式追踪经验。拆成三服务后，一个运维组要承担三套部署、告警与排障；没有追踪能力时跨服务问题定位会极慢。因此 `GAP-MS1` 阻断**全面推广**，但允许小范围实验。

6. **容量目标缺失，不下性能结论**。`ms-3` 的目标是"促销期间订单写入可扩展"，但**未给具体容量目标**。因此不能声称 B 比 C 性能更好——两者都没有可比指标。

7. **C 不是"落后选项"**。`ms-3` 的两个目标中，**支付集成独立更新**用 C 也能通过模块边界部分实现；**写入可扩展**也可考虑单体多实例、数据优化等，不能断言必须拆分。因此 C 是有效备选，只是支付演进受限。

## 输出与追溯

| 结果 ID | 结论 | 追溯 | 状态 |
|---|---|---|---|
| `BOUNDARY-B` | 候选三边界：订单核心、支付适配、通知；数据写权明确 | `ms-1`/`ms-3` | 待试验 |
| `BOUNDARY-A` | 七页面方案因数据所有权模糊被否，非因服务数量 | `ms-1` | 已判定 |
| `BOUNDARY-C` | 模块化单体为有效备选；一致性与运维最简单，支付演进受限 | `ms-1`/`ms-2` | 备选 |
| `OWN-1` | 订单状态由订单核心唯一主控，库存预约写权同属该边界 | `ms-1` | 已声明 |
| `FAIL-1` | 支付结果经事件回传订单核心，不由支付适配改订单状态 | `ms-3` | 已声明 |
| `GAP-MS1` | 跨服务恢复与追踪能力需演练；单运维组承载能力未证明 | `ms-2` | 阻断全面推广 |
| `GAP-MS2` | 容量目标缺失，无法做性能达标结论 | `ms-3` | 待补 |
| `GAP-MS3` | 无分布式追踪经验，跨服务排障手段未定义 | `ms-2` | 未决 |

本方法采用定性判断与追溯演练，没有适用的统一计算器。**方法输出的边界**：给出候选边界、数据写权与失败处置设计，**不给出**通用最优服务数量、性能预测或拆分收益估算；三边界只是候选设计——容量目标缺失使任何性能结论都无依据。

## 边界判据的四个方面

| 方面 | 问题 | 本案判断 |
| --- | --- | --- |
| 业务功能 | 这块业务能独立说清吗 | 订单核心可，七页面不可 |
| 质量目标 | 有独立的质量要求吗 | 支付适配可（外部机构约束） |
| 数据所有权 | 谁是唯一写方 | 订单核心主控状态 |
| 资源与团队 | 有人能独立运维吗 | **未知**（单运维组承载能力未证实，不等于无人可运维） |

四项全满足才构成可运行的服务边界。本案第四项不足，故阻断全面推广。

## 拆分的两种动机

| 动机 | 是否成立 | 说明 |
| --- | --- | --- |
| 数据所有权冲突 | **成立** | 天然边界 |
| 独立演进需求 | 成立 | 如支付适配 |
| 代码量太大 | 不成立 | 与业务边界无关 |
| 页面数量多 | 不成立 | 界面与业务不同层 |

## 事务边界的硬约束

`ms-1` 说订单与库存预约在同一单库事务内。在本案团队与证据条件下，暂保留这一事务边界；并非理论上永远不可拆——拆开需引入跨服务事务，而团队无此经验。因此：
- 订单核心内部继续模块化
- 不因"想更微"而拆库存

## 修改演练

**情景一：库存成为跨渠道独立权威服务**。这不是"把库存服务挪个位置"，而是**重新设计订单/预约边界及补偿**：订单核心不再直接持有库存写权，改为通过库存服务预留，需补偿事务处理预留失败。**仅移动部署框不会带来这个变化**。

**情景二：团队无能力运行 B（运维与追踪都不具备）**。保留 C，**先补运营能力**（监控、追踪、值班），而不是硬上微服务。边界正确但运营不了，等于不可用。

**情景三：容量目标补齐为"促销峰值 3 倍写入"**。此时才有依据评估 B 是否够用，但仍需实测——**有目标不等于达标**。

**影响范围**：情景一改变数据所有权与补偿设计；情景二退回 C 并新增能力建设项；情景三使 `GAP-MS2` 可被评估但仍需测试。

## 反例与输入不足

- **错误做法**：按七个前端页面拆成七个业务服务。页面不是服务边界。预期 `core-vocabulary-override`。
- **错误做法**：让多个服务直接写同一批数据库表，同时声称各自拥有数据所有权。写权共享即所有权不成立。预期 `relation-endpoint-type`。
- **错误做法**：没有失败恢复演练证据，就把候选边界标为"已实现且可靠"。预期 `missing-evidence`。
- **错误做法**：因"微服务更先进"就排除模块化单体。C 在一致性与运维上更简单，是有效备选。预期 `unsourced-maturity-rating`。
- **错误做法**：把订单与库存预约拆到两个服务，仍宣称保持"单库事务一致"。跨服务后该保证不再成立。预期 `missing-evidence`。
- **错误做法**：在容量目标缺失时宣称 B 的写入性能优于 C。无指标可比。预期 `measurement-basis-gap`。
- **错误做法**：让支付适配直接更新订单状态，理由是"减少一次事件"。回传路径被绕过。预期 `relation-endpoint-type`。

**输入不足**：材料未给具体容量目标，因此本案例不判断 B 方案能否满足促销期扩展要求（`GAP-MS2`）。`ms-2` 未说明运维组人数与值班覆盖，`GAP-MS1` 的"承载能力未证明"只能是定性判断。材料未给监控与告警现状，`GAP-MS3` 保留。

## 评审记录

- 核对三个候选边界（订单核心、支付适配、通知）各有业务理由，且没有一条来自"页面数量"。
- 核对 A 方案被否的理由是数据所有权模糊，而非服务数量多。
- 核对数据写权归属明确：订单与库存预约仍在同一一致性边界内，未被拆成两个写同一批表的服务。
- 核对支付适配的外部交易映射与幂等请求边界成立，支付结果经明确事件回传而非直接写订单表。
- 核对通知消费订单事件且可重试，失败不反向阻塞订单写入。
- 核对失败行为已列出（追踪、幂等键、超时待核对、补偿与人工对账、告警责任、部署回退），并标注为**待测试确认**而非已验证。
- 核对发布独立性与运营责任被显式检查：单运维组承载三服务的证据缺失，故 `GAP-MS1` 阻断全面推广。
- 核对容量目标缺失时**未**宣称 B 的性能优于 C。
- 核对 C 未被当作"落后选项"，其一致性优势被记录。
- 核对三项修改情景分别说明影响范围与不变项。

本例已完成编写者一致性复核；业务事实、授权与执行成效均为虚构，独立代理/业务责任人评审仍为待验证。
