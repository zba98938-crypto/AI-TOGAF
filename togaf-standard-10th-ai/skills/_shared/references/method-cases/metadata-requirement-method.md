# 从报表争议形成有范围的元数据治理需求

所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充TOGAF规定。案例完整演练不等于独立业务评审通过。

方法：`metadata-requirement-method`。来源方法：G234 §4.2–4.3。
入口：[metadata-requirement-method](../analysis-methods/metadata-requirement-method.md)。

## 决策与原始业务资料

决定首先管理哪些元数据资产及更新质量规则。

|证据 ID|原始材料|
|---|---|
|mr-1|财务与渠道看板对‘净收入’差异12万元：财务减去已确认退货，渠道仅减当日退款；两个报表都未显示口径版本。|
|mr-2|数据工程提供路径：订单表→每日聚合任务→渠道看板；退款表→财务月结视图。负责人和任务版本存于不同工具。|
|mr-3|本项目范围为上述两个看板；财务负责人要求发布口径有定义、责任人、版本、生效日和字段血缘。隐私分类清单尚未审核，暂不推断公开级别。|

## 来源规则与项目规则

1. **来源方法**：支持从业务用例自上而下、以及从数据问题自下而上两条路径引出元数据需求。
2. **来源方法**：元数据资产须有定义、责任人、版本、生效日与血缘，才具备可管理性。
3. **项目规则**：本案范围限定为"净收入"相关的两个看板（财务与渠道），**不扩为全部参考资产**。
4. **项目规则**：隐私分类清单未审核前不推断公开级别；同名术语不自动判定为同义。

**来源依据**：`references/capability-addenda/metadata-requirement-method.md`。

## 转换与推理

1. **先判差异性质，再谈修数据**。`mr-1` 的 12 万元差异来自两处口径不同：财务扣"已确认退货"，渠道扣"当日退款"。这是已确认的**口径差异**；未给逐笔对账，不能证明12万元全由它解释，也不能排除并存的管道错误。若先假定某一方有 bug 去查管道，会白费功夫且错过真正问题。

2. **同名不等于同义，先立两个术语**。据此建立 `TERM-FIN` 与 `TERM-CHANNEL` 两个独立术语，**各自带版本**，而不是合成一个"正确净收入"。合并会掩盖差异，而差异恰恰是本次要管理的对象。

3. **从业务要求反推需求，从数据路径正推资产**。两条路径在本案都用了：
   - 自上而下（业务要求 `mr-3` → 需求）：`R-DEF` 口径可追溯、`R-LIN` 字段血缘、`R-OWN` 责任清晰
   - 自下而上（数据路径 `mr-2` → 资产）：术语、数据元素、字段、任务、数据流、所有者

   两条路径**必须汇合**：需求若无资产承载则落空，资产若无需求驱动则无从裁剪。

4. **概念结构说明"谁解释谁"**：
   | 层次 | 关系 |
   | --- | --- |
   | 术语 | 术语**版本**解释数据元素的口径 |
   | 数据元素 | 映射到物理字段 |
   | 任务 | 输入/输出构成**有向**血缘 |

   血缘是有向边，方向写反会让"上游变更影响下游"的判断整体颠倒。

5. **业务语义与物理列必须分层**。逻辑结构用 `term_id + version`、生效起止、`owner_id`、`field_id` 关联。若把业务术语直接当列名，任何口径变更都会变成改表结构。

6. **生命周期四态**：`draft → reviewed → published → withdrawn`。财务与渠道**各自确认自己口径**；跨口径比较必须显示差异说明。这四个状态不是审批层级，而是"这份定义当前能否被引用"的可用性状态。

7. **未核实的保持 unknown**。隐私分类清单未审核，因此公开级别写 `unknown`，不写"内部"也不写"公开"。`mr-2` 说负责人与任务版本**存于不同工具**，这一事实直接决定了血缘要跨系统拼接，不能假设单一元数据仓已存在。

## 输出与追溯

| 结果 ID | 结论 | 追溯 | 状态 |
|---|---|---|---|
| `R-DEF` | 两个净收入术语保留独立 ID 与版本，并显示口径差异 | `mr-1` → `TERM-FIN`/`TERM-CHANNEL` | 候选需求 |
| `R-LIN` | 限定两个看板上游字段及任务血缘，不强制登记全企业资产 | `mr-2`/`mr-3` | 已定范围 |
| `R-OWN` | 每个资产需责任人、版本、生效日、定义、血缘五项 | `mr-3` | 已定要求 |
| `R-LIFE` | 术语生命周期四态，财务与渠道分别确认各自口径 | `mr-1`/`mr-3` | 已定义 |
| `GAP-MR` | 隐私分类与业务授权未核实，不能因元数据可见默认原始数据可读 | `mr-3` | 待安全评审 |

本方法采用定性判断与追溯演练，没有适用的统一计算器。**方法输出的边界**：给出应管理的资产、需求与生命周期，**不给出**元数据平台选型、实施成本或治理成熟度评分。

## 元数据资产的五项要求

| 要求 | 作用 | 缺失后果 |
| --- | --- | --- |
| 定义 | 说清口径含义 | 同名不同义 |
| 责任人 | 谁维护、谁裁决争议 | 变更无人负责 |
| 版本 | 何时生效、何时废止 | 历史无法复现 |
| 生效日 | 从哪天起适用 | 新旧混用 |
| 血缘 | 从哪来到哪去 | 出错无法定位 |

五项缺一即不具备可管理性。

## 术语与列的分层

| 层 | 内容 | 变更影响 |
| --- | --- | --- |
| 业务语义 | 术语与定义 | 改定义不改结构 |
| 逻辑结构 | 数据元素与映射 | 改映射不改物理 |
| 物理实现 | 字段与表 | 改结构需迁移 |

**三者分层的作用**：口径变更不必改表结构。若把业务术语直接当列名，任何口径调整都会变成 DDL 变更。

## 差异性质的两种解释

12 万元差异可能来自：

| 解释 | 处置 |
| --- | --- |
| 定义冲突（口径不同） | 立两个术语，分别带版本 |
| 管道错误（计算错） | 修 ETL |

**先判性质，再动手**。若先假定算错去查 ETL，会白费功夫且错过真正问题。

## 修改演练

**情景一：新增营销报表请求**。先补业务收益与数据范围，再决定是否纳入。若沿用渠道口径，**复用 `TERM-CHANNEL` 的当前版本**，不按新报表名复制一个术语——复制会产生第三个需要同步维护的定义。

**情景二：渠道口径本身发生变化**。新增 `TERM-CHANNEL` 的版本（如 v2），保留 v1 及其生效起止；评估受影响字段与看板（营销报表在列）。**不是改 v1 的内容**，否则历史报表无法复现。

**情景三：`GAP-MR2` 被证实无法跨系统拼接血缘**。则先登记 R-LIN 实现缺口并评估人工追溯或替代方案；若有权业务方批准缩范围，才可只覆盖单工具部分，并在输出中显式标注"血缘不完整"。此时不能仍宣称"字段血缘已可追溯"。

**影响范围**：情景一可能新增资产引用（不新增术语）；情景二新增术语版本并触发下游评估；情景三登记实现缺口，范围调整须另行批准。三种情形下 `R-DEF` 的"两个独立术语"结构不变。

## 反例与输入不足

- **错误做法**：把 G234 全部参考资产都列为强制交付。参考全集不是本项目范围。预期 `core-vocabulary-override`。
- **错误做法**：因两个报表用了同一个术语名，就判定二者口径相同。同名不构成同义证据。预期 `missing-evidence`。
- **错误做法**：在口径版本未记录时，任选一方数值作为"正确值"。无版本即无裁定依据。预期 `missing-evidence`。
- **错误做法**：先假定管道算错，直接去查 ETL 而不先比对口径定义。12 万元未给数据逐笔重算，不能断言差异已由定义冲突完全解释。预期 `missing-evidence`。
- **错误做法**：把 `TERM-CHANNEL` 的口径变更直接改在原版本上。历史报表将无法复现。预期 `missing-evidence`。
- **错误做法**：因元数据对分析人员可见，就认为原始明细数据也可读。元数据可见与数据可读是两件事。预期 `approval-without-evidence`。
- **错误做法**：把血缘方向写成"看板 → 任务 → 字段"。方向反了，"上游变更影响下游"的判断会整体颠倒。预期 `relation-endpoint-type`。

**输入不足**：隐私分类清单尚未审核，因此公开级别不作推断。`mr-2` 未给负责人姓名与任务版本号，本案例只记录"存在且分存两处"，不虚构具体值。材料未给 12 万元差异的时间区间，故不判断该差异是否稳定存在。

## 评审记录

- 核对两个看板的"净收入"差异（12 万元）被追溯到口径版本缺失，而非归因于某一方算错。
- 核对 `TERM-FIN` 与 `TERM-CHANNEL` 各自独立且带版本，未被合并为单一"正确净收入"。
- 核对数据路径与责任人、任务版本的存放位置分别记录，未假定同一工具。
- 核对范围限定为两个看板，未扩为 G234 全部参考资产。
- 核对每个待管理资产都有定义、责任人、版本、生效日与血缘五项要求。
- 核对血缘方向为字段/任务 → 看板（上游到下游），未写反。
- 核对业务语义（术语）与物理列（字段）分层，未把术语直接当列名。
- 核对生命周期四态存在，且财务与渠道分别确认各自口径。
- 核对隐私公开级别在清单未审核前不作推断。
- 核对三项修改情景分别说明"新增"与"改版本"的差别。
