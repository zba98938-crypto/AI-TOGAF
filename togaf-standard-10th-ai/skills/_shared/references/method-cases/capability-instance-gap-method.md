# 比较同一库存能力在门店与网站的不同实例

## 决策与原始业务资料

将网站履约实例升级，同时确定哪些现有组成可以复用。

|证据 ID|原始材料|
|---|---|
|ig-1|能力类型C-STOCK库存管理稳定存在。基线网站阶段S-WEB使用I-WEB：客服2人、电话确认流程、库存日报、旧OMS；门店阶段S-STORE使用I-STORE：店员、POS实时库存。|
|ig-2|目标网站要求承诺前验证可用量：保留客服，新增预约库存流程、共享库存API和可用量数据；门店继续运行。|
|ig-3|迁移负责人允许网站订单先试点一个仓；API未验收前继续人工确认。库存API拟与门店共用，但门店数据适配尚未验证。|

## 来源规则与项目规则

1. 来源方法：能力类型和语境实例分开；按人员、流程、信息和应用等组成比较差距并组织增量。
2. 项目分类约定：新增、改进、复用、退役、待验证分别记录；没有实例身份映射时不因同名自动合并。

## 转换与推理

1. **能力类型不随实例变化**。`C-STOCK` 是能力类型，`I-WEB` 与 `I-STORE` 是同一类型在两个语境下的实例。升级实例不等于重定义能力类型，因此 `C-STOCK` 不发生分解变化。
2. **为基线与目标各建独立实例对象**。`I-WEB-B`（基线）与 `I-WEB-T`（目标）共用 `concept_id = web-stock`、`scope_id = web-pilot`，以保证版本可追但对象不混。`I-STORE` 是另一实例，语境不同，不与 `I-WEB-*` 合并。
3. **逐类组成比较差距**。四类组成分别判定：

| 组成类别 | 基线（I-WEB-B） | 目标（I-WEB-T） | 差距类型 |
| --- | --- | --- | --- |
| 人员 | 客服 2 人 | 客服 2 人（保留） | 复用 |
| 流程 | 电话确认 | 预约确认 + 人工回退 | 改进 |
| 信息 | 库存日报 | 可用量数据 | 待替换 |
| 应用 | 旧 OMS 接单 | 旧 OMS 接单，经 API 查询 | 复用 + 新增接口 |

   分类的意义在于：**"复用"与"改进"是两种不同的增量**，混为一谈会让工作量估算失真。
4. **API 复用须分别证明兼容**。`ig-3` 说库存 API 拟与门店共用，但门店数据适配尚未验证。因此记 `GAP-IG2`，并明确**不能因为两者都叫"库存 API"就认定零成本整合**——名称相同不构成契约兼容证据。
5. **增量与依赖**。`WP-1` 实现仓内可用量与 API 试点；`WP-2` 接入网站预约；`WP-2` 依赖 `WP-1`。依赖是有向关系，不由编号顺序暗示。
6. **阶段化推进，不一次到位**。`T1` 保持人工确认（API 未验收）；`T2` 试点预约；`T3` 在对账与回退均验收后才扩大。三个状态各有其运营条件，`T2` 的成立不自动使 `T3` 成立。

7. **"共用"与"兼容"是两件事**。`ig-3` 说库存 API 拟与门店共用。共用是**意图**，兼容是**事实**。因此：
   - 共用意图 → 记 `GAP-IG2`（待验证）
   - 兼容事实 → 需契约测试证据
   
   **在无兼容证据时，"共用"这一表述本身就是风险**——它会让下游以为整合已完成。

8. **基线/目标实例的双对象结构**。`I-WEB-B` 与 `I-WEB-T` 共用 `concept_id` 但对象分离。这个设计的意义在**比较**：
   - 若只有一个对象，改动即覆盖，无法回答"原来是什么样"
   - 两个对象并存，才能逐类组成对比差距

   `scope_id` 相同则确保它们属于同一语境（`web-pilot`），不会与门店实例混淆。

9. **增量类型不是工作量等级**。"复用/改进/待替换/新增"描述的是**变化性质**，不是工作量：

| 增量类型 | 含义 | 工作量含义 |
| --- | --- | --- |
| 复用 | 原样沿用 | 未知，须核适配和验证 |
| 改进 | 在原基础上调整 | 未知，须另估算 |
| 待替换 | 换掉 | 未知，须另估算 |
| 新增 | 从无到有 | 未知，须另估算 |

   四种变化性质均不提供工作量等级。复用也可能需要大量适配和验证，新增也可能复用既有实现；本案没有估算依据，不能按类型排列工时。

10. **阶段不跳级**。`T1`（人工确认）→ `T2`（试点预约）→ `T3`（扩大）。每级的进入条件不同，**`T2` 成立不使 `T3` 成立**——`T3` 需对账与回退双双验收。

## 修改演练

**情景一：API 通过门店契约测试**。`GAP-IG2` 关闭，"复用 + 新增接口"中的复用部分得到证实。`T2` 的进入条件之一（API 验收）满足，但仍需对账证据。

**情景二：门店数据适配被证实不兼容**。共享 API 的门店兼容未成立，需评估适配或分别实现；`INC-2` 中客服与旧 OMS 的复用不因此失效。共享 API 的兼容假设失效，需另行估算适配或分别实现；本案原本没有成本工期数字，不能声称数字全部失效，但能力类型 `C-STOCK` 与实例身份不受影响。

**情景三：网站取消预约功能**。`I-WEB-T` 的流程类组成退回"查询展示"，`WP-2` 需重评。`concept_id` 保持不变以追踪目标版本演变。

**情景四：门店也改用共享 API**。只为 `I-STORE` **增加**组成/使用关系，**不复制 API 对象**。API 是被两个实例共用的组成，不是任一实例私有。

**影响范围**：情景一关闭缺口；情景二使复用降级；情景三改变目标态范围；情景四改变门店实例的组成。四种情形下"能力类型不随实例变化"的原则不变。

## 反例与输入不足

- **错误做法**：把 `I-WEB` 与 `I-STORE` 画成 `C-STOCK` 的子能力。语境实现不是能力分解。预期 `core-vocabulary-override`。
- **错误做法**：两个同名库存实例在仓库范围不同时仍按名称覆盖为一条。同名不同范围须分别标识。预期 `duplicate-id`。
- **错误做法**：在库存 API 未验收前就撤销人工确认。未验收即未可用。预期 `approval-without-evidence`。
- **错误做法**：因门店与网站都称"库存 API"，就宣布整合成本为零。名称相同不是契约兼容证据。预期 `missing-evidence`。
- **错误做法**：把"复用""改进""待替换""新增"合成一个"改造项数"并据此估算工期。四类增量的工作量性质不同。预期 `measurement-basis-gap`。

**输入不足**：门店数据适配尚未验证，因此 `I-STORE` 与目标态的一致性不作结论。`ig-3` 未给 `T3` 的对账口径与回退演练范围，`GAP-IG3` 保留未决。材料未给任何成本或工期数据，故本案例不给排期与预算。
