# 主数据四平台态：黄金记录先行、运营主控后交

## 决策与原始业务资料

在三个馆的读者数据仍由各自源系统更新的前提下，先让主数据管理承担分析用途，还是直接接管运营写入？

| 证据 ID | 原始材料 |
|---|---|
| `mdm-1` | 试点初期三馆源系统各自更新读者记录，同一读者在不同馆可能是同名不同证，也可能是同一人不同证。 |
| `mdm-2` | 现无可用的统一读者标识；跨馆借阅统计口径不一致，报告需要人工核对。 |
| `mdm-3` | 项目尚未给出主数据治理责任人、授权范围、错合并恢复流程与事件积压监控指标。 |
| `mdm-4` | 借阅交易历史保留其原系统语境，不因主数据统一而改写。 |
| `mdm-5` | 项目未提供日期与成本依据；任何排期与投入均为未知。 |

## 来源规则与项目规则

1. 来源方法（G21B）：把主数据能力分成若干**运营平台态**，每态需分别满足用例、质量、授权、恢复与支持条件；平台态不等同于 ADM 的过渡架构。
2. 来源方法：黄金记录（分析用单一视图）与运营主控（对源系统写入）是两件不同的事，可以分阶段交付。
3. 项目规则：本案例采用"先分析、后运营"的顺序，因为 `mdm-3` 的责任与恢复条件尚不具备。
4. 项目规则：`mdm-4` 的历史交易不改写，历史主数据可形成带生效时间的映射或分析视图，但不得回写历史交易事实；不等于只能处理新主数据记录。
5. 项目规则：无 `mdm-5` 依据时不设日期与预算；缺口写入结果表的"状态"列。

## 转换与推理

1. **识别当前主控**：三个源系统各自对读者记录有写权限，因此当前主控是"多源并行"，不存在单一权威源。
2. **分离两种用途**：分析用途只需要一致视图，运营用途需要唯一写入点。前者不改变源系统，后者必须改变。
3. **列出三个本地候选平台态的五类条件；标题所涉四种参考平台态的逐一映射未完成，不伪造第四个本地状态**：

| 平台态 | 用例 | 质量 | 授权 | 恢复 | 支持 |
| --- | --- | --- | --- | --- | --- |
| P1 仅分析黄金记录 | 跨馆统计可做 | 同名不同证需人工复核 | 只读，不需源系统写授权；仍需读取与分析使用授权 | 丢弃即可重建 | 依赖夜间批处理 |
| P2 内核 CRUD 主控 | 仍需 P1 才可分析 | 需定义内核字段范围 | **缺**（`mdm-3`） | **缺**错合并恢复流程 | 需事件积压监控（**缺**） |
| P3 扩至全馆 | 依赖 P2 完成 | 同上 | 同上 | 同上 | 同上 |

4. **选择演进触发**：P2 的四个缺口未闭合前不进入 P3。触发条件写明为"责任、授权、错合并恢复、积压监控四项均有证据"，而不是"到某日期"。
5. **保留历史语境**：`mdm-4` 的交易历史不参与合并，避免用当前主数据改写过去的事实。

6. **"平台态"与"过渡架构"不是一回事**。来源方法明确：运营平台态是**主数据能力的形态**，不是 ADM 的时间阶段。因此：
   - P1/P2/P3 不是"第一阶段、第二阶段"
   - 它们可以并存（例如 P1 的分析视图在 P2 建立后仍然存在）
   
   把它们读成时间阶段，会导致"P3 完成后 P1 就结束"这类错误推断。

7. **分析用途与运营用途的差别在"写权"**：

| 用途 | 是否需要改源系统 | 核心风险 |
| --- | --- | --- |
| 分析（黄金记录） | 否 | 误合并导致统计错 |
| 运营（内核主控） | **是** | 误合并传播到源系统，难以撤回 |

   风险量级不同，因此**可以分阶段交付**——先做不改变源系统的部分。这是本案例的排序依据，不是保守。

8. **P1 的"丢弃即可重建"是有条件的**。表中说 P1 恢复方式是"丢弃即可重建"。成立前提：
   - 源系统数据完好
   - 重建过程可重复（批处理幂等）
   
   若源数据已被改写（如 P2 已上线），P1 就不能简单重建。

9. **P2 的四个缺口性质各异**。`mdm-3` 列出四项缺失：

| 缺口 | 性质 | 未补齐的后果 |
| --- | --- | --- |
| 治理责任人 | 组织 | 出问题无人决策 |
| 授权范围 | 合规 | 不知道该不该写 |
| 错合并恢复流程 | 技术 + 流程 | 合并错了无法撤回 |
| 事件积压监控 | 运维 | 不知道是否在正常处理 |

   **四项都不补，P2 不能进入运营**；只补其中几项也不行——缺授权仍会越界，缺恢复仍会无法挽回。

10. **触发条件是证据，不是日期**。第 4 步明确 P3 的触发是"四项均有证据"，而非"到某日期"。日期到了但证据没到，就是没到。

## 修改演练

**情景一：补齐四项缺口，P2 可进入运营**。此时黄金记录升级为运营主控，源系统写权收归主数据平台。**但历史交易仍不改写**（`mdm-4`）——统一可改进主数据映射，但不得改写历史交易事实。

**情景二：只补齐授权与责任人，恢复流程仍缺**。P2 **仍不可进入运营**。授权解决"能不能写"，恢复解决"写错了怎么办"；后者缺失意味着每次写入都是单向的。

**情景三：P2 上线后发现批量错合并**。因有恢复流程，可通过映射版本拆分并重指向消费者。**若当初未补恢复流程，应隔离影响并评估备份、映射及消费者恢复，不能断言只能删数据重建**，且无法解释历史报表为何变化。

**情景四：业务方要求"直接上 P3"**。P3 依赖 P2 完成。跳级意味着在无责任、无授权、无恢复、无监控的条件下接管全馆写入。**这不是加速，是把四项风险同时放大到全馆。**

**影响范围**：情景一推进平台态；情景二阻断；情景三验证恢复流程价值；情景四涉及跳级风险。四种情形下"历史交易不改写"与"证据触发而非日期触发"两条规则不变。

## 反例与输入不足

- **错误做法**：把四个平台态画成 ADM 的四个过渡架构。平台态是按主控/分发方式及用例区分的运营状态，不是成熟度等级，过渡架构是按时间排列的架构演进状态，两者不是同一分类轴。预期 `relation-endpoint-type`。
- **错误做法**：黄金记录直接与源系统双向同步。黄金记录是分析用副本，双向同步会让它变成第二个主控，冲突无法裁决。
- **错误做法**：在 `mdm-3` 缺失时给出 P2 上线日期。预期 `missing-evidence`。
- **输入不足**：项目无成本与日期依据（`mdm-5`），因此本案例不产出任何排期或投入结论。
