# 技术与架构债登记：先把债说清，再谈还不还

虚构跨馆借阅试点攒下三笔债：三馆各抄一份身份匹配规则、甲馆还在手工重跑转码脚本、预约状态在两份文档里叫法不一致。本案例演练如何把"技术债"写成可核对的登记项——包括判断它是否真的需要 EA 介入，以及为什么"已排计划"不能关掉一笔债。

所有业务材料、人物、估算与规则均为虚构教学材料（`BR-01`–`BR-20`）；材料**未提供任何损失金额、利率或货币折算规则**。指南只提供方法依据，项目规则不冒充 TOGAF 规定。

方法：`technical-debt-register-method`。来源方法：G217 §2.2–2.3、附录 D.4。
入口：[technical-debt-register-method](../analysis-methods/technical-debt-register-method.md)。
素材：原料（历史材料已清理）、模型（历史材料已清理）。

## 决策与原始业务资料

要回答：**这三笔债分别是什么、影响谁、该由谁处理、怎么才算还完？**

| 证据 ID | 原始材料 |
|---|---|
| `BR-15` | 债务 `DEBT-01`：三系统各自复制姓名匹配规则且责任不清；同名读者有被误关联的风险。影响跨馆借阅与身份管理**两个产品范围**，需要 EA 协调语义与责任；偿还候选是统一最小规则与人工复核接口，对应身份规则待办。 |
| `BR-16` | 债务 `DEBT-02`：单馆报表仍使用过期 CSV 转码脚本；运行人员每周手工重跑一次。影响**仅甲馆报表**，暂无跨产品影响证据，由该产品团队处理即可；候选改动是补自动转码校验，**估算未知**。 |
| `BR-17` | 债务 `DEBT-03`：预约状态接口在两份文档中命名不一致，令消费者重复编写映射。需接口团队与业务共同统一词汇；候选偿还对应 API 契约待办。**未提供损失金额、利率或任何货币折算规则**。 |
| `BR-20` | 本例**关闭债务的项目规则**：需记录**修复交付引用、验证证据和责任人复核结论**；仅"已排计划"或"工时已消耗"**不能关闭**。 |
| `BR-18` | 修改试验：`DEBT-03` 的两个消费者回归结果 `TEST-03` 表明映射一致，可按本例关闭规则关闭该债项。 |

## 来源规则与项目规则

1. **来源方法（G217 §2.2–2.3、附录 D.4）**：技术债登记需区分债务种类、受影响范围、成因与后果；不同种类的债由不同层级处理，不是所有债都归 EA。
2. **来源方法**：偿还选项应指向具体的待办或交付，而不是"重构一下"这类无法验收的动作。
3. **来源方法**：债务的量化需有可追溯的度量基础；无基础时保持未知，不以类比数字填充。
4. **项目规则（`BR-20`）**：关闭必须同时具备**修复交付引用 + 验证证据 + 责任人复核结论**三项。缺一项不得关闭。
5. **项目规则**：`ea_involvement` 分 `cross-product-coordination` 与 `local-product-team` 两值，判定依据是**是否存在跨产品影响证据**，不是债务金额大小（`BR-15`/`BR-16` 对比即此规则）。
6. **项目规则**：无货币折算规则时 `cost_or_interest` 写 `unknown` 并注明理由，**不得**用"每周重跑一次 × 人力单价"倒推金额（`BR-16` 明示"工时和损失金额未知"）。

## 转换与推理

1. **逐笔写清四要素**：种类（kind）、受影响产品（affected_products）、成因（cause）、后果（consequence）。`DEBT-01` 为 `architecture-and-data-semantics`，影响 `["跨馆借阅","身份管理"]`；`DEBT-02` 为 `technical-local`，影响 `["甲馆报表"]`；`DEBT-03` 为 `architecture-interface`，影响 `["预约服务","两馆消费者"]`。

2. **EA 介入与否是判断题，不是金额题**。`DEBT-01` 影响两个产品、三馆语义不一致 ⇒ `cross-product-coordination`，理由写"需要跨两个产品与三馆统一语义/责任"。`DEBT-02` 只影响甲馆报表、无跨产品证据 ⇒ `local-product-team`，理由写"暂无跨产品影响证据；不要求 EA 处理所有债务"。**这条理由本身就是方法要点**：把局部债上收会挤占跨产品协调能力。

3. **偿还选项必须可验收**。`DEBT-01` 偿还选项"统一最小身份规则及人工复核接口"，并 `backlog_refs=[BL-01]`。`DEBT-03` 偿还选项"统一状态词汇并验证两个消费者映射"，`backlog_refs=[BL-02]`。`DEBT-02` 偿还选项"补自动转码校验，估算待定"，`backlog_refs=[]`——因为它还没进待办，这个空列表是**明确事实**而非缺失。

4. **三笔债一律 `not-closed`**。`verification_evidence` 均为 `[]`，`closure_decision` 均为 `not-closed`。这不是保守，而是 `BR-20` 的直接推论：没有验证证据，关闭条件不成立，哪怕 `DEBT-01`、`DEBT-03` 状态是 `selected`（已选中偿还）。

5. **成本一律未知**。`DEBT-01.cost_or_interest` 写"unknown；无货币公式/利率来源"；`DEBT-02` 写"unknown；不能把重跑次数直接当金额"；`DEBT-03` 写"unknown；未计算利息或折现"。三笔债都写 unknown，是因为材料确实没有给，**不是懒得算**。

6. **修改后只关一笔**。`BR-18` 给 `DEBT-03` 的 `TEST-03`（两个消费者回归）⇒ 具备"验证证据"；若同时具备修复交付引用（`BL-02` 契约更新）与责任人（接口负责人）复核结论，则 `DEBT-03` 可 `closed`。`DEBT-01`、`DEBT-02` 无新证据，仍 `not-closed`。

7. **关闭不等于问题消失**。`DEBT-03` 关闭后，其 `history` 追加关闭记录，但条目仍留在登记表——债务登记是账本，不是待办清单，已关闭项保留以供追溯。

## 债登记的四要素与三条判据

每一笔债必须写清四要素，缺一即无法排序或偿还：

| 要素 | 回答什么 | 本案实例 |
| --- | --- | --- |
| 种类 | 是什么类型的债 | `architecture-and-data-semantics` |
| 受影响范围 | 哪些产品/系统 | `["跨馆借阅","身份管理"]` |
| 成因 | 为什么形成 | 三系统复制规则且责任不清 |
| 后果 | 不还会怎样 | 同名误关联与复核责任缺失 |

**EA 介入的三条判据**（按顺序判断）：

1. **是否存在跨产品影响证据**？有 ⇒ `cross-product-coordination`；无 ⇒ `local-product-team`
2. **是否需要统一语义或责任**？需要 ⇒ 需 EA 协调
3. **金额是否可算**？——**不参与判断**。金额大小与"该不该 EA 管"无关

第三条最容易被违反：债务金额大就往上报，金额小就让产品团队自己处理。本案 `DEBT-02` 只影响甲馆报表，即使金额未知也应由产品团队处理。

## 关闭条件的三项构成

`BR-20` 要求三项齐备才能关闭，三者性质不同：

| 条件 | 证明什么 | 缺了会怎样 |
| --- | --- | --- |
| 修复交付引用 | 确实做了什么 | 无法确认修复已实施 |
| 验证证据 | 修复确实有效 | 无法确认问题已消失 |
| 责任人复核结论 | 有人为结果负责 | 无人对"关得对不对"负责 |

**"已排计划"与"工时已消耗"都不属于上述任何一项**。前者是意图，后者是投入——两者都不证明结果。

## 修改演练

改动一处输入：`BR-18` 声明 `TEST-03` 表明 `DEBT-03` 的两个消费者映射一致。

变化链条：
- `DEBT-03.verification_evidence`：`[]` → `["TEST-03"]`。
- `DEBT-03.closure_decision`：`not-closed` → `closed`（前提是同时存在修复交付引用 `BL-02` 与接口负责人复核结论，三者齐备才成立）。
- `DEBT-03.status`：`selected` → `closed`。
- 影响视图：`v-technical-debt-register-default` 的 `DEBT-03` 行与关系表；`DEBT-01`、`DEBT-02` 不变。

**若只有 `TEST-03` 而无修复交付引用**：仍不能关闭。此时应写 `closure_decision=not-closed` 并在缺口里注明"缺交付引用"。这条分支最能检验规则是否真被执行——有测试通过很容易让人直接关账。

反向演练：若 DEBT-02 新增有来源的"每周重跑1次、每次2小时、内部费率300元/小时"，可先算每周估算人工成本600元；另显式假设52周且频次/费率不变，可算年情景31200元。不得把情景当实际损失或债务利息。原BR-16仍不足以单独支持金额，但新增证据不能被旧未知否决。

## 反例与输入不足

- **错误做法**：`DEBT-01` 因"已进 `BL-01` 待办"就标 `closed`。排计划不是修复。预期 `debt-closure-without-evidence`。
- **错误做法**：`DEBT-02` 的 `cost_or_interest` 写"约 1.5 万元/年"，由重跑次数倒推。预期 `measurement-basis-gap`。
- **错误做法**：把 `DEBT-02` 也标为 `cross-product-coordination`，理由是"统一管理更规范"。无跨产品证据即上收，违反 `BR-16` 的判定依据。预期 `missing-evidence`。
- **错误做法**：`DEBT-03` 的 `verification_evidence` 填 `["TEST-03"]` 但 `TEST-03` 不在任何证据清单中。悬空引用。预期 `dangling-reference`。
- **错误做法**：三笔债共用一个 `DEBT-01` ID（复制粘贴未改）。预期 `duplicate-id`。
- **错误做法**：登记表省略 `closure_criteria`，只留 `status`。没有关闭标准的登记表无法判断"还完了没有"。预期 `unrepresented-attribute`。

**输入不足**：`BR-15` 未给 `DEBT-01` 的误关联发生率；`BR-16` 未给单次重跑耗时；`BR-17` 未给消费者重复映射的维护工时。三项缺口在 `TDR-GAP-1`/`TDR-GAP-2` 中列出，**不以行业均值填充**。

## 评审记录

- 核对三笔债四要素（种类/范围/成因/后果）逐项有原文依据。
- 核对 EA 介入判定依据为跨产品影响证据，未按金额或"规范统一"上收。
- 核对偿还选项均可验收，且 `backlog_refs` 明确（含明确为空）。
- 核对三笔债默认 `not-closed`，未因"已排计划"或"已选中"而关闭。
- 核对成本字段一律 `unknown` 并附理由，全表无金额、无利率、无折现。
- 核对修改后仅 `DEBT-03` 具备关闭条件，且三条件齐备的判定被显式写出。
- 核对关闭项保留在登记表中，历史可追。
- 核对两项缺口保留，未被均值或类比数字填补。
