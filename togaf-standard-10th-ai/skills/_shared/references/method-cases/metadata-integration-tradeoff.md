## 决策与原始业务资料

为财务术语、数据库模式与运营日志配置可维护的元数据方案。

|证据 ID|原始材料|
|---|---|
|mi-1|财务团队愿在新库维护正式术语；数据库模式必须继续由迁移工具主控；运营日志由监控平台维护。|
|mi-2|迁移工具可在DDL发布后推送schema JSON，监控平台仅提供每日导出；生产数据库禁止安装扫描代理，允许读取受控模式副本。|
|mi-3|方案约定：财务术语发布须双人复核；模式变更15分钟内可见；运营日志日级同步足够。未确认第三方许可成本。|

## 来源规则与项目规则

1. **来源方法（G234）**：集中式 Consolidation 保存外部副本；Hybrid 在部分范围库内主控；Unified 把完整维护与校验统一。三种组织方式**独立于**手工/推送/拉取这类同步机制。
2. **来源方法**：参考模型的分类不等于本项目已部署的结构；不得用错置的 G234 图 4-4 充当结构证据。
3. **项目规则**：权限与时效要求来自 `mi-2`（生产禁装扫描代理、允许读受控副本）与 `mi-3`（模式 15 分钟内可见、日志日级同步），为本例项目约定。
4. **项目规则**：不把"拉取"等同于数据反向传播；推送失败不等于目标已接受数据。

**来源依据**：`references/capability-addenda/metadata-integration-tradeoff.md`。

## 转换与推理

1. **先分清两个独立维度**。G234 的组织方式（主控在哪）与同步机制（数据怎么来）**不是一回事**：

   | 维度 | 取值 | 决定什么 |
   | --- | --- | --- |
   | 组织方式 | Consolidation / Hybrid / Unified | **谁有权威副本、谁做校验** |
   | 同步机制 | 手工 / 推送 / 拉取 | **数据经什么路径到达** |

   把"统一式"与"拉取式"当作同一条轴上的两个取值，是本方法最常见的第一类错误。**任一组织方式都可以配任一同步机制**，组合起来才是方案。

2. **主控权比较逐个排除**：
   - 纯 Consolidation：术语需在**库内维护**（`mi-1` 财务团队意愿），而 Consolidation 只保存外部副本 ⇒ 不满足
   - Unified：要求数据库与监控工具**都改由元数据库主控**，违反 `mi-1` 的"数据库模式必须继续由迁移工具主控" ⇒ 不满足
   - Hybrid：分域主控（财务术语库内主控，技术与运营元数据留在原工具）⇒ 满足 ⇒ 形成候选

   **排除是逐条对照约束完成的，不是按"先进程度"排序**。

3. **逐源选择同步机制，每个源单独判定**：
   | 元数据源 | 机制 | 依据 |
   | --- | --- | --- |
   | 数据库模式 | DDL 工具**推送**（15 分钟内可见） | `mi-2` 允许推送、`mi-3` 要求 15 分钟 |
   | 运营日志 | **手工**日级上传 | `mi-2` 只有每日导出（导出文件可手工也可自动接入，需另行确认）、`mi-3` 日级足够 |
   | 生产库安装扫描代理直采 | **不可行** | `mi-2` 禁装代理；不等于禁止所有无代理读取，其他方式需另取授权 |

   注意：日志用"手工"**不是技术落后**，而是 `mi-2` 只提供日级导出，且 `mi-3` 已声明日级足够。**不因偏好自动化而绕过生产限制。**

4. **方向必须分开记录，不同机制发起方不同，但元数据载荷均由源到目标**：
   - 推送：工具 → 元数据库（源主动）
   - 手工：人员导出 → 校验 → 入库（人参与，中间有校验点）
   - 拉取（候选）：元数据库发起请求 → 受控副本返回（目标主动）

   三条路径**发起方式不同；拉取的请求是目标→源，返回载荷仍是源→目标**。把它们画成一条无向线，会丢失"谁发起、失败算谁的"这两个关键信息。

5. **契约要素**。每个同步通道需约定：来源系统 ID、版本、事件 ID、时间戳、完整性校验、重试去重、错误归属、回退到上一个已发布版本。**"错误归属"尤其重要**——推送失败是源的责任还是目标的责任，决定了排障方向。

6. **成本未确认，不给总体最优**。`mi-3` 明说第三方许可成本未确认。因此 `OPT-MI` 只能是"待成本确认"的候选，不能宣布"Hybrid 是总体最优方案"。

## 修改演练

**情景一：监控平台增加事件推送，且许可可接受**。`ING-LOG` 从手工改为 push，时效可从日级收紧。**但 `OPT-MI` 的 Hybrid 主控方式不变**——采集自动化不改变"谁有权威副本"。这正是两个维度独立的意义：只动一个维度时，另一个不必跟着变。

**情景二：生产环境禁止读取任何副本**。`ING-PULL` 候选被删除，并登记能力缺口（仅副本拉取路径受阻；mi-2 的 DDL 推送未因此失效，不能说该源全部无法集成）。**不能**改成"先画一条虚线日后再说"。

**情景三：财务团队改为接受 Consolidation**。此时纯 Consolidation 重新成为候选，与 Hybrid 同台比较。**排除理由消失，方案就要重新进入比较**，不能沿用原结论。

**影响范围**：情景一改 `ING-LOG` 的机制与时效；情景二删除 `ING-PULL` 并新增缺口；情景三使 `OPT-EXCL` 的排除失效。三种情形下 `DIR-1` 的方向记录规则不变。

## 反例与输入不足

- **错误做法**：把"统一式"与"拉取式"当成同一个维度上的两个取值。二者分属不同维度。预期 `undefined-entity-type`（分类维度被混用）。
- **错误做法**：生产环境禁止安装扫描代理，却仍画一条 pull 箭头表示实时同步。不可画基于被禁代理的直采；受控副本拉取仍可列待评估，不能把所有 pull 都视为禁止。预期 `missing-evidence`。
- **错误做法**：推送成功即认为目标已接受数据。投递与接收是两件事。预期 `measurement-evidence-gap`。
- **错误做法**：因为偏好自动化，就为运营日志也设计推送方案，忽略 `mi-2` 只提供每日导出。预期 `approval-without-evidence`。
- **错误做法**：把三条采集路径画成一条无向线，不区分发起方。失败归属将无法判定。预期 `relation-endpoint-type`。
- **错误做法**：在许可成本未确认时宣布"Hybrid 总成本最低"。成本数据缺失。预期 `measurement-basis-gap`。

**输入不足**：材料未给第三方许可成本，本案例不比较方案总成本。`mi-2` 未说明受控模式副本的更新频率，故 `ING-PULL` 无法评估时效。材料未给日志量级，`ING-LOG` 的人工上传工作量不可估算。

## 评审记录

- 核对三种组织方式（Consolidation/Hybrid/Unified）与三种同步机制（手工/推送/拉取）被当作两个独立维度。
- 核对排除 Consolidation 与 Unified 时各自引用了 `mi-1` 的具体约束，不是按先进程度排序。
- 核对每个元数据源的同步机制单独判定，未一刀切。
- 核对生产环境"禁止安装扫描代理"的约束未被画成一条 pull 箭头绕过。
- 核对三条采集路径的发起方与方向分别记录，未合并为无向线。
- 核对推送成功与目标已接受数据被区分，未以后者作为前者结论。
- 核对契约包含错误归属与回退版本，不只是技术字段。
- 核对权限与时效要求可追到 `mi-2`/`mi-3`，未被表述为来源默认值。
- 核对第三方许可成本未确认时未给出总成本结论。
- 核对三项修改情景分别说明"只动一个维度"与"两个维度联动"的差别。
