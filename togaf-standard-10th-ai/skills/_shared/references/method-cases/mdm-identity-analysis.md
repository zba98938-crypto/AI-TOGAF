# 在同名客户和不同联系方式中保持身份来历

所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充TOGAF规定。案例完整演练不等于独立业务评审通过。

方法：`mdm-identity-analysis`。来源方法：G21B §4–5、附录B。
入口：[mdm-identity-analysis](../analysis-methods/mdm-identity-analysis.md)。

## 决策与原始业务资料

建立可追溯客户主视图，避免错误合并个人记录。

|证据 ID|原始材料|
|---|---|
|mdm-1|CRM记录CRM-42：李宁，联系方式尾号0101，外部会员标识M-908；电商记录WEB-8：李宁，尾号0101，会员标识缺失；CRM-77：李宁，尾号0202，会员标识M-991。|
|mdm-2|客服核实WEB-8与CRM-42属于同一自然人，依据已核验会员M-908；WEB-8原手机号为家庭共用。没有证据表明CRM-77相同。|
|mdm-3|项目约定：已核验会员ID相同可自动匹配；姓名+电话只生成候选，需管家复核；电商同意只限服务通知，CRM营销同意已撤销。旧应用暂不能直接改由MDM主写。|

## 来源规则与项目规则

1. **来源方法**：区分自然人/组织、身份标识、联系方式、同意以及主控/消费关系；匹配与合并是独立于这些分类的决策。
2. **来源方法**：合并须保留原记录 ID、核验依据、版本与合并/拆分历史，使合并可回溯、可撤销。
3. **项目规则**：本案的匹配规则（已核验会员 ID 相同才自动匹配；姓名+电话只生成候选）是**项目约定**。
4. **项目规则**：不同目的的同意**不得取并集**；电商仅同意服务通知时，不得用 CRM 的营销同意扩大其用途。

**来源依据**：`references/capability-addenda/mdm-identity-analysis.md`。

## 转换与推理

1. **先看三条记录，逐字段比对**：

   | 记录 | 姓名 | 电话尾号 | 会员标识 | 判定 |
   | --- | --- | --- | --- | --- |
   | `CRM-42` | 李宁 | 0101 | `M-908` | 与 `WEB-8` 同人 |
   | `WEB-8` | 李宁 | 0101 | **缺失** | 与 `CRM-42` 同人 |
   | `CRM-77` | 李宁 | 0202 | `M-991` | **独立** |

   **三条记录姓名完全相同**。若按姓名合并，会得到一个人；这是最危险的做法。

2. **匹配依据必须是可核验的个体级证据**。`mdm-2` 说客服核实 `WEB-8` 与 `CRM-42` 属于同一自然人，**依据是已核验会员 `M-908`**。关键点：
   - 依据是 `M-908` 这个已核验标识
   - **不是**共用电话（`mdm-2` 明说 `WEB-8` 原手机号是家庭共用）
   - 也不是姓名

   `CRM-77` 的 `M-991` 与 `M-908` 不同，且无其他证据 ⇒ **不合并**。

3. **"未合并"不等于"确认不是同一人"**。材料没有证据表明 `CRM-77` 与另两条相同，也**没有证据表明不同**。因此 `PERSON-2` 的状态是"保持独立"，**不是"已确认不同人"**。这个区别在后续若有新证据时可以翻转。

4. **标识必须带命名空间**。三个系统的数字标识不能直接比较：
   - `member:M-908`（会员体系）
   - `crm:42`（CRM 内部 ID）
   - `web:8`（电商内部 ID）
   
   若不带命名空间，"`8`"在电商是记录号、在会员体系可能是别的含义。**不同系统的同形数字不是同一标识。**

5. **同意按目的分别记录，不做并集**。`mdm-3`：电商同意**仅限服务通知**，CRM 营销同意**已撤销**。因此：
   - 服务通知：允许
   - 营销触达：**拒绝**
   
   **不能合成"同意=true"**——那会让营销触达借用服务通知的同意。这是合规上的实质差别，不是字段设计偏好。

6. **主控方式受现状约束**。`mdm-3` 说"旧应用暂不能直接改由 MDM 主写"。因此本案只能声明**下游 Consolidation**（保存副本供分析），不能声称已实现集中主控。若要向来源分发主 ID，需评估 Cooperation 模式及冲突工作流——**这是下一阶段的事，不是本阶段已完成的事**。

7. **合并必须可撤回**。维护 `source_record → person` 映射，带 `effective_from` 与 `version`。错误合并时通过**新增映射版本**拆分，**不删除原始记录**——删除会让"曾经合并过"这段历史消失，后续无法解释为何报表数字变过。

## 修改演练

**情景一：核验发现 `WEB-8` 属于另一家庭成员**。处置：
- **撤回** `PERSON-1` 的映射版本（新增一条版本记录，`effective_from` 为更正日）
- 新建 `PERSON-3` 承载 `WEB-8`
- 传播更正到依赖报表并重新核算
- **同意不随原合并迁移**——`WEB-8` 的服务通知同意属于该家庭成员，不自动转给 `PERSON-1`

  稳定来源 ID 仍保留，`CRM-42` 与 `WEB-8` 的记录不被删除。

**情景二：`CRM-77` 出现新证据表明是同一人**。`PERSON-2` 从"独立"转为与 `PERSON-1` 合并（或反之，取决于证据方向）。这印证了"未合并 ≠ 确认不同"的表述价值。

**情景三：旧应用改造完成，可改由 MDM 主写**。此时可评估 Cooperation 模式及冲突工作流，`STYLE-1` 从"下游 Consolidation"升级为"集中主控候选"。**但仍需契约与治理到位**，改造完成只是必要条件。

**影响范围**：情景一撤回映射并新增 person，影响下游报表；情景二关闭 `GAP-MDM`；情景三改变主控方式但需额外治理。三种情形下"同意按目的分别"的规则不变。

## 反例与输入不足

- **错误做法**：因姓名相同且共用家庭电话就自动合并两条客户记录。同名同号可碰撞。预期 `missing-evidence`（无个体级证据即不得合并）。
- **错误做法**：无证据地采用相似度 0.8 作为自动合并阈值。阈值与证据都不是材料给的。预期 `measurement-evidence-gap`。
- **错误做法**：把 G21B 的 Centralized 主控含义与 G234 元数据 Consolidation 的中文"集中式"互换使用。同名不同义。预期 `core-vocabulary-override`。
- **错误做法**：把 `PERSON-2` 标为"已确认不同人"。材料只支持"未合并"，不支持"已排除"。预期 `missing-evidence`。
- **错误做法**：把 `web:8` 与会员体系的数字 8 当作同一标识。不同系统的同形数字不互认。预期 `duplicate-id`。
- **错误做法**：把服务通知同意用于营销触达。`mdm-3` 明说营销同意已撤销。预期 `approval-without-evidence`。
- **错误做法**：错误合并后直接删除 `WEB-8` 原始记录以"清理"。删除会让合并历史消失。预期 `dangling-reference`。

**输入不足**：材料未给 `CRM-77` 与另两条记录的关系证据，因此 `CRM-77` 保持独立，既不合并也不排除（`GAP-MDM`）。`mdm-2` 未说明核验的执行人与核验时间，`MATCH-1` 只能引用"客服核实"这一表述。材料未给同意记录的存储形式，故不判断其技术实现。

## 评审记录

- 核对 `PERSON-1` 的匹配依据是 `mdm-2` 的客服核验记录（已核验会员 M-908），**不是**共用家庭电话。
- 核对 `PERSON-2`（`CRM-77`）保持未合并，姓名相同不构成合并证据，也未反向排除其可能性。
- 核对三条记录的同名字段被显式指出，未因姓名相同而合并。
- 核对标识使用命名空间（`member:`/`crm:`/`web:`），不同系统的数字 8 未被当作同一 ID。
- 核对同意按目的分别记录，服务通知与营销拒绝未被合成一个"同意=true"。
- 核对主控/消费方向与 `mdm-3` 的"旧应用暂不能改由 MDM 主写"一致，本案只声明下游 Consolidation。
- 核对 `source_record → person` 映射保留 `effective_from`/`version`，错误合并可通过版本拆分撤回而非删除原始记录。
- 核对本案未声称已形成运营单一真相；该结论需契约与治理到位后另行判定。
- 核对三项修改情景分别说明"撤回"与"升级"的不同处置。
