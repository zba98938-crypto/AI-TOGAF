# 将政府参考分类映射到市民预约服务而不制造事实

所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充TOGAF规定。案例完整演练不等于独立业务评审通过。

方法：`reference-model-tailoring`。来源方法：G21D §1；G21H §6；G248 §2。
入口：[reference-model-tailoring](../analysis-methods/reference-model-tailoring.md)。

## 决策与原始业务资料

为市民服务预约项目裁剪参考分类，识别本地职责与范围缺口。

|证据 ID|原始材料|
|---|---|
|ref-1|本地范围：市民预约、材料提交、资格审核和结果通知；支付由其他项目承担，国防事务不属于本机构。|
|ref-2|机构职责：服务窗口受理，业务部门审批，共享技术团队维护门户和身份服务；没有独立名为‘数字政府域’的组织。|
|ref-3|架构工作坊要求对照政府服务/业务/信息/技术等参考分类识别遗漏；所用本地参考版本记录为G21D、G21H及G248，不能混作一个官方统一层级。|

## 来源规则与项目规则

1. **来源方法（G21D、G21H、G248）**：提供不同目的的参考模型；使用前须核对适用范围，并保留原 ID 与版本。
2. **来源方法**：参考分类**不是**已部署组织、技术或已获授权的证明；未找到本地对应项不等于不适用。
3. **项目规则**：每个参考条目须标记采用、重命名、部分适用、不适用或待调查，并给出业务理由——这是本案例的项目约定。
4. **项目规则**：本地参考版本混用 G21D、G21H 与 G248 时，**不得**当作一个官方统一层级合并映射。

**来源依据**：`references/capability-addenda/reference-model-tailoring.md`。

## 转换与推理

1. **先立本地功能，再谈映射**。从 `ref-1` 提取四个本地功能：`LF-1` 预约、`LF-2` 材料受理、`LF-3` 资格审核、`LF-4` 结果通知。**本地功能是映射的锚**——先有本地事实，再去参考模型找对应项；反过来会变成"按参考模型重造业务"。

2. **映射表保留两侧身份**。每条映射同时记录 `reference_model`、`reference_item` 与本地功能 ID，**不覆盖本地 ID**。本地 ID 是组织的事实标识，参考 ID 是分类位置；两者的生命周期不同，混成一个会丢失溯源。

3. **五种裁剪标记，各有适用情形**。这是本方法的核心动作：

   | 标记 | 本案实例 | 依据 |
   | --- | --- | --- |
   | 采用 | `LF-1`/`LF-2` → 窗口与门户 | `ref-2` |
   | 采用 | `LF-3` → 业务审批部门 | `ref-2` |
   | 采用 | `LF-4` → 通知服务 | `ref-2` |
   | 部分适用 | 支付：范围外但存在跨项目依赖 | `ref-1` |
   | 不适用 | 国防事务：不属于本机构 | `ref-1` |
   | 待调查 | 共享安全治理：尚未调查 | `ref-2` |

   **"部分适用"与"不适用"是不同的**：支付虽不在本项目范围，但接口关注点不能删；国防事务是本机构职责外，可判不适用。

4. **"待调查"是最容易被滥用的标记**。`ref-2` 提到共享技术团队维护门户与身份服务，但**共享安全治理职责未调查**。此时只能标"待调查"，**不能标"不适用"**——两者差别在于：前者承认有未知，后者断言没有。

5. **参考域不得创建为组织**。`ref-2` 明说"没有独立名为'数字政府域'的组织"。因此映射只能落在既有组织（服务窗口、业务部门、共享技术团队）上，**不能因为参考模型里有某个"域"就虚构一个部门**。

6. **三个参考模型不合并成一个层级**。`ref-3` 记录本地参考版本为 G21D、G21H 与 G248，并明确"不能混作一个官方统一层级"。因此映射表要标明每条映射来自哪个模型，**不构造一个跨模型的统一层级树**。

7. **映射结果交两类人确认**：业务负责人确认职责归属（谁该做这件事），技术负责人确认现状（现在是谁在做）。**两类确认不能互相替代**。

## 修改演练

**情景一：项目新增在线缴费**。支付从"部分适用（范围外）"改为"适用"，新增本地功能 `LF-5` 在线缴费并绑定权威来源。**原裁剪记录保留历史版本**——不是改原记录，而是新增一条带日期的变更。

**情景二：参考模型版本升级（如 G21D 新版）**。逐项差异评估：哪些条目的 ID 变了、哪些含义变了、哪些新增。**不以新标签覆盖旧映射**——覆盖会让"当初为什么这样裁"无法复原。

**情景三：共享安全治理经调查确认由某部门承担**。"待调查"改为"采用"并补映射。若确认无人承担，仍需区分"职责存在但无人承担"与"机构不需该职责"：前者登记治理责任缺口，只有后者有职责依据时才可判不适用——**两种结果都需要调查证据**，不能靠推测。

**情景四：业务方要求"按参考模型重组部门"**。这超出了本方法范围。参考模型是分类工具，不是组织设计依据；此类要求应转到组织变革流程，**不在裁剪记录里执行**。

**影响范围**：情景一新增本地功能与变更记录；情景二逐项重评但不覆盖旧版；情景三关闭或转化一项待调查；情景四属于范围外请求。

## 五种裁剪标记的适用条件

- 采用：本地有对应且可映射
- 重命名：本地叫法不同但职责一致
- 部分适用：范围外但有依赖（如支付）
- 不适用：有职责依据说明不需要（如国防）
- 待调查：尚未查清，不得当作不适用

## 反例与输入不足

- **错误做法**：把 DBRM 四参考域直接等同 TOGAF 四架构域。两套分类不同源。预期 `core-vocabulary-override`。
- **错误做法**：把参考服务框当作现有部门或已部署事实。参考结构不是组织事实。预期 `undefined-entity-type`。
- **错误做法**：本地没有找到对应项就判定"不适用"。未找到不等于不适用。预期 `missing-evidence`。
- **错误做法**：因参考模型有"数字政府域"，就虚构一个同名部门承接职责。参考分类不创造组织。预期 `undefined-entity-type`。
- **错误做法**：把支付标为"不适用"并从模型中删除，连同其跨项目接口关注点一并去掉。范围外不等于无依赖。预期 `dangling-reference`。
- **错误做法**：把 G21D、G21H、G248 的条目混编成一棵统一层级树。`ref-3` 明示不可混作官方统一层级。预期 `core-vocabulary-override`。
- **错误做法**：把未调查项一律标"不适用"以让映射表"完整"。待调查与不适用语义不同。预期 `missing-evidence`。

**输入不足**：本地参考版本混用 G21D、G21H 与 G248，材料明示不能当作一个官方统一层级，因此本案例不给出统一层级映射（`GAP-REF2`）。`ref-2` 未说明共享安全治理的调查责任人与时限，`GAP-REF` 无法排期。材料未给参考模型的完整条目清单，故不判断"是否有遗漏条目"。

## 评审记录

- 核对每个参考条目都带有采用/重命名/部分适用/不适用/待调查的标记与业务理由，未留空白。
- 核对本地功能先于映射建立，四个功能均可追到 `ref-1`。
- 核对映射设计要求保留双侧ID；本案表仅展开本地功能/职责，具体参考条目ID尚待补，未声称完整参考映射已完成。
- 核对参考分类未被当作已部署组织：本地没有名为"数字政府域"的部门，也未据此虚构一个。
- 核对"部分适用"（支付）与"不适用"（国防）被区分，支付接口关注点未被删除。
- 核对未找到本地对应项时先记待调查；只有有职责依据才判不适用，不默认不适用或已具备。
- 核对不同参考模型（G21D、G21H、G248）各自保留原 ID 与版本，未被合并成单一官方层级。
- 核对裁剪记录保留历史版本，未被新标签覆盖旧映射。
- 核对映射结果分别交业务负责人与技术负责人确认，两类确认未互相替代。
- 核对四项修改情景分别说明影响范围与不变项。
