# BI 需求来源边界：译者示例不是标准需求

所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充 TOGAF 规定。案例完整演练不等于独立业务评审通过。

入口：[bi-requirement-origin-boundary-method](../analysis-methods/bi-requirement-origin-boundary-method.md)。

## 决策与原始业务资料

审计血缘需求 R1 是项目需求还是标准需求？能否声称需求全集完整？

| 证据 ID | 原始材料 |
|---|---|
| `bir-1` | 业务方提出审计血缘需求 `R1`。 |
| `bir-2` | 分析师另看到中文 G238 的 `R-13` 漂移示例。 |
| `bir-3` | 该节**明确 16 例由译者按功能补写**，完整原文需求另附电子表格且**本地未找到**。 |
| `bir-4` | 因此 `R1` 属项目需求，`R-13` 属本地示例。 |
| `bir-5` | 二者均**不能**用官方需求 ID，也不能声称需求全集完整。 |

## 来源规则与项目规则

1. 来源方法（G238）：需求需标注来源，区分标准要求、项目需求与示例。
2. 来源方法：需求全集需有权威清单支撑，缺清单时不得声称完整。
3. 项目规则：**译者补写的示例不具标准身份**（`bir-3`/`bir-4`）；引用时必须标"本地示例"。
4. 项目规则：因原文需求表未找到（`bir-3`），任何"全集完整"声明均为越界。

## 转换与推理

1. **三项来源分类**：

| 项 | 来源 | 身份 | 可否用官方 ID |
| --- | --- | --- | --- |
| `R1` 审计血缘 | 业务方提出 | 项目需求 | 否 |
| `R-13` 漂移示例 | 中文译本节 | 本地示例 | **否** |
| 其余 15 例（16 例中已含 R-13） | 译者按功能补写 | 本地示例 | **否** |

2. **为何不能用官方 ID**：`bir-5` 明确禁止。官方 ID 意味着该需求出自标准正文，而 `R-13` 出自译者补写，二者性质不同。
3. **为何不能说全集完整**：`bir-3` 说明原文需求表本地未找到。没有权威清单时，只能说"本项目识别到的需求"，不能说"全部需求"。
4. **R1 的处理**：作为项目需求，需给出验收准则与关注点映射，但不引用标准章节号作为依据——除非能定位到具体条款。

5. **四种"来源身份"必须分开，因为它们决定可信度**：

| 身份 | 依据来自哪里 | 可用于什么 | 不可用于什么 |
| --- | --- | --- | --- |
| 标准正文条款 | 指南正文 | 作为合规依据、可引用章节号 | 不可外推到未列场景 |
| 译本补写示例 | 译者按功能补写 | 作为理解参考 | **不可引用官方 ID、不可称标准要求** |
| 业务方提出的需求 | 本项目干系人 | 作为项目需求，需验收准则 | 不可冒称标准要求 |
| 项目自定规则 | 本项目决定 | 作为项目约定 | 不可写成 TOGAF 规定 |

   `bir-5` 禁止的是**第二类冒用第一类身份**，不是禁止使用本地示例。

6. **"完整性"是三类不同的断言，只有一类可声称**：
   - "这是本标准列出的全部需求" —— **不可声称**（`bir-3` 说原文需求表本地未找到）
   - "这是本项目识别到的需求" —— **可声称**
   - "这是本项目的需求全集" —— **不可声称**（除非有权威清单比对）

   材料缺的是第二类到第三类之间的那一步：**没有权威清单，就无法证明没漏**。

7. **`R1` 的处置体现"需求可成立但依据不可冒称"**。`R1` 审计血缘是业务方提出的真实需求，可给验收准则与关注点映射；但其依据只能写"业务方要求"，不能写"依据 GB/T 某某第 X 条"——**除非真能定位到具体条款**。这是本案例的核心分寸。

8. **为什么这条规则重要**。若把译本示例当标准要求写进架构契约，后续审计时无法举证；若把业务需求写成标准要求，会在争议时失去立场。**身份标注不是形式主义，是争议时的举证基础。**

## 需求来源的四种身份对照

| 身份 | 出处 | 可用作 | 不可用作 |
| --- | --- | --- | --- |
| 标准正文条款 | 指南正文 | 合规依据、可引章节 | 外推到未列场景 |
| 译本补写示例 | 译者按功能补写 | 理解参考 | 引官方 ID、称标准要求 |
| 业务方需求 | 本项目干系人 | 项目需求（需验收准则） | 冒称标准要求 |
| 项目自定规则 | 本项目决定 | 项目约定 | 写成 TOGAF 规定 |

`bir-5` 禁止的是**第二类冒用第一类身份**，不是禁止使用本地示例。身份标注是争议时的举证基础。

## 完整性断言的三档

| 断言 | 可否声称 | 依据 |
| --- | --- | --- |
| "这是标准列出的全部需求" | **不可** | 原文需求表本地未找到 |
| "这是本项目识别到的需求" | 可 | 有识别记录 |
| "这是本项目的需求全集" | **不可** | 无权威清单可比对 |

材料缺的是第二档到第三档之间的那一步：**没有权威清单，就无法证明没漏**。

## 修改演练

**情景一：取得原文需求电子表格**。`BIR-GAP-1` 关闭，此时可建立标准需求清单并与 `R1` 比对，判断 `R1` 是否与某条标准需求重复或冲突。**但**：取得表格不等于逐条核对完成，"表已到手"不能直接推出"全集完整"。

**情景二：业务方要求 `R1` 引用标准章节**。必须能给出**具体条款位置**（章节号 + 条款文字）。给不出就只能标为"项目约定"，**不能凭印象写一个章节号**。这是最常见也最难拒绝的请求。

**情景三：某译本示例被证实与标准正文一致**。该条可从"本地示例"升级为"标准条款"，但需记录核验依据（版本、页码、原文）。来源身份不能因文本相似就自动改变：保留译者示例身份，另加经核实的标准条款引用；升级或更正来源分类都需记录证据，不能把确有来源的条款无依据降为示例。

**影响范围**：情景一关闭缺口但需逐条核对；情景二决定 `R1` 的依据表述；情景三改变单条的身份标注。三种情形下"未取得原文即不可声称全集"的规则不变。


## 反例与输入不足

- **错误做法**：把 `R-13` 引用为"G238 需求 R-13"。它是译者补写示例。预期 `missing-evidence`。
- **错误做法**：把 16 个示例当作标准需求清单，声称"已覆盖 G238 全部 BI 需求"。原文表未找到。预期 `missing-evidence`。
- **错误做法**：给 `R1` 编一个官方需求 ID 以便追溯。无依据。预期 `dangling-reference`。
- **输入不足**：`BIR-GAP-1` 的原文需求表缺失。
