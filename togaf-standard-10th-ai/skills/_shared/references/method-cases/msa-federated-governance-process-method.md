# 微服务双轨治理：豁免未裁决就不能共享数据库

## 决策与原始业务资料

预约团队申请临时共享数据库（EX-1）未获决定，能否先实施？

| 证据 ID | 原始材料 |
|---|---|
| `msa-g1` | 业务赞助人审视投资价值。 |
| `msa-g2` | IT 负责人要求生产访问与变更受控。 |
| `msa-g3` | EA 委员会决定标准豁免。 |
| `msa-g4` | 团队申请临时共享数据库 `EX-1`，**未获决定**。 |
| `msa-g5` | 拟采取措施：每次发布前四眼复核、最小权限保护管道、自动测试、持续监控。 |
| `msa-g6` | 四条关系（MSA 支持 IT 治理、决策对齐 EA、MSA 扩展 EA 细节、EA 规则约束 MSA）是**本项目映射，非原图逐边转录**。 |

## 来源规则与项目规则

1. 来源方法（G21I）：微服务治理是联邦式的——中央定标准，团队负责实现细节，豁免需有裁决。
2. 来源方法：治理关系需显式声明，不能靠组织结构暗示。
3. 项目规则：**豁免未裁决前不得实施**（`msa-g4`）；申请不等于批准。
4. 项目规则：`msa-g6` 的四条关系必须标注为项目映射，不得声称是来源原图。

## 转换与推理

1. **三方职责切分**：

| 主体 | 职责 | 不可越界 |
| --- | --- | --- |
| 业务赞助人 | 投资价值 | 不裁决技术标准 |
| IT 负责人 | 生产访问与变更受控 | 不裁决架构标准 |
| EA 委员会 | 标准豁免 | 不代替团队实现 |

2. **EX-1 的状态**：`未获决定`。因此共享数据库方案处于**待裁决**，任何实施动作（建库、改连接串）都超前于治理决定。
3. **缓解措施的作用边界**：`msa-g5` 的四项措施（四眼复核、最小权限、自动测试、持续监控）是拟议缓解，效果尚未验证，但**不能替代豁免裁决**——它们既不证明风险已可控，也不等于风险已被接受。
4. **关系声明**：四条治理关系按 `msa-g6` 标注为项目映射，与来源图的关系区分。

5. **联邦治理的核心是"分层决策"，不是"层层审批"**：

| 层级 | 决定什么 | 本案主体 | 常见越界 |
| --- | --- | --- | --- |
| 价值层 | 值不值得做 | 业务赞助人 | 替 IT 定技术标准 |
| 运行层 | 怎么安全地跑 | IT 负责人 | 替 EA 定架构标准 |
| 标准层 | 能不能例外 | EA 委员会 | 替团队做实现决定 |

   越界的后果：若业务赞助人直接批准共享数据库，等于跳过 EA 的标准豁免程序，事后无法追溯"谁认定这个例外可接受"。

6. **豁免是正式裁决，不是默认允许**。`msa-g4` 说 `EX-1` 未获决定。裁决前不得建库、不得改连接串、不得在架构图中把 `EX-1` 画成既有结构。**"申请了"与"批准了"之间没有可以动手的中间态。**

7. **缓解措施降低风险，但不转移决策权**。`msa-g5` 的四项措施回答的是"如果做了，风险可控吗"，**不是"该不该做"**。把缓解措施当批准依据，是用工程严谨性替代授权。

8. **关系声明的出处必须区分**。`msa-g6` 说四条关系是**本项目映射，非原图逐边转录**。关系本身合理，问题只在出处归属——可写入本项目治理说明，不可声称"G21I 原图如此"。

9. **治理关系的方向有实质含义**。"EA 规则约束 MSA"与"MSA 扩展 EA 细节"是**两条方向相反的关系**，不能合并为"EA 与 MSA 相关"。方向不同，冲突时的裁决路径也不同。

| 类型 | 本案对应 | 说明 |

## 修改演练

**情景一：EA 委员会批准 `EX-1` 并附条件**。可实施，但**条件即约束**：若条件为"限 6 个月且需退出计划"，6 个月后必须重评，不能自动续期。批准不是一次性通行证。

**情景二：EA 委员会驳回 `EX-1`**。团队回到服务自有数据副本方案。`msa-g5` 的四项措施仍适用，但**不能用来论证"所以还是应该共享"**——被驳回的是方案，不是措施。

**情景三：业务赞助人直接批准共享数据库**。越界，需回到 EA 委员会走豁免程序。**赞助人的批准不能替代标准豁免。**

**情景四：四项治理关系被证实与原图一致**。可从"项目映射"升级为"来源转录"，但**只能逐条升级被核实的**，不能整组升级。

**影响范围**：情景一、二改变 `EX-1` 状态；情景三纠正越界；情景四改变关系出处标注。四种情形下"未裁决不实施"的规则不变。

## 反例与输入不足

- **错误做法**：以"已做四眼复核和自动测试"为由先行共享数据库。缓解措施不替代裁决。预期 `approval-without-evidence`。
- **错误做法**：把四条治理关系写成"TOGAF 规定的关系"。它们是项目映射。预期 `core-vocabulary-override`。
- **错误做法**：由业务赞助人批准技术标准豁免。越权。预期 `missing-evidence`。
- **错误做法**：在架构图中把 `EX-1` 画成已存在的共享库。申请不等于批准。预期 `approval-without-evidence`。
- **错误做法**：把"EA 规则约束 MSA"与"MSA 扩展 EA 细节"合并为一条"双向相关"。方向不同，裁决路径不同。预期 `relation-endpoint-type`。
- **错误做法**：豁免批准后不设退出条件，长期沿用。豁免通常有时限与条件。预期 `missing-evidence`。
- **错误做法**：由 IT 负责人裁决架构标准豁免。标准层属 EA 委员会。预期 `approval-without-evidence`。

**输入不足**：`msa-g3` 已给EA委员会裁决权，具体承办人、议程与时限未定，无法判断何时能有结论。`msa-g5` 未给四项措施的实现标准（如"四眼"由谁执行），措施有效性无法评估。材料未给 EA 委员会议事规则，裁决程序只能定性描述。
