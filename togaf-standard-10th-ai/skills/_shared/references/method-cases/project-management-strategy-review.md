# 架构项目管理策略审查：五个管理方面写全了，但谁批的

虚构馆群要在 ADM A–F 阶段开发预约服务架构。项目编制了一份管理策略 `PMS-1`，覆盖风险、质量、沟通、项目控制、配置五个方面。本案例演练如何审查这份策略：字段齐备是否等于可执行、容差规则里的 `>` 为什么不能写成 `>=`、以及"等待确认"与"已确认"之间隔着什么。

所有业务材料、人物、容差与流程均为虚构教学材料（`M-R1`–`M-R4`）。**所有容差、日期与频率均为项目约定，不是 TOGAF 默认值。**

方法：`project-management-strategy-review`。来源方法：G188 §3.1.8 L541–631；§4.2.1 L1524–1531。
入口：[project-management-strategy-review](../analysis-methods/project-management-strategy-review.md)。
素材：原料（历史材料已清理）、基线分析（历史材料已清理）。

## 决策与原始业务资料

要回答：**这份管理策略能拿去执行吗？缺什么？谁有权确认它？**

| 证据 ID | 原始材料 |
|---|---|
| `M-R1` | 项目治理由**项目指导组**负责时间预算质量；**架构委员会**负责跨分馆架构一致性。PMO 维护 `CONFIG-REG` 项目配置记录，逐个保存批准的范围、产品、进度版本和审批记录；**未批准内容只能存在候选区**。 |
| `M-R2` | 风险按**交付风险**与**架构实现风险**分开登记，每周识别、定性复评并指定应对责任人；**没有获批的概率/损失数据时不出定量等级**。交付物必须可追溯到需求，由编制者先自查、业务代表评审、架构委员会检查一致性，再由**交付物章程指定的业务验收人**确认；每份章程说明范围、输入和验收条件。风险日志标识 `RISK-LOG`。 |
| `M-R3` | 沟通计划 `CP-1`：指导组每周收一页要点，领域负责人每周参加工作包审查。`SM-1` 利益相关者图记录指导组关注进展风险，领域负责人关注工作包输入与交付。项目有**两个管理阶段**，阶段末各评审，**不强制与 ADM 阶段对应**；问题和变更分别进入 `ISS-LOG`/`CHG-LOG`；**未经批准变更不得写入基线**。项目规则 `TOL-1`：预测里程碑延误**大于 2 个日历日**时由项目经理上报指导组，**等于 2 日仍在其委托范围**。 |
| `M-R4` | **修改**：指导组换届后，**例外上报接收人尚未确定**；项目经理明确**暂停将上报路径标为已确定**。其他管理主题维持原约定。 |

## 来源规则与项目规则

1. **来源方法（G188 §3.1.8）**：架构项目需覆盖风险、质量、利益相关者沟通、项目控制等管理方面；配置管理另见 §4.2.1。
2. **来源方法**：管理策略须说明"由谁负责哪一类治理"，项目治理与架构治理可分离。
3. **来源方法**：字段完备不代表批准；策略本身需要有权者确认。
4. **项目规则（`M-R3`）**：容差 `TOL-1` 为"大于 2 个日历日"上报，运算符为**严格大于**；等于 2 日不越权。
5. **项目规则**：两个管理阶段与 ADM 阶段**不强制一一对应**（`M-R3`）。
6. **项目规则**：未经批准的变更**不得进入基线**（`M-R1`、`M-R3`）。
7. **项目规则**：无获批概率/损失数据时**不做定量风险等级**（`M-R2`）。

## 转换与推理

1. **治理分层先写清**。`project_governance="项目指导组负责项目时间预算质量"`；`architecture_governance="架构委员会负责架构一致性"`；`project_scope="馆群预约服务的架构开发 ADM A–F"`；`selected_method="机构既有项目管理框架，参考 G188 的管理方面"`。**两个治理主体的职责不重叠**——指导组不管架构一致性，架构委员会不管预算。

2. **五个管理方面逐项成表**：
   - `M-RISK`：交付风险与架构实现风险分开；定性复评；无数据不算定量等级；`risk_log_ref=RISK-LOG`。
   - `M-QUALITY`：四段保证流程（自查 → 业务评审 → 架构一致性 → 指定验收人）；**验收权在章程指定的业务验收人，架构委员会不代替业务验收**。
   - `M-COMMS`：`SM-1` 图、`CP-1` 计划、每周（项目约定）、一页要点。
   - `M-CONTROLS`：三级报告路径；两个管理阶段；`ISS-LOG`/`CHG-LOG`；容差 `TOL-1`。
   - `M-CONFIG`：`CONFIG-REG`；变更先入 `CHG-LOG`；未批准排除出基线。

3. **容差运算符是这条规则的全部**。`TOL-1`：`metric="预测里程碑相对批准日期延误"`、`unit="calendar-day"`、`operator=">"`、`value=2`。因此延误 2 日**不触发**上报，延误 3 日才触发。若把 `>` 改成 `>=`，2 日就会被误判为越权——这在实际项目里意味着不必要的升级与摩擦。**必须保留 `M-R3` 原文的"等于 2 日仍在其委托范围"。**

4. **配置管理与基线的关系**。`unapproved_change_rule="exclude-from-approved-baseline"`。这是一条**否定性规则**：未批准的东西不是"暂存基线后补批准"，而是根本不在基线里。`CONFIG-REG` 逐个保存批准版本与审批记录，正是为了让"基线里有什么"可核对。

5. **确认状态不等于完备状态**。`confirmation_state="awaiting-confirmation"`，而 `topic_reviews` 五项均为 `documented-awaiting-governance-confirmation`，`gaps=[]`。这个组合的含义是：**内容和结构上没有缺口，但没有人批准它**。因此整体 `state="ready-for-governance-review"`——可以送审，不能执行。

6. **修改：例外路径失效**。`M-R4` 说指导组换届后上报接收人未定，项目经理**主动**把上报路径从"已确定"降级为未定。这直接影响 `M-CONTROLS.exception_path`：路径仍写在纸面上（"项目经理向项目指导组上报并等待决定"），但**接收人是谁不知道**。审查结论：`gaps=[{id: "M-CONTROLS:exception_path", reason: ...}]`。

7. **修改不波及无关主题**。`M-R4` 明写"其他管理主题维持原约定"。因此 `M-RISK`、`M-QUALITY`、`M-COMMS`、`M-CONFIG` 四项**状态不变**。若因为例外路径失效就把整份策略判为不可用，是过度反应；若因为其他四项完好就忽略例外路径，是漏检。

本方法采用定性判断与追溯演练，没有适用的统一计算器。**本案例不给管理成熟度打分**，也不把"五个方面齐备"折算为"完备度 100%"——齐备是结构事实，可执行性取决于确认与例外路径是否成立。

## 修改演练

改动一处输入：`M-R4` 补充"指导组换届完成，新接收人为项目指导组秘书，例外路径恢复"。

- `M-CONTROLS.exception_path` 补上具体接收人，`PMS-GAP-2` 关闭，`gaps` 清空。
- `state` 仍为 `ready-for-governance-review`（缺口的消失不等于获得确认）。
- `confirmation_state` **仍为 `awaiting-confirmation`**——接收人确定与策略获准是两件事。
- 影响：`M-CONTROLS` 一项的缺口列表；其余四项不变。

反向演练：若把 `TOL-1.operator` 改为 `>=`，则 2 日延误即触发上报。这会导致 `PMS-R3` 结论翻转，并使 `project-status-highlight-report` 案例中"预测延误 2 日、不构成例外"的判断失效。**同一项目里同一条容差被两个方法引用，改一处会连带影响另一处的结论**——这是跨方法一致性的要求。

第三种演练：若 `M-QUALITY.acceptance_authority` 被改为"架构委员会"，则质量保证流程的最后一步与 `M-R1` 的职责分离冲突（架构委员会负责一致性，不负责业务验收）。此时应判为**治理职责越界**，而非简单字段错误。

## 五个管理方面与职责分离

- 风险：交付风险与架构实现风险分开登记，无概率数据不出定量等级
- 质量：自查→业务评审→架构一致性→指定验收人，四段不可省
- 沟通：利益相关者图 + 沟通计划 + 频率与格式
- 项目控制：报告层级、阶段边界、问题变更登记、容差与例外路径
- 配置：基线识别、变更审批、未批准不入基线

## 反例与输入不足

- **错误做法**：只写四个方面，漏掉 `configuration`。五个管理方面是策略的最小集。预期 `missing-management-topic`。
- **错误做法**：`TOL-1.value` 为 `null`，仍标"容差已定义"。未知容差不能当已定义。预期 `tolerance-unknown`。
- **错误做法**：`confirmation_state="confirmed"` 但无任何确认证据。预期 `PMS-1:confirmation:evidence` 缺口。
- **错误做法**：把未批准的变更写入批准基线，理由是"即将批准"。预期 `approval-without-evidence`。
- **错误做法**：把两个管理阶段强行对应到 ADM 的 A–F 六个阶段。`M-R3` 明示不强制对应。预期 `core-vocabulary-override`。
- **错误做法**：无获批概率/损失数据或项目定量口径，却生成数值风险指数并称为已证实等级。M-R2 禁止无依据定量；有依据的高/中/低定性复评本来就是允许的。预期 `unsourced-maturity-rating`。
- **错误做法**：让架构委员会代替业务验收人确认交付物。治理职责越界。预期 `approval-without-evidence`。

**输入不足**：`M-R2` 未给风险登记的具体字段清单（只给日志标识 `RISK-LOG`），因此 `M-RISK` 不细化字段。`M-R3` 未给两个管理阶段的起止日期，审查不判断阶段划分是否合理。`M-R1` 未给 `CONFIG-REG` 的存储形式，本案例不假定其为工具或纸质。

## 评审记录

- 核对项目治理与架构治理职责分离，且与 `M-R1` 原文一致。
- 核对五个管理方面齐全，各含责任人、证据引用与可执行流程。
- 核对 `TOL-1` 运算符为 `>` 且原文"等于 2 日仍在其委托范围"被保留。
- 核对质量保证四段流程完整，验收权未被架构委员会替代。
- 核对未批准变更排除出基线，非"暂存待批"。
- 核对整体状态为待治理确认，未出现"已批准/已生效"。
- 核对修改仅影响 `M-CONTROLS`，其余四项状态不变。
- 核对无定量风险等级、无成熟度评分。
- 核对跨方法容差一致性（与项目状态要点报告共用 `TOL-1`）。

本例已完成编写者一致性复核；业务事实、授权与执行成效均为虚构，独立代理/业务责任人评审仍为待验证。
