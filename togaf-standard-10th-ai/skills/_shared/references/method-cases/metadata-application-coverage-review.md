所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充 TOGAF 规定。案例完整演练不等于独立业务评审通过。

## 决策与原始业务资料

五馆联盟评估四款候选元数据平台，能否覆盖八类资产与 G234 表 5-2 的功能要求？

| 证据 ID | 原始材料 |
|---|---|
| `mcr-1` | 范围：馆藏目录与借展数据的元数据，不含全企业上线，不声称合规认证。 |
| `mcr-2` | 八类资产 A1–A8：术语表、数据字典、使用记录、分类、规则政策、问题记录、治理资产、技术质量规则。 |
| `mcr-3` | 四款工具：T-CATALOG 2.4（平台组）、T-QUALITY 1.8（质量组）、T-WORKFLOW 3.0（治理组）、T-GATEWAY 1.2（集成组）。 |
| `mcr-4` | 同一工具被多个功能复用，不能复制成多个工具条目。 |
| `mcr-5` | 规则：已实现须在明确版本/环境/日期有通过观察；计划中须有责任人与时点。 |

## 来源规则与项目规则

1. 来源方法（G234）：按功能要求逐项对照工具能力，覆盖判定需区分已实现、计划、未知。
2. 来源方法：工具能力与资产范围是两个维度，同一工具对不同资产的能力可以不同。
3. 项目规则：**已实现必须有版本/环境/日期三要素的通过观察**（`mcr-5`）；否则只能记"计划"或"未知"。
4. 项目规则：一工具多用途时只登一条，用关系表达复用（`mcr-4`），不得按功能复制工具。

## 转换与推理

1. **拟建两维矩阵**：行是八类资产 A1–A8，列应为 G234 表5-2功能项；完整列定义未载入，逐格矩阵未完成。
2. **工具能力定位**：

| 工具 | 主要覆盖 | 边界 |
| --- | --- | --- |
| T-CATALOG | A1/A2/A7 的编目与治理分组 | 不执行质量规则 |
| T-QUALITY | A6/A8 的质量规则执行 | 不管理术语 |
| T-WORKFLOW | A5 的规则审批流 | 不存储资产内容 |
| T-GATEWAY | 外部文档 URL 的接入 | 不判定内容质量 |

3. **逐格判定**：每格取"已实现／计划／未知"之一。因 `mcr-5` 要求版本+环境+日期，本轮无任何格满足"已实现"，全部为"计划"或"未知"。
4. **复用表达**：T-CATALOG 同时服务 A1、A2、A7，用一条工具记录与三条覆盖关系，不复制三个工具。

5. **两个维度必须分开，不能压成一张清单**。本方法的核心是**两维矩阵**：
   - **行**：资产类别 A1–A8（要管理什么）
   - **列**：G234 表 5-2 的功能项（要具备什么能力）
   
   同一工具在不同行列上的能力**可以不同**。T-CATALOG 能编目 A1/A2/A7，但**不执行质量规则**（那是 T-QUALITY 的列）。若把"工具"和"资产"合成一维，就会得出"T-CATALOG 覆盖 A8"这类错误结论。

6. **"已实现"的三要素是硬门槛**。`mcr-5` 要求**版本 + 环境 + 日期**三要素齐全的通过观察。缺任一项都不算：
   - 有版本无环境 → 不知道在测试环境还是生产
   - 有环境无日期 → 不知道是什么时候观察的
   - 有日期无版本 → 不知道观察的是哪个版本

   本轮全部为"计划"或"未知"，**没有一个"已实现"**。这是规则的正常结果，不是数据没收集好。

7. **一工具多用途只登一条**。`mcr-4`：T-CATALOG 服务 A1、A2、A7 三个资产，只建**一条工具记录** + **三条覆盖关系**。若复制成三个工具条目：
   - 工具清单虚增（四款变六款）
   - 任何工具属性变更要改三处
   - "同一工具"这一事实消失

8. **"计划"不等于"承诺"**。`mcr-5` 说计划须有责任人与时点。因此：
   - 有责任人 + 有时点 ⇒ 可记"计划"
   - 缺任一项 ⇒ 只能记"未知"

   把"厂商说支持"记成"计划"是常见的越界——厂商承诺不是本项目的计划。

9. **范围声明限制结论边界**。`mcr-1` 明确不含全企业上线、不声称合规认证。因此本评估的结论**只覆盖这五馆联盟的四款候选工具与八类资产**，不外推为"平台选型结论"或"合规达标"。

## 修改演练

**情景一：T-CATALOG 在生产环境 2.4 版于 2026-09-15 通过观察**。此时 A1/A2/A7 相关格可从"计划/未知"转为"**已实现**"——**但只限被观察到的那几个功能项**，不是整个 A1 类别。三要素齐全的观察是逐格的，不是逐工具的。

**情景二：T-QUALITY 升级到 1.9**。原 1.8 的观察记录需保留为历史；新版本的覆盖需重新观察。**不能因同一工具升级就沿用旧结论。**

**情景三：新增第五款工具**。它可能与现有工具能力重叠。此时需重新评估：是替换还是补充？**不能在矩阵上直接加一列了事**——重叠部分会产生"两个都覆盖"的判定，需明确哪个是主。

**情景四：业务方要求"给个覆盖率数字"**。矩阵格数可数（8 类资产 × N 个功能项），但**"已实现"为零**时，只有在功能列、适用分母及排除规则明确后才可计算已验证比例；当前列未齐，不能直接给0%实际能力覆盖率，不说明"平台不行"。

**影响范围**：情景一改变单格判定；情景二保留历史并要求重观察；情景三改变工具集合与重叠判定；情景四涉及指标解释。四种情形下"三要素齐全才算已实现"的门槛不变。

## 反例与输入不足

- **错误做法**：因采购了 T-CATALOG 即判其覆盖的八类资产全部已实现。违反 `mcr-5` 的三要素要求。预期 `missing-evidence`。
- **错误做法**：同一工具按功能复制四条记录。违反 `mcr-4`。预期 `duplicate-id`。
- **错误做法**：把"覆盖八类资产"表述为"满足 G234 全部要求"。覆盖评估不等于合规认证。预期 `missing-evidence`。
- **错误做法**：把 T-CATALOG 在 A1 的观察结果推广到 A8。工具能力按功能项逐格判定，不按资产类别整列继承。预期 `core-vocabulary-override`。
- **错误做法**：因厂商宣称支持某功能，就记该格为"计划"。计划须有本项目责任人与时点，厂商承诺不是项目计划。预期 `missing-evidence`。
- **错误做法**：矩阵"已实现"为零时，据此得出"四款工具都不合格"的结论。零只说明未验证，不说明不合格。预期 `measurement-basis-gap`。
- **错误做法**：T-QUALITY 升级到 1.9 后沿用 1.8 的观察结论。版本变了须重新观察。预期 `measurement-evidence-gap`。
- **错误做法**：把"覆盖八类资产"写成"元数据治理成熟度达标"。覆盖评估与成熟度是两个对象。预期 `unsourced-maturity-rating`。

**输入不足**：`mcr-2` 未逐项列出表 5-2 功能，矩阵列定义需补（`MCR-GAP-2`）。材料未给四款工具的实际部署环境与版本日期，故本轮无任何格可达"已实现"。`mcr-3` 未给四款工具之间的集成关系，跨工具的组合能力无法评估。

**与相邻方法的边界**：本方法评"工具能否覆盖功能要求"，不评"选哪款工具"。选型需结合成本、许可、运维与退出成本，均不在本方法输出内。
