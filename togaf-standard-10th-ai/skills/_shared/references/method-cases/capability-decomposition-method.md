# 把渠道、系统和步骤分离出稳定能力层级

所有业务资料、人物、数值、政策及证据均为虚构教学材料；指南只提供方法依据，项目规则不冒充TOGAF规定。案例完整演练不等于独立业务评审通过。

方法：`capability-decomposition-method`。来源方法：G211 §3。
入口：[capability-decomposition-method](../analysis-methods/capability-decomposition-method.md)。

## 决策与原始业务资料

零售企业要按能力规划订单改造，避免把组织重组当成能力变化。

|证据 ID|原始材料|
|---|---|
|cap-1|运营材料：订单部门负责收单、改地址、取消和查单；门店、网站均可收单。|
|cap-2|IT清单：OrderSuite记录订单；客服通过邮件批准特殊取消。现有图把‘网站’、‘订单部’、‘审批按钮’都画为子能力。|
|cap-3|业务边界：本轮管理顾客购买承诺及其变化；结算和实物配送由其他能力承担，仍须记录协作接口。|

## 来源规则与项目规则

1. 来源方法：能力描述业务能做什么，保持实现独立，并采用同层次的语义分解。
2. 项目命名规则：使用业务对象＋管理/处理表达稳定意图；本案顶层为订单管理，不把该命名法称为TOGAF强制语法。

## 转换与推理

1. **先把混在图里的四类对象分开**。现有图把五样东西都画成了"子能力"：

| 图中对象 | 真实类型 | 依据 |
| --- | --- | --- |
| 网站 | 渠道 | `cap-1` 门店、网站均可收单 |
| 门店 | 渠道 | 同上 |
| 订单部 | 组织单元 | `cap-1` 运营材料 |
| 审批按钮 | 流程活动 | `cap-2` 客服通过邮件批准特殊取消 |
| OrderSuite | 应用系统 | `cap-2` IT 清单 |

   五个对象（四类）**都保留在模型里**，只是不加入 `decomposes`（整体—部分）关系。把它们删掉会造成信息丢失；把它们留在能力层级里会造成分类错误。

2. **从业务结果提炼顶层能力**。`cap-1` 描述的是一件事：对顾客购买承诺的接收、变更与状态查询。据此提炼 `C-1` 订单管理，`C-1` 的判据是"业务能做什么"，不是"部门叫什么"。

3. **两层（父能力与三个子能力）语义分解，同层次同粒度**。`C-1` 分解为三条：
   - `C-11` 订单承诺管理：覆盖接收与确认承诺
   - `C-12` 订单变更管理：覆盖地址调整和取消
   - `C-13` 订单状态管理：覆盖状态查询

   三条**处于同一抽象层**——都是"对承诺的某类管理动作"。若把 `C-11` 再拆出"录入地址"这类步骤，就出现层次混杂。

4. **边界检查一：范围外的能力不并入**。`cap-3` 说结算与实物配送由其他能力承担。它们是 `C-2`/`C-3`，**作为外部使能能力记录协作接口**，不整体移入 `C-1`。若并入，`C-1` 会膨胀成一个"什么都管"的能力，失去分类意义。

5. **边界检查二：两个子能力的界要能说清**。`C-12` 与 `C-13` 都涉及"状态"。判定依据是：`C-12` **决定**变更（是否改、改成什么），`C-13` **呈现**状态（查询可见）。若两者都写"管理订单状态"，则界不清，后续任何状态相关需求都会双向归属。

6. **命名服务于稳定性**。项目命名规则用"业务对象 + 管理/处理"，因此得到"订单**管理**""承诺**管理**"，而非"订单模块""订单中心"这类随组织结构变化的名称。命名法本身是**项目规则**，不宣称为 TOGAF 强制语法。

## 输出与追溯

| 结果 ID | 结论 | 追溯 | 状态 |
|---|---|---|---|
| `C-1` | 订单管理 → `C-11`/`C-12`/`C-13` 为三条语义分解，关系方向整体到部分 | `cap-1`/`cap-3` | 候选分类待业务复核 |
| `APP-1` | `OrderSuite` 是实现组成，网站/门店是渠道，订单部是组织，审批按钮是流程活动；均不构成子能力 | `cap-2` | 类型已分开 |
| `APP-2` | 五个对象（四类）保留在模型中，仅未加入 `decomposes` 关系 | `cap-1`/`cap-2` | 已区分 |
| `APP-3` | `C-12`（决定变更）与 `C-13`（呈现状态）的界可一句话说清 | `cap-1` | 已核对 |
| `GAP-C1` | 特殊取消的责任授权未说明，不影响能力名称，但阻断流程权限设计 | `cap-2` | 待补 |
| `GAP-C2` | 结算与配送的协作接口内容未给，仅记录接口存在 | `cap-3` | 未决 |

本方法采用定性判断与追溯演练，没有适用的统一计算器。**方法输出的边界**：给出能力层级与类型区分，**不给出**能力成熟度评分、实现成本或改造顺序——这些需要本方法之外的输入。

## 分解的三条判据

**判据一：同一抽象层**。兄弟能力必须处于同一粒度。检验方法：能否用同一句式描述它们？

| 能力 | 句式 | 同层？ |
| --- | --- | --- |
| `C-11` 订单承诺管理 | 对承诺的**某类管理动作** | 是 |
| `C-12` 订单变更管理 | 对承诺的**某类管理动作** | 是 |
| `C-13` 订单状态管理 | 对承诺的**某类管理动作** | 是 |
| （反例）录入地址 | 一个**具体操作步骤** | 否 |

**判据二：业务意图而非实现方式**。能力名称不应绑定技术或组织形式：

| 可接受 | 不可接受 | 原因 |
| --- | --- | --- |
| 订单承诺管理 | OrderSuite 管理 | 绑定具体系统 |
| 库存可视性 | 库存报表模块 | 绑定实现形态 |
| 客户身份识别 | CRM 客户查询 | 绑定系统与操作 |

**判据三：分解不跨域**。`C-1` 分解出的子能力应都属于"订单管理"这个业务域。若某子能力实际上属于结算或配送，说明顶层能力的范围划错了。

## 类型区分的四类对照

本案把混在图里的五个对象（四类）分开，核心是四组容易混淆的对：

| 对 | 区分依据 | 本案实例 |
| --- | --- | --- |
| 能力 vs 组织 | 能力是"能做什么"，组织是"谁在做" | `C-1` vs 订单部 |
| 能力 vs 系统 | 能力是业务意图，系统是实现载体 | `C-1` vs OrderSuite |
| 能力 vs 流程活动 | 能力是稳定的"能做"，活动是具体的"正在做" | `C-12` vs 审批按钮 |
| 能力 vs 渠道 | 能力与渠道无关，渠道是触达方式 | `C-1` vs 网站/门店 |

**四者都保留在模型中，只是不进入 `decomposes` 关系**。删掉会丢失信息，纳入会破坏分类。

## 修改演练

**情景一：订单部门分拆为渠道运营与售后**。`C-1` 至 `C-13` 及全部 `decomposes` 关系**原样保留**，只修改组织映射字段（哪个组织单元承担哪个能力）。**组织重组不改变能力分类**——这正是本方法要防的错误。

**情景二：新增订阅业务**。先判定"订阅"是否引入持续承诺管理这一新业务职责：若是，新增 `C-14` 持续承诺管理，与 `C-11`–`C-13` 同层；若只是现有承诺的一次性变体，则归入 `C-11`。**不能因为上了新系统就按系统名加一个能力框**。

**情景三：`C-12` 与 `C-13` 被合并为一个"订单状态与变更管理"**。此时状态查询与变更决定同属一个能力，`GAP-C1` 的授权问题需重评查询与变更的授权边界，但能力合并不必然合并权限，更不能断言查询侧自动继承取消授权缺口。

**影响范围**：情景一改组织映射；情景二可能新增同层能力；情景三改变层级结构与 `GAP-C1` 的影响面。三种情形下 `C-1` 的顶层定义与范围外 `C-2`/`C-3` 的协作关系不变。

## 反例与输入不足

- **错误做法**：把"填写地址→点击批准→发邮件"串成父子能力。这是流程步骤，不是能力分解。预期 `core-vocabulary-override`。
- **错误做法**：因图中存在"前台"视觉分组，就把它当作可继承的父能力。视觉分组不是分类层级。预期 `undefined-entity-type`。
- **错误做法**：把"订单部"这一组织单元直接画为子能力。组织重组不等于能力变化。预期 `core-vocabulary-override`。
- **错误做法**：把 `OrderSuite` 画为 `C-1` 的子能力，理由是"它实现了订单管理"。应用是实现组成，不是能力。预期 `core-vocabulary-override`。
- **错误做法**：为消除 `C-12`/`C-13` 的边界争议，把两者合并为一个能力且不重述影响面。合并需重核授权边界，不能由能力合并推断权限自动传播。预期 `missing-evidence`。
- **错误做法**：因 `cap-3` 说结算与配送"由其他能力承担"，就把它从模型中删除。范围外不等于不需要记录协作。预期 `dangling-reference`。

**输入不足**：材料未给结算与实物配送的协作接口细节（接口内容、频率、责任方），因此只记录接口存在，不描述其内容。`cap-2` 未说明"特殊取消"的授权人是谁，`GAP-C1` 保留未决，且该缺口影响流程权限设计而非能力命名。

## 评审记录

- 核对三个子能力分别对应 `cap-1` 中的完整业务职责，无遗漏也无重复。
- 核对能力层级中不存在系统、部门或时间顺序节点。
- 核对五类被误画对象均已识别并保留在模型中，仅移出 `decomposes`。
- 核对 `C-11`–`C-13` 处于同一抽象层，无层次混杂。
- 核对范围外的结算与配送未丢失协作关系。
- 核对 `C-12`/`C-13` 的界可用"决定 vs 呈现"一句话说清。
- 核对命名法标注为项目规则，未称为 TOGAF 强制语法。
- 核对三项修改情景分别说明影响范围与不变项。
