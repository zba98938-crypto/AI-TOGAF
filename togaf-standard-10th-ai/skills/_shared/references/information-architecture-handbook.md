# 信息架构专题操作手册

用于元数据、客户主数据及 BI 演进任务。来源摘要来自 G234 §4—5／附录 A、G21B §4—6、G238 §3.2；下文的字段组织和检查流程是项目操作约定。按需选择相关段落，不把参考模型全量复制成项目事实。

## 元数据：从需求到资产、流程和技术

来源摘要：G234 区分从法规／业务用例出发的自上而下需求，以及从数据集／业务数据问题出发的自下而上需求。两者都需要明确元数据质量目标；自下而上的任务应先用具体业务价值论证后续治理和自动化。

操作时建立以下追溯链：驱动或问题 → 业务需求 → 元数据资产及质量要求 → 责任与校验工作流 → 数据模型和技术功能 → 运营证据。每条保留来源 ID、范围、状态和未决项。

| 层面 | 需要区分的对象 | 评审问题 |
|---|---|---|
| 业务语义 | 业务术语、对象、元素、值域、代码集、代码值 | 同名术语是否语境不同；对象＋属性＋值域能否定义元素 |
| 治理 | 数据域、所有者、管家、政策、分类、SLA、隐私评估 | 谁定义与批准，谁维护，阈值适用哪个业务场景 |
| 规则 | 业务质量／删除规则、对应技术规则 | 业务意图如何转成可执行检查，如何验证误报漏报 |
| 技术 | 应用、数据库、数据集、字段、数据流 | 字段与业务元素映射是否有依据，血缘方向是否明确 |
| 运营 | 访问事件、质量异常、数据量、元数据活动日志 | 是某时点事件还是永久属性，期间与单位是否一致 |

来源摘要：规范式由少数人创建、校验后只读发布，偏重精确性、一致性等；协作式多人创建编辑、动态且最终一致。操作时按元数据范围选择方式，定义草稿、复核、发布、撤回及异常处理，不用“协作式”免除责任和质量检查。

三种集成组织方式和三种采集机制是独立选择：

| 选择维度 | 方案 | 必须保留的语义 |
|---|---|---|
| 集成组织 | Consolidation 集中式（本地译名） | 提供访问点、保存副本，创建维护位于外部 |
| 集成组织 | Hybrid 混合式 | 部分范围在库内主控与校验，其余在原工具主控并同步 |
| 集成组织 | Unified 统一式 | 完整范围及维护校验流程统一，可有社区专属界面 |
| 采集机制 | 手工 | 来源导出，人工按约定格式上传 |
| 采集机制 | 推送 | 来源负责按格式、结构、范围和频率契约发起更新 |
| 采集机制 | 拉取 | 方案在来源端部署代理以采集或推断；控制发起与回传不同 |

操作时建立方案面板而非默认时序。每个面板列来源、接收者、主控权、控制命令、数据返回、触发／频率、权限、侵入性、负载、维护成本、失败重试及校验责任。只有用户给出了真实交互顺序，才另外生成时序图。拉取可能需要读取数据内容并影响关键系统，应分析授权范围和应用影响，不能只写“自动化效率高”。

G234 图 4-4 本地实际英文资产与正文不一致；正文支持“技术功能＋数据模型＋更新校验流程”三部分方案，不能把该图片当成三部分结构的核实证据。图表来源状态单独记录。

对推断方案，区分：结构化数据可从字典取得模式而无需读内容；半结构化文件的结构可能随文件及时间变化；非结构化数据通常要扫描内容先提取结构。记录提取算法、置信度、样本、扫描边界、性能和隐私约束；推断出的字段、分类或血缘不能自动标为已确认。

输出至少回答：为什么管理、管理什么、谁负责、如何更新验证、用什么支撑、如何证明有效。仅有一个名为“存储库”的应用框不能回答这些问题。

## 客户主数据：权威和身份优先于中心化工具

来源摘要：G21B 的客户可为自然人或组织；内核范围包括内部标识、外部标识、个人或法人描述、联系、偏好／同意、关系／群组。业务使用目的决定范围，不能因参考图含某字段便默认允许采集。

操作时先定义客户身份边界、标识命名空间、权威数据来源、匹配候选规则、合并与拆分、保留历史、质量例外及人工处置；同名不自动合并，同一人不同角色不自动视为不同自然人。用原始来源记录与主记录 ID 映射保存来历。

| C-MDM 集成风格 | 主控与流向 | 不能误读为 |
|---|---|---|
| 整合式 Consolidation／下游 MDM | 各系统保有数据，向中心发送，支持事后分析 | 已存在运营单一真相或已经允许中心合并客户 |
| 协作式 Cooperation | 来源向中心整合，再分发新版本真相，按主 ID 同步 | 没有时延、冲突或事务工作流需求 |
| 集中式 Centralized | MDM 主控，连接系统以服务获取并经 MDM 创建更新 | 所有旧应用都能无成本改变主控权 |

不要把此处的“集中式”与 G234 元数据 Consolidation 的中文译名等同；两个专题的主控权定义不同。每个源到中心、中心到消费点分别记录 PoA／PoC、批量／实时／同步、版本、冲突处置、删除传播、失败恢复及允许时延。参考模式可组合使用，不要求所有应用采用同一方式。

输出身份与标识模型、权威／副本矩阵、集成方案、质量和治理职责、迁移及回退安排。客户主数据图和应用／数据 CRUD 矩阵共用对象身份，但“拥有权威”与 C／R／U／D 是不同语义。

## BI：四个状态的演进理由和可运营性

来源摘要：G238 §3.2 给出从 EDW 到新一代数据平台的示例，讨论控制多样性和数据共享。它不是要求所有企业更换数仓的通用命令。正文泛称四个过渡架构，但步骤说明将第一步称现状、第四步称目标；本集合按各步明确角色建基线、两个过渡、目标，保留该措辞差异。

| 参考状态 | 内容 | 本地项目必须补充的证据 |
|---|---|---|
| 现状 | 事务应用供数到 EDW，向集市和应用输出 | 数据源、批次、质量、使用者、容量及依赖 |
| 过渡一 | 引入新平台，与现有 EDW 并存，增加数据源和用途 | 供数责任、共存成本、控制、同步、回退 |
| 过渡二 | 新平台覆盖原始数据完整范围并向 EDW 提供新数据 | 覆盖核对、对账、旧接口保留和退出条件 |
| 目标 | 新平台服务全部分析需求，图中 EDW 包含于新平台边界 | 满足用例的验证、保留／退役清单及剩余风险 |

操作时为每状态分别建视图、状态 ID、对象版本及跨状态 concept_id。入站／出站是数据方向；基线／目标颜色表示状态；边界表示归属，三者不能互相代替。对每条流记录载荷、来源、接收者、频率、延迟、质量、安全及回写目的。

业务功能（战略、质量、治理、运营、沟通等）与应用功能（采集、存储、处理、分析、监控等）分别建立层级并用实现关系连接。不能因应用框名称类似业务功能便认定已经实现。

路线图从用例和数据约束识别差距，比较保留、整合和替换选项；每工作包说明成果、前置依赖和状态退出判据。仅有四张不同颜色的架构图不足以证明迁移可行。
