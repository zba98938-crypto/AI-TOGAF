# 全量能力工作流与多视图输出

本文件是项目操作约定；具体 TOGAF 依据、译文解释及不确定性见能力规范的来源条目。支持架构分析、生成、修改和评审四种工作。只有经过证据核对的结论才能进入项目事实。

需要核对系列指南的完整定义、步骤、表格或图意时，使用 [AI 可读原文语料入口](ai-corpus.md)：中文关键词可检索英文原文，读取结果对应章节与图片 JSON，并保留 PDF 页码及来源指纹。既有中文译文和图意解释按各自质量标记使用。

完整 ADM、阶段推进或需求变更任务同时使用[ADM 周期](adm-cycle.md)：按信息需要选择执行、复用或裁剪阶段，绑定实际模型输出并保留迭代与评审记录。持续需求使用[需求追溯检查](requirements-trace.md)，贯穿阶段，而非留到最后补表。单项制品任务仍按下述选择范围直接执行。

把关注点落实到具体阶段成果时，使用[架构成果联动](architecture-delivery.md)及 `architecture_delivery.py catalog/init/check/report`。现有 17 个技能共享同一映射规则，阶段判据、制品选择、实际生成及接受记录分别核对。

## 选择与裁剪

1. 从用户需要作出的决策识别利益相关者、关注点、五维语境和所需演进状态。读取 capabilities.json 中主责为当前技能的工作产品、视图和分析方法；不要把完整清单当成项目必须交付的清单。
2. 先读取对应规范及其引用的方法，选择制品族和 profile；没有完全匹配的 profile 时明确提出候选视点及待验证之处，不能把通用图声明为来源模板。
3. 区分项目事实、用户约束、参考架构、候选方案、假设和虚构示例。来源图帮助定义表达能力，不证明项目存在同名对象或关系。原图、译文和 JSON 有冲突时，在证据登记中记录各自说法、采信理由和未决部分。

## 从原始材料开展分析

交易、事件或台账达到大规模时，使用[大规模企业投影工作流](large-enterprise-projection.md)，先进行独立数据核算和有哈希的 SQL 聚合，再建立关注点范围内的共享架构对象。

- 保留输入材料的来源与定位；把复合陈述拆成可追溯的单点，统一同义名称，再区分对象、行为、关系、要求和评价。名称相同并不自动合并，名称不同也不自动创建两个业务概念。
- 建立 glossary 与稳定 ID。能力表达企业能够做什么；流程表达有顺序和条件的行为；同一能力在多个阶段的具体实现建为实例，回链能力类型。组织、应用或流程变化不直接要求创建新能力。
- 为模型建立最小闭合范围：每个被选中的关系都引用存在的端点；对视图外对象使用显式范围说明或边界接口，不丢弃关系来使图好看。属性未知填写缺口，不能用零、空列表或 unknown 基数替代已知的不存在。
- 形成有理由的分析结论：说明观察、约束、选项、判据、权衡、建议及待验证项。模型的 analysis 字段记录本次推理结论；不能只复述模板标题。
- 所需输入不足时，输出可建立的对象与草稿、阻断结论的缺口、需收集的材料和可继续的分析。关键分值、依赖、授权或审批缺失时不生成确定性结论。

## 常用分析的操作规则

### 架构工作、角色与技能

架构实践建立、任务配置及人员发展使用 [G249 工作流](g249-operational-workflow.md)。把任务依据、预期决策、职责、技能要求、方法、制品和验收证据连接起来。普通制品生成按决策范围选择角色视角和领域方法，无需收集人员评价。官方参考等级、企业裁剪目标、人员观察结果分别记录；输入不足保留缺口，不从职位、课程或缺少高级证据推断等级。角色指导、治理、任务协调与人事汇报分别建模。

### 能力、价值流与变革

从业务结果和对象定义能力，分别核对同层粒度、分解覆盖和不重叠；确定评价维度及量表，再记录有证据的现状与期望。热力颜色必须由所声明的维度派生；尚不存在的未来能力不能当作最低成熟度。

价值流从受益者、触发和最终价值开始，逐阶段确定进入条件、退出条件、价值项及使能能力。阶段顺序、能力分解和实例组成是不同关系。价值链采用主要／支持活动及价值或成本视点，不把它改成客户价值流。

比较基线与目标前，明确范围、身份和比较标准。把保留、改进、新增、整合、退役及相应差距分开；由差距提出候选工作包，核对依赖与资源。每个过渡状态应说明运营、数据一致性、控制、依赖及回退条件，不能仅以时间节点代替可运营状态。

### 风险、安全与治理

先确定业务目标、风险资产、影响边界、风险偏好及采用的评价规则；再分析威胁主体／事件、脆弱性、损失事件、固有风险、控制及剩余风险。缺少概率或影响证据时可做定性描述，不能套用任意乘法产生精确风险值。

从业务属性或控制目标引出安全需求，再追溯到安全服务、控制实施、验证证据与责任人。安全域表示安全策略边界，信任关系需说明主体、条件、方向和允许的行为；数据访问、关系存在和经过授权不能混为一谈。

合规评审逐项比对适用要求、实现证据和判据，分别记录符合、偏离、证据不足与不适用及理由。自动生成不能创建豁免、批准或已验证运行有效的事实。

### 成熟度、就绪度与选项决策

声明所选模型、版本、量表锚点、访谈或观察证据及评价范围。G203 的美国商务部 ACMM 是示例框架，具有六级九要素；加权等级与逐级达成比例是不同输出，权重和达成规则不明时不代算。

G212 的采用定位、管理关注因素、因素缺失后果与七级问卷分别处理。采用类型不是成熟度等级；后果关联不自带概率与优先级；只在用户或来源给出完整聚合规则时汇总。

决策矩阵先筛除违反硬约束的选项，再声明准则、优化方向、尺度、权重和缺失值处理。给出逐项证据及敏感性分析；不同量纲不能直接相加，未指定权重时保留比较表和待决问题。

G176 §12.8 的示例先把成本、资源、对问题的贡献、可行性转为 1—5 偏好值（5 最佳），再按需要加权。成本列此时不是原始金额，不能再按“越低越好”反转一次。使用 `preference-weighted-decision` 计算这种评分；使用 `weighted-normalized-decision` 时须注明它是项目另选的归一化算法，输入原始值、上下界及方向。

G212 §5.2、§5.4、附录 A 的复核对象是因素等级。“同意／非常同意”以外的因素需要管理关注；如采用1—7编码及数值关注阈值，必须显式声明为项目映射，不冒称原文默认规则，也不能发明整份问卷总分合格线。`dtra-factor-review`要求显式因素评级形成规则，检查七项基础、五项影响、三项持续因素；因素不全或基础条件未满足时不自动赋予类型。ABCD的横轴为普及度，纵轴为速度：A左上、B右上、C右下、D左下。本地G212图5-2重绘把C／D左右放反，使用正文定义并登记来源冲突。

### 信息、主数据、元数据与 BI

概念模型描述业务信息含义及关联；逻辑模型补充属性、标识、域、可选性、约束和基数；物理实现另建并追溯。信息被能力使用或修改应明确方向，不能从颜色或卡片邻近关系猜测。

元数据需求从法规、业务用例、数据问题或数据集出发，确定业务／技术／运营元数据范围与质量要求，再确定资产、责任、校验工作流、存储库和交换契约。集中／混合／统一组织方式与手工／推送／拉取采集方式是不同选择维度；每个方案比较时效、安全、源系统负担和维护成本。

主数据需说明主记录权威、匹配与合并、质量、分发和数据使用责任。BI 架构状态分别记录数据源、处理、存储、分析使用及入站／出站流，再比较各过渡状态的共存与迁移条件。参考模型是可裁剪起点，不自动成为用户选择的技术产品。

BI 用途从用户痛点、决策、业务对象与赞助人开始，再定义目标与测量。G238 的参考指标方向不提供项目目标、ROI公式或权重；完整配套需求电子表格缺失，中文说明性例子不计为官方需求全集。BI/C-MDM 功能覆盖逐参考行登记实际证据、计划、未知或有理由不适用，保留宏观/子功能粒度与参考身份，不由产品名称推断全部覆盖。数据价值链区分原始、技术准备、业务信息与语义消费；模型运营监控需有业务责任、测量依据、版本和失败回退。相关可调用规范见[信息架构能力包](togaf-information-data-package.md)及[需求能力包](togaf-requirements-package.md)。

### 微服务组织与运营

先核对单团队对服务开发、部署、运营至退役的责任、技能、自治护栏和试点学习。G21I 只引用 OSIMM，不在此提供完整模型或评分规则；不得把就绪问题的答复数量合成为 TOGAF 成熟度分数。治理同时处理 MSA 专属决定和企业约束；豁免请求与委员会决定证据分开。目录记录每服务的单一 ABF、实际/计划状态、业务价值，以及开发/运营、已分配/计划四类资源的单位和期间；未知资源不当作零成本。按需读取[技术能力包](togaf-technology-architecture-package.md)和[应用能力包](togaf-application-architecture-package.md)。

### 环境与价值度量

记录核算对象、生命周期阶段、年度、Scope、单位、分摊、排放因子版本及估算来源。新增、退役、净值、抵消分别记录；不同范围不能直接求和或比较。原图印刷值与分项存在差异时同时保存并登记差异，不悄悄改正。历史统计、示例目标和情景假设均保留原身份。

## 模型、输出与修改

字段以`entity_attribute_semantics`的类型限定契约为先，兼容旧无歧义`attribute_semantics`。未知值按字段的unknown policy处理；不把缺max默认为无界，不把未来不存在当作零分。`check_specs`的machine条目绑定实际执行器，professional条目只形成待审问题；规则文件不因生成参考文档而替换人工`decisions.md`。

v2 中 artifact_id 是制品族，profile_id 决定专门语义和模板，view.id 是具体成果身份。同一制品族可有多个视图和多过渡状态。选择 reference 布局时核对模板来源状态；选择 adaptive 布局时保持其关系与空间语义。

运行 validate.py 后，用 generate.py 的 --artifact、--profile 或 --view 选择生成；--deliverable 组装实际引用的视图；--all 仅生成模型中已分析的全部内容。图形加 --render 得到 SVG／PNG。每个视图检查 coverage.json 中的遗漏、错误、必要属性与实际表示位置；表格对照已保存 Markdown 的字段和值，图形核对图中方向、边界、层级及空间语义。只有 JSON 保留数据不算输出已表达，表格生成也不替代来源图视觉验收。

交付物按[动态组装规则](deliverable-assembly.md)使用 `assembly`、实际 `view_ids`、章节绑定和分析 ID，从所选模型记录与计算结果形成正文。`sections` 人工文字属于待核对背景。严格模式有缺口则阻止交付正文生成，草稿模式展示缺口；无编码缺口的 `assembled-awaiting-review` 仍需业务评审。未启用组装的旧模型标为 `legacy-unassembled`，不能计为当前组装验收。

保存 `manifest.json` 的模型/规范/模板版本及模型、注册表、渲染器、生成器、组装规则和运行依赖指纹。输出或评审只有在适用范围、视图状态和指纹一致时才能复用；变更后对受影响输出重新生成并核对，不以旧目录名称或曾经的通过状态代表新版本。

修改时保留 ID、来源和变更理由，更新受影响的关系、评价、视图及交付物；先用 analyze.py 给出候选影响范围，再逐条判断实际影响。基线目标比较按已对齐的对象和具体状态进行，不能把记录缺失直接判为退役。

## 评审与交付

依次检查决策问题是否得到回答、事实是否有证据、模型语义是否成立、跨制品是否一致、图形是否完整且可读。分类、分组、方向、基数、边界、图例和不确定性均是检查对象。

交付模型、分析结论、制品和交付物索引、表格或图形可编辑源、图形 SVG／PNG、覆盖台账、版本指纹及验证结果。分别报告定义核实、模型、分析、生成、修改、评审和视觉状态；表格的视觉图模板要求不适用不等于对应来源图已通过，缺依据或未评估的项目不能列为已通过。数量从注册表及来源清单推导，分类统计见全面对标（历史材料已清理）。
