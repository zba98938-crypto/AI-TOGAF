# 过渡架构可运营性判定

方法 ID：`transition-operability-check`。主责：[togaf-migration-roadmap](../../../togaf-migration-roadmap/SKILL.md)。

来源：G248 §2、G186 §9。定义状态：`project-operational-method`。判定的是"这个中间状态能不能真的运行"，不是"项目完成了多少"。

## 输入

必需，五项运营条件逐项给出：

| 条件 | 要回答的问题 |
| --- | --- |
| 人员 | 谁在过渡期承担运营责任，是否已任命 |
| 系统 | 哪些系统在过渡期并行、哪些只读、哪些已下线 |
| 数据 | 过渡期的数据一致性如何保证，如何对账 |
| 控制 | 过渡期的访问控制与审计如何维持 |
| 回退 | 回退触发条件、责任人与验证方法 |

可选：过渡期时长、服务水平要求。

## 步骤

1. 逐项检查五项条件是否齐备。
2. 任一项缺失即判 `不可运营`，并输出缺失项 ID。
3. 五项齐备时，检查回退方案是否有可验证的触发条件。
4. 输出判定结果与逐项说明。

## 输出

| 字段 | 含义 |
| --- | --- |
| `operable` | `true` / `false` |
| `missing_conditions` | 缺失的条件名与缺口 ID |
| `rollback_verifiable` | 回退触发条件是否可验证 |
| `notes` | 逐项说明 |

## 检查

- 只给进度百分比就判可运营 → `transition-operability-gap`
- 五项齐备但回退无触发条件 → `transition-operability-gap`
- 过渡期并行的旧系统未标只读边界 → `missing-evidence`

## 误读

- **进度百分比不是可运营性证据。** 70% 完成的架构仍可能完全无法运行。
- 过渡架构必须是"功能完整、可运营"的状态，不是主线的快照。
- 五项齐备不等于业务已接受，仍需责任方确认。

## 反例

| 错误输入 | 预期 | 为什么不通过 |
| --- | --- | --- |
| 过渡架构仅给出「完成 70%」，未说明人员、系统、数据、控制与回退 | `transition-operability-gap` | 只给进度百分比就判定过渡可运营 |

## 可执行项目规则

本方法现有确定性辅助接口，详见[迁移计算接口](../migration-calculations.md)。以同名 `method_id` 放入共享模型的 `analyses`，通过 `analyze.py --evaluate` 调用。它只执行显式输入与项目规则，不替代专业判断、真实观察、授权或企业接受；既有手写案例中的判断仍保留各自证据边界。
